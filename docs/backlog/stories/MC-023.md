## Context

`docs/wiki/audits/app-window-2026-09-13.md`, evidence **E-3**, found three
surviving mutants in `gui.rs`'s `progress_bar`:

```
crates/app/src/gui.rs:516:29: replace == with != in progress_bar
crates/app/src/gui.rs:519:21: replace / with % in progress_bar
crates/app/src/gui.rs:519:21: replace / with * in progress_bar
```

These are not cosmetic. `516:29` inverts `if total == 0`, so for **every real
run** the fraction is `0.0` and the bar never moves from empty while the count
beneath it climbs to the end. That is a functional defect a user hits on their
first drop, and it is the highest-impact survivor in the audit that is not a
deliberate gap.

The audit's **Decided-3** settles the fix and this story implements it without
reopening it: the fraction does not belong in the painter. Every other number
the window prints already lives in `lib.rs` so it can be compared as a value —
`result_line`, `progress_text`, `rows`, `dropzone_text` — and `lib.rs` killed
31 of 31 viable mutants precisely because of that (audit E-2). The fraction is
the one number that escaped into the paint, where only a rendered image can see
it. Move it to the view-model and it is killable by an ordinary unit test.

**Decided-3 is settled; the numbers in `## Evidence` are not.** This story
depends on E-3 only for *which lines survived*, which is directly checkable:
re-run the audit's command in E-1 and confirm those three lines are still in
`missed.txt` before starting.

The required gate that would fail if this story's artifact broke is **`unit`**
(`cargo test --workspace`), which is required for the repo. The `coverage` gate
also binds here: the new function lives in `lib.rs`, which is **not** excluded
from coverage, unlike `gui.rs`.

## Acceptance criteria

- **AC-1** — Given `done` and `total`, when the view-model is asked for the
  progress fraction, then it answers `done / total` as a value in `0.0..=1.0`
  — 0 of 4 is `0.0`, 1 of 4 is `0.25`, 4 of 4 is `1.0`.

- **AC-2** — Given `total == 0`, when the view-model is asked for the fraction,
  then it answers `0.0` and does not produce NaN or infinity. *Control: the
  mutant `replace == with != in progress_bar` (`gui.rs:516:29`) makes exactly
  this branch answer `0/0`. A test that only checks `total > 0` cases would
  pass against it.*

- **AC-3** — Given `done > total` (a late or duplicated progress message), when
  the view-model is asked for the fraction, then it answers at most `1.0`. *The
  window must not paint a bar past its own end; `Model::handle` does not
  currently reject such an event, so the fraction is where it is contained.*

- **AC-4** — Given the painter, when it draws the progress bar, then the
  fraction it passes to `egui::ProgressBar` is the value the view-model
  returned and is computed nowhere else in `gui.rs`.

- **AC-5** — Given the view-model mutated so the fraction function returns `0.0`
  unconditionally, and separately so that `done / total` becomes `done % total`,
  when the new tests run, then each mutation fails at least one of them.
  *Record both failures under `## Gate probes`. `%` is the audit's own
  `gui.rs:519:21` survivor, and it is the sharper of the two: `done % total`
  agrees with `done / total` at `done == 0`, so a test suite whose only case is
  "a run that has not started" would miss it.*

## Model guidance

Oracle partition for RED:

| Criterion | Kind | Instruction |
|---|---|---|
| AC-1, AC-2, AC-3 | **Mechanical** | Arithmetic with named inputs and named outputs. Pin exact values; leave nothing open-ended. Float comparison is exact here — `0.25` and `1.0` are representable. |
| AC-4 | **Mechanical** | A structural claim about where the computation lives. |
| AC-5 | **Mechanical** | Two named mutations. Apply, watch red, revert, paste the output. |

Nothing here is oracle-free and nothing needs a metric invented. If RED finds
itself designing a tolerance, it has taken a wrong turn.

`Model::handle` is MC-014's and is fully pinned (audit E-2). AC-3 is about the
fraction clamping, **not** about adding a guard to `handle`: changing the state
machine's acceptance of a `Progress` event would be a behaviour change that no
acceptance criterion here authorises, and MC-014's own tests would have to be
revisited to allow it. Contain it in the fraction.

## Out of scope

- The look-only survivors — the bar's fill colour, its track colour, its corner
  radius, its 4 px height. MC-021.
- The truncation survivors (MC-022) and `shell::count` (MC-024).
- Whether `Model::handle` should reject a `Progress` where `done > total`. AC-3
  contains the symptom; deciding the state machine's contract is a question for
  the product owner and a story of its own.
- Any change to `progress_text` or to the `{done} of {total}` string. That is
  `voice.md`'s, it already lives in `lib.rs`, and its mutants were all caught.
- Animating or smoothing the bar. `animate(false)` is `components.md`'s.
