## Context

`docs/wiki/audits/app-window-2026-09-13.md`, evidence **E-3**, found three
surviving mutants in `gui.rs`'s `progress_bar`:

```
crates/app/src/gui.rs:516:29: replace == with != in progress_bar
crates/app/src/gui.rs:519:21: replace / with % in progress_bar
crates/app/src/gui.rs:519:21: replace / with * in progress_bar
```

These are not cosmetic. `516:29` inverts `if total == 0`, so for **every real
run** the fraction is `0.0` and the bar never moves from empty while the count
beneath it climbs to the end. That is a functional defect a user hits on their
first drop, and it is the highest-impact survivor in the audit that is not a
deliberate gap.

The audit's **Decided-3** settles the fix and this story implements it without
reopening it: the fraction does not belong in the painter. Every other number
the window prints already lives in `lib.rs` so it can be compared as a value —
`result_line`, `progress_text`, `rows`, `dropzone_text` — and `lib.rs` killed
31 of 31 viable mutants precisely because of that (audit E-2). The fraction is
the one number that escaped into the paint, where only a rendered image can see
it. Move it to the view-model and it is killable by an ordinary unit test.

**Decided-3 is settled; the numbers in `## Evidence` are not.** This story
depends on E-3 only for *which lines survived*, which is directly checkable:
re-run the audit's command in E-1 and confirm those three lines are still in
`missed.txt` before starting.

The required gate that would fail if this story's artifact broke is **`unit`**
(`cargo test --workspace`), which is required for the repo. The `coverage` gate
also binds here: the new function lives in `lib.rs`, which is **not** excluded
from coverage, unlike `gui.rs`.

## Acceptance criteria

- **AC-1** — Given `done` and `total`, when the view-model is asked for the
  progress fraction, then it answers `done / total` as a value in `0.0..=1.0`
  — 0 of 4 is `0.0`, 1 of 4 is `0.25`, 4 of 4 is `1.0`.

- **AC-2** — Given `total == 0`, when the view-model is asked for the fraction,
  then it answers `0.0` and does not produce NaN or infinity. *Control: the
  mutant `replace == with != in progress_bar` (`gui.rs:516:29`) makes exactly
  this branch answer `0/0`. A test that only checks `total > 0` cases would
  pass against it.*

- **AC-3** — Given `done > total` (a late or duplicated progress message), when
  the view-model is asked for the fraction, then it answers at most `1.0`. *The
  window must not paint a bar past its own end; `Model::handle` does not
  currently reject such an event, so the fraction is where it is contained.*

- **AC-4** — Given the painter, when it draws the progress bar, then the
  fraction it passes to `egui::ProgressBar` is the value the view-model
  returned and is computed nowhere else in `gui.rs`.

- **AC-5** — Given the view-model mutated so the fraction function returns `0.0`
  unconditionally, and separately so that `done / total` becomes `done % total`,
  when the new tests run, then each mutation fails at least one of them.
  *Record both failures under `## Gate probes`. `%` is the audit's own
  `gui.rs:519:21` survivor, and it is the sharper of the two: `done % total`
  agrees with `done / total` at `done == 0`, so a test suite whose only case is
  "a run that has not started" would miss it.*

## Model guidance

Oracle partition for RED:

| Criterion | Kind | Instruction |
|---|---|---|
| AC-1, AC-2, AC-3 | **Mechanical** | Arithmetic with named inputs and named outputs. Pin exact values; leave nothing open-ended. Float comparison is exact here — `0.25` and `1.0` are representable. |
| AC-4 | **Mechanical** | A structural claim about where the computation lives. |
| AC-5 | **Mechanical** | Two named mutations. Apply, watch red, revert, paste the output. |

Nothing here is oracle-free and nothing needs a metric invented. If RED finds
itself designing a tolerance, it has taken a wrong turn.

`Model::handle` is MC-014's and is fully pinned (audit E-2). AC-3 is about the
fraction clamping, **not** about adding a guard to `handle`: changing the state
machine's acceptance of a `Progress` event would be a behaviour change that no
acceptance criterion here authorises, and MC-014's own tests would have to be
revisited to allow it. Contain it in the fraction.

## Out of scope

- The look-only survivors — the bar's fill colour, its track colour, its corner

- The truncation survivors (MC-022) and `shell::count` (MC-024).
- Whether `Model::handle` should reject a `Progress` where `done > total`. AC-3
  contains the symptom; deciding the state machine's contract is a question for

### The export shape the tests already pin

Nothing below is a suggestion. Each name and signature is already imported or
matched by a test, so getting it wrong is a compile error or a red assertion
rather than a debate.

```
crates/app/src/lib.rs   (crate root of `manhwa_cropper`, beside `progress_text` at line ~408)

  pub fn progress_fraction(done: u32, total: u32) -> f32
```

- A **free `pub fn` at the crate root**, not a method and not inside a module:
  `tests/model.rs` imports it as `manhwa_cropper::progress_fraction` in the
  same `use` list as `progress_text`.
- The parameters are `u32, u32` in the order `(done, total)` - the tests call
  `progress_fraction(1, 4)` and expect `0.25`, so a swapped order is red.
- The return type is **`f32`, not `f64`**. `assert_eq!` alone would infer
  either, but AC-4's structural test requires the value to be handed straight
  to `egui::ProgressBar::new`, which takes `f32`.
- `#[must_use]` and a doc comment naming the token it serves are the file's
  convention (`progress_text`, `path_text`, `dropzone_text` all carry both).
  No test pins them; the `format` and `lint` gates do not either. Match the
  neighbours anyway.

In `crates/app/src/gui.rs`, AC-4's tests key on these exact strings:

- `fn progress_bar(` must still exist as a top-level `fn` whose closing brace
  is in column zero. The test slices its body from that prefix to the next
  `\n}\n`.
- That body must contain the literal substring `progress_fraction(done, total)`
  - so the call stays *inside* `progress_bar` rather than moving up into
  `status_slot`.
- That body must also contain **either**
  `ProgressBar::new(progress_fraction(done, total))`
  **or both** `let fraction = progress_fraction(done, total);` **and**
  `ProgressBar::new(fraction)`. Those two forms are the whole permitted set;
  either is fine, a third spelling is red.
- The **whole file** `gui.rs` must contain none of these six substrings:
  `done as f32`, `total as f32`, `total == 0`, `total != 0`, `/ total`,
  `done /`. The list deliberately names `done` and `total` rather than division
  in general, because `gui.rs` has one legitimate f32 division at line ~661
  (`step as f32 / SEGMENTS as f32`, the corner-arc helper) that must keep
  working.
- Importing the function is expected: extend the existing
  `use crate::{...}` list at `gui.rs:48` with `progress_fraction`.

**Not constrained, and yours to choose.** How the clamp is written
(`.min(1.0)` versus an early `if done >= total { return 1.0; }`), whether the
zero-total guard is an early return or an `if/else`, the doc comment, and
whether `progress_bar` keeps its `palette` parameter. Both clamp forms were
measured against all four new tests and both are green - see the table below,
which is the one place the choice has a visible consequence.

Reference values for the exactness claim, measured the same way:
`1.0f32 / 4.0f32 == 0.25f32` is `true`, `4.0/4.0 == 1.0` is `true`,
`0.0/4.0 == 0.0` is `true`. No tolerance is needed or wanted.

One measured surprise worth knowing: `f32::min` returns the *other* operand
when one is NaN, so `(0.0f32 / 0.0f32).min(1.0)` is `1.0`, not `NaN`. That is
why AC-2's test asserts `== 0.0` *as well as* `!is_nan()` - against a
`.min(1.0)` implementation with a broken zero guard the NaN never survives to
be seen, and only the value assertion catches it.

### Notes for the implementer

- **Do not touch `Model::handle`.** AC-3 is contained in the fraction. Adding a
  guard that rejects a `Progress` with `done > total` would change MC-014's
  state machine, is out of scope by name, and would require revisiting MC-014's
  own tests.
- `progress_text` and the `{done} of {total}` string are untouched and must
  stay untouched; the existing `progress_reads_as_a_count_out_of_a_total` and
  `progress_moves_the_count_and_asks_for_nothing` still pin them.
- `tests/model.rs`'s module header states the file's standing rule: every
  expected value is a literal, never re-read from the module under test. The
  new tests follow it, which for arithmetic means the expected fraction is
  written `0.25` and never `1.0 / 4.0` or `done as f32 / total as f32`. Do not
  "tidy" them into the formula during GREEN; that would be a test edit, and
  tests are frozen.
- All four new `model.rs` tests run in well under a millisecond (the 169-pair
  sweep is 169 float divisions), so the `coverage` gate's instrumentation
  budget is not a concern here.
- `tests/gui.rs` gained a file-level `const PAINTER_SOURCE: &str =
  include_str!("../src/gui.rs")`. That makes the `gui` test target depend on
  `gui.rs`'s bytes, so editing the painter forces that target to rebuild. This
  is intended and is what makes AC-4 checkable at all.

### GREEN's implementation choice, and what it selected

`.min(1.0)` for the clamp with an **explicit early return** for `total == 0`,
rather than relying on the clamp to contain the zero case. That is the right
way round for a reason RED measured and recorded: `f32::min` returns the *other*
operand when one is NaN, so `(0.0f32 / 0.0f32).min(1.0)` is `1.0`, not `NaN` -
a clamp would silently convert a broken zero guard into a full bar. It also
selects the **1-test** row of the handoff's AC-5 table for mutation (b), which
is the row `## Gate probes` P1 confirms.
