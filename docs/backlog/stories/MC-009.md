## Context

The brief's feature 6 for lossy inputs, with decision 4 from
`architecture.md`: JPEG is re-encoded at quality 100, WebP is re-encoded
lossless (the maximum WebP quality, and what the pure-Rust encoder in the
`image` crate supports). Also the two non-detector flags: `Unsupported`
(anything that is not PNG, JPEG or WebP by content) and `DecodeFailed`
(a file that claims a supported format and does not decode). Both are
copied unchanged, so every input ends up in the output folder. Format is
detected from the file's content, not its extension.

Gate that fails if this breaks: `unit`.

## Acceptance criteria

- **AC-1** - Given a recipe rendered to RGB8 and saved as JPEG at quality 95, when `process_file` runs, then the output is a JPEG named like the input, decodes to `rect.w x rect.h`, and its mean absolute per-channel error against the *decoded source* pixels inside the rect is at most 2.0. *Control on the number:* the same crop encoded at quality 30 scores above 4.0 on the same fixture (measured value recorded in the handoff).
- **AC-2** - Given a recipe saved as lossless WebP, when processed, then the output is a WebP named like the input, decodes to `rect.w x rect.h`, and every pixel equals the decoded source pixel inside the rect.
- **AC-3** - *Deferred to MC-018 by amendment, 2026-09-11 - see `## Amendments`.* No encoder reachable from this workspace can write a lossy WebP, so this criterion has no fixture here. It is carried into MC-018 as its AC-6, against a real lossy WebP screenshot the corpus requires anyway. The behaviour is unchanged and is not weakened: a lossy WebP that reaches `process_file` must still come back as a lossless re-encode of its decoded pixels.
- **AC-4** - Given a `.bmp` file and a `.txt` file, when processed, then each outcome is `Flagged { reason: Unsupported, output }` and the output bytes equal the input bytes.
- **AC-5** - Given a file named `x.png` containing 200 random bytes, when processed, then the outcome is `Flagged { reason: DecodeFailed(_), output }` and the output bytes equal the input bytes.
- **AC-6** - Given a PNG file named `x.jpg`, when processed, then it is treated as PNG (cropped losslessly, `SourceFormat::Png`) and the output is `out_dir/x.jpg`.

## Model guidance

Model: default. Oracle partition:

- **Settled**: JPEG quality 100; WebP lossless; the 2.0 MAE bound.
- **Mechanical**: outcomes and the file names; pin. Bootstrap (MC-001) verified that the pinned `image` version encodes WebP; if it did not, this story's Context is wrong and must stop for an amendment rather than swap the encoder silently.
- **Oracle-free**: AC-1's control. The Test Developer measures the quality-30 error on the fixture and records it; if it is not comfortably above 4.0 the fixture's texture is too smooth and must be made rougher, not the bound lowered.

## Amendments

### AC-3 deferred to MC-018 (2026-09-11, approved by ryanczhang7)

**What it said.** "Given a recipe saved as lossy WebP, when processed, then
the output is a WebP whose pixels equal the *decoded* source pixels inside the
rect (lossless re-encode of what was decoded)."

**What it says now.** Deferred to MC-018, where it becomes that story's AC-6
against a real lossy WebP screenshot. The behaviour is not changed and not
weakened - only the story that tests it moves.

**Why.** The criterion has no obtainable fixture. Nothing reachable from this
workspace can *write* a lossy WebP, so "a recipe saved as lossy WebP" cannot be
produced. The Test Developer found this and escalated rather than writing a
test that pretended; I reproduced it from the crate sources the lock pins,
independently of their probe:

* `image-webp-0.2.4/src/encoder.rs` - the encoder has exactly two places where
  it writes an image payload chunk (lines 686 and 728) and **both write
  `b"VP8L"`**, the lossless codec. `EncoderParams` has one field,
  `use_predictor_transform`, and no option selects a lossy path.
* `image-webp-0.2.4/src/vp8.rs` - zero encoder symbols; `grep -c` for
  `pub fn encode|Encoder` returns **0**. VP8 is present as a decoder only
  (`decoder.rs:193`, `b"VP8 " => Self::VP8`, `ImageKind::Lossy`).
* `image-0.25.10/Cargo.toml` - the `webp` feature is `["dep:image-webp"]` and
  nothing else. There is no optional `libwebp` backend to turn on.

So the gap is on the **input** side only. `## Model guidance` told this story
to stop for an amendment if the pinned `image` could not encode WebP; it can,
losslessly, which is what `architecture.md` decision 4 specifies, and AC-2
tests it. Decoding lossy WebP also works. The single thing that does not exist
is a way to *author* the fixture.

**Why MC-018 and not a committed binary.** MC-018 is the corpus story, it
already `depends_on: [MC-009]`, and its AC-3 already requires a `webp`-tagged
entry supplied by the user from real screenshots - which are overwhelmingly
lossy. The criterion therefore lands where a genuine lossy WebP has to exist
anyway, instead of making MC-009 the first story to commit binary test data,
generated by a browser that is not in `environment.md` and that CI could never
regenerate. MC-018 gains an explicit AC-6 in the same commit, so the deferral
is a move and not a deletion.

**Rejected alternatives.** Committing the out-of-band fixture (verified to
work end to end - 5,340 bytes, lossy VP8 payload, decodes `Rgb8 147x120`, MAE
1.9564 against the rendered plane, same `Rect { x: 12, y: 19, w: 126, h: 96 }`)
was ranked second and declined for the provenance reasons above. Dropping the
criterion outright was declined because a lossy input reaching the lossless
encoder is a real user path and deserves a test somewhere. Adding a
`libwebp`-backed dev-dependency was declined as a stack decision that
contradicts a pure-Rust `stack.md`, taken to avoid one fixture.

## Out of scope

EXIF orientation (not read; a rotated-by-EXIF JPEG is cropped in its stored
orientation - note for the corpus story), ICC profiles and metadata (not
preserved), progressive JPEG output (baseline is fine), animated WebP
(decodes as its first frame or fails; whichever the crate does is accepted),
JPEG chroma-subsampling settings beyond what `image` exposes.

### The byte-equality control, which is a different argument from MC-008's

MC-008 needed a `tEXt` chunk because a flat PNG re-encoded by this crate came
back byte-identical, so "copied, not re-encoded" would have passed for a
re-encoder. Here the argument is stronger and
`no_copy_of_an_unsupported_file_could_be_a_re_encode` makes it executable in
three linked steps:

1. **The engine writes three containers and no others**, and that is *measured
   through the engine* rather than read off a dependency's feature list: the
   scene is put through `process_file` as a PNG, as a JPEG and as a WebP, and
   each output's leading bytes are asserted to be that container's signature.
   The enumeration is closed by an exhaustive `match` on `SourceFormat` in the
   test's own `container_signature` helper - `write_crop` has one arm per
   variant, so a fourth variant stops this file compiling rather than quietly
   shrinking the claim.
2. **The engine calls none of the three fixtures one of those formats**:
   `detect_format` answers `None` for the BMP, the text file and the junk, from
   the bytes alone.
3. **None of the three begins with any of those signatures** - the BMP begins
   `42 4D`, which is not the PNG signature, not `FF D8` and not `RIFF`.

So whichever of its three encoders had run, the bytes it produced would have
begun with a signature none of these files carries. Byte equality therefore
means a copy. The text file and the 200 bytes carry the argument further still
and are asserted to fail both `image::guess_format` and `image::open`: they are
not images in any format, so no decoder could reach an encoder at all.

**This is the second form of the argument, and `## Regressions` records why the
first one was withdrawn.** RED originally asserted that the `bmp` codec was
compiled out of this build (`ImageFormat::Bmp.reading_enabled()` and
`writing_enabled()` both `false`). That premise is false under `cargo test
--workspace`, the `unit` gate's own command, and false only on some platforms -
cargo unifies `image`'s features across the workspace and `arboard` takes
`image` with `bmp` **on Windows only**. A control that passes or fails by
operating system is not a control. Nothing AC-4 claims was ever in doubt: the
engine's answer for a BMP is a policy mapping in `codec::source_format`, not a
question about decoders, which is exactly why step 2 above can be asserted
without naming a feature.

### The mechanical partition, and one thing that could not be pinned as the AC words it

AC-6 says the file is treated as PNG "(cropped losslessly, `SourceFormat::Png`)".
`SourceFormat` is **not** observable through `Outcome`, and must not become so:
`crates/engine/tests/process_file.rs` is MC-008's, frozen and passing, and it
constructs `Outcome::Cropped { rect, output }` by field name - a new field on
that variant is a compile error in a frozen test file. So AC-6's
`SourceFormat::Png` is pinned through `codec::detect_format`, the content
detector the story's Context requires anyway, and the *behavioural* half of
"treated as PNG" is pinned by the output's container and pixels.

### Edges, and the non-goals

Zero, one, many: 200 bytes of junk, a 77-byte text file, a 16x12 BMP, and the
147x120 scene in four containers. Boundaries: quality 100 against 99, 95 and 75
at the quantisation tables; the 2.0 bound against 0.3467 below it and 5.7838
above. Errors: both flag reasons, each asserted to be *not* the other. Of
`## Out of scope`, none is cheap to pin without inventing a fixture the story
does not call for: EXIF orientation, ICC profiles and animated WebP would all
need files no encoder here can write - the same wall AC-3 hit - and progressive
JPEG and subsampling settings are not exposed by `image`. They are left alone
rather than approximated.

### What GREEN must export

Nothing below is a suggestion. A test already imports each name, so a different
choice is a compile error.

```rust
// crates/engine/src/codec.rs, imported as `cropper_engine::codec::detect_format`
pub fn detect_format(bytes: &[u8]) -> Option<SourceFormat>;
```

That is **the only new item in the whole story**. Everything else the tests
import already exists and is unchanged: `process_file(&Path, &Path, &Tuning)
-> FileResult`, `FileResult { input, outcome }`, `Outcome::{Cropped { rect,
output }, Flagged { reason, output }, Failed { error }}`,
`Flag::{Detector(FlagReason), Unsupported, DecodeFailed(String)}`,
`SourceFormat::{Png, Jpeg, WebP}` and `codec::to_luma`.

What the assertions destructure:

* `detect_format` takes a **byte slice**, not a path: the story's Context says
  the format comes from the content. The tests pass the whole file. It returns
  `None` for a BMP, for text and for junk - `None` means "not one of the three
  formats the engine handles", not "unreadable".
* `SourceFormat` is compared with `assert_eq!` against `Option<SourceFormat>`,
  so it keeps `PartialEq` and `Debug`. It is already `Copy`.
* `Flag::DecodeFailed(String)` is matched and its `String` is asserted
  non-empty after trimming.

**Do not add a field to `Outcome::Cropped`** (or to any `Outcome` variant).
`crates/engine/tests/process_file.rs` is MC-008's, frozen, and constructs those
variants by field name; a new field is a compile error in a test you may not
edit. AC-6's `SourceFormat::Png` is observed through `detect_format` for exactly
this reason.

**Deliberately not constrained**, and still GREEN's to choose: how
`process_file` decides between `Unsupported` and `DecodeFailed` (only the
outcomes are pinned); whether `detect_format` inspects 16 bytes or all of them;
whether the pipeline uses `ImageReader` or `fs::read` plus `image::guess_format`;
the wording of any `DecodeFailed` message; the WebP encoder's predictor
transform; and whether the JPEG and WebP encoders are reached through
`ImageEncoder` or called directly - though see the note below, because
`save_with_format` cannot satisfy AC-1.

### What should change the implementation approach

1. **`image::open` reads the extension, not the content, and that is the whole
   of AC-6.** `image::open` is `ImageReader::open(path)?.decode()`
   (`image-0.25.10/src/images/dynimage.rs:1632`), and `ImageReader::open` is
   documented "format will be guessed from path". Measured: on the PNG named
   `x.jpg` it fails with *"Format error decoding Jpeg: Error parsing image.
   Illegal start bytes:8950"*. `process_file` calls `image::open` today, so
   AC-6 fails on the current code for this exact reason.
2. **One mechanism satisfies all five testable criteria**, and it was measured
   end to end. `ImageReader::open(path)?.with_guessed_format()?` replaces the
   extension's guess with the content's *when the content is recognised* and
   keeps the extension's otherwise, and `reader.format()` is public. Measured,
   per fixture:

   | Fixture | `format()` | `decode()` |
   |---|---|---|
   | `shot.png` | `Some(Png)` | `Ok(Rgb8 147x120)` |
   | `shot.jpg` | `Some(Jpeg)` | `Ok(Rgb8 147x120)` |
   | `shot.webp` | `Some(WebP)` | `Ok(Rgb8 147x120)` |
   | `x.jpg` (a PNG) | **`Some(Png)`** | `Ok(Rgb8 147x120)` |
   | `x.bmp` | `Some(Bmp)` | `Err("The image format Bmp is not supported")` |
   | `x.txt` | `None` | `Err("The file extension ... was not recognized")` |
   | `x.png` (junk) | **`Some(Png)`** | `Err("Format error decoding Png: Invalid PNG signature.")` |

   Map `Some(Png|Jpeg|WebP)` to a decode whose error is `DecodeFailed`, and
   everything else to `Unsupported`, and all five criteria fall out - including
   the one that looks contradictory: **AC-4's `.txt` and AC-5's junk `x.png`
   are both unrecognisable by content, so the extension is what separates
   `Unsupported` from `DecodeFailed`**. A purely content-based classifier
   returns `Unsupported` for AC-5's file and fails that criterion. This is the
   single most important thing in this handoff.
3. **`detect_format` is still needed, and not only because a test imports it**:
   the *encoder* has to be chosen from the content (AC-6), so the format has to
   be a value the code carries. Whether `process_file` gets it from
   `detect_format` or from `reader.format()` is yours; they must agree.
4. **Quality 100 must be explicit.** `JpegEncoder::new` is
   `new_with_quality(w, 75)` (`encoder.rs:391`), and `save_with_format` goes
   through it. Construct `JpegEncoder::new_with_quality(w, 100)`. Measured: the
   default fails both AC-1 assertions.
5. **The JPEG encoder is narrower than the PNG one.** `JpegEncoder::encode`
   accepts only `ExtendedColorType::{L8, Rgb8}` in 0.25.10 - an RGBA or 16-bit
   `DynamicImage` handed to it directly returns `UnsupportedErrorKind::Color`.
   `save_with_format` avoids this by narrowing first (`make_compatible_img`); a
   direct encoder call does not. Every fixture here decodes to `Rgb8`, so
   nothing in this suite catches it - which is exactly why it is written down.
   The WebP encoder accepts `{L8, La8, Rgb8, Rgba8}` and narrows 16-bit to
   8-bit rather than failing.
6. **`WebPEncoder::new_lossless` is the only WebP encoder**, so decision 4's
   "lossless" is free. `image-webp` 0.2.4 writes a `VP8L` chunk and has no
   other mode (`src/encoder.rs`: "Only supports \"VP8L\" lossless encoding").
7. **Reuse `copy::copy_unchanged` for both new flag paths.** It is MC-002's,
   already byte-exact and already creates `out_dir`, and it is what MC-008 uses
   for a detector flag. Nothing here needs a second copy.
8. **Coverage should improve.** MC-008 left `process.rs:119-121` (the
   `Outcome::Failed` arm) uncovered and named it MC-009's; AC-4 and AC-5 now
   reach that area of the code. Note the arm itself may stay uncovered if
   `Failed` is no longer how a decode error is reported - which is the point of
   AC-5 - so read the number rather than predicting it.

## Regressions

### The control that asserted a build detail (2026-09-11)

**What was wrong.** `no_copy_of_an_unsupported_file_could_be_a_re_encode`
asserted `!ImageFormat::Bmp.reading_enabled() && !ImageFormat::Bmp.writing_enabled()`,
on the stated grounds that "the workspace pins image with features
[png, jpeg, webp]". Under `cargo test --workspace` - which is the `unit`
gate's own command - that is false: `eframe` -> `egui-winit` (whose
`clipboard` feature is unconditional) -> `arboard` takes `image` with
`["png", "bmp"]` on Windows for the clipboard's DIB format, and cargo
unifies features across the workspace. `cargo tree --workspace -e features -i
image` lists `image feature "bmp"`; `cargo tree -p cropper-engine ...` does
not.

**Why it was a defect and not a surprise.** `arboard-3.6.1/Cargo.toml:156`
is `cfg(windows)` and asks for `["png", "bmp"]`; line 78 gives
unix-not-macOS `["png"]` and line 100 gives macOS `["tiff"]`. **The
assertion therefore passes on Linux and fails on Windows**, for the same
workspace and the same lockfile. A control that passes or fails by operating
system is not a control - and CI runs `windows-latest`.

**AC-4 and AC-5 were never in doubt.** Both passed throughout, in the same
`--workspace` run that failed the control. `codec::source_format` maps
`ImageFormat::Bmp` to `None` as a matter of *policy* - MC-009 AC-4 says a
BMP is `Unsupported` - and never asks which decoders are compiled in, so the
implementation was indifferent to the unification that broke the control.
What was owed was the control's argument for the BMP row, not the
behaviour.

**What it asserts now.** Three linked steps, none of them a claim about a
feature list: the engine writes three containers and no others (measured
through `process_file`, with the enumeration closed at compile time by an
exhaustive `match` on `SourceFormat`); `detect_format` answers `None` for
all three fixtures; and none of the three fixtures begins with any of those
signatures. So whichever encoder had run, the bytes would have begun with
something none of these files carries, and byte equality means a copy. The
BMP no longer carries a "does it decode" assertion at all - that is the
platform-dependent question, and it is not a question about this product.

* `image-webp-0.2.4/src/encoder.rs` - "Only supports \"VP8L\" lossless
  encoding"; the two places it writes a payload chunk both write `b"VP8L"`.
  `EncoderParams` has one field, `use_predictor_transform`. There is no lossy
  path and no option that would produce one.
* Nothing else in `Cargo.lock` encodes WebP.

The story's `## Model guidance` anticipated the neighbouring question - "if
[the pinned `image`] did not [encode WebP], this story's Context is wrong and
must stop for an amendment" - and the `## Notes` above answer it correctly for
the *output*: lossless is the only mode, and lossless is what decision 4 wants.
The gap is on the *input* side. Writing AC-3's source file needs a lossy WebP
encoder, and that is a different capability from the one that was checked.

**What is not a way out.**

* No lossy WebP encoder is installed on this machine: `cwebp`, `ffmpeg` and
  `magick` are all absent, and `python`/`python3` resolve to the Windows Store
  alias shim that `rules.md` warns about.
* A `libwebp`-backed dev-dependency (`webp`, `libwebp-sys`) is a `Cargo.toml`
  change - frozen in RED - and pulls a C toolchain into a workspace whose
  `stack.md` is pure Rust. That is a stack decision, not a test decision.
* Hand-writing a VP8 keyframe means implementing a boolean arithmetic coder,
  the token trees and quantisation in the test harness: several hundred lines
  of unverifiable encoder to test one criterion.

**One option that does work, and needs your decision rather than mine.** A
lossy WebP of this story's own recipe *can* be produced out of band and
committed as a binary fixture (`fixtures/**` is a test path in `paths.conf`,
so the phase lock permits it). I verified the route end to end rather than
proposing it blind: headless Chrome, drawing the recipe PNG into a canvas and
calling `toDataURL('image/webp', 0.85)`, produced a 5,340-byte file whose RIFF
chunk is `VP8X` (an extended container wrapping a lossy VP8 payload and an
`ICCP` chunk). Measured against it:

* `image` 0.25.10 decodes it: `Rgb8 147x120`.
* It is genuinely lossy - the decoded plane is **not** the rendered plane, mean
  absolute difference **1.9564**.
* The detector still answers `Crop(Rect { x: 12, y: 19, w: 126, h: 96 })`, the
  same rect as every other container, so AC-3's "inside the rect" would be
  comparable with AC-2's.

I did not commit it, and I think the decision is yours for three reasons: the
fixture could never be regenerated by CI or by this workspace, so it is test

its provenance is a browser, which is not in `docs/wiki/environment.md`; and it
carries an ICC profile, which this story's `## Out of scope` says is not
preserved - harmless for a decoded-pixel comparison, but it means the file is
not quite "a recipe saved as lossy WebP" either.

**The three ways forward I can see**, in the order I would rank them:

1. **Defer AC-3 to MC-018**, the corpus story, and record an `## Amendments`
   entry here saying so. Real-world WebP screenshots are overwhelmingly lossy,
   so the corpus is where such a file belongs, and MC-009 still ships the
   lossless WebP path that decision 4 is actually about.
2. **Amend AC-3 to name a committed fixture** produced out of band, and accept
   the binary in `fixtures/`. I can add the test in one more RED pass; the
   measurements above say it would pass with a correct implementation.
3. **Amend AC-3 away** on the grounds that `image` cannot produce a lossy WebP
   either way, so the criterion tests the decoder rather than this story's
   code. I like this least: a lossy input reaching the lossless encoder is a
   real user path, and it deserves a test somewhere.

Either of the first two is an `## Amendments` entry under the frozen-criteria
rule; I have made neither. Note also that **whatever you choose, AC-3 as
written is satisfiable by a correct implementation** - the decoded-pixels
comparison is exactly AC-2's assertion applied to a different input - so this

### The greyscale-JPEG narrowing: my ruling, and it stays

The Feature Developer flagged that `write_jpeg` narrows with `to_rgb8`, so a
greyscale JPEG comes back as a grey *RGB* JPEG rather than `L8`, and asked
whether to add a `match` arm. **Leave it as written.**

MC-008 AC-2 attaches "the same colour type and bit depth as its input" to PNG,
and `architecture.md` decision 4 says nothing about JPEG's colour type - only
its quality. No criterion in this story asks for it and no fixture exercises
it, so a `match` arm would be a branch no test reaches: untested production
code, added speculatively, that the coverage gate would then have to be told
to ignore. That is a worse trade than the behaviour it would fix.

It is a real if small behaviour - a greyscale JPEG screenshot comes back about
three times its necessary size - so it is written down here rather than
forgotten, as a candidate for a later story if the corpus (MC-018) turns up
greyscale JPEGs in practice. It is not a defect in MC-009.
