## Context

**The request (2026-09-30):** the user, asked by [MC-059](MC-059.md) whether
to fix `Screenshot (67).png`'s art box before that spike tries any rule:
"Fix the box first".

`Screenshot (67).png` (`kunmanga`, `tuning`) is marked
`{ x: 1012, y: 290, w: 523, h: 1098 }`, rows 290..1388. Its art starts on row
**293**. MC-059 read the pixels
([`site-header-search.md`](../../wiki/site-header-search.md) §5):

- in the mark's columns, rows 290 and 291 are exactly 255 (page white) and
  row 292 is the site header's closing line, luma about 235 across the full
  width; the first row with art is 293 (largest departure from white inside
  the column: 0, 0, 20, then 192 on row 293);
- rows 281..292 are **byte-identical** over the full width to the same rows of
  `Screenshot (73).png`, whose site header the user ruled to end at 293
  (MC-059, 2026-09-30), and whose mark starts at 293.

By `corpus.md`'s marking rule ("the rectangle holds the page's own artwork and
nothing else"), rows 290..292 are outside the mark: two rows of flat page and
one of the site's own furniture. This is the same kind of correction as
MC-027's and MC-049's column corrections ("Corrected marks"), on the row
axis: the mark is **3 rows too tall at the top**. The bottom edge, 1388, is not
in question and does not move.

**Why it matters now.** MC-050 §3 and MC-059 found the conflict: the user
ruled the header's end at 293 while the mark claims 290..292. MC-059 §5 shows
it is worse than one miss. A rule that reads the header gives `(67)` and
`(73)` the same top, so while the mark stands, any rule that removes the
`kunmanga` header clips `(67)`, and any rule that does not tops out under the
pass line. MC-059 waits on this story.

**What the user saw.** The question in plain words: the art box starts at 290,
the art at 293, and rows 290..292 are blank page plus the thin grey line under
the site's menu, pixel for pixel the same as on `(73)`, where the user marked
them as header. The user chose the fix. The user has **not** been shown a
zoom of rows 285..296. RED shows one (Open question 1) before the manifest
is edited, as MC-049 did for `Screenshot (2630).jpg`.

  255 and the share of pixels within `uniform_tolerance` (10) of the row's
  median, showing rows 290..292 flat and row 293 not.
- **AC-3** — *Nothing else moved.* Given the correction, when the `unit` and
  `integration` suites run, then every test passes, and any test whose
  expected value changed is named in the story with the reason (a value
  derived from `(67)`'s mark top or height). The crop does not change: this
  story edits no source file.

  on `Screenshot (67).png` still contains it (the crop is rows 167..1392, a

  existing zero-clip suite asserts it and passes.
