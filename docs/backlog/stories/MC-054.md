## Context

**The bug.** `detect.rs::a_detected_rect_holds_all_the_art_and_no_more_than_two_pixels_of_junk`
is a random property test in the required `unit` and `coverage` gates. On
2026-09-25 it drew a recipe on which the crop **cuts 20 rows off the bottom
of the art**: art `150,0 156x206`, crop `147,0 162x186`, on a 515x206 image.
MC-053's Test Developer found it in RED, and it has nothing to do with that
story's column axis.

**Where it came from, reproduced by the orchestrator on 2026-09-25.** The
persisted case (proptest `cc 3deeecef…`) was replayed twice on each build:

| Build | Result |
|---|---|
| `0f94c75` (before MC-048's viewport stage) | passes, twice |
| `26eddcb` (MC-048) | fails, twice: `h: 186` against the art's 206 |
| `c004d96` (MC-052) | fails: the same rect |

So MC-048's viewport stage introduced it, and MC-052's widening did not
cover it. It is a row-axis clip, which is the defect this product treats as
worst.

**It is a known family.** MC-052's GATES stress run (MC-052 `## Notes`,
"GATES: the proptest clip") measured about **1 clip in 12,500** generated
cases on MC-048's stage, 6 in 75,000. It reported its fixed stage at 0 in
those 75,000. This recipe is outside those seeds, so that 0 did not cover the
whole family. At the gate's 256 cases a run, the required `unit` and
`coverage` gates go red on `main` about 2 % of the time, for a reason no
commit caused.

**The recipe**, in full, from the proptest persistence file:

```
Recipe { art_w: 156, art_h: 206, top: Border { thickness: 0, colour: 0, spread: 0 }, right: Border { thickness: 183, colour: 137, spread: 0 }, bottom: Border { thickness: 0, colour: 0, spread: 0 }, left: Border { thickness: 140, colour: 127, spread: 0 }, layout: Bands, seed: 2647894579, top_chrome: [], bottom_chrome: [], left_chrome: [Chrome { thickness: 10, background: 68, deviation: 20, flat_fraction: 0.86 }], right_chrome: [Chrome { thickness: 26, background: 108, deviation: 20, flat_fraction: 0.9514212616192819 }] }
```

MC-052's notes carry two more recipes that pin its GATES rules 2 and 3 (seed
107 case 3690; seed 7 case 1458). No deterministic test pins them either.

**The user's ruling, 2026-09-25:** a separate fix story, run after MC-053.
During MC-053 the persisted line was set aside on the orchestrator's machine,
so that MC-053's gates judge MC-053. A copy is kept in the session scratchpad.

Real chrome does: `chrome-row-search.md` §3c measures chrome rows at a median

**The rule (step 6 of `viewport.rs`'s module doc).** After MC-052's widening,
on each side where the viewport would cut rows off the page column, the cut
stands only if the rows it cuts (`column.y .. top` above, `bottom ..
column.y + column.h` below) hold a run of at least `MIN_RUN` rows that the
whole-margin reading does not find page-like. Otherwise that side has no
strip, and the viewport runs to the image's edge there (`top = 0` /
`bottom = rows`).

*Why it covers the family, not the four.* The family is a margin whose share
straddles `PAGE_LIKE` on every row; on it a single page-like run of 16 is
chance, and so is its position. Step 4 already refused to believe fewer than
`MIN_RUN` page-like rows; it believed any number of non-page-like rows. The
rule asks the same resolution of the chrome, so a boundary is placed only
where both sides of it are evidence and not texture. It only ever keeps rows
(it can move `top` up or `bottom` down, never the reverse), so MC-052's
guarantee - every row MC-048's stage kept is kept, and a decline stays a
decline - still holds; rule 2's early return runs before it, untouched.

*No new constant.* `MIN_RUN` (16) is the settled one, applied to the other
kind of row. `PAGE_LIKE`, the tone and `uniform_tolerance` are untouched.
The two choices inside the rule were measured, not fitted:

- *Which reading decides "not page-like".* The first version asked for rows
  page-like in **neither** reading (whole margin and reader window). It also
  measured 0 clips, 0 junk in 240,000, and every test passed with the
  window's half removed - so that half was code no test demanded. Worse,
  under it MC-052's rule 2 was no longer pinned (probe MA green on all
  seven). The shipped version reads the whole margin alone - the reading that
  decides whether the stage speaks at all - and under it MA is red again
  (below).
- *Where a failing side goes: the image edge, not the column edge.* A side
  with no strip is what a decline is on both sides, and a decline's viewport
  is the whole image, so the margin may take its 3 px as it did before
  MC-048. Probe EDGE-AT-COLUMN (`top = first`, `bottom = end`) also passes
  all seven: **this choice is not pinned by any test.** On the recipes it
  changes only whether the 3 px margin is taken on that side (207:464: crop
  top 403 against 406).
