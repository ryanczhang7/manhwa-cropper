## Context

First real file goes through the detector. `cropper-engine::codec` decodes a
path with the `image` crate, converts to `Luma` (BT.601 weights: 0.299 R +
0.587 G + 0.114 B, alpha ignored), asks `cropper_core::decide`, crops the
decoded pixels to the rect without resampling and encodes PNG at the source
bit depth and colour type. The brief's constraint: "PNG in means identical
pixels out inside the crop, same resolution." `process_file(input, out_dir,
&Tuning) -> FileResult` is the single-file entry the batch (MC-011) will
parallelise; it writes to `out_dir/<original file name>` (collisions are
MC-010). Fixtures: the MC-003 recipes rendered to RGB and written as PNG into
a `tempfile` dir by the tests.

Gate that fails if this breaks: `unit`.

## Acceptance criteria

- **AC-1** - Given an RGBA8 PNG rendered from a recipe with uniform borders and a chrome band, when `process_file` runs, then `out_dir/<name>.png` exists, `FileResult.outcome` is `Cropped { rect, output }`, the output decodes to `rect.w x rect.h`, and every output pixel equals the source pixel at `(rect.x + i, rect.y + j)` channel for channel.
- **AC-2** - Given the same recipe saved as 8-bit greyscale, RGB8 and RGB16 PNGs, when processed, then each output has the same colour type and bit depth as its input and pixel-identical content inside the rect.
- **AC-3** - Given RGB pixels `(255,0,0)`, `(0,255,0)`, `(0,0,255)`, `(255,255,255)` and an RGBA pixel `(255,255,255,0)`, when `codec::to_luma` runs, then the luma values are `76`, `150`, `29`, `255`, `255` (rounded, alpha ignored).
- **AC-4** - Given the input is named `Shot.PNG`, when processed, then the output is `out_dir/Shot.PNG` (the original file name, case and extension untouched).
- **AC-5** - Given a uniform PNG (the detector flags it), when processed, then the outcome is `Flagged { reason: Detector(Uniform), output }` and the output file's bytes equal the input's (copied, not re-encoded).

## Model guidance

Model: default. Oracle partition:

- **Settled**: the BT.601 weights and the rounding in AC-3.
- **Mechanical**: `process_file(&Path, &Path, &Tuning) -> FileResult`, `FileResult { input: PathBuf, outcome: Outcome }`, `Outcome { Cropped { rect, output }, Flagged { reason: Flag, output }, Failed { error: String } }`, `Flag { Detector(FlagReason), Unsupported, DecodeFailed(String) }`, `SourceFormat { Png, Jpeg, WebP }`. Pin.
- **Oracle-free**: none.

## Out of scope

JPEG and WebP (MC-009), unsupported and corrupt files (MC-009), name
collisions (MC-010), palette PNGs (the `image` crate expands them; the
output colour type for a palette input is whatever it decodes to and is not
asserted here), a file whose extension lies about its format (encoded per
its decoded format, untested), metadata chunks (not preserved).

## Test plan

Two integration test targets and one fixture module, all under
`crates/engine/tests/` - **not** `#[cfg(test)] mod tests` inside `src/`, which
`paths.conf` classifies as source and reserves for GREEN, and which is how
`src/copy.rs` carries its tests. The consequence is deliberate: an integration
test is an external crate, so everything it touches has to be `pub`, including
`codec::to_luma`.

| Level | Target | Why there |
|---|---|---|
| Integration | `tests/process_file.rs` | The contract is a file on disk. Nothing about "the output's bytes equal the input's" or "the output keeps its bit depth" can be seen from inside the module; it needs a real temp directory and a real PNG. |
| Integration | `tests/codec.rs` | `to_luma` is a pure function and would be a unit test in any other layout; the external-crate rule puts it here. It is separated from `process_file.rs` so a conversion failure and a file-handling failure never appear as the same red. |
| Fixture | `tests/common/mod.rs` | One screenshot scene and one uniform scene, written out in four PNG colour types. Self-contained - see "Why not `crates/core/tests/common/`" below. |

### The oracle, and why it is not re-derived

`the_fixture_decides_to_crop_the_art_plus_the_margin` is the single assertion
every rect in the suite rests on: `decide(&screenshot(), &Tuning::default())`
is `Crop(Rect { x: 12, y: 19, w: 126, h: 96 })`. MC-007 settled `decide`, so
this story reads its answer out rather than re-deriving it, and the four colour
renderings of the scene are grey - `r = g = b = v`, and the BT.601 weights sum
to exactly 1.0 - so all four reach the detector as that same plane and share
that one rect.

That assertion also subsumes the fixture's internal numbers. If the chrome band
drifted below `chrome_flat_fraction`, `decide` would answer `Flag(Ambiguous)`;
if an art line went flat, the peel would eat it and the rect would shrink.
Both are one failing assertion away, so the flat fractions are recorded in the
handoff as diagnostics rather than asserted separately.

### The mechanical partition

`FileResult`, `Outcome`, `Flag` and `SourceFormat` are pinned by constructing
every variant and comparing the `Debug` string. That pins the variant *names*
(`Png`, not `PNG`), the struct-variant *field* names, and the derives - and it
exercises every arm the derives generate, which keeps three type-only variants
from costing line coverage. `Flag::Unsupported` and `Flag::DecodeFailed` are
pinned as **types only**: MC-009 owns the behaviour, and a test that reached
those paths here would push GREEN into writing MC-009.

### Edges, and the non-goals

Zero, one and many: a 1x1 RGBA image, a 4-pixel strip, and a 17,640-pixel
plane converted sample by sample. Boundaries: luma 0 and 255, and 16-bit 0 and
65,535. Of the `## Out of scope` list, exactly one is cheap enough to pin and is
pinned - "metadata chunks (not preserved)" is asserted by the AC-5 control,
where it is load-bearing rather than incidental. Palette PNGs, JPEG, WebP,
corrupt files, lying extensions and name collisions are all left alone.

### Why not `crates/core/tests/common/`

Its generator is richer than this story needs and lives in another crate's test
tree; reaching it with `#[path = ...]` would drag a `proptest` dev-dependency
into `cropper-engine` - a `Cargo.toml` change, frozen in RED, for recipes,
layouts and strategies MC-008 never draws. `tests/common/mod.rs` here is 400
lines that build two scenes and read a PNG header, and it borrows the two ideas
that matter (a checkerboard art texture, a chrome band at a chosen flat
fraction) rather than the machinery.

### What GREEN must export

Stated as fact, not suggestion: a test already imports each of these, and a
different choice is a compile error.

```rust
// reachable from the crate root of `cropper-engine`
pub mod codec;                 // `pub`, because an integration test is an external crate
pub use codec::SourceFormat;   // or define it at the root; the tests import the root path

pub fn process_file(input: &Path, out_dir: &Path, tuning: &Tuning) -> FileResult;

#[derive(Debug, Clone, PartialEq)]     // Eq is free and welcome
pub struct FileResult { pub input: PathBuf, pub outcome: Outcome }

#[derive(Debug, Clone, PartialEq)]
pub enum Outcome {
    Cropped { rect: Rect, output: PathBuf },
    Flagged { reason: Flag, output: PathBuf },
    Failed  { error: String },
}

#[derive(Debug, Clone, PartialEq)]
pub enum Flag { Detector(FlagReason), Unsupported, DecodeFailed(String) }

// crates/engine/src/codec.rs
pub fn to_luma(img: &image::DynamicImage) -> cropper_core::Luma;

#[derive(Debug, Clone, PartialEq)]      // Copy is free and welcome
pub enum SourceFormat { Png, Jpeg, WebP }
```

Details the assertions destructure or print, each of which is pinned:

* `process_file` takes `&Path`, `&Path`, `&Tuning` **in that order** and returns
  `FileResult` by value. `FileResult.input` must equal the `input` argument.
* `FileResult` is destructured as `FileResult { input, outcome }`, both fields
  `pub`, typed `PathBuf` and `Outcome`. Its `Debug` must contain `FileResult`.
* `Outcome`'s `Debug` must contain `Cropped`, `rect: Rect { x: 1, y: 2, w: 3,
  h: 4 }`, `Flagged`, `Detector(Uniform)` and `Failed { error: "no such file" }`
  - i.e. the plain derive, and the field names `rect`, `output`, `reason`,
  `error`.
* `Flag`'s `Debug` for `[Detector(Ambiguous), Unsupported,
  DecodeFailed("bad header")]` must print exactly that; `Detector` wraps
  `cropper_core::FlagReason` and `DecodeFailed` wraps `String`.
* `SourceFormat`'s `Debug` for the three variants must print exactly
  `[Png, Jpeg, WebP]`.
* `to_luma` returns a value with `width: u32`, `height: u32` and
  `data: Vec<u8>` compared against a `Vec<u8>` - `cropper_core::Luma`. It is
  called with `DynamicImage::ImageRgb8`, `ImageRgba8` and `ImageRgb16`, so it
  must handle at least those three; `ImageLuma8` arrives through
  `process_file`.

**Deliberately not constrained**, and so still GREEN's choice: which module
`process_file`, `FileResult`, `Outcome` and `Flag` are *defined* in (only the
root re-export is pinned - `cropper-core` does the same with `pub use
decide::{...}`); how `to_luma` narrows a 16-bit sample; whether anything
derives `Serialize` (MC-011's problem, not pinned here); whether `process_file`
creates a missing `out_dir` (every test passes one that exists, and
`copy::copy_unchanged` already creates it); any `SourceFormat` constructor or
format detection (MC-009); the encoder's compression level, filter choice and
metadata handling; the wording of any error string.

### What should change the implementation approach

1. **Do not call `image`'s `to_luma8`, `into_luma8` or `DynamicImage::grayscale`.**
   `image` 0.25 uses the BT.709 coefficients; this product specified BT.601
   (`architecture.md`, "cropper-core", and AC-3). Measured:
   `[54, 182, 18, 255]` against the required `[76, 150, 29, 255]`. Write the
   weights. Integer arithmetic works if you prefer it -
   `(2990 R + 5870 G + 1140 B + 5000) / 10000` gives all five AC-3 values and
   maps every grey to itself.
2. **Reuse `copy::copy_unchanged` for the flagged path.** MC-002 already copies
   bytes byte-for-byte under the input's own file name and creates `out_dir`;
   that is AC-5's "copied, not re-encoded" and AC-4's naming in one function,
   and `architecture.md`'s `batch` bullet says a flagged file is copied rather
   than re-encoded. AC-5's control exists precisely because a re-encode of a
   flat image is otherwise indistinguishable from a copy.
3. **Crop before encoding, without resampling.** `DynamicImage::crop_imm`
   preserves the variant (`ImageRgb16` stays `ImageRgb16`), and saving a
   `DynamicImage` picks the PNG colour type from the variant - verified:
   `ImageLuma8 -> (8, 0)`, `ImageRgb8 -> (8, 2)`, `ImageRgb16 -> (16, 2)`,
   `ImageRgba8 -> (8, 6)`. Anything that routes through `to_rgba8()` on the way
   out fails all three AC-2 tests.
4. **A coverage tension worth knowing about before you write it.**
   `Flag::Unsupported`, `Flag::DecodeFailed` and `Outcome::Failed` are pinned as
   *types* here and no test reaches them as *behaviour* - that is MC-009. Their
   derived `Debug`/`PartialEq` arms are exercised by the shape tests, so the
   derives cost nothing, but any `Err` arm you write in `process_file` (a
   decode failure has to become something, since the function returns
   `FileResult` rather than `Result`) will be one to three uncovered lines. The
   workspace is currently at **100.00% of lines** against a 95% floor, so that
   is affordable - but it will be the first drop below 100%, it is expected, and
   the answer is *not* to write a test (tests are frozen in GREEN) or to make
   the error path unreachable. Keep it to one expression and say so in the
   story if the coverage gate's number moves.
5. **`image::open` handles the uppercase extension.** `Shot.PNG` decoded
   correctly in the RED harness. MC-009 owns detecting the format from the
   container rather than the extension; nothing here forces that yet.
6. **`image` 0.25 decodes WebP but does not encode it** - already recorded in
   this story's PLANNED -> RED note. Not MC-008's problem (only PNG is encoded
   here), but `SourceFormat::WebP` is pinned in this story, so whoever picks up
   MC-009 should check the encoder situation before assuming the type implies a
   capability.

The test developer reported that `image`'s own `to_luma8` is BT.709, so AC-3's

constants, which is a different source of evidence
(`~/.cargo/registry/src/index.crates.io-*/image-0.25.10/src/color.rs:606`):

That is Rec. 709 / sRGB luma. AC-3 asks for BT.601 (0.299 / 0.587 / 0.114), so

**AC-3 catches a second mistake the handoff did not name, and it is worth
recording.** The crate's conversion is an integer division - it truncates. AC-3
says *rounded*, and exactly one of its four RGB cases separates the two:

    (255 0 0)     exact=76.2450   round=76   trunc=76
    (0 255 0)     exact=149.6850  round=150  trunc=149
    (0 0 255)     exact=29.0700   round=29   trunc=29
    (255 255 255) exact=255.0000  round=255  trunc=255

So a BT.601 implementation that truncates returns 149 where AC-3 demands 150.
AC-3 therefore discriminates on *both* axes - the weights and the rounding -
and a GREEN that gets the weights right can still fail it on one value.

### The `tEXt` chunk in AC-5's fixture: approved

The test developer flagged this as the one place it added machinery a criterion
did not literally ask for, and asked me to look. I did, and it stays.

AC-5 says the output's bytes equal the input's "(copied, not re-encoded)". That
parenthetical is only testable if a re-encode would produce different bytes,
and for a flat image written by this crate's own encoder it would not - 278
bytes either way, measured. Without the marker, AC-5 would pass for an

precisely the implementation the criterion exists to forbid. The fixture

proving the discriminator is real (359 bytes with the marker, 278 without).

states that metadata chunks are not preserved, so the marker's disappearance
under a re-encode is established behaviour being *used*, not new behaviour
being asserted.

### Correction to the WebP risk noted in PLANNED -> RED
