## Context

**Asked for by the user on 2026-11-03** ("can we create an icon for this
application"). Three sketches were shown; the user picked **"Crop corners"**:
a blue rounded tile, four white crop-corner brackets, a faint tall panel in
the middle. The artwork, its colours and the exact pixel values the tests read
are recorded in [`docs/wiki/design/icon.md`](../../wiki/design/icon.md). That
page is the authority; this story implements it.

It reverses a recorded v1 decision. `docs/wiki/design/layout.md`, "Window",
said `Icon: none in v1 (the exe's default)`; that row now points at
`icon.md` and these two stories, with the user's approval and date.

**No epic.** Every epic in the backlog is about cropping, or about the
window's contents (EPIC-04 and EPIC-06, both done). This is the exe's identity
in Windows, two stories long, and is filed without one, as MC-057 and MC-058
were.

**Why two stories.** The request has two parts that Windows reads from two
different places, and either can be shown working without the other:

- **this story**: the icon the running window hands Windows, which the title
  bar, the taskbar button and alt-tab show. It is set through eframe at
  runtime (`gui::viewport()`, `crates/app/src/gui.rs` ~line 193, the
  `ViewportBuilder` that `main.rs` opens). It also introduces the build step
  that renders the SVG, which MC-087 reuses.
- **[MC-087](MC-087.md)**: the icon *embedded in the exe file* as a Windows
  resource, which File Explorer, the Send-to shortcut and the pinned taskbar
  entry read before the app ever runs. That needs a resource compiler and a
  test that reads the exe's resource section, which is a separate behaviour
  with its own failure modes (the Windows SDK's `rc.exe`, PE parsing).

Together they were one story joined by "and", touching the window, the build
script, two new build-dependencies and the binary format at once.

**How it is built, and who writes what.** No phase here is SCAFFOLD; this is
an ordinary feature.

| File | Category (`paths.conf`) | Written in |
|---|---|---|
| `crates/app/tests/icon.rs` (new) | test | RED |
| `crates/app/assets/icon.svg` (new; the SVG from `icon.md`, byte for byte) | source | GREEN |
| `crates/app/build.rs` (new; renders the SVG to a 256x256 RGBA raster in `OUT_DIR`) | source | GREEN |
| `crates/app/Cargo.toml` (`[build-dependencies] resvg = { workspace = true }`), root `Cargo.toml` (`resvg = "0.49"` in `[workspace.dependencies]`, per `stack.md`) | config | GREEN |
| `crates/app/src/gui.rs` (`viewport()` gains `.with_icon(...)`) | source | GREEN |

The raster is generated by the build into `OUT_DIR` and never committed; that
is what "nobody pastes a PNG by hand" means in practice. If GREEN finds a
reason the raster must be committed instead, that is a design change: stop
and say so, do not quietly commit a binary.

**Required gate that would fail if this broke:** `unit`
(`cargo test --workspace --no-fail-fast`) runs `crates/app/tests/icon.rs`.
`gui.rs` is excluded from line coverage by the coverage gate's regex, so the
coverage gate is not evidence for this story; the tests are.

## Acceptance criteria

All coordinates are pixels in the icon's own image, (x, y), origin top-left.
Every expected value is read out of `docs/wiki/design/icon.md`, "Sample
points".

- **AC-1** — Given the app's window settings (`gui::viewport()`), when they
  are read, then they carry an icon of exactly 256 x 256 pixels in RGBA (its
  pixel buffer is 256 * 256 * 4 bytes long).
  *Control:* `ViewportBuilder::default()` with no icon set - today's
  `viewport()` - must fail this.

- **AC-2** — Given that icon, when its pixels are sampled, then the four
  image corners (0,0), (255,0), (0,255), (255,255) are fully transparent
  (alpha 0), and the tile samples (32,128), (128,32), (224,128), (128,224)
  are exactly `#0067C0` with alpha 255.
  *Control:* a solid 256 x 256 `#0067C0` square, alpha 255 everywhere, must
  fail on all four corners.

- **AC-3** — Given that icon, when its pixels are sampled, then each crop
  bracket's vertical arm - (56,72), (200,72), (56,184), (200,184) - is exactly
  `#FFFFFF` with alpha 255, and the gaps between brackets - (56,128) on the
  left edge and (128,52) on the top edge - are exactly `#0067C0` with alpha
  255.
  *Controls:* (a) the tile with no brackets must fail all four arm samples;
  (b) the tile with a full white rectangular frame on the bracket line
  (stroke 4 units, the whole perimeter rather than four corners) must pass
  the arm samples and fail both gap samples - this is the control that
  proves the gap samples tell "corners" from "frame".

- **AC-4** — Given that icon, when the panel sample (128,128) is read, then
  it is opaque (alpha 255) and each of R, G, B is within 2 of (89, 156, 214),
  the 35 % white panel over `#0067C0`.
  *Control:* the tile and brackets with the panel left out reads
  (0, 103, 192) there and must fail, by 89 on red.

- **AC-5** — Given the existing window tests (`tests/window.rs`,
  `tests/gui.rs`), when the suite runs, then the title, default size and
  minimum size `viewport()` asks for are unchanged - adding the icon replaces
  nothing else in the builder.

**What only a person can check.** The tests prove what the app *hands*
Windows. Whether Windows *shows* it - in the title bar, on the taskbar
button, in alt-tab - is checked by eye: at REVIEW the user runs
`bash scripts/task.sh dev` and looks, and the PR says it was looked at and by
whom. Until MC-087 lands, a pinned taskbar entry or the exe in Explorer still
shows the default icon; that is expected, not a failure of this story.

## Model guidance

No model change: nothing here calls for judgement a different model would
add. The oracle partition, which the RED brief must carry:

- **Settled** - AC-1 to AC-4. Every number (size, sample points, colours, the
  panel value and its tolerance of 2) is read out of `icon.md`. Do not derive,
  tune or "calibrate" them against what the renderer happens to produce; if a
  sample point lands on an anti-aliased edge in the real raster, that is a
  finding to report, not a coordinate to move.
- **Mechanical** - AC-1's type and size, AC-5. Pin exactly.
- **Oracle-free** - none.

**Controls belong in the suite.** Write the sample checks as a function over
any `egui::IconData`, and run every control above through it as its own test,
constructing the control images in the test file. That way each control is
run in RED - where `viewport()` exists and has no icon, so the suite compiles
and fails on assertion, not on import - and stays a permanent check that the
sampler itself can tell the shapes apart. Record each control's result in the
handoff.

## Out of scope

- **The exe's embedded icon** (Explorer, shortcuts, the Send-to entry, a
  pinned taskbar entry). That is [MC-087](MC-087.md). No `.rc`, `.ico` or
  resource compiler in this story.
- **The 16, 24, 32 and 48 px rasters.** MC-087 makes them; this story makes
  only the 256.
- **Redesigning the artwork.** The SVG in `icon.md` is final. Not a pixel of
  it changes during RED or GREEN - not to dodge an anti-aliased sample, not
  to "sharpen" small sizes. A drawing change goes back to the user.
- **A dark-mode or high-contrast variant**, or switching the icon with the
  Windows theme. One icon for both themes (`icon.md`).
- **Icons inside the window.** `voice.md`'s "no icons standing in for words"
  still governs the window's contents; nothing in the drop zone, the button
  or the list gains a glyph.
- **An installer, Start-menu entry, or file association.** No installer in v1
  (`architecture.md`, "Deployment shape").
- **macOS or Linux icon formats** (`.icns`, `.desktop`, freedesktop sizes).
  Windows 11 only.
- **Committed raster files** (`.png`, `.ico`) - see Context.
