## Context

`docs/wiki/audits/app-window-2026-09-13.md`, evidence **E-5**, found that
`shell.rs` has exactly two surviving mutants and both are in `fn count`:

```
crates/app/src/shell.rs:269:5: replace count -> u32 with 0
crates/app/src/shell.rs:269:5: replace count -> u32 with 1
```

Everything else in the wiring is pinned — `read_files`' hover flag, `drain`,
`dispatch` and `perform` were all caught. `count` is the `usize` → `u32`
conversion that `ThreadRunner` applies to the engine's `Progress`, and it is
used **nowhere else**: the eleven fake-runner tests in `crates/app/tests/shell.rs`
push `Event::Progress` straight down the channel with counts of their own, so
they never exercise it.

The one test that uses a real `ThreadRunner`,
`a_real_run_of_two_screenshots_writes_both_crops_and_reports_them`
(`crates/app/tests/shell.rs:1035`), polls until the model leaves `Processing`
and then asserts the final summary. It never observes a `Progress` at all. With
`count -> 0` the window reads `0 of 0` under a motionless bar for the whole of
every real run — including an Explorer "Send to" launch, which is the product's
headline flow — and then snaps to the correct summary.

**The audit's `## Decided` is settled.** **E-5 is not, and it flags the exact
thing that decides this story's shape:** a test that calls `count` as a pure
function kills both mutants without pinning the wiring that made them matter,
whereas a test that observes a real `Progress` needs enough input files that the
run cannot finish inside one poll interval — and *how many* is unmeasured. The
audit did not measure it. Measure it in RED before committing to a number, and
put the measurement in the handoff.

The required gate that would fail if this story's artifact broke is **`unit`**
(`cargo test --workspace`), which is required for the repo.

## Acceptance criteria

- **AC-1** — Given a real `ThreadRunner` started over N images into a scratch
  folder, when the window is stepped until the run ends, then at least one
  frame showed a progress count whose `total` was N. *`total` is the criterion's
  anchor because it is constant for the whole run and therefore not a race;
  `done` is timing-dependent and AC-2 handles it separately.*

- **AC-2** — Given the same run, when the frames it passed through are
  considered in order, then every progress count observed had `done` no greater
  than `total`, and the last one before the summary had `done` greater than 0.
  *Phrased over what was observed rather than over an exact sequence: which
  intermediate counts a test sees depends on scheduling, and an AC that demands
  a specific sequence would be flaky by construction.*

- **AC-3** — Given a `usize` count larger than `u32::MAX`, when it is converted
  for the window, then the result is `u32::MAX` and the process does not panic.
  *The saturation `shell.rs` documents but nothing exercises. Control: the
  boundary values `u32::MAX as usize`, `u32::MAX as usize + 1` and `0` must all
  convert without panicking, and the first two must not be equal to each other
  before saturation is applied — if they are, the test is running on a 32-bit
  target and asserts nothing.*

- **AC-4** — Given `fn count` replaced by one returning `0` unconditionally, and
  separately by one returning `1`, when the tests for AC-1 and AC-2 run, then
  each mutation fails at least one of them. *The audit's two named survivors,
  used as this story's negative controls. Record both failures under
  `## Gate probes`. A `count`-as-pure-function test alone would satisfy this
  criterion's letter while leaving the wiring exactly as unpinned as it is now —
  AC-4 is satisfied by the AC-1/AC-2 tests, not by an AC-3 test.*

- **AC-5** — Given the test for AC-1 and AC-2, when it is run 20 times in
  succession, then it passes every time. *A test that observes a thread is a
  test that can flake, and a flaky test in a required gate is worse than the gap
  it closed. Record the 20 runs and the command in the handoff.*

### Why two files and not one

`saturation.rs` has to import `manhwa_cropper::shell::count`, which is private
today, so that file does not compile. **A test target that does not compile
takes every assertion in its binary with it**: had AC-1 and AC-2 lived in the
same file, no assertion in this story would have executed in RED, no number
below could have been measured, and the whole of the design - `N`, the poll
period, the negative controls - would have been a claim. Splitting them is what
let RED watch `progress.rs`'s assertions both pass and fail while `saturation.rs`
was still an `E0603`.

The second reason is the one `tests/truncation.rs` (MC-022) set the precedent
for: `tests/shell.rs`'s own module docs say "**Measured**: nothing is an
expectation here", and half of `progress.rs` *is* a measurement. It states a
different contract, so it gets its own header. Third: a test binary is its own
process, and `MANHWA_CROPPER_CONFIG_DIR` is process-wide, so keeping three
~100 ms runs out of MC-016's binary keeps its eleven fast tests from queueing
behind them on that binary's environment lock.

### The shape chosen for AC-1 and AC-2 (oracle-free, so here is the metric)

The window is stepped in a loop, and **the count the window showed is recorded
in every frame it was still `Processing`**, in frame order. That list - the
trace - is the whole metric. The run ends when the state stops being
`Processing`; the loop never records the summary frame, so the last entry in the
trace is literally "the last count before the summary" that AC-2 names.

    [0/96, 0/96, 12/96, 26/96, 41/96, ..., 90/96]   a healthy run
    [0/96, 0/0, 0/0, ..., 0/0]                      count -> 0
    [0/96, 0/96, 1/1, 1/1, ..., 1/1]                count -> 1

**AC-1 is asserted as `done > 0` AND `total == 96`, and the first half is
load-bearing.** Read literally, "a frame showed a progress count whose `total`
was N" is satisfied by the *first* entry in every trace above:
`Model::files_dropped` sets `Processing { done: 0, total: N }` from a
`u32::try_from` of its own, before the runner has even been started, and audit
E-2 already pinned that conversion - it is not the one this story is about. So a
frame showing `total == 96` alone is satisfied by a window that never received a
single `Progress`, and `count -> 0` would survive. `done > 0` is the only thing
in a count that tells a genuinely-applied `Progress` from the pre-run frame,
because `batch::run` calls its callback with `done` running `1..=total` - every
count the engine produces has `done >= 1`.

That reading is a **strengthening of AC-1, not a change to it**: the AC says "a
progress count", and the pre-`Progress` frame's count did not come from a
`Progress`. It is also exactly what the story's own AC-4 demands - see the
`count -> 1` trace above, which satisfies every word of AC-2 and is caught only
by `total == 96`.

### N = 96 files, and the measurement behind it

The failure mode is that `Shell::drain` applies every buffered event of a frame
*in* that frame, so a run that finishes between two polls collapses its whole
progress history and its `Finished` into one frame and no count from the running
batch is ever seen. What decides whether that happens is the **gap**: the wall
time between the first `Progress` reaching the channel and `Finished` reaching
it. Only a stall of the GUI thread longer than the *whole gap* can lose the
observation, so **the gap is the margin - not the number of polls**.

The gap is roughly `run time * (1 - cores / N)`: rayon finishes files in waves
of one per core, so with `N <= cores` every `Progress` and the `Finished` land
in one wave. That is precisely why MC-016's two-file run never sees one, and it
is why N has to be several times the core count.

Measured on this machine (Windows, **12 logical cores**, `profile.test`
`opt-level = 2`), 20 consecutive runs at each size, counting frames whose count
satisfied AC-1's predicate:

| N | qualifying frames | gap (ms) | run (ms) | setup (ms) | runs with **zero** |
|---|---|---|---|---|---|
| 2 (MC-016's) | 0-1 | ~0 | 6.3 | 1.4 | see below |
| 24 | 1..5 | 5.7..30.7 | 14.1..36.6 | 10.4..19.1 | 0/20 |
| 48 | 4..7 | 22.6..40.8 | 28.5..46.8 | 21.5..36.5 | 0/20 |
| **96 (chosen)** | **5..13** | **45.9..80.9** | **56.1..97.2** | 43.9..775.1 | **0/20** |
| 144 | 7..13 | 72.6..104.1 | 79.9..111.9 | 71.1..785.3 | 0/20 |

The two setup maxima are outliers - one run in twenty at each size - and they
are filesystem jitter while writing the images, not the run. Setup happens
before the drop, so it costs wall time and buys no margin; typical is 44-95 ms.
That is the reason not to go past 96, and the reason the *run* column, not the
setup column, is where the decision was made.

At N=2 with a 5 ms poll the single observation was `0/2` - the pre-run frame -
and **zero** qualifying frames, which is the bug the story exists to fix, now
measured rather than argued.

**96 is the smallest size whose worst gap is an order of magnitude clear of a
Windows scheduling quantum**: losing the observation would take a 45 ms stall of
the GUI thread. 48 halves the cost and halves the margin to 22 ms, which is one
bad quantum. 144 doubles the setup for a margin nothing needs.

**Instrumentation and CI both move this the safe way.** Under
`cargo llvm-cov`, 20 runs at N=96 gave **9..30** qualifying frames, a
**139.8..194.1 ms** gap and a 164.3..220.1 ms run - three times the margin,
because instrumentation slows the engine and not `thread::sleep`. Fewer cores on
a runner does the same thing, because fewer cores means more waves. The
instrumented run is the slow case for wall time and the *safe* case for the
observation.

The whole `progress.rs` binary - three 96-file runs - costs **0.41-0.47 s plain
and 0.74 s instrumented**, measured inside the `unit` and `coverage` gate logs.
No escalation to the `integration` gate is needed and `required_gates` does not
change.

The poll period is 5 ms, the same `tests/shell.rs` uses. It only has to be
comfortably shorter than the gap; at N=96 it is nine or more polls inside the
worst measured gap. The `RUN_TIMEOUT` failure bound is 30 s, against a projected
worst case of about 2 s on a 2-core runner under instrumentation.

### AC-3: the one production change this story needs

The saturating branch is only reachable by calling the function - a real run
cannot hand it a count past `u32::MAX` without a drop of four billion files - and
`fn count` is private at `crates/app/src/shell.rs:269`. Three routes were
considered:

| Route | Verdict |
|---|---|
| Reach the saturation through the window | **Impossible**, not merely expensive. There is no input that makes the engine report more than `u32::MAX` files. |
| An in-module `#[cfg(test)] mod tests` in `shell.rs` | **Not taken.** `paths.conf` classifies in-module tests under `src/` as `source`, written in GREEN - so AC-3's test would be written by the Feature Developer against code that already satisfies it, and AC-3 would have no RED at all. That is the exact failure mode `rules.md` names. |
| Make `count` `pub` and test it from `tests/saturation.rs` | **Taken.** One word of production change, the test is owned by RED, and the function already carries the doc comment that explains why it saturates. |

This widens the crate's public surface by one pure conversion, which is a
deliberate cost and is flagged in the handoff for the product owner to overrule
if they would rather not pay it.

### Edges covered

- **Zero**: `count(0) == 0`; and the "the trace is empty" clause in
  `assert_every_count_made_sense`, which is what a run that collapsed into one
  frame would hit.
- **One**: `count(1) == 1`; and AC-1 requires only *one* qualifying frame, which
  is the weakest thing that can be true and still mean something.
- **Many**: 96 real files through the real engine; `count(4_000_000_000)`.
- **Boundary, both sides**: `u32::MAX as usize` (unchanged) and
  `u32::MAX as usize + 1` (saturated), so a conversion that clamped one file too
  early is visible. The invariant `done <= total` is the other boundary.
- **Errors**: a run that ends in anything but a summary panics in `observe_run`
  naming the state; a run still `Processing` after 30 s panics naming both
  causes; the folder picker panics if the shell ever opens a dialog during a run.
- **Non-goals pinned cheaply**: `Out of scope` forbids changing what
  `ThreadRunner` reports or how often the engine calls back, and nothing here
  asserts a *particular* intermediate count or a number of callbacks - only the
  trace's shape. The `NeverPicker` pins "a real run opens no dialog", which
  MC-016 asserted for two files.

### Deliberately not asserted

- No exact intermediate count and no exact trace length. Which counts a frame
  catches is the scheduler's business; an AC that demanded a sequence would be
  flaky by construction, which the story says in AC-2's own note.
- Nothing about `Event::Progress`'s type, the position of the conversion, or
  throttling. `Out of scope` forbids all three.
- Nothing about `settings.json`. The environment guard here is containment, not
  an assertion; MC-016 owns the settings criteria.
- Nothing read from the AccessKit tree. MC-015 and MC-022 own what the window
  *says*; this story is about what the model was *told*.
