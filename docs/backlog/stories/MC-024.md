## Context

`docs/wiki/audits/app-window-2026-09-13.md`, evidence **E-5**, found that
`shell.rs` has exactly two surviving mutants and both are in `fn count`:

```
crates/app/src/shell.rs:269:5: replace count -> u32 with 0
crates/app/src/shell.rs:269:5: replace count -> u32 with 1
```

Everything else in the wiring is pinned — `read_files`' hover flag, `drain`,
`dispatch` and `perform` were all caught. `count` is the `usize` → `u32`
conversion that `ThreadRunner` applies to the engine's `Progress`, and it is
used **nowhere else**: the eleven fake-runner tests in `crates/app/tests/shell.rs`
push `Event::Progress` straight down the channel with counts of their own, so
they never exercise it.

The one test that uses a real `ThreadRunner`,
`a_real_run_of_two_screenshots_writes_both_crops_and_reports_them`
(`crates/app/tests/shell.rs:1035`), polls until the model leaves `Processing`
and then asserts the final summary. It never observes a `Progress` at all. With
`count -> 0` the window reads `0 of 0` under a motionless bar for the whole of
every real run — including an Explorer "Send to" launch, which is the product's
headline flow — and then snaps to the correct summary.

**The audit's `## Decided` is settled.** **E-5 is not, and it flags the exact
thing that decides this story's shape:** a test that calls `count` as a pure
function kills both mutants without pinning the wiring that made them matter,
whereas a test that observes a real `Progress` needs enough input files that the
run cannot finish inside one poll interval — and *how many* is unmeasured. The
audit did not measure it. Measure it in RED before committing to a number, and
put the measurement in the handoff.

The required gate that would fail if this story's artifact broke is **`unit`**
(`cargo test --workspace`), which is required for the repo.

## Acceptance criteria

- **AC-1** — Given a real `ThreadRunner` started over N images into a scratch
  folder, when the window is stepped until the run ends, then at least one
  frame showed a progress count whose `total` was N. *`total` is the criterion's
  anchor because it is constant for the whole run and therefore not a race;
  `done` is timing-dependent and AC-2 handles it separately.*

- **AC-2** — Given the same run, when the frames it passed through are
  considered in order, then every progress count observed had `done` no greater
  than `total`, and the last one before the summary had `done` greater than 0.
  *Phrased over what was observed rather than over an exact sequence: which
  intermediate counts a test sees depends on scheduling, and an AC that demands
  a specific sequence would be flaky by construction.*

- **AC-3** — Given a `usize` count larger than `u32::MAX`, when it is converted
  for the window, then the result is `u32::MAX` and the process does not panic.
  *The saturation `shell.rs` documents but nothing exercises. Control: the
  boundary values `u32::MAX as usize`, `u32::MAX as usize + 1` and `0` must all
  convert without panicking, and the first two must not be equal to each other
  before saturation is applied — if they are, the test is running on a 32-bit
  target and asserts nothing.*

- **AC-4** — Given `fn count` replaced by one returning `0` unconditionally, and
  separately by one returning `1`, when the tests for AC-1 and AC-2 run, then
  each mutation fails at least one of them. *The audit's two named survivors,
  used as this story's negative controls. Record both failures under
  `## Gate probes`. A `count`-as-pure-function test alone would satisfy this
  criterion's letter while leaving the wiring exactly as unpinned as it is now —
  AC-4 is satisfied by the AC-1/AC-2 tests, not by an AC-3 test.*

- **AC-5** — Given the test for AC-1 and AC-2, when it is run 20 times in
  succession, then it passes every time. *A test that observes a thread is a
  test that can flake, and a flaky test in a required gate is worse than the gap
  it closed. Record the 20 runs and the command in the handoff.*

## Model guidance

Oracle partition for RED:

| Criterion | Kind | Instruction |
|---|---|---|
| AC-1, AC-2 | **Oracle-free** | The number of input files and the polling strategy are yours to design; the audit measured neither. Demand a control that fires hard — AC-4 is it. State the chosen N and *why* that N, with the timing you measured. |
| AC-3 | **Mechanical** | Named boundary values. Pin exactly. |
| AC-4 | **Mechanical** | Two named mutations at a named line. Apply, watch red, revert, paste. |
| AC-5 | **Mechanical** | A repetition count and a command. |

The tension to resolve deliberately: **more input files makes AC-1 reliable and
makes the suite slower.** Say in the handoff what N you chose, how long the test
takes, and what the margin was — the next agent will otherwise reduce N to save
seconds and reintroduce the flake. If the honest answer is that no N gives a
comfortable margin on the `unit` gate's budget, that is a finding for the
product owner: the alternative is the `integration` gate, and moving it there
means adding `integration` to this story's `required_gates` **before** RED, not
after.

## Out of scope

- Anything in `gui.rs`. MC-021, MC-022 and MC-023 cover the painter's survivors.
- Changing what `ThreadRunner` reports, how often the engine calls back, or
  adding throttling. This story observes the existing reporting.
- Changing `Event::Progress`'s `u32` type or pushing the conversion into the
  engine. `lib.rs`'s module docs give the reason the boundary is where it is,
  and MC-014 pinned it.
- Cancelling a run, queueing a second drop, or anything else EPIC-04 lists under
  "Deliberately not in this epic".
- The `count` mutants' cousins in `Model::files_dropped`
  (`total: u32::try_from(inputs.len()).unwrap_or(u32::MAX)`). Those were caught;
  `lib.rs` killed 31 of 31 (audit E-2).
