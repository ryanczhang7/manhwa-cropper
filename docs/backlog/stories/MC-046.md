The user reported this, and it was first reproduced during [MC-045](MC-045.md)
against `scripts/gates.sh` at b820614. It is harness work filed under

### The defect, in the current code (HEAD 1fa9815, after MC-045)

MC-045 rewrote how the manifest is *parsed* (builtins in place of
`trim`/`cut`). It did not change how the manifest is *read* or how gates are
*run*. The gate loop in `scripts/gates.sh` still reads the manifest on the
loop's stdin (`while IFS= read -r line; do … done < "$CONF"`, ~line 418 to
~line 677), and runs each gate inside that loop without redirecting stdin
(~line 611):

```bash
( cd "$ROOT/$cwd" && eval "$cmd" ) 2>&1 | tee "$log"
```

The gate command therefore inherits the loop's stdin, which is the unread rest
of `project.conf`. A gate that reads stdin (`cat`, a tool that drains its
input, anything that waits for a prompt answer) consumes every later line. The
loop then sees EOF and ends. The later gates never run, never appear in the
summary and are never counted, and nothing reports that they are missing.

### Reproduced at PLANNED (2026-09-23, HEAD 1fa9815)

Fixture from `make_project_fixture` / `write_conf` (`.claude/tests/_lib.sh`),
full run, no flags.

**Case A, the user's report.**

```
gate | eats  | required | . | cat >/dev/null; printf 'Tests 1 passed\n'
gate | later | required | . | printf 'Tests 2 passed\n'
```

```
All required gates passed (1 ran, 0 unconfigured, 0 known).
exit=0
```

`later` does not appear anywhere in the output.

**Case B, worse than reported: a failing required gate is swallowed.**

```
gate | first | required | . | printf 'Tests 2 passed\n'
gate | eats  | required | . | cat >/dev/null; printf 'Tests 1 passed\n'
gate | later | required | . | exit 1
```

```
PASS         first (0s) -- no evidence line: a vacuous pass would go unnoticed
PASS         eats (0s) -- no evidence line: a vacuous pass would go unnoticed
All required gates passed (2 ran, 0 unconfigured, 0 known).
exit=0
```

A required gate that exits 1 turns into exit 0 and "All required gates
passed". A full run with `--story` records that as `pass` in the story's
`## Gate results`, and `check-boundaries.sh` accepts it, because the record is
genuine for a run that silently skipped a gate. `--list` on the same config
shows all three gates, because it never runs a command.

**Case C, `--gate later`, is not affected.** The loop reaches `continue` for
`eats` before running it, so nothing reads the manifest's stdin. Output:
`All required gates passed (1 ran …)`, and `later` is the gate that ran.

### Two traps in the obvious fix, also reproduced at PLANNED

The obvious one-line fix reads the manifest on another descriptor
(`read -u 3 … done 3< "$CONF"`). Applied to a scratch copy of the fixture's
`gates.sh` (never to the repo), it gives this:

| Gate command | Next gate: `later`, required, `exit 1` | Result |
|---|---|---|
| `cat >/dev/null; …` | `FAIL later (exit 1)`, `1 required gate(s) failed.` | fixed |
| `cat <&3 >/dev/null 2>&1; …` | not run; `All required gates passed (1 ran …)`, exit 0 | **still broken** |
| `printf 'got:'; cat` with `printf 'CALLER-DATA\n' \| bash scripts/gates.sh` | the gate's log shows `got:CALLER-DATA` | **the caller's stdin leaks into gates** |

So moving the manifest to fd 3 relocates the defect instead of removing it.
The eval'd command inherits fd 3 and can still drain it. The gate also
inherits whatever `gates.sh` was given on stdin. In a terminal that is the TTY,
where a stdin-reading gate blocks forever, which is the "looks like a hang"
failure MC-043 and MC-044 already lost time to. The criteria below are written
as behaviour so that they reject this fix, not so that they prescribe another
one.

### Which required gate would fail if this broke

None in `project.conf`, and that is expected for harness work. See "Gate
decision" in `## Notes`. The regression tests live in
`.claude/tests/gates.test.sh`, which CI runs through `bash scripts/selftest.sh`
(`.github/workflows/gates.yml` line 37, a blocking step).

All fixtures come from `make_project_fixture` / `write_conf`. Every gate
command is a `printf`/`cat`/`wc` one-liner, so no real toolchain is involved.
"Runs" means the gate's `=== gate: <id>` banner appears and its outcome line
appears in `--- gate summary ---`.

- **AC-1** — *The reported bug, as its permanent regression test.* Given a
  manifest whose first required gate reads all of its stdin
  (`cat >/dev/null; printf 'Tests 1 passed\n'`), when a full `gates.sh` run
  executes, then:
  (a) if the second required gate prints `Tests 2 passed` and exits 0, both
  gates appear as `PASS` in the summary and it reads
  `All required gates passed (2 ran, 0 unconfigured, 0 known).`;
  (b) if the second required gate exits 1, the summary shows `FAIL` for it,
  the run prints `1 required gate(s) failed.` and exits 1.
  *Control:* on today's `gates.sh`, (a) prints `(1 ran, …)`, (b) exits 0 with
  `All required gates passed`, and the second gate's id is absent from the
  output (measured, see Context, cases A and B). Red on arrival.
- **AC-2** — *No inherited descriptor reaches the manifest.* Given a manifest
  whose first required gate tries to drain stdin and every descriptor from 3
  to 9 (`for fd in 0 3 4 5 6 7 8 9; do cat <&$fd >/dev/null; done 2>/dev/null;
  printf 'Tests 1 passed\n'`, or an equivalent that reads each one), followed
  by a required gate that exits 1, when a full run executes, then the second
  gate is reported `FAIL` and the run exits 1.
  *Control:* red on arrival on today's `gates.sh` through fd 0. The criterion
  exists because of its second control, the fd-3-only fix from Context: it
  passes AC-1 and must fail AC-2 (measured: `1 ran`, exit 0). RED shows the
  test tells the two apart. Apply the fd-3-only edit to a **fixture copy** of
  `gates.sh`, confirm that the AC-1 test goes green and the AC-2 test stays
  red, and paste both results into `## Handoff`.
- **AC-3** — *A gate reads end-of-input, not the caller's stdin.* Given a
  manifest with a required gate `printf 'stdin-bytes=%s\n' "$(wc -c | tr -d
  ' ')"` followed by one more gate line, when `gates.sh` is invoked with data
  piped to it (`printf 'CALLER-DATA\n' | bash scripts/gates.sh`), then the
  gate's log (`.claude/state/gate-logs/<id>.log`) contains `stdin-bytes=0`,
  and the run finishes (the test runs it under the suite's normal timeout
  discipline and does not block).
  *Control:* on today's `gates.sh` the gate reads the rest of the manifest, so
  the count is the byte length of the following line(s), not 0. On the fd-3-only
  fix it reads `CALLER-DATA\n`, which is 12 bytes. Both are red. The TTY case,
  where a stdin-reading gate would block forever, cannot be exercised in the
  selftest harness. This criterion is its proxy: a gate that sees end-of-input
  on a pipe also sees end-of-input when the caller is a terminal.
- **AC-4** — *The subsets use the same loop, so they get the same guarantee.*
  Given the AC-1(b) manifest plus a third gate `slow_one` carrying a `slow`
  line with a reason, when `gates.sh --fast` runs, then `later` is reported
  `FAIL`, `--fast skipped: slow_one` is printed, and the run exits 1. And
  when `gates.sh --required` runs on the AC-1(b) manifest, `later` is
  reported `FAIL` and the run exits 1.
  *Control:* on today's `gates.sh`, both runs exit 0 and never mention `later`.
  Red on arrival. (`--gate <id>` is deliberately not here, see Context case C.
  A filtered-out gate hits `continue` before anything runs, so it has no defect
  to reproduce, and a test for it would pass on arrival and earn nothing.)
- **AC-5** — Given `bash scripts/selftest.sh`, when it runs in full after
  GREEN, then every suite passes, and the output tail is pasted into
  `## Notes`. *Control:* `selftest` is a CI step, not a `project.conf` gate,
  and never appears in `## Gate results`. That makes this the story's only
  in-story evidence that the rest of the harness still works: the lock tests,
  the `--list`/`--audit` tests and the MC-045 exec-count tests all run
  `gates.sh` (see "Gate decision" in `## Notes`).

**Oracle partition.**

- **Mechanical, pin exactly:** AC-1, AC-2, AC-4. The oracle is the summary
  lines, the `(N ran, …)` count and the exit code, and the expected strings
  are quoted in the criteria. Do not loosen them to "contains FAIL" when the
  gate id is available. A summary that says FAIL for the wrong gate must not
  pass.
- **Settled, read the numbers out:** each control's measured value on today's
  code (`1 ran`/exit 0 for AC-1, AC-2 and AC-4, `stdin-bytes=43` for AC-3 on the PLANNED fixture,
  meaning the byte length of the rest of the fixture manifest, and 12 bytes
  under the fd-3-only fix). Those were measured at PLANNED on HEAD 1fa9815. Do
  not re-derive them. If a number differs, report it rather than adjusting the
  test.
- **Oracle-free:** none.

**The one judgement call RED makes.** The AC-2 test must be shown to
discriminate between today's code, the fd-3-only fix and a real fix, using the
fixture-copy mutation that AC-2 prescribes. A test that goes green against the
fd-3-only fix fails the criterion, however it is written.

## Out of scope

<!-- Explicit non-goals. Prevents the Feature Developer from over-building. -->

- **An accounting invariant in the summary** ("refuse when fewer gates ran than
  the manifest declares"). It is a real idea, and it belongs in its own story,
  not here. The reasons:
  1. *It is a different behaviour with a different oracle.* This story makes
     a gate unable to consume the manifest. The invariant makes the summary
     refuse to certify a run whose accounting does not close, whatever the
     cause.
  2. *After this fix it has no reproducible failure to be red against.* The
     only known way to lose a gate line is the one this story removes. A test
     for the invariant would pass on arrival, and it could be earned only by
     mutating `gates.sh` or by adding a fault-injection seam. Choosing between
     those is a design decision this story should not make in passing.
  3. *Its definition is not settled.* The categories it would have to close
     over are `ran`, `unconfigured`, `known`, config-error FAILs that
     `continue` before running (bad `floor`, `ci-factor`, a waiver on a
     required gate, a reasonless `slow`/`no-count`), `--fast` skips,
     `--gate`/`--required` filters and `--list`/`--audit`. Each of these is a
     product decision about which subsets it may assert over. Folding that into
     a one-line fix would make the story two cycles.

  Recommended as a follow-up `fix` or `feature` under the same epic. It is not
  filed yet: the user decides whether they want it.
- **`--gate <id>`.** Not affected, because filtered-out gates `continue` before
  running (Context, case C). No change and no test.
- **`--list` and `--audit`.** Neither runs a gate command, so neither is
  affected. Their output must not change: the MC-045 byte-identical and
  exec-count tests already pin them, and AC-5 runs them.
- **The first parse loop** (the tables, ~line 239). It runs no command, and
  nothing in it can read stdin.
- **Any other change to how a gate runs.** That covers its cwd, the
  `2>&1 | tee` pipeline, `PIPESTATUS`, evidence and floor evaluation, the
  lock and `record_in_story`. The one change is what the gate command's stdin
  and inherited descriptors can reach.
- **Sandboxing gate commands in general.** A gate can still `rm` the manifest,
  `exec` over the shell and so on. `project.conf` is trusted input written by
  the Lead PO. The defect here is an *accidental* read by an ordinary tool,
  not a hostile gate. Descriptors 0 and 3 to 9 are the ones an ordinary shell
  command can reach by accident, and they are the boundary.
- **The `fd 255` script descriptor, the lock's descriptor if any, and other
  high-numbered fds.** A gate does not reach these by accident, so no criterion
  covers them.
- **`lib.sh`, `phase.sh`, `selftest.sh`, `check-boundaries.sh` and
  `project.conf`.** Only `scripts/gates.sh` changes on the source side.

## Notes

### Gate decision (PLANNED, 2026-09-23)

`required_gates: []`. I re-derived this rather than inheriting it, following
the reasoning MC-045 used. The only executable lines this story changes are in
`scripts/gates.sh`. Every `gate` line in `project.conf` (lines 192–198:
`format`, `lint`, `typecheck`, `unit`, `coverage`, `integration`, `build`)
runs `cargo`, and none runs `scripts/selftest.sh` or reads
`.claude/tests/**`. So no gate, required or optional, can go red if this
story's artifact breaks, and escalating one would bind nothing.

What does verify it is `.github/workflows/gates.yml` line 37 (re-checked
2026-09-23), which runs `bash scripts/selftest.sh` as a blocking step, followed
by `gates.sh --list` and `gates.sh --audit` against the real config. AC-5
brings the full selftest into the story as evidence.

`## Gate probes`: not required. This story changes no `gate`, `evidence`,
`floor` or other manifest line, and no gate command. It changes what a running
gate command can read. The criteria are red on arrival against the real
`gates.sh`, and AC-2 carries its own discriminating mutation (the fd-3-only
fix, applied to a fixture copy). That is the gate-probe discipline applied to
the runner.

### Tests and commands

- Tests go in `.claude/tests/gates.test.sh`, under a new `describe`, using the
  suite's existing `gates()` helper and `make_project_fixture` / `write_conf`.
- Run: `bash scripts/selftest.sh gates`. MC-045 made that suite fast; it was
  5–13 minutes before.
- Full: `bash scripts/selftest.sh` (AC-5).
- `gates.sh` flags are `--fast`, `--required`, `--gate <id>`, `--list`,
  `--audit`, `--no-wait` and `--story <id>`. There is no `--required-only`.

### Split decision

One story, not split. AC-1 to AC-4 are one behaviour: nothing a gate command
reads can change which gates the loop runs. They are four views of it (the
report, the descriptor generalisation, the caller's stdin and the subset
flags), and one change to one call site in one file satisfies all of them. The
accounting invariant was the candidate second behaviour, and it is split out
(see `## Out of scope`, first bullet).

`[MC-045]`, which is DONE, so `phase.sh set` is not blocked. It is listed
rather than omitted because this story edits the gate loop MC-045 rewrote. The
