## Context

The second half of the user's request of 2026-11-03 for an app icon (see
[MC-086](MC-086.md), Context, for the request, the choice of "Crop corners",
and why it is two stories). The artwork and its sizes are in
[`docs/wiki/design/icon.md`](../../wiki/design/icon.md); that page is the
authority.

MC-086 makes the *running* window show the icon. This story embeds it *in the
exe file* as a Windows icon resource, which is what File Explorer, the
Send-to shortcut the user makes in `shell:sendto`, and a pinned taskbar entry
read - before the app runs, and whether or not it ever does.

**No epic**, as MC-086.

**How it is built, and who writes what.** No phase here is SCAFFOLD.

| File | Category (`paths.conf`) | Written in |
|---|---|---|
| `crates/app/tests/exe_icon.rs` (new) | test | RED |
| `crates/app/build.rs` (extended: render the SVG at 16, 24, 32, 48 too; assemble an `.ico` in `OUT_DIR`; compile and link an `.rc` naming it) | source | GREEN |
| `crates/app/Cargo.toml` (`[build-dependencies] embed-resource = { workspace = true }`), root `Cargo.toml` (`embed-resource = "3"`, per `stack.md`) | config | GREEN |

The `.ico` and `.rc` are generated into `OUT_DIR` and never committed. An ICO
file whose entries are PNGs is a 6-byte header, a 16-byte directory entry per
image and the PNG bytes; GREEN may write it by hand in `build.rs` or add the
`ico` crate, and records which in `stack.md`.

`embed-resource` drives the Windows SDK's `rc.exe`. It is present on this
machine (`C:\Program Files (x86)\Windows Kits\10\bin\10.0.26100.0\x64\rc.exe`)
and on CI's `windows-latest`. If CI cannot find it, that is a GATES finding
to fix in the workflow's toolchain step, not a reason to skip the resource on
CI.

**How the test sees the exe.** Cargo builds `manhwa-cropper.exe` before it
runs `crates/app`'s integration tests and hands its path to them as
`env!("CARGO_BIN_EXE_manhwa-cropper")` (`tests/cli.rs` already spawns it that
way). The build script runs for that debug build exactly as for release, so
the `unit` gate reads a real exe with the real resource. The test parses the
PE file's `.rsrc` section itself (resource directory -> `RT_GROUP_ICON` (14)
-> `RT_ICON` (3) entries); no new dev-dependency is needed, since RED cannot
edit `Cargo.toml`. `image` (PNG) is already a dev-dependency for decoding the
entries.

**Required gate that would fail if this broke:** `unit` runs
`crates/app/tests/exe_icon.rs`. The `build` gate also builds the release exe
through the same build script, so a broken `.rc` fails `build` too.

## Acceptance criteria

- **AC-1** — Given the built exe, when its resource section is read, then it
  holds exactly one icon group (`RT_GROUP_ICON`), and that group lists exactly
  five images whose sizes are 16, 24, 32, 48 and 256 px square, each 32 bits
  per pixel. (In an icon group a width or height byte of 0 means 256.)
  *Controls:* today's exe, which has no icon group, must fail; a group listing
  only the 256 must fail on the missing sizes.

- **AC-2** — Given each image the group points to, when its `RT_ICON` data is
  read, then it is a PNG whose decoded width and height equal the size the
  group lists for it, whose pixel (0,0) has alpha 0, and whose pixel at unit
  (8,32) of the 64-unit grid - (2,8) at 16, (3,12) at 24, (4,16) at 32,
  (6,24) at 48, (32,128) at 256 - is `#0067C0` with alpha 255, each channel
  within 2 at 16 and 24 px and exact at the others.
  *Controls:* an entry whose PNG is a different size from the one the group
  declares must fail; a solid `#0067C0` entry must fail on pixel (0,0).

- **AC-3** — Given the 256 px image in the exe, when it is decoded to RGBA,
  then it is byte-for-byte the same pixels as the icon MC-086 sets on the
  window (`gui::viewport()`'s icon). One artwork, one raster: Explorer and
  the taskbar never disagree.
  *Control:* the same check with the window icon's pixel (128,128) altered
  must fail.

**What only a person can check.** The tests prove the exe *contains* the
icon. Whether Explorer *shows* it is checked by eye at REVIEW: the user opens
the folder holding the built exe (`target\release\manhwa-cropper.exe` after
`cargo build --release --workspace`) in File Explorer at small, medium and
extra-large icon views, and looks at their Send-to shortcut. Windows caches
icons per path; if an old icon shows, copying the exe to a new folder is the
honest test, not a cache-clearing script. The PR says it was looked at and by
whom.

## Model guidance

No model change. The oracle partition for the RED brief:

- **Mechanical** - AC-1 and AC-2's structure (resource types, five sizes,
  32 bpp, PNG entries, declared size = decoded size). Pin exactly; leave
  nothing open-ended.
- **Settled** - AC-2's sample values and AC-3's identity. Read them out of
  `icon.md` and MC-086's runtime icon. The tolerance of 2 at 16 and 24 px is
  the only allowance, for the renderer's anti-aliasing at sizes where one
  unit is under half a pixel; do not widen it, and do not move a sample off
  an edge it turns out to sit on - report it.
- **Oracle-free** - none.

**The PE parser is the part that can be quietly wrong.** In RED the exe has
no icon group, so a parser that never finds anything would also "fail
correctly". RED therefore records, in the handoff, what the parser *does*
find in today's exe (the list of resource types present, which may be just a
manifest or nothing, and the `.rsrc` section's presence or absence), and runs
the parser once - not committed - against a Windows exe known to carry icons
(for example `C:\Windows\explorer.exe`), pasting the groups it lists. GREEN
confirms the parser finds the five entries in the new exe.

## Out of scope

- **The runtime window icon**, the SVG asset and the 256 raster: MC-086.
- **Version info, product name, company or copyright resources**
  (`VERSIONINFO`), a manifest change, or any resource other than the icon
  group and its images. One `ICON` statement in the `.rc`, nothing else.
- **Redesigning the artwork**, including hand-tuned or pixel-hinted small
  sizes. Every size is rendered from the SVG as `icon.md` says. If the 16 px
  render looks muddy by eye, that is a design question for the user, raised
  at REVIEW, not something GREEN fixes.
- **Sizes beyond 16/24/32/48/256** (20, 40, 64, 96, 128 ...).
- **BMP/DIB icon entries** for pre-Vista Windows. PNG entries only.
- **A dark-mode or high-contrast variant.**
- **An installer, Start-menu entry, file association, or creating the
  Send-to shortcut for the user** (`architecture.md`, "Deployment shape").
- **macOS or Linux icon formats.**
- **Committed `.ico`, `.png` or `.rc` files.**

## Test plan

One file, `crates/app/tests/exe_icon.rs`, integration level: the contract is
the exe file on disk, and the cheapest thing that can falsify it is reading
that file. The file holds a PE `.rsrc` parser and the checks as functions over
parsed data; every check returns a list of named failures, and every control
asserts the exact set of names it fails.

| AC | Oracle | Real-exe test | Controls (in-memory, same check functions) |
|---|---|---|---|
| AC-1 | mechanical | `the_exe_holds_one_icon_group_listing_16_24_32_48_and_256_at_32_bpp` | no icon group (manifest-only and no resources at all); two groups; 256-only group; five-size group passes (positive, and byte 0 reads 256); 8 bpp at 16; a sixth 64 px image; malformed/truncated header |
| AC-2 structure | mechanical | `every_icon_image_in_the_exe_is_a_png_of_the_size_the_group_declares` | 48 declared / 32 px PNG; DIB entry; missing `RT_ICON` id; five correct PNGs pass (positive) |
| AC-2 samples | settled | `every_icon_image_in_the_exe_has_a_clear_corner_and_the_blue_tile` | solid `#0067C0` entry fails (0,0) - one size, and all five; tolerance pinned: +-2 inside at 16/24, +-3 outside, +-1 outside at 32/48/256, alpha 254 outside everywhere |
| AC-3 | settled | `the_exes_256_image_is_the_window_icon_pixel_for_pixel` | window icon's own pixels pass (positive); window icon with (128,128) altered fails, naming that pixel; 256 entry encoded from premultiplied pixels fails; group without a 256 fails |

AC-2. Not pinned: `VERSIONINFO` or other extra resource types (the AC says
nothing about them, and a manifest would be legitimate), `wPlanes`,
`dwBytesInRes`, language id, group name/id.

**Notes for GREEN.**

- ICO file vs resource: the `.ico` GREEN writes has a 6-byte header
  (0, 1, count) and 16-byte `ICONDIRENTRY`s ending in a `u32` offset to the
  image bytes. `rc.exe` turns it into one `RT_GROUP_ICON` whose 14-byte
  entries end in a `u16` `RT_ICON` id, plus one `RT_ICON` per image. The test
  reads the resource form. As far as I know `rc.exe` copies `bWidth`,
  `bHeight`, `wPlanes` and `wBitCount` from the ICO directory rather than
  deriving them from the PNG, so write `wPlanes` 1 and `wBitCount` 32, and
  width/height byte 0 for 256 - verify against the AC-1 failure listing.
- `embed-resource` links with `cargo:rustc-link-arg-bins`, so the resource
  lands in the bin, which is what `CARGO_BIN_EXE_manhwa-cropper` points at.
  Under the coverage gate the exe is `target\llvm-cov-target\debug\...` and
  the build script runs there too.
- Encode every PNG as RGBA8 with straight alpha (demultiply, as `build.rs`
  already does for the 256). An RGB PNG would decode with alpha 255 at (0,0)
  and fail samples.
- Interpretation recorded: "#0067C0 with alpha 255, each channel within 2"
  is read as RGB within 2 and alpha exactly 255 at 16/24, as MC-086 read the
  panel sample. If the 16 or 24 render puts alpha below 255 at (2,8)/(3,12),
  report it rather than widening.
- Timing: the whole file runs in 0.02 s plain and 0.02 s under the coverage
  gate (`gates.sh --fast`, 2026-11-04).
