## Acceptance criteria

- **AC-1** — Given a finished run, when the status slot is painted, then the
  result line is vertically centred in the 40 pt slot: the space above it and
  the space below it are equal, within a tolerance no larger than one point
  (`layout.md`, the status slot; `centred_line`).
  *Measure both gaps in the same frame from the painted line's own height, not
  against a constant: a font update moves the line's height and must not move
  this criterion. Control: the same assertion must fail for a line painted flush
  to the top of the slot, which is what `(SIZE_STATUS - content) / 2.0` becoming
  `* 2.0` or `% 2.0` produces.*

- **AC-2** — Given a run under way, when the status slot is painted, then the
  progress bar and the count beneath it are centred **as one block** — equal
  space above the bar and below the count — and separated by `space-tight`
  (`tokens.md`), within the same tolerance.
  *This is the sum at `gui.rs:481`: a mutated sum mis-measures the block, so the
  block is centred as though it were a different height. Control: swap the two
  gaps and the assertion must fail.*

- **AC-3** — Given a flagged row whose file name is too long for the list, when
  the row is painted, then the whole painted row — name, separator and reason —
  is no wider than the width the list gives it.
  *Drop this criterion before RED if the check in `## Context` shows MC-022's
  suite already reddens on the same mutation; record the result either way.*

- **AC-4** — Given the shipped painter mutated so that `centred_line`'s
  `(SIZE_STATUS - content) / 2.0` becomes `(SIZE_STATUS + content) / 2.0`
  (today `gui.rs:505`), when the new tests run, then at least one fails. And
  given `status_slot`'s `SIZE_PROGRESS + SPACE_TIGHT + …` mutated so the first
  `+` becomes `-` (today `gui.rs:481`), when they run, then at least one fails.
  *Two named survivors as this story's negative controls, on the two different
  functions AC-1 and AC-2 cover. Record both under `## Gate probes`.*

Every assertion here is a **relation between two measurements in the same
frame** — gap above against gap below, painted width against available width.
Do not assert an absolute y coordinate: it encodes the window's whole layout
above the slot, so any change anywhere above it breaks a test that is about
none of those things. MC-022 took the same approach with widths and its
`## Test plan` explains why.

Re-use MC-021's helper for finding a widget's shapes in the paint list.

### The hard part: the status slot paints no boundary of its own

"Equal space above and below" is a statement about the **slot**, and
`status_slot` is an `allocate_ui_with_layout` with `set_min_size`: it reserves
space and paints nothing. Its top and bottom edges are not in the paint list,
and `## Model guidance` rules out writing them down as coordinates, because
`192.0` encodes the window margin, the drop zone's height, the folder row's
height and both gaps above the slot — none of which this story is about.

**The slot is derived from its neighbour above, the folder button:**

```
slot.top    = the folder button's painted bottom edge + `space-stack`
slot.bottom = slot.top + `size-status`
```

`paint` stacks the four regions in one `Ui` whose `item_spacing.y` is
`space-stack`, and `layout.md`'s column table gives the folder row
`size-control` — the button's own height — so the button's painted bottom edge
is the row's. Two design constants and one painted measurement.

Three properties decided it over the flagged row below, which `## Notes` in the
orchestrator's brief offered as anchor 1:

1. **It exists in every state.** The flagged list paints nothing at all while a
   run is under way, so an anchor taken from below is unavailable to AC-2 and
   would have forced a cross-frame comparison — two harnesses, plus an argument
   that the two frames agree above the slot. The button is painted in `Done`
   and in `Processing` alike (`Rect [[371.0 152.0] - [496.0 184.0]]` in both),
   so both criteria are measured **in the frame they are about**, which is what
   `## Model guidance` asks for.
2. **It cannot move when the slot's arithmetic is wrong.** This is not
   hypothetical and it is the reason to prefer above over below.
   `allocate_ui_with_layout` allocates `max(min_size, content)`, so AC-4's
   first mutation — which centres a 16 pt line as though the slot were 56 pt —
   makes the slot's content 44.0625 pt tall, the slot allocates 44.0625 instead
   of 40, and **everything below it moves down by 4.0625 pt**. An anchor taken
   from the row below would have followed the defect: the measured disagreement
   would have been 24.0 pt rather than the true 32.125. It would still have
   gone red, but it would have under-reported the error and made the handoff's
   predicted magnitude wrong. Verified rather than assumed, per the brief.
3. **It is found by the caption inside it**, through MC-021's
   `innermost_rect_containing` verbatim — so the identification does not depend
   on a position, which is the quantity these tests measure.

**The anchor is checked, not assumed.**
`the_status_slot_these_gaps_are_measured_in_is_where_both_its_neighbours_put_it`
derives the slot from the button above and asserts the flagged list's own
painted box begins exactly `space-stack` below it. Measured: slot 192.0–232.0,
list box top 240.0, gap 8.0 — exactly `space-stack`, to 0.0. Two independent
neighbours agree on where the slot is, so "the slot is 40 pt and sits here" is
a fact about the frame.

### Why every assertion is a relation and not a coordinate

| Assertion | Left of the comparison | Right of the comparison |
|---|---|---|
| AC-1 | the painted result line's top minus the derived slot top | the derived slot bottom minus the line's painted bottom |
| AC-2, centring | the painted bar's top minus the derived slot top | the derived slot bottom minus the painted count's bottom |
| AC-2, separation | the painted count's top minus the painted bar's bottom | `space-tight` |
| AC-3 | the painted row's width | the painted content column's width |
| instrument | the painted list box's top minus the derived slot bottom | `space-stack` |

Every left-hand side is a difference of two measurements taken from the same
frame; the derived slot is itself a painted measurement plus two constants. No
assertion in the file names an absolute y coordinate. The controls deliberately
place their slot at y = 1000, nowhere near the real window, so a check that
started reading absolute positions would fail there.

### Where the tolerance comes from

Not from what the painter produces. Every length in the chain — `size-status`,
`space-stack`, `space-tight`, `size-progress`, the button's bottom edge — is
exact arithmetic on constants. **Exactly two steps are not:**

1. **Half a physical pixel.** `centred_line` centres
   `ui.text_style_height(&TextStyle::Body)`, which is egui's *unrounded* row
   height for the font; the galley it then paints has its row height rounded to
   a whole physical pixel (`epaint-0.36.2/src/text/text_layout.rs:971`,
   `max_row_height = point_scale.round_to_pixel(max_row_height)`). Since
   `gap_above - gap_below` reduces algebraically to `painted - reserved`, this
   contributes at most `0.5 / pixels_per_point`. The harness runs at 1 pixel
   per point, so 0.5 pt.
2. **One 1/32 pt grid step.** `Ui::allocate_space` snaps the space above the
   content to a multiple of emath's `GUI_ROUNDING` (1/32,
   `emath-0.36.2/src/gui_rounding.rs:18`). A shift of `d` there lengthens one
   gap and shortens the other, so it moves their *difference* by `2d`, and
   `|d| <= 1/64`. So at most 1/32.

**Tolerance = 0.5 / ppp + 1/32 = 0.53125 pt**, read off the harness at run time
rather than written down, and asserted to be inside AC-1's stated ceiling of
1 pt rather than assumed to be.

This is where the earlier guess in the brief — that the residual would be zero
and the tolerance could be tiny — turned out to be wrong, and it is worth
recording: the shipped painter does **not** produce equal gaps. It produces
11.9375 above and 12.0625 below, because it centres the height it reserved and
the paint list shows the height it painted. The 0.125 pt is 16.125 − 16.0, the
pixel rounding above, and no amount of correct code removes it. A tolerance
"derived from what the code does" would have been 0.125; a tolerance derived
from the mechanism is 0.53125 and survives a font change.

### AC-3: what "the width the list gives it" is measured against

The list's own width is not in the paint list, and **the row's own container is
useless as a bound**: a row too wide for its box *grows the box*
(`allocate_ui_with_layout` allocates `max(min_size, content)`), so a mutant that
overflows the list would quietly widen the very number it was being judged
against and the test would pass. Checked: with the budget mutated the row is
578.1875 pt wide and its container grows to match.

So the bound is the **content column** — the drop zone's painted rect.
`paint` reads `ui.available_width()` once inside the `space-window` margin and
hands that one number to the drop zone, the folder row and the status slot;
`flagged_list` is shown the same `Ui`. `layout.md` says the same: "Every region
is the full inner width." A scroll bar can only make the list *narrower* than
the column, never wider, so `row <= column` is **implied by** the criterion and
never implies it: a necessary condition, deliberately the conservative half,
and it cannot be inflated by the defect it judges. Stated in the test's own
docs so no later reader mistakes it for the tight bound.

**The margin is 3.0 pt out of 472**, which is thin in absolute terms and was
worth a second look. It is not a calibration: `truncate_right` keeps characters
until the next one would not fit, so a row *ought* to come within one glyph of
filling its budget, and the 3.0 pt is "the next character was 3 pt wide". The
inequality is mechanical and holds by construction of the painter at any font
size; nothing here is tuned. Against it the mutant is 106.1875 pt over — the
discrimination is 35x the margin, in the direction that matters.

### The controls, and why each one calls a primitive

Every check in the file is a function returning `Vec<String>`, and four tests
feed those functions the numbers each defect would produce. **Each control
calls the specific check it claims to pin, not the composite that wraps it.**
That is not stylistic: the first draft of the missing-bar control called
`progress_block_problems`, and it **passed with the empty guard deleted** —
folding `min` over no rects yields `+inf`, the separation check objects to an
infinite gap, the control sees a non-empty problem list and reports success.
A pass, for a reason with nothing to do with the bar being missing. The guard
was split into its own `bar_problems` and the control aimed at it; see
`## Regressions` for the run that found this and the run that closes it.

Each control also feeds its check the **shipped** numbers and asserts they are
accepted, so a check that rejected everything would satisfy no control here.
