## Context

Found while planning [MC-038](MC-038.md) on 2026-09-19. `integration` has an
`evidence` line and **no `floor`**:

```
$ grep -E "^(evidence|floor|slow) \| integration" .claude/harness/project.conf
slow     | integration | release rebuild of the workspace plus the 100-image timing run and the corpus; minutes
evidence | integration | test result: ok\. [1-9][0-9]*
```

`project.conf` states the distinction this story acts on:

> An `evidence` line catches a gate that did NOTHING. A `floor` catches one
> that quietly started doing much less: a test project dropped from the
> workspace, a lint target narrowed to one directory, a suite that went from 47
> tests to 3. All of those exit 0 and match the evidence regex.

So `integration` today would report `PASS` on a suite that shrank from fourteen
tests to one. That gate is the only thing running `crates/engine/tests/corpus.rs`
and `corpus_accuracy.rs` — the two suites that **score** the corpus and that
carry MC-037's `Split::Tuning` filter. Every v1 accuracy number, and every
number MC-038's document will produce, is denominated by them.

### The trap this story exists to walk into carefully

`project.conf` is explicit that a floor is measured from the first run of
digits at or after the start of the evidence match, and equally explicit about
what that means in practice:

> The first `test result: ok. N` line cargo prints belongs to the first test
> binary that ran at least one test. Cargo runs the workspace members in the
> order `Cargo.toml` lists them (`crates/core` first) and each member's test
> targets alphabetically [...] **this number tracks ONE binary, not the
> workspace's 124 tests**, and a new target sorting before `content` would move
> it.

Under `-- --ignored` that ordering question is **different from the `unit`
gate's and has not been worked out**, because most targets contribute zero
ignored tests and `test result: ok. 0` does not match `[1-9][0-9]*`. Which
binary supplies the first *matching* line is therefore a property of which
targets have ignored tests at all, and that is the thing to measure rather than
assume. MC-037's run observed `integration (139s, observed 9)` — 9 being
`corpus.rs`'s nine tests — but one observation is not a derivation.

**This is why it is a story and not a one-line edit**, and why it was
explicitly kept out of MC-038: a floor whose number moves when an unrelated
test target is added is a coin-toss gate that looks exactly like a real one, as
`project.conf`'s `no-count` section documents at length for `lint`, `typecheck`
and `build`.

### The gate question

`required_gates: [integration]` — the gate this story changes, escalated here
at PLANNED. It is `optional` in `project.conf` and stays that way: this story
puts a floor under it, it does not promote it. But a story that changes a gate
and does not run it has checked nothing, and `gates.sh` binds `required_gates`
while it runs.

**Note for whoever picks this up after [MC-039](MC-039.md):** this is a `chore`,
not a `spike`, so `check-boundaries.sh` already enforces that escalation
against the recorded run. MC-039 is what makes the same true for a spike.

## Acceptance criteria

- **AC-1** — Given `.claude/harness/project.conf`, when `bash scripts/gates.sh --audit` runs, then it accepts the new `floor | integration | <n>` line: the gate has an evidence line, the regex covers the whole number, and the gate is not declared `no-count`. *Control:* `--audit` refuses a floor without an evidence line and a floor that is not a number; both refusals are to be observed, not assumed, and pasted in `## Gate probes`.
- **AC-2** — *The floor is measured, not guessed.* Given a full `bash scripts/gates.sh` run, then `## Gate results` records `observed <n>` for `integration`, and the floor set in `project.conf` is that measured `n`. The story records **which test binary supplied the first matching `test result: ok. N` line**, and how that was determined. *Control:* a floor set above the observed count fails the gate immediately; a floor set to 1 passes on any non-empty suite and defends nothing. Both bounds are to be shown.
- **AC-3** — *The floor has been observed to fail.* Given the floor in place, when the `integration` gate **command** is narrowed in `project.conf` — a test-name filter appended, nothing under `crates/engine/tests/**` touched — so that the counted binary reports fewer tests than the floor, then `integration` **FAILS** naming the floor and the observed count. Revert the narrowing, re-run, confirm green. Output pasted in `## Gate probes` — a gate that has never been seen to fail is not a gate.
- **AC-4** — *The counted binary is named where the next person will look.* Given `project.conf`, then a comment above the floor records which binary the number tracks, what would move it, and that lowering it to make the gate pass is forbidden — the same treatment the `unit` floor already has. *Control:* the `unit` floor's comment is the template; a floor with no comment is one the next agent lowers without knowing what it defended.

## Model guidance

Model: **default**. Every criterion is mechanical. The one piece of judgement —
which binary supplies the counted line under `--ignored` — is a measurement,
and AC-2 requires it to be made rather than reasoned about.

**Oracle partition:**

| Kind | What |
|---|---|
| **Settled — read out, never re-derive** | `project.conf`'s rules for `floor`, `evidence` and `no-count`; the `unit` floor's comment as the template for AC-4; that `integration` stays `optional` |
| **Oracle-free** | The floor's value. It is whatever AC-2 measures, and AC-2's controls bracket it from both sides |
| **Mechanical — pin exactly** | AC-1, AC-3, AC-4 |

## Out of scope

- **Promoting `integration` to `required`.** It is `slow` — a release rebuild
  plus the 100-image timing run, minutes — and that is why it is optional. This
  story changes the floor, not the severity.
- **Making the suites faster, or splitting them.** If the counted binary turns
  out to be a poor thing to count, say so in `## Notes` and file a story; do
  not reorder test targets to move the number.
- **Touching `crates/engine/tests/corpus.rs` or `corpus_accuracy.rs`** at all.
  AC-3's probe narrows the gate command instead of the suite; see
  `## Amendments`.
- **Any other gate's floor.** `lint`, `typecheck` and `build` are declared
  `no-count` and `gates.sh --audit` refuses a floor on them; that is correct
  and is not to be worked around.

**AC-3, amended at PLANNED on 2026-09-21 by the user (Lead PO escalated).**

*Was:* "Given the floor in place, when **a corpus suite is reduced** so that the
counted binary reports fewer tests than the floor, then `integration` FAILS

*Now:* "Given the floor in place, when the `integration` gate **command** is

tests than the floor, then `integration` FAILS naming the floor and the observed

*Why.* The criterion as written could not be satisfied in the phase that owns
it. `## Gate probes` is the Feature Developer's section, written in GREEN and
GATES, and the probe demanded a write to a `test` path:

```
$ bash -c '. .claude/hooks/lib.sh; classify "crates/engine/tests/corpus.rs"'
test
$ grep -E '^(GREEN|GATES)' .claude/harness/phases.conf | cut -d'|' -f2

 vendor,ignored,source,config,docs,harness
```

`test` is absent from both, so the phase lock refuses the mutation at exactly
the phase AC-3 happens in. The story's own "Out of scope" anticipated that
mutation, so this is a defect in the plan and not a misreading of it.

`project.conf` classifies `harness` and is writable in every phase, so the
narrowing is legal where the probe lives. The probe's discriminating power is
unchanged: the floor is measured out of the first matching `test result: ok. N`
line, and that number cannot distinguish a suite whose tests were deleted from
one whose tests were filtered out — it reads a count either way. Narrowing is
also the archetype `project.conf` itself names for what a floor catches ("a
lint target narrowed to one directory"). This is recorded here rather than left
as a PLANNED-phase edit because `check-boundaries.sh` 3d compares the criteria
against the base branch "whatever phase the edit was made in".

Stated as fact — the tests read these, so a different shape is a failure, not a

1. A line in `.claude/harness/project.conf` matching, after `|`-splitting and

### One discovery that should change nothing but deserves recording

`scripts/gates.sh`'s `work_count()` comment says a regex that stops mid-number —
"the `[1-9]` in `test result: ok\. [1-9]`" — "measures a truncated count". It
does not, and this was measured while building control #7:

```
1 wide  on 14 -> [14]      # test result: ok\. [1-9][0-9]*
2 narrow on 14 -> [14]     # test result: ok\. [1-9]      <- not truncated
3 wide  on  0 -> []
4 anydig on  0 -> [0]      # test result: ok\. [0-9]
5 raw narrow match: [test result: ok. 14 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out]
```

The reason is line 289 of `gates.sh`: the match is `(<regex>).*`, so the trailing
`.*` extends it to the end of the line and the first digit run is read from the
whole remainder. Truncation would need digits *between* the match start and the
count. So AC-1's "the regex covers the whole number" is a **manifest rule with
no observable consequence at this call site**, which is why assertion #8 checks
the regex text rather than a measurement, and says so in a comment. The
load-bearing part of `[1-9][0-9]*` is the **leading `[1-9]`**, which keeps
`test result: ok. 0` lines from supplying the count — that is asserted
functionally by #6. Nothing here needs fixing for this story to be correct;
`scripts/**` is out of this story's scope, and the comment in `gates.sh` is a
documentation defect worth a separate story if anyone agrees it is one.

### `work_count`'s comment is wrong, and the real consequence is a different one

The test-developer escalated that `scripts/gates.sh`'s `work_count()` comment
does not reproduce. Re-derived independently here — `gates.sh`'s own
`clean_log`/`work_count`, against real log *files* so `clean_log` runs, on five
inputs the subagent did not use:

```
inputs the subagent did NOT use:
  836 passed                         narrow=836    wide=836
  9 passed                           narrow=9      wide=9
  1000 passed                        narrow=1000   wide=1000
  5 passed, CRLF                     narrow=5      wide=5
  203, ANSI colour                   narrow=203    wide=203

if the comment were right, narrow would read 8, 9, 1, 5, 2 respectively.
```

`narrow` is `test result: ok\. [1-9]` — the exact regex the comment calls
truncating — and `wide` is `test result: ok\. [1-9][0-9]*`. They agree on every
input. The cause is in the implementation: the match is `($2).*`, so the
trailing `.*` runs to end of line and `grep -oE '[0-9]+' | head -1` then reads
the first *complete* digit run out of that span. A regex cannot truncate a
count it does not have to contain.

The comment is not merely wrong, it obscures a real consequence that is
narrower and sharper: a restrictive **leading** digit class does not truncate,
it makes the line *not match at all*, so the count is taken from some later
line instead. `test result: ok. 0` against `[1-9]` yields no measurement — and
that is precisely the mechanism this story's AC-2 ordering question turns on,
since most targets contribute zero ignored tests under `-- --ignored`.

**No impact on this story.** `integration`'s evidence regex is already the wide
form, so AC-1's "the regex covers the whole number" holds either way; the
suite pins that clause as a manifest rule with a control, rather than
behaviourally, which is the honest reading. Nothing in `scripts/**` was
touched. A documentation fix to `gates.sh` lines 271-273 is out of scope here
and wants its own story.

### A red found in GREEN that did NOT reproduce — load-induced, not a standing failure

GREEN reported that `bash scripts/selftest.sh` — the step
`.github/workflows/gates.yml` runs before the gates — was "no longer all green
on this machine", with `gates: 78 passed, 4 failed`, all four in the
lock-waiting block of `.claude/tests/gates.test.sh`:

```
    FAIL waiting is the default
         expected to contain: Waiting for it to finish
         actual:               note: the gate run lock was left behind by pid 3652562, which is gone. Taking it over.
    FAIL and it gives up out loud / saying nothing ran / and exits 3
```

**The Lead PO could not reproduce it.** Run on an idle machine, immediately
after GREEN returned and against the same shipped manifest:

```
$ time bash scripts/selftest.sh gates
gates: 82 passed, 0 failed
1 harness suite(s) passed.

real    3m18.001s
```

82/0 — the same count RED recorded on 2026-09-21. So the suite is green and
this is **not** a standing red, not a CI blocker, and not something to file
against `gates.test.sh` as a defect.

**GREEN's diagnosis was reasonable and its arithmetic does not hold.** It timed
`bash scripts/gates.sh --list` at 73-154 s per invocation and reasoned that the
fixture's eight setup invocations cost ~812 s against a live `sleep 30 &` lock
owner, so the owner was dead before the wait assertions ran. That timing
reproduces here — five runs at 103, 72, 96, 91, 142 s — but it cannot be the
explanation, and the whole-suite run above is the disproof: the `gates` suite
makes far more than eight `gates.sh` invocations and finishes in 198 s. If an
invocation inside the fixture cost 90 s, the suite could not complete at all.

The per-invocation cost therefore belongs to the *outer* shell path — a fresh
top-level `bash` under this environment's command layer, with whatever scanning
sits in front of it — and not to `gates.sh`. Invocations made as children of
one already-started script do not pay it. Measuring the outer path and applying
the number to the inner one is the mistake; it is the same shape as the
`ci-factor` trap `project.conf` documents at length, where gate wall time was
extrapolated to per-test time and read 14x against a real 3.4x.

**What is real, and is worth a story.** The fixture is time-coupled: it pins
lock-waiting behaviour against a `sleep 30 &` owner, so under heavy enough load
— GREEN was running several minutes-long release rebuilds concurrently — the
owner dies during setup and `gates.sh` correctly takes the lock over, which is
the behaviour a *different* assertion in the same file pins. That is a genuine
flake with a real failure mode on a loaded CI runner, and it wants an injected
staleness signal rather than a wall clock. It is not this story's: nothing here
touches `.claude/tests/**`, and `gates.test.sh` never reads the real manifest
(its only occurrence of `project.conf` is a comment on line 397).

No follow-up is needed for "bash on this box costs 80-150 s per script" as a
machine fault; that cost is real but is paid by the tooling layer, not by the
harness, and it does not reach the fixture.
