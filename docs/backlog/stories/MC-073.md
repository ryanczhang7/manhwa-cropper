## Context

[MC-071](MC-071.md)'s held-out run (scored commit `4539e12`) cut one column
of `n05`, `2025-11-01 12_34_31.png` (`toongod`, dark, 2560x1440):

- crop at margin 0: columns **1007..1538**, rows 167..1400 (end exclusive);
- the user's mark: `1006,167 532x1233`, columns **1006..1538**;
- MC-071's frozen oracle: `T` 167, `B` 1400. The rows are exact; the only
  fault is the left column.

[MC-072](MC-072.md) moves it to `tuning` and names it in the zero-clip
suites' `KNOWN_CLIPS`, pinned to today's crop. This story removes it.

**Nothing below is a finding.** No agent has measured this image. The causes
are candidates, from the numbers MC-071 recorded and from the corpus pins:

- **Candidate A: column 1006 is a dim edge column**, like `Screenshot
  (2705).png`'s column 1472 in [MC-070](MC-070.md) (mean luma 35.1 against a
  site background of 11). There, the fix that kept the column moved six other
  `tuning` crops outward, the predicate could not tell them apart, and the
  user re-marked: *"Mark ends at 1471"* (MC-070 `## Amendments`).
- **Candidate B: a dark, row-varying art edge read as margin**, like `f09`'s
  right edge in [MC-067](MC-067.md) (`Margin::belongs` branch 1 in
  `crates/core/src/flat.rs`), on the left side this time. `f09` shares the
  reader, the layout and the mark's left column (`1006,167 533x1233`), and its
  crop's left edge was right.
- **Anything else** the measurement shows.

**Before RED, the Lead PO measures** (MC-069 and MC-070's practice): column
1006's luma over the mark's rows (mean, median, max, share at the site's
background value) against column 1005 (site) and column 1007 (art), with
`flat::locate_column`'s and `Margin::belongs`' view of each. The criteria
below are drafted and are **re-cut by that measurement before RED**, with no
Amendment needed while the story is PLANNED.

**Whether column 1006 is art is the user's call, not an agent's** (MC-070's
precedent). If the measurement says it reads like (2705)'s column 1472, the
question goes to the user in plain words with the numbers, before RED:
re-mark the box to start at 1007, or fix the crop. A re-mark changes the
manifest entry and the frozen tables that pin it (`FRESH_HELD_OUT`,
`MARKED_TUNING_RECTS`), and this story then becomes taking `n05` off the
lists with its mark amended. It is never decided by an agent.

## Acceptance criteria

"Both margins" means 0 (the default) and 3. Column bounds are end-exclusive.
Drafted; re-cut by the Lead PO's measurement before RED (see `## Context`).

- **AC-1** — *`n05` keeps its left edge.* **Given**
  `2025-11-01 12_34_31.png`, **when** it is processed at both margins,
  **then** the outcome is `Cropped` and the crop:
  - contains the mark `1006,167 532x1233` on all four sides, so its left edge
    is at column 1006 or left of it;
  - lies within rows 167..1400 (`T` and `B` from MC-071's frozen oracle);
  - at margin 0, keeps no column of the site background beyond the mark (the
    crop is the mark's columns, 1006..1538, unless the measurement shows a
    background column the user rules otherwise).
  It is taken off every MC-072 list it is on (`KNOWN_CLIPS` in each suite,
  `KNOWN_MISSES`, the crop pins), and its `MAIN_CROPS` rows are re-measured.
  Red on `main` (after MC-072): today's crop starts at 1007.
- **AC-2** — *Nothing else moves, and no clip anywhere.*
  - Every other marked `tuning` crop is exactly what `main` produces at both
    margins (`corpus_tuning_crops_unmoved.rs`). The only exception is a row
    re-measured and listed, named and explained in `## Notes`, and approved
    by the user if it widens or narrows a crop by a column the user marked
    outside or inside the art.
  - Zero clips holds on every marked `tuning` entry at both margins, except
    the entries MC-074 to MC-076 own while they remain listed.
  - Every flag entry stays flagged.
  - `EPIC-08`'s side-edge suites (`corpus_sides.rs`, `corpus_page_column.rs`)
    pass unloosened: no side starts carrying page background on any other
    entry.
  - **Controls:** the existing one-column-wider control
    (`widening_every_expected_rect_one_pixel_on_the_columns_makes_the_zero_clip_check_fail`)
    still fires; reverting the fix turns AC-1 red on `n05`. The probe is
    recorded in `## Notes`.
- **AC-3** — *A generated reproduction*, in the required `unit` gate, of the
  cause the Lead PO measured: a generated image with `n05`'s left-edge shape,
  red on `main` (cut by one column at both margins), and a **control** on the
  same geometry that differs only in the cause (for candidate B, the fringe
  column replaced by the site value) which crops exactly to the art and
  passes today and after. If it cannot be built to fail today, `## Notes` says
  why, with the attempt's output, and AC-1 carries the regression alone.

## Model guidance

Model: default. The Lead PO measures the cause before RED and orchestrates;
the Test Developer writes RED; the Feature Developer writes GREEN.

**Oracle partition.**
- **Settled, so read it out:** `n05`'s mark (MC-068's frozen table); `T` 167
  and `B` 1400 (MC-071's frozen oracle); MC-071's recorded crop; zero clips;
  every `Tuning` field.
- **Mechanical, so pin it exactly:** AC-1's bounds and list removals, AC-2's
  unmoved crops.
- **Oracle-free: the cause.** RED states it as a generated reproduction with
  a control that differs only in the cause (AC-3), and demands the control
  fire hard.
- **A person's call:** whether column 1006 is art (only if the measurement
  makes it a question); any `Tuning` field moving.

**Success condition, which can come out either way:** `n05` passes AC-1, the
integration command with `--no-fail-fast` is green with no other crop moved,
and AC-3's reproduction is red on `main` and green after while its control
holds. It **fails** on any other moved crop not named and approved, a clip
anywhere, a threshold swept until `n05` passes, a colour signal, or a mark
changed without the user's ruling. A trustworthy "the fix moves other crops,
so it stops and asks" (MC-070's outcome) is a legitimate result, not a
failure of the story.

## Open questions

1. **Only if the measurement makes it a question:** *"Your box for this
   screenshot starts one column further left than the app's crop. That column
   is [numbers]: dimmer than the art beside it, brighter than the background.
   Should the box start one column right, or should the app keep that
   column?"*
   - *Recommended: decided on the numbers.* If the column reads like the
     (2705) column you re-marked, and keeping it moves other crops, start the
     box one column right, as you chose then. If it is plainly art, fix the
     crop.
2. If the fix would move any `Tuning` field (a threshold), it is put to the
   user with the measured cause first. Fixes never move thresholds without
   asking.
