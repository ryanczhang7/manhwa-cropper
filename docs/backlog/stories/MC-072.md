### How the failures enter `tuning`

**Open question 3.** Recommended, as MC-064 did: named known exceptions,
**exact in both directions**. Each list pins **today's crop exactly**, rect
and outcome at both margins, measured on the scratch copy. A test naming the
list fails if any *other* marked `tuning` entry fails it, and fails if a
listed entry's crop moves at all, so each fix story has to empty its own
entries from the lists and cannot leave a stale exception behind. The lists
already exist and are empty (`KNOWN_CLIPS` in `corpus.rs`,
`corpus_accuracy.rs`, `corpus_sides.rs`, `corpus_viewport.rs`;
`MC064_CROPS` in `corpus_accuracy.rs` and `corpus_sides.rs`; `KNOWN_MISSES`;
`KNOWN_BACKGROUND_SIDES`; `STAGE_DECLINED`). A crop that keeps furniture
where the stage located a viewport gets a named list of its own in
`corpus_viewport.rs` (a known-not-furniture-free list), exact both ways, if
and only if a test fails on it. An entry goes on a list only where a test
measurably needs it; one no test needs is left off and the reason recorded,
as MC-064 left `f09` off `corpus_viewport.rs`'s list.

### The route: RED, then SCAFFOLD

`fixtures/corpus/manifest.json` and every file under `crates/engine/tests/`
classify as `test`. The route is MC-042's, MC-056's and MC-064's: **RED**
writes the new pins, floors and exception lists and watches them fail
against the unmoved manifest; **SCAFFOLD** changes the four `split` values
and writes `corpus.md`. No production source is written; `## Scaffold
inventory` names the manifest and the test files, as MC-064's does.

**Required gate that would fail if the artifact broke:** `unit`
(`corpus_manifest.rs`) for AC-1 and AC-2; `integration` for AC-3 and AC-4,
hence `required_gates: [integration]`.

## Model guidance

Model: default. The Lead PO measures the break list at PLANNED -> RED, as for
MC-056 and MC-064. The Test Developer writes the pins in RED (MC-064's RED is
the template: same lists, same probes, same hazard). The Lead PO drives
SCAFFOLD.

**Oracle partition.**
- **Settled, so read it out:** the four file names and their marks (MC-068's
  frozen table, `FRESH_HELD_OUT`); MC-071's recorded margin-0 crops of the
  four; the floors as the user rules them; the precedent shape of an
  exception list, exact in both directions.
- **Mechanical, so pin it exactly:** the four `split` values; every count;
  every row RED adds to a pin table, measured and never chosen; which list
  each entry lands on, by what the measured run fails.
- **A person's call:** Open questions 1 to 4.
- **Oracle-free:** none.

**Success condition, which can come out either way:**
- after the move, the integration command with `--no-fail-fast` is green;
- the only exceptions it carries are the four, each pinned to its measured
  crop, and each list entry is one some test measurably needs;
- removing any one exception turns its suite red;
- the record says which of the four the viewport stage declines on.

It **fails** if any of these happens:
- any pin row is typed rather than measured;
- any of the 11 unread fresh entries is decoded by a test or a measurement;
- a floor moves without the user's ruling recorded beside it;
- MC-071's margin-0 crops and RED's measured crops disagree and RED carries
  on anyway.

## Open questions — answer before it starts

Put to the user in these words. Each has a recommended answer.

1. **The test set drops from 15 screenshots to 11. Lower its minimum to 11?**
   The four that failed have been looked at one by one, so they move to the
   practice set, as last time. The check that the test set holds at least 15
   would then fail.
   - *Recommended: yes, 11,* matching what is left, as 15 matched the set
     when it was drawn. The 11 cannot give another real score anyway; the
     next real score needs a new draw, which sets its own minimum.
   - *Alternative:* draw four new screenshots first. That is its own story
     and would hold up the fixes.
2. **After the move, the test set has screenshots from three sites, not
   four. Lower that minimum to 3?** The only demonicrevolution screenshot in
   the test set is one of the four failures (`Screenshot (2507)`).
   - *Recommended: yes, 3.* The set is spent, so the minimum only guards
     against losing a site by accident from here on. The next fresh draw sets
     it again.
   - *Alternative:* keep 4 and add a new demonicrevolution screenshot to the
     test set. That needs a draw and your marking, as its own story, before
     any fix can start.
3. **Two of the four are screenshots where the app cut into the art. Once
   they join the practice set, the practice checks fail on them until their
   fixes land. How should that be handled?**
   - *Recommended: list them by name as known problems,* exactly as last time
     (`f09`, `f18`, `f20`). Each list records exactly what the app does now. It
     fails if a fifth screenshot starts going wrong, and also if one of these
     stops going wrong, so each fix has to clear its own names and cannot
     forget to. The two that keep the browser bar are listed the same way
     wherever a check catches them.
   - *Alternative:* do the move and the fixes in one story. That is four
     cycles in one.
4. **Should the other 11 test screenshots also move to practice now?** They
   passed, and nobody has looked at them one by one.
   - *Recommended: no, leave them,* as last time. They are spent but still
     unexamined. Moving them is cheap at any time.
   - *Alternative:* move all 15, so the practice set gains 11 more to check
     changes against.

## Out of scope

- **Any change to the crop or the detector.** Those are MC-073 to MC-076.
- **Moving the other 11 fresh entries**, unless Open question 4 is answered
  "move all". They stay `held-out` and spent.
- **Any mark change.** The four marks are the user's, frozen by MC-068, and
  MC-071 AC-2a found no conflict. If RED's measurements suggest a mark error
  (for instance, `n05`'s column 1006), it is put to the user, not corrected
  here; MC-073 owns that question.
- **Viewing the four images.** The move needs no look at the pixels. The
  diagnosis is each fix story's, measured by the Lead PO before its RED.
- **Finding which of the 11 unread entries the stage declined on.** Not
  measured, now or later.
- **Any change to `held-out-score.md`'s numbers**, and any re-run of the 15.
- **Changing the `integration` gate's command** (`--no-fail-fast` is used by
  hand, as in MC-056 and MC-064).
- **A new held-out draw.** That is its own MC-068-shaped story.
- **Repository settings.** No auto-merge; the user merges the PR.
