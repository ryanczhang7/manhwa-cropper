### How the clips enter `tuning`

This is Open question 1. **Recommended:** name them as known exceptions,
**exact in both directions**. The precedents are:
- `KNOWN_AMBIGUOUS` (MC-056);
- `KNOWN_CROPPED_FLAGS` and `KNOWN_MISSES` (MC-062).

Each list pins **today's crop exactly**, rect and outcome at both margins. A
test naming the list then fails in two cases:
- any *other* marked `tuning` entry clips;
- a listed entry stops clipping, or its crop moves at all.

So MC-065 has to empty the list, and cannot leave a stale exception behind.
`f13`, which does not clip, is named the same way in whichever suites its
wide crop fails.

### For the Lead PO to judge before SCAFFOLD

1. **`f09` is not in `corpus_viewport.rs`'s `KNOWN_CLIPS`.** AC-3 says the
   three clips are named "in every zero-clip suite's exception list". In
   `no_marked_tuning_crop_clips_its_mark_at_either_margin`, `f09` does not
   fail: at margin 3 its crop `1003,167 537x1233` contains the mark (the
   margin hides the 2 px clip), and at margin 0 that test counts rows only,
   which hold. A list entry there would be an exception nothing needs, and
   the Model guidance's "removing any one exception turns its suite red"
   would be false for it. I followed the measurement and the MC-056
   precedent (`corpus_viewport_stage.rs` took no exception there). `f09`
   is in the other five zero-clip tests' lists.
2. **`f18` is `STAGE_DECLINED`, a new measured list, not an exception.**
   `viewport::locate` returns `None` beside `f18`'s page column
   (`1828,0 717x1440`), so `STAGE_MEASURED` cannot hold a row for it. It is
   kept out of `viewport_entries` the way the two WebPs are, and
   `corpus_viewport_stage.rs` asserts the decline exactly. Its crop
   (`0..1440` rows, chrome and taskbar included) is still pinned by
   `MAIN_CROPS` and by the clip lists. If you would rather it were an
   exception list ("the stage must decline here"), the shape is the same;
   it is a naming call.
3. **`KNOWN_MISSES` gains all four, and no single one of them is needed
   alone.** Without any of the four the bar is 53 of 59 (89.8 %, red,
   measured in probe A). With any three it is 53 of 56 (94.6 %), green.
   That is the same property MC-062's "Skip all four" had. Each of the four
   is still pinned two ways: it must still be a miss (the existing
   assertion), and its crop must equal `MC064_CROPS` (new).
4. **Three controls were kept from going slack.** The known clips clip
   before any widening and before any narrowing, and `f13` sits 1381 px
   outside any column window. Left in, they would make three controls pass
   whatever the comparison did. So:
   - `corpus_accuracy.rs`'s 1 px widening control leaves out `KNOWN_CLIPS`;
   - its column-window control leaves out `KNOWN_MISSES`;
   - `corpus_sides.rs`'s narrowed-crop control leaves out `KNOWN_CLIPS`.

   Measured values are in the controls table. `corpus.rs`'s
   `the_left_and_right_edges_...` control was left as it was. It is a floor
   of 15 rejections out of 49, the known clips add to it, and it is not an
   MC-064 test.
5. **Hazard: a shared `CARGO_TARGET_DIR` runs stale binaries.** Test
   binaries have the same hash in the repo and in the scratch worktree, and
   `common/corpus.rs` bakes in `env!("CARGO_MANIFEST_DIR")`. Cargo rebuilds
   by mtime. My first repo integration run reused the scratch build. It read
   the **scratch** manifest and reported 36 passed with the manifest
   unmoved. Touching the repo's test files forced a rebuild, and then it went
   red as below. Before any repo run that follows a scratch run (or the
   reverse), run `touch crates/engine/tests/*.rs crates/engine/tests/common/*.rs`,
   or use a separate target dir, and check that the run says `Compiling`. I
   left the repo's files touched last, so the next repo run rebuilds.

No hidden failure involved an entry other than the four. No count or
