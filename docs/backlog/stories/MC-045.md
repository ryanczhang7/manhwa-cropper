## Context

Found while driving [MC-043](MC-043.md) on 2026-09-22, and out of scope there:
MC-043 is forbidden to touch any executable line of `scripts/gates.sh`. This
story is the executable half.

`scripts/gates.sh` has a startup cost that scales with the size of the working
tree. Measured on this checkout, which carries a 28 GB / 62,368-file `target/`:

```
bash -c true                      69 ms
scripts/phase.sh show            416 ms
gates.sh --list  (test fixture)   12,587 ms
gates.sh --list  (this repo)      73,321 ms / 105,685 ms
```

`--list` parses `project.conf` and prints it. It runs no gate, takes no lock
(there is a test pinning that), and should be effectively instant. A minute and
a half to parse a config file is not a slow gate; it is a defect in the
script's own startup.

### It is not simply a slow machine

`bash -c true` forks in 69 ms and `phase.sh show` — another harness script that
sources the same `lib.sh` — completes in 416 ms. Sourcing `.claude/hooks/lib.sh`
on its own costs 75 ms. So neither bash, nor the library, nor this machine's
fork cost in general explains it.

**On the variance, and one withdrawn reading.** These numbers move by a factor
of two between runs. An initial measurement of 372,978 ms was taken while a
background `selftest.sh` was contending for the machine; it does not reproduce
and is not evidence of anything. The two readings in the table above are clean,
and a `--fast` run in the same period spent 89 s across its five gates. Any
criterion this story writes has to survive that variance, which is the main
argument against a wall-clock threshold.

A `PS4='+$EPOCHREALTIME:$LINENO' bash -x` trace of the **fixture** run (12.5 s,
the fast case) shows no single stall. It shows ~288 traced lines with the cost
spread evenly across them, individual forked `cut`, `tr`, `printf` and
`hostname` calls each costing 0.3–0.7 s:

```
  0.67s  after  :212 trim BOOTSTRAPPED=yes
  0.65s  after  :112 hostname
  0.61s  after  :215 cut '-d|' -f2
  0.60s  after  :411 floor=
  0.58s  after  :82  printf %s ' unit '
  0.56s  after  :380 trim ' unit '
```

The 6-8x gap between the fixture (12.6 s) and this repo (73-106 s) is the part
that points at the tree: the fixture differs from the real checkout mainly in
not having `target/`. Whether that is glob expansion, a `git` call, or
something in the per-fork cost on Windows is **not yet diagnosed** — do that
before writing criteria.

### Why it is worth a story rather than a shrug

It is not cosmetic, and the cost is paid by agents rather than by a human who
can see a spinner:

- The `gates` self-test suite makes ~40 fixture invocations, so
  `bash scripts/selftest.sh gates` needs 5–13 minutes.
- During MC-043 two such runs were killed at a 400-second timeout (exit 124)
  and were read as a hang — in the same file MC-044 had just fixed a genuine
  lock-waiting flake, which is exactly the wrong place to have a second,
  unrelated reason to suspect deadlock. The phase cost real time before the
  cause was understood, and the eventual explanation had to be written into
  MC-043's brief so the Test Developer would not repeat it.
- The same cost is paid on every CI run, where `gates.sh --list`,
  `gates.sh --audit` and `gates.sh` each pay it again.

### The gate question

Not yet settled — decide it at PLANNED, before RED, and do not inherit
MC-043's `required_gates: []`. This story changes **executable** lines in
`scripts/gates.sh`, which MC-043 deliberately did not, so the reasoning that
made an empty list honest there does not transfer. Note that no `gate` line in
`project.conf` runs the harness suite (they all run `cargo`), while CI does run
`bash scripts/selftest.sh` as a blocking step with no `continue-on-error`
(`.github/workflows/gates.yml` line 37). A story that changes how `gates.sh`
measures or locks needs a `## Gate probes` entry as well.

### Starting points, not conclusions

- Diagnose the fixture-vs-repo gap before choosing a fix; a micro-optimisation
  of the 288 forks attacks the constant, not whatever the tree contributes.
- A timing assertion is the obvious criterion and the obvious trap: a wall-clock
  threshold on hardware this variable will flake. Prefer pinning something
  structural and deterministic — e.g. a count of subprocesses, or that `--list`
  does not touch the tree at all — with the wall clock as a recorded
  before/after measurement rather than a gate.
- `--list` and `--audit` are the cheapest cases to attack first: both are
  read-only, both already take no lock, and both are on CI's critical path.

### Diagnosis (PLANNED, 2026-09-22): it is `project.conf`, not `target/`

The tree hypothesis does not survive measurement. The fork cost does not depend
on the working directory: 20 forks of `/usr/bin/true` took 2.4 s from the
scratchpad, 3.3 s from the repo root, 4.0 s from `target/` and 3.1 s from
`docs/`, which is noise around ~0.15 s per fork on this machine. Nothing on the
`--list` path reads the tree: the only `git` calls are in `record_in_story`,
which `--list` never reaches.

What differs between the fixture and this repo is **the length of
`project.conf`**: the fixture's is 2–3 lines, and this repo's is 295 lines, of
which 30 are content. Both parse loops (`scripts/gates.sh` ~line 210, the
tables, and ~line 385, the gates) run `case "$(trim "$line")"` on **every**
line before deciding whether it is a comment. `trim` is `printf | sed`, so each
comment or blank line costs a subshell plus a `sed` exec per loop. Each content
line then costs three to five further `$(trim "$(printf | cut)")` pairs.

Counted with a PATH shim that logs every exec of `sed cut tr grep head date
hostname git awk mkdir …` (deterministic and repeatable, unlike the clock):

| `project.conf` | `--list` execs | `--audit` execs |
|---|---|---|
| this repo (295 lines, 7 gates) | **860** (721 `sed`, 132 `cut`) | — |
| fixture: 1 gate + evidence | 36 | 36 |
| same + 100 comment/blank lines | 236 (+2 per line) | 236 |
| fixture: 10 gates, each with evidence | 270 (+26 per gate) | — |

About 8 of the 36 are a fixed constant (`hostname`, `date`, `mkdir`, `dirname`,
the `BOOTSTRAPPED` `grep|head|cut|tr`), and that constant is not this story.
At ~0.15 s per fork, and with every `$(…)` adding a subshell fork on top of each
exec, 860 execs is the 1–3 minutes measured. The "tree" reading came from the
fixture having a short config, not from it lacking `target/`.

So the fix is to parse `project.conf` with bash builtins (parameter expansion
for trim and field split, or one `awk` pass), not to touch anything to do with
the tree. The CI audit and list steps pay the same per-line cost.

Two process counts are used below, and both are deterministic, unlike
wall-clock time on this machine (see "On the variance"):

- **execs**: processes `gates.sh` execs through `PATH`, counted by a directory
  of logging shims prepended to `PATH` for the invocation.
- **nested commands**: lines of a `bash -x scripts/gates.sh …` trace at
  nesting depth ≥ 2 (prefix `++`), meaning commands run inside a command
  substitution or subshell. This is the oracle for forks that exec nothing,
  such as `$(trim "$line")` with a pure-bash `trim`, which cost as much as an
  exec on this machine. Verified at PLANNED: bash replicates the first `PS4`
  character once per level, so `a=$(f x)` traces `++ f x` and `+ a=x`.

- **AC-1** — *Comment and blank lines are free.* Given a fixture
  `project.conf` with one gate and its evidence line, when `gates.sh --list`
  and then `gates.sh --audit` run against it and against the same config with
  100 comment and blank lines added (interleaved, not only appended), then for
  each command both the **exec** count and the **nested-command** count are
  **identical** across the two configs, and the two outputs are byte-identical.
  *Control:* on today's `gates.sh`, every comment or blank line costs +2 execs
  (measured: +100 lines, 36 → 236) and +6 nested commands (measured: +20 lines,
  136 → 256), for both `--list` and `--audit`. So this criterion is red on
  arrival.
- **AC-2** — *Gate lines are free to parse.* Given a fixture config declaring
  one gate and one declaring ten gates, where every gate carries `evidence` and
  the config as a whole includes at least one `floor`, `waiver`, `slow`,
  `ci-factor` and `no-count` line, when `gates.sh --list` and `gates.sh
  --audit` run against each, then for each command both the **exec** count and
  the **nested-command** count are **identical** for the 1-gate and 10-gate
  configs. *Control:* on today's `gates.sh`, ten gates with evidence cost +234
  execs over one gate (36 → 270, `--list`) and +1161 nested commands (136 →
  1297, both `--list` and `--audit`). So this criterion is red on arrival. The
  test also asserts both 1-gate counts are **> 0**, so a shim that intercepts
  nothing, or a trace that was never captured, cannot pass vacuously. Every
  per-gate substitution on these two paths is parse work (`trim`/`cut`, the
  six `table_lookup` calls, the `ci-factor` split), so this is satisfiable
  without touching anything but the parser.
- **AC-3** — *The parse means what it meant.* Given a fixture config that
  exercises every parsing edge today's `trim`/`cut` handles: leading and
  trailing spaces and tabs around every field, CRLF line endings, an evidence
  regex containing `|` (alternation, which relies on today's `-f3-`), an empty
  cwd field (which becomes `.`), a `ci-factor` value with and without its
  `|`-separated source, a line with no `|`, and indented comments, when `gates.sh
  --list` and `gates.sh --audit` run, then their output equals, **exactly**, the
  output today's `gates.sh` produces for that config, captured in RED and pinned
  as an expected-output literal in the test. *Control:* this test passes on
  arrival because the implementation already exists, so under the
  non-negotiables it is earned by a probe. Change `trim` so it keeps trailing
  whitespace (or change the `-f3-` split to `-f3`), watch the assertion go red,
  revert, and paste the output into `## Handoff`.
- **AC-4** — Given `bash scripts/selftest.sh`, when it runs in full after GREEN,
  then every suite passes, and the output is pasted into `## Notes` together
  with the wall time of `bash scripts/gates.sh --list` on this repo before and
  after. The wall time is a **recorded measurement, not a threshold**. No
  criterion here depends on the clock. *Control:* `selftest` is a CI step, not
  a `project.conf` gate, and never appears in `## Gate results`, so this is the
  story's only in-story evidence that the whole harness still works (see "Gate
  decision" in `## Notes`).

## Out of scope

- The fixed startup constant (~8 execs: `hostname`, `date`, `mkdir`, `dirname`,
  the `BOOTSTRAPPED` pipeline). It does not scale with anything.
- The per-gate cost of **running** gates (log scanning with `grep`,
  `record_in_story`'s `git`/`awk`). A full run's execs legitimately grow with
  the gates it runs. Only the *parse* is in scope, although a full run and
  `--gate`/`--fast` will benefit because they share the parse loops.
- Changing what `project.conf` means, adding syntax, or reformatting this
  repo's `project.conf` to be shorter. Shrinking the input would hide the defect,
  not fix it.
- `lib.sh`, `phase.sh`, `selftest.sh`, and the lock. No executable line outside
  `scripts/gates.sh`'s parsing (`trim`, the two parse loops, the `ci-factor`
  split) changes.

**AC-2 fixture choice.** A `no-count` cannot sit on the same gate as a

still pass the audit cleanly. It carries four; the ten-gate config carries all
five and scales every table with the gate count, so table parsing *and* the six
`table_lookup`s per gate are measured growing, not just the gate loop.

**AC-3 edge-case config**, built with `printf` so tabs and CRs are real bytes:
CRLF on most lines and plain LF on a few; spaces *and* tabs around every field
of the `unit` gate and its evidence line; a gate `cmd` containing `|` and an
internal tab (relies on `-f5-`, and on trim not touching the inside); an

### What the tests pin, and what they do not

**Pinned:** only CLI behaviour of `bash scripts/gates.sh --list` and
`--audit` run from a fixture root: stdout, stderr, exit code, the number of
`PATH`-resolved execs, and the number of depth-≥2 xtrace lines. **No function
or variable of `gates.sh` is imported or named by the tests** - there is no
export shape; `trim`, `table_lookup`, the tables and the loop structure can be
renamed or removed freely.

**Not pinned (implementer's choice):** parameter expansion vs one `awk` pass;
whether the two loops are merged; how tables are stored.

**What the counts mean in practice for GREEN:**
- Nothing that runs **once per line** or **once per gate** may fork: no
  `$(...)`, no pipeline (`... | while read` is a subshell - every iteration
  would trace at depth 2), no external command. A `$(table_lookup ...)`
  becomes a function that assigns a variable; the `ci-factor` split at ~500/504
  (reached only by `--audit`, which is why audit's 1-gate baseline is 80 not
  76) also has to become builtins.
- A **constant** number of forks is fine: one `$(awk ... "$CONF")` for the
  whole file, or the existing startup constant (`hostname`, `date`, `mkdir`,
  `dirname`, the `BOOTSTRAPPED` pipeline - out of scope), costs the same for
  every fixture and cancels out of every equality.
- A builtin `while` over table entries inside a lookup function is fine for
  both oracles (depth 1, no exec), even though it traces more lines as the
  tables grow - only `++` lines are counted.
- Output must not change by a byte on the AC-3 config. The traps it pins:
  whitespace inside a value is preserved (`3.4 <TAB> | <TAB> measured from CI
  run 12345 | job coverage` is printed verbatim in both modes - only the ends
  of the whole `-f3-` value are trimmed, not each `|` segment); a `cmd`
  containing `|` keeps everything after the fourth `|` (`printf "a|b"  |<TAB>cat`);
  a single trailing CR is stripped before trimming; `read -r` with a non-empty
  `IFS` would collapse or split things the old parse kept.

### Known limits

  absolute path hides from it. The nested count still sees such a call if it is

- Shimmed: sed cut tr grep head tail date hostname git awk mkdir cat wc sort
  basename dirname rm mv cp ls find uname mktemp env sleep tee xargs od
  readlink realpath expr uniq. Not `bash`. A fix that introduced an unshimmed
  external per line (`perl`, say - which rules.md forbids anyway) would be
  caught only by the nested count, and only if inside a substitution.
- Multi-line xtrace entries (an assignment whose value contains newlines)
  continue on lines that do not start with `++` unless the value itself does;
  no fixture value does.
- AC-3's literal was captured from today's `gates.sh`, so it pins behaviour,
  quirks included (e.g. `ci-factor: 1.5 |` is printed with its dangling `|`).
  That is the criterion: "means what it meant".

### Known limits of the two oracles

The exec shim counts only execs resolved through `PATH`, so a fix that called
`/usr/bin/sed` by absolute path would hide from it. The nested-command count
would still see that call, because it runs inside a `$(…)`. A pipeline with no
substitution, such as `printf | sed` at top level, traces at depth 1 and is
seen only by the shim. So each oracle covers the other's blind spot, and that
is why AC-1 and AC-2 demand both.
