## Context

The brief's features 4 and 7 in the engine: many files in, every one
processed, one `RunSummary` out with counts and the flagged names.
`batch::run(&[PathBuf], out_dir, &Tuning, progress) -> RunSummary` plans
names (MC-010), processes files on the rayon pool (decision 12), keeps
results in input order, and never lets one file's failure stop the others.
`progress` is `&(dyn Fn(Progress) + Sync)` with `Progress { done, total }`,
called once per completed file. `RunSummary` serialises to JSON with a
stable shape because MC-012 writes it to disk and MC-015 renders it.

Gate that fails if this breaks: `unit`.

## Acceptance criteria

- **AC-1** - Given five inputs - three croppable PNGs, one uniform PNG and one `.txt` - when `run` completes, then `results` has five entries in input order with outcomes `Cropped, Cropped, Cropped, Flagged(Detector(Uniform)), Flagged(Unsupported)`, and `cropped() == 3`, `flagged() == 2`, `failed() == 0`.
- **AC-2** - Given one of the inputs does not exist, when `run` completes, then that entry is `Failed { error }`, every other input was still processed, and `failed() == 1`.
- **AC-3** - Given `n` inputs, when `run` completes, then the progress callback was called exactly `n` times, each call carried `total == n`, and the sequence of `done` values is `1..=n` (strictly increasing by one).
- **AC-4** - Given `out_dir` does not exist, when `run` starts, then it is created; given it cannot be created (a path under a file), then every result is `Failed` and nothing panics.
- **AC-5** - Given a `RunSummary`, when serialised with `serde_json`, then it has the shape `{"cropped": u32, "flagged": u32, "failed": u32, "results": [{"input": str, "outcome": "cropped" | "flagged" | "failed", "output": str | null, "rect": {x,y,w,h} | null, "reason": str | null, "error": str | null}]}` with `reason` being the `Flag` variant name (`Uniform`, `NoBorderFound`, `LowContent`, `Ambiguous`, `Unsupported`, `DecodeFailed`); and `flagged_names()` returns the flagged inputs' file names in order.
- **AC-6** - Given 32 inputs on a machine with more than one core, when `run` completes, then the files were processed on **more than one thread**: the work is observed from at least two distinct `std::thread::ThreadId`s. No wall-clock duration appears in the assertion. *Control:* a deliberately sequential implementation is observed on exactly one thread and fails this **every time**, where the wall-time comparison this criterion replaced wrongly passed 20-80% of the time (measured). *Amended 2026-09-12 - see `## Amendments`.*

## Amendments

### AC-6 replaced: a thread observation instead of a wall-time comparison (2026-09-12, approved by ryanczhang7)

**What it said.** "Given 32 inputs, when `run` completes, then the wall time is
less than the sum of the per-file times measured by processing them
sequentially with `process_file` (the batch is parallel; this is checked on a
machine with more than one core and skipped with a recorded note otherwise)."

**What it says now.** The files are processed on more than one thread, observed
as at least two distinct `ThreadId`s, with no wall-clock duration in the
assertion.

**Why: no correct implementation can satisfy the old wording under a required
gate.** `coverage` runs this suite under `cargo llvm-cov`. LLVM's source-based
coverage counters are process-global and are incremented without atomics, so
threads running the same instrumented functions contend on the same cache
lines. The sequential side pays the documented instrumentation cost; the
parallel side pays an order of magnitude more, and the comparison inverts.

The Test Developer measured this on the story's own fixture and escalated
rather than writing a test that skipped or a tolerance that hid it. **I
reproduced the mechanism independently, on code with nothing to do with this
project** - no `image`, no `cropper-core`, no rayon, no cargo; a single
`rustc` file doing integer arithmetic on 12 `std::thread`s, compiled twice:

    $ rustc -O probe.rs -o probe_plain.exe
    $ rustc -O -C instrument-coverage probe.rs -o probe_cov.exe

    === PLAIN (no instrumentation) ===
    seq_sum 0.055s  parallel 0.011s  ratio 5.27
    seq_sum 0.054s  parallel 0.008s  ratio 6.56
    === INSTRUMENTED (-C instrument-coverage) ===
    seq_sum 0.057s  parallel 0.241s  ratio 0.24
    seq_sum 0.057s  parallel 0.256s  ratio 0.22

**The signature is unmistakable and it is not about this project's fixtures.**
Instrumentation leaves the sequential time essentially unchanged - 0.055s to
0.057s - while the parallel time rises 22x. Cost that appears only when
threads write the same counters concurrently is contention on those counters,
which is precisely the mechanism claimed. Plain, the old AC-6 passes with a
5-6x margin; instrumented, it fails by 4x. There is no implementation of a
parallel batch that passes it under `coverage`.

**The second reason, which matters as much.** Even where it ran, the old
criterion was a weak control: for a sequential implementation it compares one
quantity with itself, so the verdict is decided by run-to-run noise. Measured
against a deliberately sequential batch it **wrongly passed** 3/5, 2/5 and 1/5
at three image scales. A criterion that is precise, measurable and blind is
more dangerous than a vague one - it survives review and goes green over the
defect it exists to catch.

**Why this replacement and not the alternatives.** `## Model guidance` states
AC-6's purpose: *"a weak timing claim; its purpose is to catch a batch that is
accidentally sequential, not to measure performance (MC-017 does)"*. A thread
observation serves that purpose strictly better - it fails **every time** for a
sequential batch rather than 20-80% of the time - and it is unaffected by
instrumentation, so it keeps running under `unit` and `coverage`, both
required.

Moving the timing check to the `integration` gate was ranked second and
declined: `integration` is **optional** and currently waived (*"no `#[ignore]`
test exists until MC-017"*), so that would put the criterion where nothing
blocks on it. That is the exact failure the `story-authoring` skill documents -
three individually correct decisions adding up to `All required gates passed`
printed over a story no required gate exercised. It would have needed
`required_gates: [integration]` and the waiver removed as well, and would still
have left a 20-80% control. Dropping AC-6 entirely was declined because
decision 12's rayon pool would then be unverified until MC-017.

**What is not amended.** "Gate that fails if this breaks: `unit`" still holds,
and more strongly than before: the old AC-6 could not run under `coverage` at
all, and the new one runs under both.

**The residual risk, named rather than hidden.** A thread observation asserts
something about the scheduler, not about arithmetic: a parallel batch that
happened to run every item on one thread would fail it. RED is required to
measure that flake rate over many repetitions, exactly as it measured the old
criterion's, and to escalate again rather than to widen anything if it is not
zero.

### Level

Integration, in `crates/engine/tests/`. `batch::run` is not a pure function:
its whole subject is what happens when real files are planned, processed in
parallel and reported together, and the failures the story cares about -
a missing input, an output folder under a file, a name collision between two
inputs - only exist against a filesystem. There is nothing below this level
that could falsify any of the six; the pure parts (`decide`, `plan_outputs`)
are already pinned by MC-007 and MC-010 and are not re-tested here. AC-6 in
particular has no lower level available: "it ran on more than one thread" is
a property of the composed run and of nothing smaller.

### Target layout

One new target, `crates/engine/tests/batch.rs`, holding all thirteen tests.

* `common/mod.rs` is compiled into every target in the directory, so a second
  target would cost a recompile of 1,046 lines of fixtures and nothing else.
  Cheap enough that it is not an argument either way.
* The argument that would have bitten is scheduling. `cargo test` runs the
  tests **inside one binary concurrently** on as many threads as it has cores,
  and runs the binaries themselves one after another. A *timing* test sharing
  a binary with twelve filesystem tests would be measured while they compete
  for the cores it is trying to prove it can use, so under the original AC-6 a
  second target (`batch_parallel.rs`) would have been mandatory.
* **The amendment removes that constraint**, which is a second, smaller
  benefit of it: a `ThreadId` count does not care what else is running. The
  measurement bears it out - 50 runs of the whole file at the default test
  parallelism, no failure - so AC-6 shares the target with the rest. If a
  timing claim ever returns here, so does the second target.

`args.rs`, `codec.rs`, `formats.rs`, `naming.rs`, `naming_case.rs`,
`process_file.rs` and `scaffold.rs` are untouched. No existing assertion was
changed.

### What each criterion is tested by, and what makes it a real test

* **AC-1** is two tests. The first compares `summary.results` **as a whole
  vector**, `input` paths, rects and output paths included, against the five
  it must be; the second reads the three counts. Comparing the vector rather
  than the outcomes is what makes "input order" mean something: see the
  negative control below.
* **AC-2** puts the missing input at index 1, so that "the files after it were
  still processed" is a claim about a file the failure could have swallowed,
  and reads the output folder to confirm it.
* **AC-3** compares the whole log of progress calls against
  `[(1,5), (2,5), (3,5), (4,5), (5,5)]`, plus a batch of one and a batch of
  none. Zero, one, many.
* **AC-4** is two tests: the folder that does not exist yet (created, and
  holding all three outputs), and the folder under a file (five results, all
  `Failed`, five progress calls, and the blocking file unharmed). "Nothing
  panics" needs no assertion: rayon resumes a worker's panic on the calling
  thread, so reaching the assertions at all is the proof.
* **AC-5** is two tests: one `assert_eq!` of `serde_json::to_value(&summary)`
  against a `json!` literal covering all four outcome shapes -
  `Cropped`, `Flagged(Detector(Uniform))`, `Flagged(Unsupported)`,
  `Flagged(DecodeFailed(..))` and `Failed` - and one on `flagged_names()`.
  `Value` equality compares the key *set*, so the literal pins the absence of
  extra keys and the presence of every `null` as well as every value.
* **AC-6** collects `std::thread::current().id()` inside the progress callback
  over 32 inputs and asserts at least two distinct ids. The callback is the
  only hook a caller has *inside* the run, so it is the only observation point
  the public API offers - and it is a sound one, with a consequence for GREEN
  spelled out in the handoff. Skipped, with a note, only when
  `available_parallelism() < 2`, which is the criterion's own condition.

Two tests are not criteria and are here deliberately:
`two_inputs_with_the_same_file_name_both_reach_the_output_folder` is the
MC-020 dependency made real (this story is the first place two files arrive at
once, and the first place the writes are parallel), and
`a_folder_given_as_an_input_is_failed_rather_than_recursed_into` pins one line
of `## Out of scope` for the price of six.

### AC-6: escalated, amended, and measured both ways

**The decision is recorded in `## Amendments` and is not reopened here.** AC-6
was a wall-time comparison; it is now a thread observation. What follows is the
measurement that produced the escalation and the measurement that validates
the replacement, both on this machine (12 cores, `profile.test` at
`opt-level = 2`), with 32 copies of the MC-008 screenshot scene at 1x
(147x120) and 3x (441x360).

#### Why the old wording had to go

**1. Under the `coverage` gate a correct parallel batch is two to three times
SLOWER than the same work done sequentially, so the assertion fails.** LLVM's
source-based coverage counters are process-global and are incremented without
atomics; threads running the same instrumented functions contend on the same
cache lines. The sequential side pays the documented ~1.6-1.9x instrumentation
cost. The parallel side pays ~20x.

| | plain | instrumented | |
|---|---|---|---|
| 32 x 441x360, sequential sum | 112-127 ms | 221-226 ms | 1.9x slower |
| 32 x 441x360, 12-thread batch | 31-33 ms | 605-614 ms | **20x slower** |
| ratio `seq_sum / batch` | 3.35-4.08 | **0.36-0.37** | |

Twelve instrumented runs - two scales x two thread counts x three repetitions
- failed the assertion 10 times; the two that passed read 1.01 and 1.02, which
is noise and not a pass. Plain, it passed 12 of 12. The coordinator reproduced
the *mechanism* independently on a single `rustc` file doing integer
arithmetic on 12 `std::thread`s, with no `image`, no `cropper-core`, no rayon
and no cargo: sequential 0.055s -> 0.057s, parallel 0.011s -> 0.241s. See
`## Amendments`.

**2. Even where it ran, the old criterion was a weak control.** For a
sequential implementation it compares one quantity with itself, so the verdict
is run-to-run noise. Against a deliberately sequential batch it *wrongly
passed* 3/5 at 147x120, 2/5 at 294x240 and 1/5 at 441x360.

#### What the replacement measures

The amendment commits us to a flake rate, because a thread observation asserts
something about the scheduler rather than about arithmetic: a parallel batch
that happened to run all 32 items on one thread would fail it. So it was
measured the same way the old criterion was, running the **whole file** at the
default test parallelism, which is the condition the gates run it in.

| Condition | AC-6 passes | AC-6 fails |
|---|---|---|
| plain, rayon `par_iter` | **50/50** | 0/50 |
| plain, at 1x instead of 3x | **50/50** | 0/50 |
| instrumented, rayon `par_iter` | **25/25** | 0/25 |
| plain, sequential control | 0/25 | **25/25** |
| instrumented, sequential control | 0/25 | **25/25** |

Zero flake in either direction, and the control fails 100% of the time rather
than the old criterion's 20-80%. The sweep was run twice with identical
results.

"Instrumented" here means `RUSTFLAGS="-C instrument-coverage"` applied to
**every** crate in the build, which is stricter than the `coverage` gate (that
instruments workspace members and not `image`). The instrumentation is
demonstrably active and the contention is the same one that killed the old
wording: AC-6 alone costs **0.07 s plain and 0.57-0.64 s instrumented, ~9x** -
and the thread count is identical at both. That is the whole point of the
replacement, stated as a number: the assertion is untouched by the very effect
that inverted its predecessor.

A first attempt at this measurement was **wrong and was redone**. Running
`cargo llvm-cov --package <scratch>` instrumented only the scratch package and
not its path dependencies, so the parallel section showed no slowdown at all
(0.07 s instrumented, i.e. 1.0x) and the "instrumented" flake numbers were
really plain ones. The tell was the missing slowdown; it is recorded here
because the same mistake would make any future instrumented measurement in a
scratch crate look clean.

#### The fixture

A 3x nearest-neighbour upscale of the MC-008 scene, 441x360, still `Cropped`
at `Tuning::default()` (`Rect { x: 42, y: 63, w: 366, h: 276 }`), 32 of them.
**1x was equally clean over 50 runs**, so the scale is margin rather than a
fix for a measured flake: the failure mode is likelier the cheaper an item is,
50 clean runs do not exclude a one-in-fifty rate, and 3x buys ~4.6 ms of real
work per item against 1x's ~1 ms for 0.05 s of test time. `AC6_SCALE` in the
test file says the same thing next to the constant.

### Notes for the implementer

* **The progress callback must be called under the same lock that increments
  the counter.** AC-3 pins the *observed sequence* as `1..=n`, strictly
  increasing. An `AtomicUsize::fetch_add` followed by an unsynchronised
  `progress(..)` is a race: two workers can take 1 and 2 and call in the order
  2, 1. That would make the test flaky rather than wrong, which is worse. The
  reference implementation took one `Mutex<usize>`, incremented it and called
  the callback while still holding it; 12 runs, no reordering.
* **The progress callback must be made by the worker that finished the file,
  not by the calling thread afterwards.** This is a constraint AC-6 adds and
  it is stated here because it is not obvious from the criterion's words. The
  callback is the only hook a caller has inside `run`, so it is the only place
  the test can read a `ThreadId`; that makes "which thread called me" an
  observable, and AC-6 observes it. A batch that is genuinely parallel but
  collects the results and then fires all `n` callbacks from the caller
  **passes AC-1 to AC-5 and fails AC-6** (mutation M12, measured). That is the
  intended reading rather than an accident of the test: `## Context` says the
  callback is "called once per completed file", and MC-015's progress bar has
  to move while the run is happening. Concretely, `inputs.par_iter().map(|..|
  { let r = process_file(..); lock, increment, call; r }).collect()` satisfies
  both this and the bullet above; deferring the calls does not.
* **`plan_outputs` must be called once, before any file is written**, and its
  result indexed positionally. It already documents why (MC-010's module
  docs); `two_inputs_with_the_same_file_name_both_reach_the_output_folder` is
  what fails if a worker chooses its own name.
* **`process_file` reports, it does not unwind.** Nothing in AC-4's second
  half needs a guard: `fs::create_dir_all` under a file returns
  `Err(os error 183)`, `run` turns it into `Outcome::Failed`, and the batch
  carries on. The only way that test panics is if the batch does.
* **AC-5's JSON is flatter than the types.** `Outcome` has an `output` on two
  variants and an `error` on the third; the wire shape has all six keys on
  every entry, three of them usually `null`, and `reason` is a bare variant
  name with `Flag::DecodeFailed`'s message discarded. A derive on `Outcome`
  will not produce it. The reference used a private `#[derive(Serialize)]`
  shadow struct built from `&FileResult`, which is about twenty lines.
* **`floor | unit | 47` does not move.** It tracks the first test binary with
  at least one test, which is `crates/core tests/content.rs`; this story adds
  a target to `crates/engine`, which cargo runs after every `crates/core`
  target. Confirmed still 47 with `cargo test -p cropper-core`.
* Nothing in `args.rs`, `codec.rs`, `formats.rs`, `naming.rs`,
  `naming_case.rs`, `process_file.rs` or `scaffold.rs` was changed.

#### AC-6 is a timing assertion, and timing assertions are how suites become flaky

This machine has **12 cores**, so AC-6 runs rather than skips here. Three
things about it that RED must get right, and they are the difference between a
control and a coin flip:

1. **It must compare two measurements taken in the same run**, as the criterion
   words it - the batch's wall time against the *sum of per-file times measured
   sequentially in that same test*. Never an absolute threshold. The `coverage`
   gate runs this suite instrumented and `ci-factor | coverage | 1.63` says a
   test there is roughly 1.6x its local self; a ratio survives that, a constant
   does not. The same goes for CI's slower, fewer-core hardware.
2. **The skip on a single-core machine is authorised by the criterion itself**
   and by nothing else. It is conditioned on the core count and it records a
   note. It is *not* a way to make a red go away: if the assertion fails on a
   multi-core machine, that is a real failure. GitHub's `windows-latest`
   runners have more than one core, so CI exercises it.
3. Small images, well under a second, per `## Model guidance`.
