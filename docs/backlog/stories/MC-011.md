## Context

The brief's features 4 and 7 in the engine: many files in, every one
processed, one `RunSummary` out with counts and the flagged names.
`batch::run(&[PathBuf], out_dir, &Tuning, progress) -> RunSummary` plans
names (MC-010), processes files on the rayon pool (decision 12), keeps
results in input order, and never lets one file's failure stop the others.
`progress` is `&(dyn Fn(Progress) + Sync)` with `Progress { done, total }`,
called once per completed file. `RunSummary` serialises to JSON with a
stable shape because MC-012 writes it to disk and MC-015 renders it.

Gate that fails if this breaks: `unit`.

## Acceptance criteria

- **AC-1** - Given five inputs - three croppable PNGs, one uniform PNG and one `.txt` - when `run` completes, then `results` has five entries in input order with outcomes `Cropped, Cropped, Cropped, Flagged(Detector(Uniform)), Flagged(Unsupported)`, and `cropped() == 3`, `flagged() == 2`, `failed() == 0`.
- **AC-2** - Given one of the inputs does not exist, when `run` completes, then that entry is `Failed { error }`, every other input was still processed, and `failed() == 1`.
- **AC-3** - Given `n` inputs, when `run` completes, then the progress callback was called exactly `n` times, each call carried `total == n`, and the sequence of `done` values is `1..=n` (strictly increasing by one).
- **AC-4** - Given `out_dir` does not exist, when `run` starts, then it is created; given it cannot be created (a path under a file), then every result is `Failed` and nothing panics.
- **AC-5** - Given a `RunSummary`, when serialised with `serde_json`, then it has the shape `{"cropped": u32, "flagged": u32, "failed": u32, "results": [{"input": str, "outcome": "cropped" | "flagged" | "failed", "output": str | null, "rect": {x,y,w,h} | null, "reason": str | null, "error": str | null}]}` with `reason` being the `Flag` variant name (`Uniform`, `NoBorderFound`, `LowContent`, `Ambiguous`, `Unsupported`, `DecodeFailed`); and `flagged_names()` returns the flagged inputs' file names in order.
- **AC-6** - Given 32 inputs, when `run` completes, then the wall time is less than the sum of the per-file times measured by processing them sequentially with `process_file` (the batch is parallel; this is checked on a machine with more than one core and skipped with a recorded note otherwise).

## Model guidance

Model: default. Oracle partition:

- **Mechanical**: everything in AC-1..AC-5; pin the JSON shape exactly - it is a contract with MC-012 and MC-015.
- **Oracle-free**: AC-6 is a weak timing claim; its purpose is to catch a batch that is accidentally sequential, not to measure performance (MC-017 does). Use small images so it runs in well under a second.

## Out of scope

The `--summary` file and exit codes (MC-012), the window's progress bar
(MC-015), the 100-image budget (MC-017), cancellation, retrying a failed
file, recursion into folders (a directory input is `Failed`).

### MC-020 inserted ahead of this story (2026-09-12)

`depends_on` gained **MC-020**, which fixes a case-collision defect in
`naming::plan_outputs`: two inputs whose names differ only by letter case are
planned as two names and written as one file, because `PathBuf` equality is
byte-wise and NTFS is not. Reproduced on the filesystem alone; the evidence is
in MC-020's `## Context` and MC-010's `## Notes`.

**It is a dependency of this story specifically**, not merely an earlier one.
MC-011 is the first point at which a user hands the program two files at once,
so it is where the overwrite becomes reachable - and it is also the story that
parallelises the writes, which makes a lost file harder to notice, not easier.
