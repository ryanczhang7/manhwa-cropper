## Context

Completes the headless path that Explorer "Send to" and scripts use
(`architecture.md`, `main.rs` and decisions 6 and 10). `--no-gui` runs the
batch (MC-011) and exits; `--summary <path>` writes the JSON summary;
without `--out` the remembered folder (MC-013) is used, and if none was ever
chosen, a `cropped` folder beside the first input is created and used. Exit
codes: 0 when every input was cropped or flagged, 1 when any input was
`Failed`, 2 on bad arguments. The end-to-end tests spawn the exe with
`MANHWA_CROPPER_CONFIG_DIR` pointed at a temp dir. The real Send-to flow
(no `--no-gui`) opens the window and is MC-016.

Gate that fails if this breaks: `unit`.

## Acceptance criteria

- **AC-1** - Given three supported images, when the exe runs with `--no-gui --out <out> --summary <s.json> a.png b.jpg c.webp`, then the three outputs exist in `<out>`, `s.json` parses to the MC-011 JSON shape with `cropped + flagged == 3`, and the exit code is 0.
- **AC-2** - Given one of the inputs does not exist, when the exe runs as in AC-1, then the other outputs still exist, `s.json` records one `failed`, and the exit code is 1.
- **AC-3** - Given `--no-gui` and no input paths, when the exe runs, then nothing is written and the exit code is 2.
- **AC-4** - Given no `--out` and a settings file whose `output_dir` is `<remembered>`, when the exe runs with `--no-gui a.png`, then the output is written under `<remembered>`.
- **AC-5** - Given no `--out` and no settings file, when the exe runs with `--no-gui <dir>/a.png`, then `<dir>/cropped/a.png` is written, the folder having been created, and the settings file is *not* modified (the fallback is not remembered as a choice).
- **AC-6** - Given `--out <out>`, when the run completes, then the settings file still holds its previous value (a command-line folder is a one-off, not a choice).

## Model guidance

Model: default. Oracle partition: all **mechanical**. Read exit codes and
files only - never stdout (decision 10). `args::parse` was pinned in MC-002;
this story adds the resolution of the output folder as a pure function
`resolve_out_dir(&Invocation, &Settings) -> PathBuf` so AC-4..AC-6 have a
unit-level test as well as the spawned-exe one.

## Out of scope

Opening the window (MC-016), creating the Send-to shortcut (decision 9; the
user does this by hand via `shell:sendto`), a `--help` text (the exe has no
console; `--help` is an unknown flag and exits 2), recursion into folders.

## Test plan

Two files, at two levels, because two different things can be wrong.

**`crates/engine/tests/resolve_out_dir.rs` - unit, 10 tests.** The output
folder rule is a pure function, `resolve_out_dir(&Invocation, &Settings) ->
PathBuf`, and AC-4, AC-5 and AC-6 are all *precedence* claims about it: an
explicit `--out` beats the remembered folder, the remembered folder beats the
fallback, and the fallback is `cropped` beside the **first** input. Precedence
is a table, and a table is cheapest to falsify at the unit level - three
spawned processes would pin three of its cells and leave the rest.

There is a second, harder reason the rule has to live in the engine: the
`coverage` gate runs with
`--ignore-filename-regex 'crates[/\\]app[/\\]src[/\\](main|gui)\.rs'`, so
**anything left in `main.rs` is not coverage-measured at all**. A resolution
rule in `main.rs` would be invisible to the gate that is supposed to judge it.

**`crates/app/tests/headless.rs` - end-to-end, 7 tests.** One spawn of the real
exe per criterion, reading exit codes and files only - never stdout or stderr
(decision 10). This is the layer where `--no-gui`, `--summary`, the exit codes
and the wiring of `resolve_out_dir` into a run actually meet, and none of that
is provable below it.

**A new file rather than more tests in `cli.rs`.** MC-002's `cli.rs` is a
finished story's, and its `run_exe` spawns with the test process's own
environment. Every spawn in MC-012 must set `MANHWA_CROPPER_CONFIG_DIR` on the
child or the run reads - and for AC-5 and AC-6 could *write* - the developer's
real `%APPDATA%\manhwa-cropper\config`. The fix is to make the config
directory a mandatory parameter of the spawn helper, so it cannot be forgotten,
and that cannot be applied to a frozen file. The cost is that the
spawn-with-timeout harness, `Scratch` and `entries` are duplicated near
verbatim; that is accepted, because the alternative is editing a frozen test.

**Making AC-1 non-vacuous.** `cropped + flagged == 3` is satisfied by three
files that are junk - random bytes behind a PNG signature are `DecodeFailed`,
which is *flagged*, which counts, and which is exactly what MC-002's
`sample_png` is. So AC-1's fixtures are the MC-008 screenshot scene rendered as
PNG, JPEG and WebP, all three of which really crop, and the test asserts the
whole summary document with `"outcome": "cropped"` three times plus the 126x96
output dimensions. Both halves matter: the outcome catches a batch that flagged
everything, the dimensions catch a run that copied rather than cropped.

**Coverage of the shape.** Zero, one, many: no inputs (AC-3, twice), one input
(AC-4, AC-5, AC-6), three inputs (AC-1, AC-2). Boundaries of the precedence
table: every cell of `--out` present/absent x settings set/unset, plus an input
with no folder component and an input list that is empty. Errors: a missing
input mid-list (AC-2). Out of scope, pinned cheaply: `resolve_out_dir` creates
nothing on disk, so "where would this go?" stays a question anyone can ask.

### Notes for the implementer

1. **Two tests already pass against the *pre-story* exe**, for reasons that
   will not survive this story, and both were confirmed by running them against
   the current `main.rs` in the throwaway copy:
   `no_input_paths_and_no_out_folder_creates_no_fallback_and_exits_2` (today
   `headless()` exits 2 because `--out` is missing, not because the input list
   is empty) and, before the 126x96 assertion was added to it,
   `an_out_folder_on_the_command_line_does_not_become_the_remembered_folder`
   (today nothing in the exe reads or writes settings at all). Once `--out` is
   optional both become real discriminators - see the mutation table rows for
   "an empty input list is not rejected" and "any resolved folder is saved
   back". The other five failed against the pre-story exe with exactly the
   assertion each is named for.
2. **The empty-input case in `resolve_out_dir` is pinned as a *totality*
   decision, not an acceptance criterion.** AC-3 exits 2 before a folder is
   ever needed, so `main` must never reach it; the test exists because the
   function must still be total and must not panic, and the answer it pins
   (`PathBuf::from("cropped")`) is what the documented rule degenerates to -
   the same answer as an input with no folder component. If you would rather it
   were something else, that is a return to RED and a conversation, not an
   edit.
3. **`main.rs` needs a `Settings` value before it can resolve.** Loading it
   unconditionally is safe - `Settings::load` never writes and never creates
   the config directory - but note that MC-002's `cli.rs` spawns *without*
   `MANHWA_CROPPER_CONFIG_DIR`, so an unconditional load reads the developer's
   real `%APPDATA%\manhwa-cropper\config` during those seven tests. It is a
   read, so nothing is at risk; loading only when `inv.out_dir.is_none()` would
   avoid it entirely. Your call.
4. **All seven of MC-002's frozen tests survive the switch from `copy::copy_all`
   to `batch::run`**, verified rather than assumed: `sample_png()` is
   `Flag::DecodeFailed` -> flagged -> copied byte-for-byte, so the three
   copy-and-exit-0 tests still hold with `["a.png"]` in the output folder; a
   missing input is `Outcome::Failed` with the output folder measured empty
   afterwards, so exit 1 with nothing written still holds; and the three exit-2
   tests fail in `args::parse` and never reach the batch. None of the seven
   uses `--no-gui` without `--out`, so none of them pins the behaviour AC-4 and
   AC-5 change.
5. `batch::run` already calls `fs::create_dir_all(out_dir)`, and
   `process_file` creates the output's parent as well, so AC-5's "the folder
   having been created" needs no new code - which is why `resolve_out_dir` is
   required to create nothing.
6. `bash scripts/gates.sh --fast` was **not** run in this phase: the
