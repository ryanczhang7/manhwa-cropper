## Context

Decision 7 in `architecture.md`: same file name from two source folders, or
a second run into the same output folder, must never overwrite. Explorer's
convention: `name (2).png`, `name (3).png`. Because the batch (MC-011) runs
files in parallel, names are planned up front, sequentially, before any file
is written: `naming::plan_outputs(out_dir, &inputs) -> Vec<PathBuf>` returns
one distinct, currently-free path per input in input order, accounting for
files already on disk and for duplicates within the batch. `process_file`
(MC-008) gains an explicit output path parameter so the planner decides
names and the codec only writes.

Gate that fails if this breaks: `unit`.

## Acceptance criteria

- **AC-1** - Given `out_dir` does not contain `a.png`, when `plan_outputs(out_dir, ["x/a.png"])` runs, then it returns `[out_dir/a.png]`.
- **AC-2** - Given `out_dir/a.png` exists, when planned for `["x/a.png"]`, then it returns `[out_dir/a (2).png]`.
- **AC-3** - Given `out_dir/a.png` and `out_dir/a (2).png` exist, when planned, then it returns `[out_dir/a (3).png]`.
- **AC-4** - Given two inputs `x/a.png` and `y/a.png` in one batch and an empty `out_dir`, when planned, then it returns `[out_dir/a.png, out_dir/a (2).png]` - the in-batch duplicate is resolved without anything on disk.
- **AC-5** - Given an input `Shot.PNG` that collides, when planned, then the result is `Shot (2).PNG` (stem and extension case preserved); given an input with no extension `notes`, then `notes (2)`.
- **AC-6** - Given `process_file` is called twice with the same input and the planned paths, when both complete, then both output files exist with distinct names and the first is unchanged by the second.

## Model guidance

Model: default. Oracle partition: all **mechanical**. Pin
`plan_outputs(&Path, &[PathBuf]) -> Vec<PathBuf>` and the exact ` (n)`
formatting (space, parentheses, ASCII digits).

## Out of scope

Recursion into folders, a limit on `n`, Unicode normalisation of file names,
cleaning up a partially written file after a crash.

### The two controls, and what they are for

Neither calls `naming`. They exist because the criteria in this story are
assertions about *absence* - no file was overwritten - and an assertion about
absence is worth nothing unless the alternative is shown to be present.

1. `the_naive_plan_collides_in_every_scenario_these_criteria_pin` measures what
   `out_dir.join(file_name)` - the answer MC-008 ships - gives in AC-2's,
   AC-3's and AC-4's scenarios: a path that already exists, twice, and then one
   path shared by two inputs. Without it, a reader cannot tell whether AC-2 to
   AC-4 demand work or restate what already happens. The matching whole-planner
   mutation was measured: 8 of 14 fail.
2. `two_writes_to_one_path_leave_one_file` measures the loss AC-6 forbids: one
   directory entry, and the first write's bytes gone. AC-6's "both output files
   exist with distinct names" is only a demand because of this.

Both were executed outside the test framework during RED, since the file does
not compile while `naming` is missing; their numbers are in the handoff for
GREEN to confirm.

### One thing measured and deliberately not tested

Two inputs differing only in case - `a.png` and `A.PNG` - are not mentioned by
any criterion, and this story does not invent one. RED measured the behaviour
instead, and the measurement is in the handoff under
`### The case question: measured, not criteria`. It found a real overwrite, so
it is escalated there rather than absorbed into a test here.

### Edges, and the non-goals

Zero, one, many: the empty batch, one input, five inputs sharing a name over a
directory that already holds two. Boundaries: the counter at its first value
(2) and at 3, and the five-input run at 7. Errors: there is no fallible path in
`plan_outputs` - it returns `Vec<PathBuf>`, not a `Result` - so the error
shapes here are "the directory does not exist" (covered) and "the file name
collides" (the whole story). Of `## Out of scope`, recursion into folders and a
limit on `n` are not pinned because pinning them would state a behaviour the
story deliberately leaves open; Unicode normalisation would need a fixture
whose correct answer this story has not decided; crash cleanup has no test that
does not invent a criterion.

### What GREEN must export

Nothing below is a suggestion. A test already imports each name, so a different
choice is a compile error in a file GREEN may not edit.

```rust
// crates/engine/src/naming.rs, reached as `cropper_engine::naming::plan_outputs`
// (so `pub mod naming;` in lib.rs; a root re-export as well is GREEN's choice)
pub fn plan_outputs(out_dir: &Path, inputs: &[PathBuf]) -> Vec<PathBuf>;

// crates/engine/src/process.rs, re-exported at the crate root exactly as today
pub fn process_file(input: &Path, output: &Path, tuning: &Tuning) -> FileResult;
```

What the assertions require of them:

* `plan_outputs` takes a **slice of `PathBuf`** - the tests pass `&Vec<PathBuf>`,
  a borrowed array literal and `&[]` - and an `&Path` for the output directory,
  in that order (`out_dir` first). It returns an owned `Vec<PathBuf>` compared
  with `assert_eq!` against `vec![out.join(..), ..]`, so the order of the
  returned paths is the order of the inputs.
* It must not require the inputs to exist. Every input in AC-1 to AC-5 is a
  bare path under a folder that was never created, exactly as the criteria word
  them (`x/a.png`, `y/a.png`).
* It must not write anything: two tests read the output directory back after
  planning and assert it is unchanged (empty in AC-4's, the two occupied files
  in AC-3's).
* **`process_file`'s second parameter is the output path, not the output
  directory.** It returns that same path in `Outcome::Cropped { output }` and
  `Outcome::Flagged { output }`, and writes the file *there*, under that exact
  name - the case included.
* Unchanged and still pinned by MC-008 and MC-009: `FileResult { input,
  outcome }`, `Outcome::{Cropped { rect, output }, Flagged { reason, output },
  Failed { error }}`, `Flag::{Detector, Unsupported, DecodeFailed}`,
  `SourceFormat`, `codec::{detect_format, to_luma}`. **Do not add a field to
  any `Outcome` variant**: three test files construct and destructure them by
  field name and none may be edited in GREEN.

**Deliberately not constrained**, and GREEN's to choose: how `plan_outputs`
asks the filesystem (`Path::exists`, `try_exists`, one `read_dir` cached); what
it uses to remember the batch; whether the search from `n` is linear; whether
`naming` is re-exported at the crate root; what happens to an input with no
file name, such as `..` (no test passes one); double extensions like
`a.tar.gz`, where `Path::extension` gives `gz` and the obvious implementation
yields `a.tar (2).gz` (measured, unpinned); dotfiles; any cap on `n`
(`## Out of scope`).

### The case question: measured, not criteria

**A real overwrite is possible, and a follow-up story should be put to the
user.** This is a measurement, not a criterion; no test in this story asserts
it and no acceptance criterion was added for it.

The two halves of a planner disagree about case on Windows, which controls 7
and 8 above state separately. Driving the implementation-shaped planner
(`Path::exists` for the disk, `HashSet<PathBuf>` for the batch) over one batch
of `x/a.png` and `y/A.PNG` into an empty output folder:

| Step | Measured |
|---|---|
| the plan | `["a.png", "A.PNG"]` - two names, and they *are* distinct as `PathBuf`s |
| after MC-011's batch writes both | the folder holds **one** file, `a.png` |
| its bytes | `A.PNG`'s, not `a.png`'s - the first input's output is gone |

So a planner that is correct about everything this story pins can still hand
two inputs the same file, and the loss is silent: both writes succeed and the
run summary reports two files. That contradicts the story's own Context
("must never overwrite") for a case the criteria do not cover, which is why it
is escalated rather than fixed here.

The mitigation is one line and was measured too, for whoever writes that story:
folding the in-batch set to lower case gives `["a.png", "A (2).PNG"]` and two
files on disk. It is **not** in scope here and GREEN must not add it - it would
be an untested behaviour in a story whose criteria are frozen. Note also that
it is the *right* answer only on a case-insensitive filesystem, which is the
only one this product ships on.

### What should change the implementation approach

1. **Who creates the output directory, since no AC pins it.** `plan_outputs`
   must create nothing - two tests assert the folder is untouched after
   planning, and one plans into a folder that does not exist. The parent
   directory therefore stays `process_file`'s job, exactly where MC-008 left
   it (`write_crop` and `copy::copy_unchanged` both call `create_dir_all`);
   with an output *path* that becomes `fs::create_dir_all(output.parent())`.
   No test pins it either way - `workspace()` in all three test files creates
   `out` first - so this is GREEN's call as it was MC-008's, and the
   recommendation is to keep it: decision 6's fallback `cropped` folder and
   MC-011's batch both rely on somebody creating it, and `Outcome::Failed` is
   the only channel through which failing to is reportable.
2. **`copy::copy_unchanged` does not have to change, and changing it is not
   free.** It joins the input's name onto a directory, which is no longer what
   the flagged path wants. Its six `#[cfg(test)]` tests live in
   `crates/engine/src/copy.rs` - classified *source*, so GREEN may edit them -
   and `copy_all` is used by `crates/app/src/main.rs`, whose `tests/cli.rs` is
   frozen. The cheapest route, and the one the RED reference took, is a
   sibling that copies to an exact path, leaving `copy_unchanged` and
   `copy_all` for MC-011 to retire.
3. **Three clippy errors follow from the signature change**, and `lint` is
   `-D warnings`. Measured on the reference implementation: with `output:
   &Path` in `write_crop`, `cropped.save_with_format(&output, ..)` (twice) and
   `write_jpeg(&cropped, &output)` become `needless_borrows_for_generic_args`
   and `needless_borrow` - drop the `&` - and `use crate::{codec, copy};`
   becomes an unused import if the flagged path stops calling `copy`.
4. **Plan sequentially, and keep it that way.** The whole point of a separate
   `plan_outputs` is that MC-011 runs the writes in parallel: "find a free
   name, then write it" inside a worker is a race that loses a file. The tests
   cannot catch that - they are single-threaded - so it is stated here.
5. **The five-input test is the one to read first** if the counter is wrong: it
   prints the whole planned list, so an off-by-one is visible as a list rather
   than as one path.
6. **Confirm the ten control values above before writing anything else.** They
   were measured against a std-only program and the real filesystem, not
   against the shipped module; MC-009's row 9 diverged for exactly that reason
   and cost a return to RED.

#### One thing the criteria are silent about, to be measured and not invented

AC-4 resolves an in-batch duplicate from two inputs both named `a.png`. Nothing
says what happens when two inputs differ only in **case** - `a.png` and
`A.PNG`, which is a real pairing when a user drops files from two folders.
It matters here and nowhere else in this codebase, because the two halves of
the planner disagree about case on Windows: `Path::exists` asks a
case-insensitive filesystem, while an in-batch set of `PathBuf`s compares
bytes. A planner that is right about disk can still hand two inputs the same
name.

That is **not** a criterion of this story and I am not making it one: no AC
mentions it and inventing one is the amendment path, not a shortcut through it.
RED is asked to *measure* the behaviour and record it. If it turns out that
this program can overwrite a user's file, that is a finding for a follow-up
story put to the user - not scope taken silently here.
