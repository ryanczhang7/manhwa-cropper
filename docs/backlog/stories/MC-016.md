## Context

Makes the window work: the `Choose folder…` button opens the native dialog
(`rfd`, title `Choose output folder`), dropped files become
`Event::FilesDropped`, `Command::StartBatch` spawns `batch::run` on a worker
thread with an `mpsc` progress channel drained each frame
(`architecture.md`, Threading), `Command::SaveSettings` writes the settings
file, and the Send-to flow from decision 6: launched with file paths and
without `--no-gui`, the window starts processing them at once into the
remembered folder or the `cropped` fallback, and shows where they went. The
dialog and the runner are injected as traits (`FolderPicker`, `BatchRunner`)
so kittest can drive the shell with fakes, plus one true end-to-end test with
the real runner on two tiny PNGs.

Gate that fails if this breaks: `unit`.

## Acceptance criteria

- **AC-1** - Given a fake `FolderPicker` that returns `Some(p)`, when the `Choose folder…` button is clicked in the harness, then the picker was called with title `Choose output folder`, the path label reads `p`, and `settings.json` under `MANHWA_CROPPER_CONFIG_DIR` holds `output_dir == p`.
- **AC-2** - Given the picker returns `None`, when the button is clicked, then the model is unchanged and the settings file is untouched.
- **AC-3** - Given a folder is chosen and a fake `BatchRunner`, when two files are dropped (through the harness's raw-input `dropped_files`, or through `Shell::on_dropped(paths)` if kittest 0.32 cannot inject drops - the handoff records which), then the runner was started with those two inputs and that folder, and after the fake reports `Progress { 1, 2 }` then `Finished(summary)`, successive frames show `1 of 2` and then the result line.
- **AC-4** - Given `Invocation { inputs: [d/a.png, d/b.png], no_gui: false, out_dir: None }` and no remembered folder, when the shell is constructed and one frame painted, then the runner was started with out dir `d/cropped`, the state is `Processing { 0, 2 }`, the path label reads `d\cropped`, and the settings file was not written.
- **AC-5** - Given the same launch with a remembered folder `r`, when constructed, then the runner was started with `r`.
- **AC-6** - Given a launch with no inputs, when constructed, then the state is `Idle` and the runner was not called.
- **AC-7** - Given the real `BatchRunner` and two small croppable PNGs in a temp folder, when they are dropped in the harness and frames are stepped until the state leaves `Processing` (bounded by a 10 s timeout), then both outputs exist in the chosen folder and the result line reads `2 cropped, 0 flagged`.

## Model guidance

Model: default. Oracle partition: all **mechanical**. Pin
`trait FolderPicker { fn pick(&self, title: &str) -> Option<PathBuf>; }`,
`trait BatchRunner { fn start(&self, inputs: Vec<PathBuf>, out_dir: PathBuf, tx: Sender<Event>); }`,
`Shell::new(model, picker, runner)` and `Shell::from_invocation(inv, settings, picker, runner)`.
AC-7 is the one place a real thread runs in a test; poll with
`harness.step()` and a sleep of a few ms between steps, never a fixed sleep.

## Out of scope

Cancelling a run, queueing drops while processing, dropping a folder
(engine reports it `Failed`; the row says `Not written`), the Send-to
shortcut itself (decision 9), `--no-gui` (MC-012).

## Design notes

This story makes the painted states of MC-015 change in response to input.
Components touched: the `Choose folder…` button (default → active → the
native dialog; disabled while processing), the drop target (the whole
window, `layout.md`), the status slot (progress bar and count, then the
result line or message), and the native folder dialog.

**Button activation (AC-1, AC-2).** Click, `Enter` and `Space` all activate
(`accessibility.md`, keyboard path); the picker is called with exactly
`folder.dialog_title` = `Choose output folder` and, when a folder is known,
that folder as the starting directory. The test should drive at least one
activation from the keyboard: `Tab` (the button is the only stop, so the
first `Tab` lands on it and the ring paints), then `Enter`. Cancel is
`None`: no event, no state change, no settings write, focus stays on the
button (do not surrender focus after the dialog closes). The dialog is
modal and blocking; the window does not paint until it closes - that is the
button's "loading" state and needs no spinner.

**Disabled during processing.** While `Processing`, the button is painted
with `ui.add_enabled(false, ..)` (`control-disabled` fill, 1 px `border`,
`text-disabled` text) and is out of the Tab order. Wiring must not call the
picker on a click or `Enter` that arrives in that state; a test should click
the disabled button (and press `Tab` then `Enter`) while a fake runner holds
the state in `Processing` and assert the picker's call count stays 0. Drops
in that state are dropped on the floor by the model (MC-014 AC-6); the
shell adds no message.

**Drops (AC-3, AC-7).** `ctx.input(|i| i.raw.hovered_files)` non-empty sets
the `hovering` flag MC-015 paints; `dropped_files` non-empty raises
`FilesDropped` with every path in Windows' order. The `Shell::on_dropped`
route is acceptable only if kittest cannot inject `dropped_files`; either
way the painted result is the same. Progress is drained from the `mpsc`
channel at the top of each frame and the shell calls `ctx.request_repaint()`
while `Processing`, so the count advances without the user moving the
mouse. The first frame after a drop shows `0 of {total}` (AC-4's
`Processing { 0, 2 }`); each `Progress` replaces the count in one frame, no
tween; `Finished` swaps the slot to the result line in one frame.

**Send-to launches (AC-4, AC-5, AC-6).** The path label must show the
folder the files are actually going to: with a remembered folder, that
folder; with none, the `cropped` fallback next to the first input, as a
Windows path (`d\cropped`). Do this by constructing the model with the
resolved folder (`Model::new(Settings { output_dir: Some(resolved) })`) so
`path_text` shows it from the first frame - the user "always sees where files
went" (`components.md`, rules). The fallback is shown but not remembered:
no `SaveSettings`, no settings file (AC-4). The drop zone reads
`dropzone.busy` and the button is disabled from that same first frame;
nothing has focus on launch.

**Failure text.** A runner `Failed(detail)` paints `error.run_failed` in
`danger`. `error.folder_unwritable` (`voice.md`) has no producer in MC-014
or here: if the fallback or chosen folder cannot be created or written,
this story's runner can only surface it as `Failed(detail)`, so the user
would read `Cropping stopped: …` rather than the designed
`Cannot write to {path}. Choose a different output folder.` Raised for the
Lead PO as a gap; do not invent an event here to close it.

**Keyboard floor for this story.** `Tab` reaches the button; `Enter`/`Space`
open the dialog; `Esc` in the dialog cancels; files reach the app without
the window via Explorer Send-to (this story's launch path). With the button
disabled there is no focus stop, and that is correct.

No criterion forces an interaction that cannot work.

The last two rows of the table before AC-4 are the two behaviours the Design
notes mandate and no criterion states outright. They are here because
`accessibility.md`'s keyboard floor and `components.md`'s disabled row are the
part of this story a user feels and no AC names.

**The shapes pinned, and why.** `Shell` is generic in both collaborators -
`Shell<P: FolderPicker, R: BatchRunner>` - rather than holding boxed trait
objects. The tests own the concrete fakes and read what was recorded through a
cloned `Arc`, so nothing needs dynamic dispatch; the harness carries the shell
as `egui_kittest`'s `State` (`build_ui_state`), which makes `Shell<P, R>`
appear in a type position and therefore fixes the arity at two parameters. The
shipped window instantiates `Shell<RfdPicker, ThreadRunner>` with no vtable.
`Shell::model(&self) -> &Model` is how a test reads the state and the folder,
which is what AC-4 and AC-6 assert about directly.

**`FolderPicker::pick` takes two arguments.** `## Model guidance` pins
`fn pick(&self, title: &str) -> Option<PathBuf>` while `## Design notes` (and
`components.md`) say the dialog opens "starting in the current output folder
when one is known". Those disagree, and AC-1 only requires the title, so both
readings satisfy every criterion. The richer form is taken -
`fn pick(&self, title: &str, start_in: Option<&Path>) -> Option<PathBuf>` - so
that the design note is testable too, and both arguments are asserted: the
title is always `Choose output folder`, `start_in` is `None` with no folder
chosen and `Some(current)` when one is. This is a reconciliation of two
documents that already disagreed, not a change to a criterion; no `##
Amendments` entry is owed.

**How drops are injected: through raw input, not a back door.** AC-3 left the
route open. egui 0.36.2 settles it: `RawInput::dropped_files` is a
`Vec<DroppedFileHandle>` over the **public** `egui::DroppedFile` trait
(`fn path(&self) -> &Path`, `fn bytes(&self) -> Result<Vec<u8>, String>`), so
a test implements that trait on a one-field struct and pushes
`Arc::new(..)` into `harness.input_mut().dropped_files`. `Shell::on_dropped`
is not needed and is not pinned. This is the stronger route: it exercises the
shell's own reading of `ctx.input(|i| i.raw.dropped_files)`. Hover is the same
idea with the plain `egui::HoveredFile { path, mime }` struct. Both were run
in RED against a throwaway probe: the two paths arrive in order, on the frame
after they are set, and `dropped_files` is consumed once while `hovered_files`
persists until cleared.

**How AC-7 polls.** The drop is made, one `step()` establishes `Processing`,
and then a `while matches!(state, Processing { .. })` loop asserts
`started.elapsed() < RUN_TIMEOUT` (10 s), sleeps `POLL` (5 ms) and calls
`harness.step()` again. There is no fixed sleep anywhere: the loop leaves on
the frame the shell drains `Finished` from the channel, and the timeout is
only ever reached by a failure.

**Cost, measured in RED.** The real work AC-7 bounds - `batch::run` over two
147x120 PNGs of the MC-008 screenshot scene on a worker thread, writing both
crops - took **5-6 ms** of wall time when driven directly from a probe, and
reported `2 cropped, 0 flagged` with progress `1 of 2`, `2 of 2`. The test
adds a handful of 5 ms polls and about a dozen headless frames, so it is tens
of milliseconds, not seconds. `libtest` imposes no per-test timeout, so the
"quarter of the framework's timeout" budget has no framework number to measure
against here; the story's own 10 s bound is the only one, and the measured run
is ~0.06% of it. At the `ci-factor | coverage | 1.63` recorded in
`project.conf` that is still ~10 ms of instrumented CI time, and at
`| unit | 1.42` ~8 ms. This test is not where a CI timeout will come from.

**Levels.** Everything is an integration test at the one level that can
falsify these criteria: the shell wired to a real `egui` context and a real
AccessKit tree, with the two things it cannot do in a test (a modal native
dialog, a worker thread) behind traits. The pure rules underneath are MC-014's
and are already unit-tested in `tests/model.rs`; the paint is MC-015's and is
already tested in `tests/gui.rs`. AC-7 is the one end-to-end path - real
runner, real thread, real files, real wall clock - and it is deliberately the
only one.

**Why every test takes the environment lock.** `crates/engine/tests/settings.rs`'s
`ENV_LOCK` pattern is reused verbatim: one `static Mutex<()>`, a guard that
restores the previous value of `MANHWA_CROPPER_CONFIG_DIR` from `Drop` while
the lock is still held. Unlike that file, *every* test here takes it rather
than only the ones that assert about `settings.json`. The reason is that every
test builds a `Shell`, and a `Shell` is the thing that can call
`Settings::save`: a test that did not own the variable would let a defective
shell write into the developer's real `%APPDATA%\manhwa-cropper\config` (which
this project has done twice - see `tests/headless.rs`'s module docs) or, worse,
into the scratch directory of whichever test *does* own it, which would make
AC-4's "the settings file was not written" depend on the scheduler. Every test
here needs the variable pointed somewhere safe, which is what the lock buys.
The cost is that this binary is serial: eleven fast tests and one that takes a
few milliseconds.

**No new dependency.** `tests/shell.rs` reaches the engine's PNG fixture
generator with `#[path = "../../engine/tests/common/mod.rs"]`, exactly as
`tests/headless.rs` does, and has its own `Scratch` (unique under
`std::env::temp_dir()`, removed on `Drop`) copied from the same file.
`egui_kittest`, `image` and `serde_json` are already dev-dependencies and
`eframe`, `cropper-engine` and `cropper-core` are already dependencies. Nothing
in `Cargo.toml` was touched, and nothing needed to be.

### Notes for the implementer

1. **`gui::paint` throws the button's `Response` away, and its signature cannot
   change.** `folder_row` calls `folder_button(..)` and discards the
   `Response`; `paint` returns `()`. That signature is frozen from outside this
   story: MC-015's `tests/gui.rs` does
   `.build_ui(move |ui| gui::paint(ui, model, hovering))`, whose closure is
   `FnMut(&mut egui::Ui)` and therefore *requires* `paint` to return `()`.
   Giving `paint` a return value breaks a frozen test file. So the activation
   has to leave `gui.rs` by a new door - a second entry point that returns it,
   with `paint` delegating and discarding, or an equivalent - and that door is
   **not pinned by any test here**: `tests/shell.rs` only ever calls
   `Shell::frame`. This is the one thing in the story that has no obvious
   shape, and it is worth deciding before anything else.
2. **Put the real `rfd` picker where the coverage gate cannot see it.** That
   gate ignores only `crates/app/src/main.rs` and `gui.rs`; a new
   `crates/app/src/shell.rs` is measured against the workspace's 95% line
   floor. A `pick` that opens a modal native dialog can never be executed by a
   test, so its body belongs in `main.rs` (or `gui.rs`), not in `shell.rs`.
   `ThreadRunner` is fine in `shell.rs` - AC-7 executes it for real. This is
   also why the Lead PO put `shell.rs` outside `gui.rs` in the first place.
3. **`ThreadRunner::new()`, and a `Default` impl beside it.** Measured, not
   guessed: with `ThreadRunner` as a unit struct, `ThreadRunner::default()` in
   the test failed `cargo clippy -- -D warnings` on
   `clippy::default_constructed_unit_structs`; and a public argument-less
   `new()` without a `Default` fails `clippy::new_without_default`. The test
   calls `new()`, so ship both.
4. **kittest facts this suite depends on**, all measured in RED:
   `HarnessBuilder::build_ui_state` paints **3 frames at construction** before
   the test's first `step()` - which is why "the runner was started exactly
   once" is a fair assertion and a per-frame start is a bug this suite catches.
   `Harness::run()` panics once `max_steps` (4) is exceeded if the ui keeps
   requesting a repaint, so every test in a `Processing` state uses `step()`
   and only the `Idle` ones use `run()`. `RawInput::dropped_files` is *moved*
   each frame (one drop, one delivery) and `hovered_files` is *cloned* (it
   persists until the test clears it).
5. **The harness reaches `frame` as
   `let ctx = ui.ctx().clone(); shell.frame(&ctx, ui);`** inside the
   `build_ui_state` closure. It compiles; the two-argument shape is workable
   and needs no change.
6. **The frame order the tests pin**: read input and drain the channel
   **before** painting, so one `Progress` moves the window in one frame (see
   the mutation table). MC-014's `Model` already refuses a drop while
   `Processing`, so a Send-to launch cannot start a second run by itself.
7. **AC-4's path label needs the model built from the *resolved* folder**, as
   the Design notes say (`Model::new(Settings { output_dir: Some(resolved) })`),
   not from the settings as they arrived - otherwise the label reads
   `No output folder chosen` while files are being written to `{dir}\cropped`.
8. `main.rs`'s `open_window` and `CropperApp` still build the old
   `Model`-only window. Wiring them to `Shell` is this story's `## Context`
   and is not pinned by a test (both files are coverage-excluded and
   `tests/window.rs` is MC-001's); do it, but know that the suite will not
   catch it if you do not.
