## Context

The view-model in `crates/app/src/lib.rs` (`architecture.md`, "manhwa-cropper"):
a pure `Model { state: AppState, output_dir: Option<PathBuf> }` whose
`handle(&mut self, Event) -> Vec<Command>` owns every rule in
`docs/wiki/design/components.md`, "Rules the view-model owns", and every
user-visible string is produced here from the frozen table in
`docs/wiki/design/voice.md`, so egui (MC-015) only paints. No egui type
appears in this file. Effects are returned as data (`Command`) so the tests
assert them without threads or dialogs.

Gate that fails if this breaks: `unit`.

## Acceptance criteria

- **AC-1** - Given `Settings { output_dir: None }`, when `Model::new(settings)` runs, then `state == Idle` and `output_dir == None`; given `Some(p)`, then `output_dir == Some(p)`.
- **AC-2** - Given `output_dir == None`, when `FilesDropped(vec![a.png])` is handled, then `state == Error { message: "No output folder chosen. Choose one, then drop the files again." }` and no commands are returned.
- **AC-3** - Given `output_dir == Some(out)` and `state` is `Idle`, `Done` or `Error`, when `FilesDropped` with `n >= 1` paths is handled, then `state == Processing { done: 0, total: n }` and the commands are exactly `[StartBatch { inputs, out_dir: out }]`.
- **AC-4** - Given `Processing`, when `Progress { done: 3, total: 10 }` is handled, then `state == Processing { done: 3, total: 10 }`; when `Finished(summary)` is handled, then `state == Done { summary }`; neither returns a command.
- **AC-5** - Given `FolderChosen(p)`: in `Idle`, then `output_dir == Some(p)`, state stays `Idle`, commands are `[SaveSettings(Settings { output_dir: Some(p) })]`; in `Done { summary }`, then the summary is kept and the same command is returned; in `Error`, then `state == Idle`, `output_dir == Some(p)` and the same `SaveSettings` command is returned; in `Processing`, then nothing changes and no command is returned.
- **AC-6** - Given `Processing`, when `FilesDropped` is handled, then nothing changes and no command is returned; given any state, when `FilesDropped(vec![])` is handled, then nothing changes and no command is returned.
- **AC-7** - Given `Processing`, when `Failed("disk full")` is handled, then `state == Error { message: "Cropping stopped: disk full. Drop the files again." }`.
- **AC-8** - Given a `RunSummary` with 10 cropped, 0 flagged, 0 failed, when `result_line(&summary)` runs, then it returns `"10 cropped, 0 flagged"`; with 7 cropped, 2 flagged, 1 failed, then `"7 cropped, 2 flagged, 1 failed"`.
- **AC-9** - Given each outcome, when `row_text(&FileResult)` runs, then the text is `"<basename> — <reason>"` (space, U+2014, space) with reasons `Uniform -> Blank`, `NoBorderFound -> No border`, `LowContent -> Low content`, `Ambiguous -> Ambiguous`, `Unsupported -> Unsupported format`, `DecodeFailed -> Unreadable`, `Failed -> Not written`; and `rows(&summary)` lists only flagged and failed results, in input order.
- **AC-10** - Given a folder is known, when `dropzone_text(&model, hovering: bool)` runs, then it returns `"Drop images here"` in `Idle`/`Done`/`Error`, `"Release to crop"` when hovering in those states, `"Cropping…"` in `Processing`; given no folder, then `"Choose an output folder, then drop images here"` whether hovering or not. `path_text` returns the full path or `"No output folder chosen"`; `progress_text` returns `"3 of 10"`.

## Model guidance

Model: default. Oracle partition: everything is **mechanical** or
**settled** (the strings are frozen in `voice.md`; read them out
character for character, including U+2026 and U+2014). Pin the shapes:
`AppState { Idle, Processing { done: u32, total: u32 }, Done { summary: RunSummary }, Error { message: String } }`,
`Event { FilesDropped(Vec<PathBuf>), FolderChosen(PathBuf), Progress { done: u32, total: u32 }, Finished(RunSummary), Failed(String) }`,
`Command { StartBatch { inputs: Vec<PathBuf>, out_dir: PathBuf }, SaveSettings(Settings) }`,
all deriving `Debug, Clone, PartialEq`.

## Out of scope

Painting anything (MC-015), the folder dialog, threads and the progress
channel (MC-016), launch arguments (MC-016), queueing drops during a run
(designer decision 1, ratified: ignored silently), remembering window
position.

## Design notes

Nothing is painted here; this story implements the "Rules the view-model
owns" list in `docs/wiki/design/components.md` and produces every string in
the frozen table of `docs/wiki/design/voice.md`. MC-015 must be able to paint
the `Model` without touching a string literal, so every text the window can
show has a function here.

**Rule to criterion.** `FilesDropped` with no folder → `Error{error.no_folder}`,
no command (AC-2). `FilesDropped` while `Processing` is ignored silently, no
message (AC-6; ratified designer decision 1 - the disabled drop-zone look and
`dropzone.busy` in MC-015 are the only signal). `FolderChosen` keeps a `Done`
summary and clears an `Error` to `Idle` (AC-5); in `Error` it should return
the same `[SaveSettings]` command as in `Idle`, since the folder was the usual
cause of the error and the user has just fixed it - AC-5 is silent on the
command in `Error`, so the test should assert it, not leave it unspecified.
`Failed{detail}` → `Error{error.run_failed}` (AC-7).

**Strings, by key.** `dropzone_text` → `dropzone.no_folder` /
`dropzone.ready` / `dropzone.hover` / `dropzone.busy` (AC-10; with no folder
the hover flag is ignored and `dropzone.no_folder` is returned).
`path_text` → the full path via `Path::display()` as Windows shows it, no
quoting, no truncation (left-truncation is MC-015's painter), or
`folder.none`. `progress_text` → `progress.count`. `result_line` →
`result.line` plus `result.failed_suffix` only when `failed > 0`
(AC-8; `12 cropped, 0 flagged, 0 failed` is invalid). `row_text` →
`list.row` with the seven `reason.*` words (AC-9); `{filename}` is
`path.file_name()`, extension included. Tests should copy the bytes from
`voice.md`: `Cropping…` is U+2026, the row separator is space U+2014 space,
and the two error messages end in a full stop while every label does not.

**`{detail}` placeholder.** `voice.md` strips a trailing full stop from the
engine's detail so `error.run_failed` never reads `…disk full.. Drop…`. AC-7
uses `"disk full"` with no stop; the test should also cover
`Failed("disk full.")` producing the identical message. That is a second
case under an existing criterion, not a new one.

**`error.folder_unwritable` has no producer.** No event in this story's
`Event` enum carries an unwritable output folder, so no `handle` path yields
that string. `components.md` says an unwritable folder is reported in the
slot at drop time. Either the runner reports it as `Failed(detail)` (the user
then reads `Cropping stopped: …`, which is acceptable but not the designed
message) or a later story adds an event. Raised for the Lead PO; not worked
around here.

**Send-to fallback.** `Model::new(Settings{output_dir: Some(fallback)})`
(AC-1) is how MC-016 makes the resolved `cropped` folder appear in
`path_text` from the first frame. The model does not distinguish a remembered
folder from a fallback; that is MC-016's job, and it must not emit
`SaveSettings` for a fallback.

Keyboard, tokens, states: none apply - no widget exists in this crate file.

## Test plan

One new test target, `crates/app/tests/model.rs`, **35 tests**. Nothing else
was added: no egui, no filesystem, no threads, no fixture files.

**Level.** A `tests/` integration target rather than `#[cfg(test)]` in
`src/lib.rs`. The view-model *is* the app crate's public surface - MC-015 and
MC-016 are its only callers and they see exactly what this file sees - so
testing it from outside the crate pins the export shape as well as the
behaviour. Nothing here needs crate internals.

**Oracle partition.** Every criterion is **mechanical** or **settled**. There
is no threshold, no tolerance and no invented metric anywhere in this story, so
nothing was designed: every expected value is an exact enum value, an exact
`Vec<Command>`, or a string whose bytes are frozen in `voice.md`. The strings
were copied character for character out of the frozen table and typed as
literals in the assertions - never read back from a constant in the module
under test, which would assert nothing. `Cropping…` is U+2026 and the row
separator is space U+2014 space; both were checked byte by byte with `od`
after the file was written (`e2 80 94` and `e2 80 a6`).

**Why each criterion is tested the way it is.**

**AC-10's unreachable cell.** `Processing` with `output_dir == None` has no
entry in the table and no string in `voice.md`, because AC-3 says a batch
cannot start without a folder. Rather than invent a string for a state the
user cannot reach - which would be a design decision this story has no mandate
to make, and a cell a later refactor could satisfy either way - test 29,
`no_event_can_start_a_run_while_no_folder_is_known`, pins the
*unreachability*: from both folderless states, every event other than
`FolderChosen` is applied and neither `AppState::Processing` nor
`Command::StartBatch` may result (2 states x 5 events = 10 cases). GREEN may
therefore return whichever string falls out of its match arms for that cell;
no test constrains it.

**Signatures pinned** (Lead PO's call, stated in the task; AC-10 fixes only
the first explicitly):

**Cost.** The suite is pure arithmetic and string formatting: no I/O, no
sleeps, no generated collections. Measured against a throwaway implementation
in a scratch workspace (see `## Handoff`), `libtest` reports the whole binary

58 ms / 66 ms / 63 ms, process start included. The `coverage` gate's
`ci-factor` is 1.63, so the whole target is ~100 ms instrumented on CI -
three orders of magnitude under any framework timeout, and no single test is
individually measurable. Nothing here needs a timeout override.

**Admissibility.** `bash scripts/gates.sh --fast` was run: `format` PASS;
`lint`, `typecheck`, `unit` and `coverage` FAIL, each with exactly one error,
`E0432 unresolved imports`, and nothing else (`.claude/state/gate-logs/*.log`
checked for other diagnostics). In Rust `clippy --all-targets` and
`cargo check --all-targets` compile the test targets, so a missing module
necessarily reddens `lint` and `typecheck` too; that is the stack, not a
defect in the tests. Their real admissibility was established separately: with
the module present, `cargo clippy -p manhwa-cropper --all-targets -- -D

`[(&str, fn() -> Model); N]` - which is exactly the failure `--fast` exists to
catch; it is fixed with a `type Start = (&'static str, fn() -> Model);` alias.

From `manhwa_cropper` (the **crate root** of `crates/app/src/lib.rs`):

```rust
pub enum AppState {
    Idle,
    Processing { done: u32, total: u32 },
    Done { summary: RunSummary },
    Error { message: String },
}

pub enum Event {
    FilesDropped(Vec<PathBuf>),
    FolderChosen(PathBuf),
    Progress { done: u32, total: u32 },
    Finished(RunSummary),
    Failed(String),
}

pub enum Command {
    StartBatch { inputs: Vec<PathBuf>, out_dir: PathBuf },
    SaveSettings(Settings),
}

pub struct Model {
    pub state: AppState,          // read directly by the tests
    pub output_dir: Option<PathBuf>,  // read directly by the tests
}

impl Model {
    pub fn new(settings: Settings) -> Model;          // by value
    pub fn handle(&mut self, event: Event) -> Vec<Command>;
}

pub fn result_line(summary: &RunSummary) -> String;
pub fn row_text(result: &FileResult) -> String;
pub fn rows(summary: &RunSummary) -> Vec<String>;
pub fn dropzone_text(model: &Model, hovering: bool) -> &'static str;
pub fn path_text(model: &Model) -> String;
pub fn progress_text(done: u32, total: u32) -> String;
```

All three of `AppState`, `Event` and `Command` must derive
`Debug, Clone, PartialEq`: the tests compare them with `assert_eq!`, clone an
`Event` inside test 29's table, and clone an `AppState` in test 15.
`done`/`total` are `u32` in both `AppState::Processing` and `Event::Progress`,
and `progress_text` takes `u32` - `Event::Progress` is *not* the engine's
`batch::Progress` (that one is `usize`), so MC-016 converts at the boundary.

**Not constrained, and therefore GREEN's choice**: whether `Model` derives
anything (no test clones a `Model` - that is what `type Start` exists for);
whether `handle` is `#[must_use]` (the tests bind or discard the result
either way); the string constants' names and visibility; any private helper;
whether `AppState`/`Event`/`Command` also derive `Eq` or `Default`; the
behaviour of `Progress`, `Finished` and `Failed` in states other than
`Processing` (no AC and no test covers them); `Finished` arriving while
already `Done`; and the text `dropzone_text` returns for the unreachable
`Processing`-with-no-folder cell.

### Things that should change the implementation approach

- **`cropper-core` is not linked to the app library.** Item 4 above. This is
  the one change that is invisible from the test file and stops the build
  dead; it cost a rebuild to find in RED.
- **`Event::Progress` is `u32`, `batch::Progress` is `usize`.** The view-model
  deliberately does not take the engine's type. MC-016's channel adapter is
  where the conversion belongs; `u32::try_from(inputs.len())` is also needed
  when `FilesDropped` sets `total`.
- **`RunSummary` has no public counters other than the derived methods**
  (`cropped()`, `flagged()`, `failed()`, `flagged_names()`), all returning
  `usize`, and a public `results: Vec<FileResult>`. `result_line` and `rows`
  should read those rather than re-counting - note that `flagged_names()` is
  *not* what `rows` wants, since `rows` must include `Failed` results too and
  needs the reason word.
- **`error.folder_unwritable` still has no producer**, as the 2026-09-10
  Notes entry records. No test in this file asserts it and none should.

  in v1 an unwritable output folder is reported by the batch runner as
  `Failed(detail)` and shown through `error.run_failed` (AC-7). The string is

- 2026-09-13 (Feature Developer, GREEN): **the four cells no AC and no test
  constrains**, chosen deliberately and documented in the doc comment beside
  each one in `crates/app/src/lib.rs`. None of them invents a string; every
  text the module can return is still a key from `voice.md`.
  - `Progress`, `Finished` and `Failed` **outside `Processing`**: ignored -
    no state change, no command. House style (a drop during a run is ignored
    in silence); outside a run these describe a run that is already over, and
    ignoring is the only option that cannot overwrite what the user is
    reading.
  - `Finished` **while already `Done`**: the same rule, so it is ignored.
    `components.md`'s "`Finished` replaces any earlier summary" is satisfied
    by the reachable path - a new drop goes `Done -> Processing -> Done` and
    the new summary replaces the old - and a second `Finished` with no run
    behind it is a stale message, not a newer result.
  - `dropzone_text` for the unreachable **`Processing` with no folder**:
    `dropzone.busy` (`Cropping…`), because the `Processing` arm is matched
    first. That ordering is required anyway (hover must not beat busy,
    mutation 6), it states what the state says is true, and it avoids
    inventing a string for a cell `voice.md` does not have.
  - `row_text` of a **cropped** result: the `reason.failed` word. `rows`
    filters cropped results out, so nothing reachable asks for it; a cropped
    file has no word in `voice.md`, and folding it into the `Failed` arm was
    preferred to the two alternatives - inventing a seventh reason word (a
    design decision this story has no mandate for) or writing a branch the
    frozen suite cannot reach, which the `coverage` gate measures and which
    the story's own rule says should not exist.
