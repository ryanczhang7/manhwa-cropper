## Context

[`EPIC-07`](../epics/EPIC-07.md) `## Stories` item 1, first half. Everything
else in that epic is blocked on a corpus that can report an honest number, and
this story builds the machinery for one: a `split` field on every manifest
entry, validated, documented, and with the one invariant that actually protects
the result nailed down in a test.

**The methodological problem, stated plainly, because the next agent will not
know it.** Every rule v1 ever tried — MC-025, MC-028, MC-031, MC-032, MC-034,
MC-035 — was tuned *and* scored on the same 21 marked entries. There is no
held-out set, so every v1 number is optimistic by an unknown amount, and any v2
number produced the same way would be too.

**Therefore the existing 28 entries cannot become the held-out set, or any part
of it.** They are already contaminated: six investigations have fitted
thresholds against them, and the people and agents planning v2 have read the
per-file tables. A held-out set has to be built from **new** screenshots that
no tuning has ever seen. A story that assigned some of the existing 21 to
"held out" would produce a number that *looks* rigorous and is not — which is
the exact failure mode this story exists to prevent. That is why AC-2 below is
the load-bearing criterion and the rest is plumbing.

So this story assigns `"tuning"` to all 28 existing entries and freezes that by
name. The held-out set is legitimately **empty** when this story is done.
MC-037 fills it, and only MC-037 can put a floor under its size.

**Why this is a `chore` under SCAFFOLD and not a `feature`.** The obvious
reading is that a validated manifest field with real invariants is testable
behaviour, which points at a RED→GREEN cycle. It does not survive contact with
the path classification:

```
$ bash -c '. .claude/hooks/lib.sh; classify "fixtures/corpus/manifest.json"; \
           classify "crates/engine/tests/corpus_manifest.rs"; classify "docs/wiki/corpus.md"'
test test docs
```

`paths.conf` classifies `fixtures/**` and `**/tests/**` as `test`. Every file
this story touches is therefore `test` or `docs`, and **GREEN may write neither
of the first** — GREEN's permissions are source, config, docs, harness, with
tests frozen. A `feature` here would reach GREEN with nothing it is allowed to
write, and the only ways out are a phase-lock workaround (forbidden by law 5)
or a sham GREEN. The deeper reason is the same one: a manifest is *data a
person authors*, not behaviour that production code produces. There is no
production code that could make AC-1 pass; you make it pass by editing the
fixture. That is MC-018's situation exactly, and MC-018 is the precedent —
`chore`, SCAFFOLD, Lead PO drives it.

**The price of SCAFFOLD, which is not optional.** Every assertion here will be
written against a manifest the author has just edited to satisfy it. All of
them pass on first execution; none has ever been observed to fail; any of them
could assert nothing and nothing would notice. `## Gate probes` is where that
is discharged — one mutation, one run, one revert, per assertion, with the
output pasted. MC-018's `## Gate probes` is the shape to copy, and its P1 is
the reason to bother: that probe found a real defect the annotation tool had
introduced, before it reached MC-019.

**Gate that fails if this story's artifact breaks: `unit` (required).**
`crates/engine/tests/corpus_manifest.rs` is deliberately **not** `#[ignore]`d,
so `cargo test --workspace` runs it on every commit. `required_gates` is
therefore `[]` — see `## Out of scope` for the constraint that keeps it true,
which is the whole reason this paragraph exists.

**Consumers that must keep working.** `crates/engine/tests/common/corpus.rs` is
included by `#[path]` into `corpus_manifest.rs`, `corpus.rs`, `corpus_accuracy.rs`
and (via `common/mod.rs`) the app crate's `headless.rs`. Adding a required field
to `RawEntry` changes the parse for all of them. `corpus.rs` and
`corpus_accuracy.rs` are `#[ignore]`d and run under the optional, `slow`
`integration` gate, so `gates.sh --fast` will not notice a break there: run the
full gates before REVIEW, as the law requires anyway.

## Acceptance criteria

All four are **mechanical**. None names a statistic, a metric or a threshold,
so none carries a negative control; what earns them instead is a probe each in
`## Gate probes`.

- **AC-1** — Given `fixtures/corpus/manifest.json`, when `corpus::load()` runs, then every entry carries a `split` whose value is exactly `"tuning"` or `"held-out"`, exposed on `CorpusEntry`; and an entry with a missing `split`, or one whose value is any other string, makes `load()` panic naming the file and the offending value.
- **AC-2** — Given the 28 entries that existed before EPIC-07 — the full contents of `fixtures/corpus/manifest.json` at commit `a453aaa`, carried in the test as a settled `const` list of file names, never re-derived — when the manifest is validated, then **every one of them carries `split: "tuning"`**, and an entry whose file name is in that list and whose split is `"held-out"` fails the test naming it. The test additionally asserts that the list is non-empty and that every name in it is present in the manifest, so it cannot pass by measuring nothing.
- **AC-3** — Given `docs/wiki/corpus.md`, when the validator runs, then the two permitted `split` values are **read off that page** — from a table introduced by a `<!-- split-vocabulary -->` marker, parsed the same way `documented_tag_vocabulary()` parses the tag table — and any manifest split value absent from the page fails the test. The page carries, in prose beside the table, what each set is for and the rule that the held-out set is scored once and never tuned against.
- **AC-4** — Given `corpus::load()`, when it runs, then it still returns every entry **in manifest order** with `path`, `expect` and `tags` unchanged in shape and value, and the twelve pre-existing tests in `corpus_manifest.rs` still pass; the split is additive.

## Model guidance

Model: **default**. Every criterion is mechanical: exact strings, exact counts,
an exact list of file names. There is no metric to invent and no threshold to
calibrate, which is the situation where a stronger model has nothing to add.

**Oracle partition**, for whoever writes the assertions under SCAFFOLD:

| Kind | What |
|---|---|

## Out of scope

- **Any detection rule, of any kind.** This story adds a field to a fixture. It
  does not touch `crates/core/src/**`, `Tuning`, or anything that looks at a
  pixel. EPIC-07's stories 2 and 3 are where a signal is proposed.
- **Re-marking anything.** The marks stay tight, by the user's decision of
  2026-09-17 (`architecture.md` decision 14, amendment). MC-031 section 9
  Option C was considered and declined. No rectangle in `manifest.json` changes
  by so much as a pixel in this story.
- **The column axis.** Settled at 20 of 21 and not reopened.
- **Adding, removing or re-tagging any screenshot.** The corpus is the same 28
  files before and after; only a field is added to each entry. New files are
  MC-037.
- **Any floor on the size of either set.** The held-out set is empty when this
  story is done and that is correct, not a defect: there is nothing legitimate
  to put in it yet. `MIN_ENTRIES` stays at 20 and stays a whole-corpus floor.
  MC-037 adds the per-set floors.
- **A `site` dimension.** Proposed in MC-037, where the user — who took the
  screenshots — can supply the labels. Reading a site off a screenshot is an
  agent guessing, and `corpus.md` is explicit that a guessed tag is worse than
  an absent one (`overhang-text`).
- **Asserting disjointness as its own test.** It is a consequence of the
  representation: one `split` string per entry means an entry cannot be in both
  sets and cannot be in neither, once AC-1 holds. A test for it could not fail
  without AC-1 failing first, and a test that cannot fail is the thing this
  harness exists to keep out. If a later story ever moves the split to two
  lists of names, disjointness becomes a real assertion and arrives with that
  change.
- **Moving the new tests anywhere but `crates/engine/tests/corpus_manifest.rs`.**
  `corpus.rs` and `corpus_accuracy.rs` are `#[ignore]`d and run only under the
  optional `integration` gate; an assertion placed there could go unrun while
  `All required gates passed` printed over this story. The new tests are
  non-`#[ignore]`d, in `corpus_manifest.rs`, and that is what makes
  `required_gates: []` honest.

## Test plan

Built under SCAFFOLD. Sixteen tests in `crates/engine/tests/corpus_manifest.rs`
now, none `#[ignore]`d: the twelve that were there, plus one per AC.

- **`crates/engine/tests/common/corpus.rs`** — a `Split` enum (`Tuning`,
  `HeldOut`) with `as_str()`, a required `split: Split` on `CorpusEntry`, and
  the parse in `load()` that panics naming the manifest, the entry and the
  offending value (AC-1, AC-4).

  **One departure from the shape sketched in PLANNED, and why.** That sketch
  said `RawEntry` gains a required `split: String`. It gained
  `split: Option<String>` instead, with `load()` panicking on `None`. The field
  is no less required — `load()` refuses either way — but serde's own
  missing-field error reads `missing field \`split\` at line 61 column 7`, which
  names a byte offset rather than the entry. With the `Option`, P1b below prints
  `entry "Screenshot (93).jpg" has no "split"`, which is the message the person
  who has just added a screenshot and forgotten one actually needs. AC-1 asks
  the panic to name the file; this names the entry as well. There is
  deliberately no `#[serde(default)]`: a default would decide an entry's
  contamination status silently, which is the one thing the field exists to
  stop.

- **`crates/engine/tests/corpus_manifest.rs`** —
  - `PRE_EPIC_07_ENTRIES: [&str; 28]`, the literal output of
    `git show a453aaa:fixtures/corpus/manifest.json`, in manifest order, beside
    `DIAGONAL_GUTTER_ENTRIES` and with the same kind of doc comment: read out,
    never re-derived, and specifically *not* defined as "the manifest minus the
    new ones" — that definition would absorb a future entry and launder it into
    the tuning set (AC-2).
  - `documented_split_vocabulary()`, which reuses the tag-table parse against
    `<!-- split-vocabulary -->`. The reuse is literal: `documented_vocabulary`
    was extracted out of `documented_tag_vocabulary` and both now call it, so
    there is one parser rather than two copies of one (AC-3).
  - `raw_splits()`, a second independent parse of the manifest with
    `serde_json::Value`. AC-1 and AC-3 compare the loader's answer against this
    rather than against the loader again — a loader that mapped every value to
    one variant would satisfy any check that asked the loader twice.
  - `every_entry_carries_the_split_its_manifest_entry_states` (AC-1),
    `every_pre_epic_07_entry_is_in_the_tuning_split` (AC-2),
    `every_split_in_the_manifest_is_in_the_documented_vocabulary` (AC-3),
    `the_loader_still_reports_path_expect_and_tags_exactly_as_the_manifest_gives_them`
    (AC-4).
- **`fixtures/corpus/manifest.json`** — `"split": "tuning"` on all 28 entries.
  No rectangle, tag or file name changed; the diff is 28 added fields.
- **`docs/wiki/corpus.md`** — `## The tuning / held-out split`, carrying the
  `<!-- split-vocabulary -->` table, why the split exists, the scoring rule
  stated so it cannot be read two ways, and the permanence of the 28.

### What AC-1's test does *not* assert, and where that half went

A post-load `filter(|e| !matches!(e.split, Tuning | HeldOut))` would be vacuous:
`Split` has two variants, so the filter can never match. The "makes `load()`
panic" half of AC-1 is therefore discharged by P1a and P1b below, not by an
assertion — no assertion inside a test process can observe a panic the loader
raises before returning.

## Gate probes

Every assertion here was written against a manifest and a page the author had
just edited to satisfy it, so all four passed on first execution and none had
ever been observed to fail. Five probes fix that. One mutation, one run, one
revert each; `fixtures/corpus/manifest.json`, `docs/wiki/corpus.md` and
`crates/engine/tests/common/corpus.rs` were copied beforehand and each revert
verified with `diff -q` rather than assumed.

Command throughout: `cargo test -p cropper-engine --test corpus_manifest`.

**P1a — AC-1, an unrecognised split value.** Changed the first entry's split
from `"tuning"` to `"holdout"`.
