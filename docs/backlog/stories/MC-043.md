## Context

Found while driving [MC-040](MC-040.md) on 2026-09-22. `scripts/gates.sh` lines
267–275 document `work_count()` with a consequence that does not reproduce:

> The consequence is that a regex which stops mid-number - the `[1-9]` in
> `test result: ok\. [1-9]` - measures a truncated count; widen it to cover the
> whole number if you want a floor on that gate.

The implementation is:

```bash
work_count() {
  clean_log "$1" \
    | grep -oE -m1 -- "($2).*" 2>/dev/null | head -1 \
    | grep -oE '[0-9]+' 2>/dev/null | head -1
}
```

The match is `($2).*`. The trailing `.*` runs to end of line, so the span handed
to the second `grep` contains the whole number whatever the evidence regex
stopped at, and `grep -oE '[0-9]+' | head -1` reads the first **complete** digit
run out of it. **A regex cannot truncate a count it does not have to contain.**

### Reproduced three times, independently

Twice during MC-040 (once by the Test Developer, once by the orchestrator using
`gates.sh`'s own `clean_log`/`work_count` against real gate logs), and once more
at PLANNED here on inputs neither earlier probe used. `narrow` is
`test result: ok\. [1-9]` — the exact regex the comment calls truncating —
against `wide`, `test result: ok\. [1-9][0-9]*`:

```
log      narrow     wide
a.log    836        836      # "test result: ok. 836 passed; 0 failed; 0 ignored"
b.log    47         47
c.log    9          9        # "ok. 0 passed; 0 failed; 14 ignored" then "ok. 9 passed"
d.log    205        205      # two "ok. 0" lines, then "ok. 205 passed"
e.log    5          5        # CRLF line endings
f.log    203        203      # ANSI colour around the number
```

If the comment were right, `narrow` would read 8, 4, 9, 2, 5, 2.

### The real consequence is different, sharper, and load-bearing

A restrictive **leading** digit class does not truncate a count; it makes the
line **not match at all**, so the count is taken from some later line. The same
probe with the leading class widened to `[0-9]` — `test result: ok\. [0-9][0-9]*`
— on the same files:

```
log      [1-9]...   [0-9]...
c.log    9          0
d.log    205        0
```

`ok. 0 passed` matches `[0-9][0-9]*` and supplies the count; it does not match
`[1-9][0-9]*` and is skipped. That is not a detail — it is the whole mechanism
[MC-040](MC-040.md) rests on. Under `cargo test --workspace --release -- --ignored`
**twelve** `test result: ok. 0` lines go by unmatched before the first match,
which is why `floor | integration | 9` tracks `crates/engine tests/corpus.rs`
and not whatever cargo runs first. The comment as written points the next agent
at a property that does not exist and away from the one that decides the number.

### Three places say it, and they do not say the same thing

All three were read at PLANNED before the criteria froze:

1. **`scripts/gates.sh` ~267–275** — the block quoted above. Wrong as written.
2. **`.claude/harness/project.conf` ~56–59** — "The number is measured out of
   the evidence match [...] so a floor needs an evidence line, and that regex
   must cover the whole number. `gates.sh --audit` refuses a floor without one,
   or a floor that is not a number." The *rule* is stated; note that the
   enforcement sentence after it claims only that `--audit` refuses a floor with
   no evidence line and a floor that is not a number. It does **not** claim
   `--audit` enforces the whole-number clause.
3. **`gates.sh --audit`** — and indeed it does not. Read at PLANNED: the floor
   validation at `scripts/gates.sh` ~451–475 checks three things — the floor is
   a number, the gate has an evidence line, the gate is not `no-count` — and
   nothing about the regex's shape. So `project.conf` is not lying about its own
   enforcement; it states a rule that nothing enforces, next to enforcement it
   does have. That is a smaller defect than the `gates.sh` comment and it is
   fixed by correcting the rule, not by adding enforcement (see `## Out of scope`).

### And a fourth place, which is a test

[MC-040](MC-040.md) shipped `.claude/tests/manifest.test.sh`, which pins "covers
the whole number" as a **manifest rule** via:

```bash
covers_whole_number() { printf '%s' "$1" | grep -qE '\[[^]]*\][*+]'; }
```

precisely because it could not be pinned behaviourally — and now we know why it
could not: there is no behaviour there to pin. That assertion is still worth
keeping (`[1-9][0-9]*` is the clearer regex and states its intent), but its
stated justification — "not just its first digit" — repeats the wrong claim. The
rule survives; the reason under it is rewritten. AC-4.

### Why this is a `chore` and not a `fix`

Considered, and `fix` was rejected. A `fix`'s criteria reproduce a bug and its
first test is a failing regression test. Here `work_count()` is **correct**: the
three reproductions above show it reads the whole number exactly as it should.
What is wrong is prose. No test can be red before this story and green after,
because nothing executable changes.

That leaves this story's tests **green on arrival**, which the non-negotiables in
`.claude/harness/rules.md` already have a rule for: a test written against code
that already exists earns its place by a probe — mutate the specific production
behaviour it pins, watch that one assertion go red, revert, paste the output.
AC-2 makes that the price of the assertions, and it is the point of the story:
a comment nothing tests drifted for months, and the fix for that is not a better
comment but a test.

`chore` in this repo does **not** mean SCAFFOLD. MC-040 is a `chore` and ran the
full PLANNED → RED → GREEN → GATES → REVIEW path; so does this one. SCAFFOLD is
not to be used here — there is nothing indivisible about it.

## Acceptance criteria

- **AC-1** — *The `gates.sh` comment states what the function does.* Given `scripts/gates.sh`, then the block documenting `work_count()` no longer claims that a regex stopping mid-number measures a truncated count, and instead states both halves of the real behaviour: (a) the trailing `.*` means the counted span always reaches the end of the line, so the evidence regex's *width* does not affect the number read; (b) the evidence regex's *leading* digit class decides **which line** supplies the count, because a line it does not match is skipped entirely. *Control:* the corrected text must be falsifiable against the probe table in `## Context` — if a reader could run that probe and find the new text wrong, it is wrong. The existing paragraph about `no-count` and stopwatches below it is correct and stays.
- **AC-2** — *Both halves are pinned by tests that have been watched to fail.* Given `.claude/tests/gates.test.sh`, when `bash scripts/selftest.sh gates` runs, then it covers, with at least one assertion each: (a) a narrow evidence regex (`test result: ok\. [1-9]`) and a wide one (`test result: ok\. [1-9][0-9]*`) read the **same** count from the same log; (b) a log whose first `test result: ok. N` line has `N = 0` yields the **later** line's count under a `[1-9]`-leading regex and `0` under a `[0-9]`-leading one. *Control:* both assertions pass on arrival, so each is earned by a probe recorded in `## Regressions` — one mutation, one run, one revert, output pasted. Worked example for (a), measured at PLANNED: delete the trailing `.*` from `"($2).*"` and the narrow case reads `8` for a log saying `836` while the wide case still reads `836` — a single-assertion catch, which is where a vacuous test hides. The Test Developer chooses the mutation for (b), and for **both** states the predicted catch count before running and compares it after.
- **AC-3** — *`project.conf` states the rule that is actually load-bearing.* Given `.claude/harness/project.conf`, then the `floor` documentation no longer rests the whole-number clause on a truncation that does not happen, and says instead that the leading digit class selects the counted line — with the `integration` case named as the live example: twelve `test result: ok. 0` lines skipped, the number coming from `crates/engine tests/corpus.rs`. The sentence about what `--audit` refuses is left describing only what it refuses. *Control:* the `floor | integration | 9` comment block already added by MC-040 is the worked example and must not be contradicted by the new text; if it is, one of the two is wrong and the story stops.
- **AC-4** — *The manifest rule keeps its assertion and loses its wrong reason.* Given `.claude/tests/manifest.test.sh`, then `covers_whole_number()` and the two assertions built on it still exist and still pass, and the assertion text and surrounding comment no longer justify the rule by "not just its first digit". *Control:* the self-control already in that file — `covers_whole_number 'test result: ok\. [1-9]'` must stay **false**, so the predicate is still discriminating. A change that made the predicate accept everything would go green and defend nothing.
- **AC-5** — Given `bash scripts/selftest.sh`, when it runs in full, then every suite passes and the output is pasted in `## Notes`. No suite other than `gates.test.sh` and `manifest.test.sh` is edited. *Control:* this is the story's only evidence that its artifact was verified, because `selftest` is a CI step rather than a `gates.sh` gate and so never appears in `## Gate results` (see "The gate question"). A pasted summary without the run is what `## Gate results` exists to prevent elsewhere, and the same standard applies here.

## Out of scope

- **Making `gates.sh --audit` enforce the whole-number clause.** It does not
  today, and it should not be made to by this story. Two reasons, and the second
  is the real one. First, it is a behaviour change to a gate-adjacent script and
  brings its own `## Gate probes` obligation — a second cycle's worth of work.
  Second, and decisively: the evidence above shows the whole-number rule is
  **not what makes a count correct**. Enforcing it would harden a rule this
  story exists to demote from "the consequence" to "a readability preference".
  If the whole-number rule should become enforced, that is a separate product
  decision on a separate story, and it should be argued for on clarity grounds
  rather than on the truncation claim, which is false.
- **Removing or replacing `covers_whole_number()`.** AC-4 keeps it. Deleting a
  test because the prose that motivated it was wrong is the wrong direction; the
  regex it enforces is still the better regex.
- **Changing `work_count()`, `clean_log()`, or any other executable line in
  `scripts/gates.sh`.** The code is correct. This story changes a comment in
  that file and nothing else in it. If a reading of AC-1 seems to require a code
  change, stop — it does not, and the story is being misread.
- **Changing any `gate`, `evidence`, `floor`, `no-count`, `slow`, `ci-factor`,
  `waiver` or `discovery` line in `project.conf`.** Comments around them only.
  In particular `evidence | integration | test result: ok\. [1-9][0-9]*` and
  `floor | integration | 9` are [MC-040](MC-040.md)'s and stay byte-for-byte.
  This is what makes `required_gates: []` correct; changing one would make it
  wrong.
- **Re-measuring MC-040's floor, or any floor.** The twelve skipped `ok. 0`
  lines are quoted from MC-040's measured run and are cited, not re-derived.
- **The lock-waiting flake in `.claude/tests/gates.test.sh`.** Same file,
  unrelated defect, and it is [MC-044](MC-044.md). This story adds assertions to
  that file; it does not touch the `one run at a time` block.
- **Auditing the rest of `gates.sh`'s comments for other drift.** Tempting and
  unbounded. If something else is found wrong while working, write it in
  `## Notes` and file a story.

## Notes

### AC-2's worked mutation, confirmed independently at PLANNED (2026-09-22)

AC-2 hands RED a worked example rather than a guess, so it was re-run by the
orchestrator before the story was filed — a premise RED inherits is worth one
cheap check, and a false one would cost the phase.

Both `work_count` variants built from `scripts/gates.sh`'s shipped source, the
mutation being the removal of the trailing `.*` from `"($2).*"`, against a log
line reading `test result: ok. 836 passed; 0 failed; 0 ignored`:

```
           narrow         wide
shipped    836            836
mutated    8              836
```

`narrow` is `test result: ok\. [1-9]`, `wide` is `test result: ok\. [1-9][0-9]*`.

The prediction holds exactly. Two things follow, and both matter to RED:

- the **shipped** row is the defect this story documents — the width of the
  regex makes no difference, which is what the `gates.sh` comment denies;
- the **mutated** row is a single-assertion catch: only the narrow case moves.
  A lone predicted failure is where a vacuous assertion hides, which is why
  AC-2 names this mutation specifically and asks for the count to be predicted
  before the run and compared after.
