## Context

Found while driving [MC-040](MC-040.md) on 2026-09-22. `scripts/gates.sh` lines
267–275 document `work_count()` with a consequence that does not reproduce:

> The consequence is that a regex which stops mid-number - the `[1-9]` in
> `test result: ok\. [1-9]` - measures a truncated count; widen it to cover the
> whole number if you want a floor on that gate.

The implementation is:

```bash
work_count() {
  clean_log "$1" \
    | grep -oE -m1 -- "($2).*" 2>/dev/null | head -1 \
    | grep -oE '[0-9]+' 2>/dev/null | head -1
}
```

The match is `($2).*`. The trailing `.*` runs to end of line, so the span handed
to the second `grep` contains the whole number whatever the evidence regex
stopped at, and `grep -oE '[0-9]+' | head -1` reads the first **complete** digit
run out of it. **A regex cannot truncate a count it does not have to contain.**

### Reproduced three times, independently

Twice during MC-040 (once by the Test Developer, once by the orchestrator using
`gates.sh`'s own `clean_log`/`work_count` against real gate logs), and once more
at PLANNED here on inputs neither earlier probe used. `narrow` is
`test result: ok\. [1-9]` — the exact regex the comment calls truncating —
against `wide`, `test result: ok\. [1-9][0-9]*`:

```
log      narrow     wide
a.log    836        836      # "test result: ok. 836 passed; 0 failed; 0 ignored"
b.log    47         47
c.log    9          9        # "ok. 0 passed; 0 failed; 14 ignored" then "ok. 9 passed"
d.log    205        205      # two "ok. 0" lines, then "ok. 205 passed"
e.log    5          5        # CRLF line endings
f.log    203        203      # ANSI colour around the number
```

If the comment were right, `narrow` would read 8, 4, 9, 2, 5, 2.

### The real consequence is different, sharper, and load-bearing

A restrictive **leading** digit class does not truncate a count; it makes the
line **not match at all**, so the count is taken from some later line. The same
probe with the leading class widened to `[0-9]` — `test result: ok\. [0-9][0-9]*`
— on the same files:

```
log      [1-9]...   [0-9]...
c.log    9          0
d.log    205        0
```

`ok. 0 passed` matches `[0-9][0-9]*` and supplies the count; it does not match
`[1-9][0-9]*` and is skipped. That is not a detail — it is the whole mechanism
[MC-040](MC-040.md) rests on. Under `cargo test --workspace --release -- --ignored`
**twelve** `test result: ok. 0` lines go by unmatched before the first match,
which is why `floor | integration | 9` tracks `crates/engine tests/corpus.rs`
and not whatever cargo runs first. The comment as written points the next agent
at a property that does not exist and away from the one that decides the number.

### Why this is a `chore` and not a `fix`

Considered, and `fix` was rejected. A `fix`'s criteria reproduce a bug and its
first test is a failing regression test. Here `work_count()` is **correct**: the
three reproductions above show it reads the whole number exactly as it should.

because nothing executable changes.

## Acceptance criteria

- **AC-1** — *The `gates.sh` comment states what the function does.* Given `scripts/gates.sh`, then the block documenting `work_count()` no longer claims that a regex stopping mid-number measures a truncated count, and instead states both halves of the real behaviour: (a) the trailing `.*` means the counted span always reaches the end of the line, so the evidence regex's *width* does not affect the number read; (b) the evidence regex's *leading* digit class decides **which line** supplies the count, because a line it does not match is skipped entirely. *Control:* the corrected text must be falsifiable against the probe table in `## Context` — if a reader could run that probe and find the new text wrong, it is wrong. The existing paragraph about `no-count` and stopwatches below it is correct and stays.
- **AC-2** — *Both halves are pinned by tests that have been watched to fail.* Given `.claude/tests/gates.test.sh`, when `bash scripts/selftest.sh gates` runs, then it covers, with at least one assertion each: (a) a narrow evidence regex (`test result: ok\. [1-9]`) and a wide one (`test result: ok\. [1-9][0-9]*`) read the **same** count from the same log; (b) a log whose first `test result: ok. N` line has `N = 0` yields the **later** line's count under a `[1-9]`-leading regex and `0` under a `[0-9]`-leading one. *Control:* both assertions pass on arrival, so each is earned by a probe recorded in `## Regressions` — one mutation, one run, one revert, output pasted. Worked example for (a), measured at PLANNED: delete the trailing `.*` from `"($2).*"` and the narrow case reads `8` for a log saying `836` while the wide case still reads `836` — a single-assertion catch, which is where a vacuous test hides. The Test Developer chooses the mutation for (b), and for **both** states the predicted catch count before running and compares it after.
- **AC-3** — *`project.conf` states the rule that is actually load-bearing.* Given `.claude/harness/project.conf`, then the `floor` documentation no longer rests the whole-number clause on a truncation that does not happen, and says instead that the leading digit class selects the counted line — with the `integration` case named as the live example: twelve `test result: ok. 0` lines skipped, the number coming from `crates/engine tests/corpus.rs`. ### Things GREEN should know that change the approach

1. **The trailing `.*` is load-bearing — just not for the reason the comment
   gave.** Probe 1 (removing it) broke **four existing assertions** as well as
   the new one: the alternation case, the `Finished .* profile` stopwatch case,
   and the `TOTAL` floor case. Those are evidence regexes whose match ends
   *before* the number, so without `.*` there is nothing to count. The corrected
   comment must therefore not say the `.*` is harmless — it says the counted
   span always reaches end of line, which is simultaneously why width does not
   matter and why `TOTAL` can still measure 1629.
2. **`required_gates: []` still looks right.** The story's "The gate question"
   reasoning was re-checked here: nothing in `project.conf` runs the harness
   suite, and CI runs `bash scripts/selftest.sh` as a blocking step. RED did
   **not** run `bash scripts/gates.sh --fast`: on this checkout
   `gates.sh --list` alone takes ~373 s against a 28 GB `target/`, and no gate
   it would run touches bash or comments. The equivalent slower command for

### Out of scope, found while working: `gates.sh` is pathologically slow here

`## Out of scope` says to write such a finding down and file a story rather
than chase it, so: `scripts/gates.sh` has a startup cost that scales with the
size of the working tree, and on this checkout it is severe.

```
bash -c true                      69 ms
scripts/phase.sh show            416 ms
gates.sh --list  (test fixture)   12,587 ms
gates.sh --list  (this repo)      73,321 ms / 105,685 ms
```

`--list` parses `project.conf` and prints; it runs no gate and should be
instant. A `PS4='+$EPOCHREALTIME:$LINENO'` trace of the fixture run shows no
single stall — ~288 traced lines, each forked `cut`/`tr`/`printf`/`hostname`
costing 0.3–0.7 s. Bash itself forks in 69 ms, so this is not simply a slow
machine; it is the number of subprocesses multiplied by a per-fork cost that
grows with the tree. This repo carries a 28 GB, 62,368-file `target/`.

The figure varies a lot, and one reading is worth flagging because it was
recorded here first and then withdrawn: an initial measurement of **372,978 ms**
was taken while a background `selftest.sh` run was contending for the same
machine, and does not reproduce. Three later clean runs gave 73 s, 106 s and a
`--fast` whose five gates totalled 89 s of gate time. The defect stands on the
reproducible numbers, not the outlier.

The practical consequence, which cost this phase two false "hangs" (two
`selftest.sh gates` runs killed at exit 124 before the cause was understood):
the `gates` suite makes ~40 fixture invocations and needs 5–13 minutes, and any
agent given a 400-second budget will report it as hung.

Nothing here is MC-043's to fix — it is a performance defect in executable
lines of `scripts/gates.sh`, which this story is explicitly forbidden to touch.
Filed as [MC-045](MC-045.md), which owns the executable half.
