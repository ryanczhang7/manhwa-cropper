## Context

This is the follow-up that [MC-046](MC-046.md) recommended in its
`## Out of scope`. The user asked for it on 2026-09-23. It is harness work
filed under [EPIC-07](../epics/EPIC-07.md), like MC-043 to MC-046, because that
is the epic in flight.

MC-046 stops a gate command from consuming the manifest through stdin or an
inherited descriptor. This story adds the defence behind it. **A gate run must
not print `All required gates passed`, exit 0 or record `pass` unless every
`gate` line that `project.conf` declares has been accounted for.** That holds
whatever the cause of a loss. Today nothing compares what ran against what was
declared. The summary counts only what reached it, so a gate the loop never
reached leaves no trace.

### Why this is a `fix` and not a `feature`: a loss path MC-046 does not close

MC-046's Out of scope expected that after its fix "no known path loses a
gate". That turned out to be wrong. The following was measured at PLANNED on
2026-09-23, HEAD 1fa9815, with a fixture from `make_project_fixture`:

```
gate | first | required | . | printf 'BOOTSTRAPPED=yes\n' > .claude/harness/project.conf; printf 'Tests 1 passed\n'
gate | later | required | . | exit 1
```

```
PASS         first (0s) -- no evidence line: a vacuous pass would go unnoticed
All required gates passed (1 ran, 0 unconfigured, 0 known).
exit=0
```

`first` reads no stdin. It rewrites the manifest **in place**, by path. The
gate loop streams `project.conf` from an open descriptor, so its next `read`
lands past the new end of file and the loop ends. `later` exits 1, yet it never
runs and never appears in the output, and the run certifies a pass.

The same fixture was then run against the **smallest fix that satisfies
MC-046's criteria**: `</dev/null` on the gate subshell (line 611), applied to
a **fixture copy** of `gates.sh` and never to the repo. That fix turns MC-046
case B into `FAIL later … exit=1` and MC-046 AC-2's fd-draining gate into
`FAIL later … exit=1`, so it passes both. The in-place rewrite still prints
`All required gates passed (1 ran, 0 unconfigured, 0 known).` and exits 0.
An atomic rewrite (`> p.tmp && mv p.tmp project.conf`) does *not* lose the
gate, because the loop keeps the old inode. Only an in-place truncating write
does.

This is consistent with MC-046, which declares "a gate can still `rm` the
manifest" out of scope. It is also exactly the class of loss the invariant
exists to catch. It is the reason this story is a `fix`: AC-1 reproduces it.

### How the tests earn their failure: a fault-injection seam

Rules.md requires every test to be watched to fail for the right reason. After
MC-046, a stdin-based loss no longer exists to be red against. The in-place
rewrite above is red today, but whether it stays red depends on how MC-046 is
implemented: a loop that snapshots the manifest before running anything
closes it. A test of the invariant that relies on some *real* way of losing a
gate therefore guards the invariant only as long as that way exists. The day
someone closes it, the test passes whether or not the invariant is present,
and it passes forever.

Three options were considered:

1. **Run RED against pre-MC-046 code** (order this story first). Rejected. It
   earns the red exactly once. Once MC-046 lands, the stdin fixture loses
   nothing, so the test is vacuous from then on. It also contradicts
   `depends_on: [MC-046]`, and it would change the controls MC-046 measured.
2. **A one-off mutation recorded in `## Regressions`** (break `gates.sh` so it
   loses a gate, watch the test go red, revert). Rejected as the *primary*
   mechanism. A test still needs some way to lose a gate on every run. Without
   one, it has nothing to be red against, and the mutation proves only that
   the test *was* able to fail once.
3. **A fault-injection seam in `gates.sh`: chosen.** An environment variable,
   `GATES_FAULT_LOSE`, names gate ids that the run loop must lose: treat their
   lines as though they had never been read. This gives a deterministic,
   permanent loss that does not depend on MC-046's implementation or on any
   future rewrite of the loop. A test that sets it is red whenever the
   invariant is missing or broken, on every run, forever.

Why the seam is safe to ship. Its only effect is to make a run **fail**, never
pass: that is AC-3, the invariant itself. It announces itself on every run
that uses it (AC-2). It reads nothing that CI sets. It is the smallest
production surface that makes the invariant testable, and one test demands it,
so it is production code with a failing test, as the law requires.

What the seam does *not* prove is that the invariant's "declared" side is
independent of the loop. An implementation that recomputed "declared" by
re-reading `project.conf` after the loop would pass every seam test and still
certify the in-place rewrite. AC-1 is the test that closes that gap, using a
real loss rather than a simulated one.

The RED failure of the seam-based tests is "the seam does not exist yet": the
env var is ignored, both gates run, and the run passes. That is the right
reason, but it is not the whole proof, because it is the analogue of a suite
failing at import. So each control's expected value goes in the handoff, and
after GREEN the orchestrator runs the mutations listed under each AC below
against the committed implementation. Those runs are recorded in `## Notes`
(see "Verification plan").

### Which required gate would fail if this broke

None in `project.conf`, as for MC-044 to MC-046. See "Gate decision" in
`## Notes`. The tests live in `.claude/tests/gates.test.sh`, which CI runs
through `bash scripts/selftest.sh` (`.github/workflows/gates.yml` line 37, a
blocking step). The invariant also runs on every CI job, because line 49 runs
`bash scripts/gates.sh` in full against the real manifest. A false refusal
there would block every PR, which is why AC-6 exists.

**Definitions used by every criterion.** These are the counting rules, and
each one is also listed for confirmation under "Open questions for the PO/user"
in `## Notes`.

- **Declared.** One entry per `gate` line in `project.conf`, counted per
  *line*, not per unique id. The list is read **before any gate command
  runs**. It applies only to runs that execute gates, not to `--list` or
  `--audit`.
- **Accounted for.** A declared entry is accounted for when the run loop
  reached its line and gave it exactly one of these dispositions:
  1. *ran*: reported `PASS`, `FAIL`, `WARN` or `KNOWN`;
  2. *unconfigured*: reported `UNCONFIGURED`, or `FAIL … (required gate has no
     command in project.conf)`;
  3. *refused before running*: one of the existing manifest-error `FAIL`s
     (`slow` or `no-count` with no reason, a broken `floor`, a broken
     `ci-factor`, a waiver on a required gate);
  4. *left out by `--fast`*: named in `--fast skipped:`;
  5. *not selected*: excluded by `--gate <id>` or `--required`. This is
     accounted for without being printed, but only if the loop actually
     reached the line and the filter excluded it.
- **Lost.** A declared entry that is not accounted for. A lost gate is lost
  whether it is required or optional, and whether or not a filter would have
  excluded it.
- **Refusal.** For each lost gate, in manifest order, the summary shows the
  line `FAIL         <id> (declared in project.conf but never accounted for)`,
  with the same 13-column prefix as every other summary line. It is followed
  by the line `<N> declared gate(s) never accounted for; this run certifies
  nothing.` The run exits **1** and does not print `All required gates
  passed`. `.claude/state/last-gate-run` records `RESULT=fail`. A full run
  records `result: fail (…)` in the story.
- **Unchanged on a healthy run.** When nothing is lost, every existing line is
  byte-for-byte what it is today. That includes
  `All required gates passed (<ran> ran, <u> unconfigured, <k> known).`, which
  MC-046's tests pin.

All fixtures come from `make_project_fixture` / `write_conf`. Every gate
command is a `printf` / `exit` one-liner.

- **AC-1** — *The reproduction: a gate that rewrites the manifest in place
  cannot make a later gate vanish from a certified run.* Given the manifest
  ```
  gate | first | required | . | printf 'BOOTSTRAPPED=yes\n' > .claude/harness/project.conf; printf 'Tests 1 passed\n'
  gate | later | required | . | printf 'Tests 2 passed\n'
  ```
  when a full run executes, then **either** `later` runs (its `=== gate: later`
  banner appears, `PASS         later` is in the summary, and the run reports
  `(2 ran, 0 unconfigured, 0 known)`), **or** the run refuses and names
  `later`. In no case does it print `All required gates passed` while
  `later` is absent from the output. A second case uses the same manifest
  with `later` changed to `exit 1`. That run exits 1, and its summary contains
  a `FAIL         later` line, either the gate's own failure or the refusal.
  *Control:* measured at PLANNED on HEAD 1fa9815, and again on the
  `</dev/null` MC-046 candidate: `All required gates passed (1 ran, 0
  unconfigured, 0 known).`, exit 0, `later` absent, in both cases. Red on
  arrival **if** MC-046's merged loop still streams the manifest. RED
  re-measures this on the post-MC-046 code *first*. If it is green on arrival,
  stop and report to the PO, per the escalation note in `## Notes`.
  *Why a disjunction:* snapshotting the manifest so that it cannot be lost is
  an acceptable fix as well as refusing. The product claim is "never a false
  certification", not a particular mechanism. (Open question 7.)
- **AC-2** — *The seam loses what it names, and says so.* Given a healthy
  three-gate manifest (`a`, `b` and `c`, all required, each printing
  `Tests 1 passed`), when a full run executes with
  `GATES_FAULT_LOSE='b'` in the environment, then no `=== gate: b` banner
  appears, the output contains a line beginning
  `note: GATES_FAULT_LOSE is set` that names `b`, and it is printed before the
  first `=== gate:` banner. `a` and `c` run. With `GATES_FAULT_LOSE='a c'`,
  neither `a` nor `c` has a banner, and `b` runs.
  *Control:* on today's code the variable is ignored and all three banners
  appear. That is red on arrival, for the right reason.
- **AC-3** — *The invariant: a lost gate refuses the run.* Given the AC-2
  manifest, when a full run executes:
  (a) with `GATES_FAULT_LOSE='b'`, the output contains `FAIL         b
  (declared in project.conf but never accounted for)` and `1 declared gate(s)
  never accounted for; this run certifies nothing.`, it does not contain
  `All required gates passed`, and it exits 1;
  (b) with `GATES_FAULT_LOSE='a c'`, both refusal lines appear, `a` before
  `c`, with `2 declared gate(s) never accounted for; …`, and it exits 1;
  (c) with `b` changed to `optional` and `GATES_FAULT_LOSE='b'`, the same
  refusal applies and it exits 1. A lost optional gate is not a WARN.
  *Control:* this must be earned twice. On today's code the seam is absent,
  so all three gates run, the run passes and it exits 0. That is red for the
  wrong half of the reason. After GREEN, the orchestrator mutates the
  committed `gates.sh` so the refusal never fires, keeping the seam. Every
  case (a) to (c) must go red, and a seam-only implementation must print
  `All required gates passed (2 ran, …)` / `(1 ran, …)`, exit 0.
- **AC-4** — *The refusal reaches the record.* Given the AC-2 manifest, a
  story file in the fixture, and `GATES_FAULT_LOSE='b'`, when
  `gates.sh --story <id>` runs in full, then the story's `## Gate results`
  block has `result: fail`, and its summary lines include the refusal line for
  `b`. `.claude/state/last-gate-run` contains `RESULT=fail`.
  *Control:* with the refusal mutated away (the AC-3 mutation), the record
  reads `result: pass (2 ran, 0 unconfigured, 0 known)` and the stamp reads
  `RESULT=pass`. On today's code it reads `result: pass (3 ran, …)`.
- **AC-5** — *The subsets refuse on a lost gate, and never blame one they
  excluded.* Given the AC-2 manifest plus a required gate `s`
  (`printf 'Tests 1 passed\n'`) with `slow | s | fixture: stands in for a
  release build`, and an optional gate `o` (`printf 'Tests 1 passed\n'`):
  (a) `--fast` with `GATES_FAULT_LOSE='b'`: `b` is refused, `--fast skipped:
  s` is printed, no refusal line names `s`, and it exits 1;
  (b) `--required` with `GATES_FAULT_LOSE='b'`: `b` is refused, no refusal
  line names `o`, and it exits 1;
  (c) `--gate b` with `GATES_FAULT_LOSE='b'`: `b` is refused, and it exits 1,
  not 2 (`b` is declared, so the "no gate named" error must not fire);
  (d) `--gate a` with `GATES_FAULT_LOSE='b'`: `b` is refused, and it exits 1,
  because a lost line was never reached to be excluded (open question 5).
  *Control:* on today's code all four exit 0 (the seam is absent). After
  GREEN, (a) to (d) go red under the AC-3 mutation, and the AC-6 subset cases
  go red under their own mutations.
- **AC-6** — *No false refusal: every disposition counts as accounted for.*
  These are the negative controls on the invariant itself. The invariant also
  runs on every CI job, so a false refusal blocks every PR. Two manifests,
  both **measured at PLANNED on HEAD 1fa9815**, with outputs that must stay
  exactly as they are, minus timings:
  - *Healthy*:
    ```
    gate     | a | required | . | printf 'Tests 3 passed\n'
    evidence | a | Tests [1-9]
    gate     | k | optional | . | exit 1
    waiver   | k | fixture: known red
    gate     | w | optional | . | exit 1
    gate     | u | optional | . |
    gate     | s | required | . | printf 'Tests 2 passed\n'
    evidence | s | Tests [1-9]
    slow     | s | fixture: stands in for a release build
    ```
    | Flags | Summary line | Exit |
    |---|---|---|
    | none | `All required gates passed (4 ran, 1 unconfigured, 1 known).` | 0 |
    | `--fast` | `(3 ran, 1 unconfigured, 1 known)`, plus `--fast skipped: s` | 0 |
    | `--required` | `(2 ran, 0 unconfigured, 0 known)` | 0 |
    | `--gate w` | `(1 ran, 0 unconfigured, 0 known)` | 0 |
    | `--gate u` | `(0 ran, 1 unconfigured, 0 known)` | 0 |
  - *Manifest errors*: one gate per pre-run refusal (`e_slow` with a
    reasonless `slow`, `e_nocnt` with a reasonless `no-count`, `e_floor` with
    `floor | e_floor | abc`, `e_cif` with a sourceless `ci-factor | e_cif |
    3.4`, `e_waive` required with a waiver, `e_nocmd` required with no
    command), plus `ok`. A full run shows exactly the six existing `FAIL` lines
    with their current reasons, `PASS ok`, `6 required gate(s) failed.`, and
    exit 1.
  In every one of these runs, `never accounted for` appears nowhere in the
  output.
  *Control:* these pass on arrival, because there is no invariant yet, and
  they earn their red after GREEN by mutation. The orchestrator makes the
  invariant forget one disposition at a time, restoring the file between
  runs:
  (m1) `--fast` skips are not counted, so the `--fast` row must refuse `s`;
  (m2) filtered gates are not counted, so the `--required` and `--gate` rows
  must refuse;
  (m3) pre-run manifest-error FAILs are not counted, so the error manifest must
  add refusals;
  (m4) `UNCONFIGURED` is not counted, so the full and `--gate u` rows must
  refuse.
  Each mutation must turn at least one AC-6 case red.
- **AC-7** — Given `bash scripts/selftest.sh`, when it runs in full after
  GREEN, then every suite passes, including MC-046's tests and the MC-045
  byte-identical and exec-count tests. The output tail is pasted into
  `## Notes`. *Control:* `selftest` is a CI step, not a `project.conf` gate,
  so this is the story's only in-story evidence that the rest of the harness
  still works.

**Oracle partition.**

- **Mechanical, pin exactly:** AC-2, AC-3, AC-4, AC-5. The refusal line, the
  count line, the `note:` prefix, the exit code and the record's `result:`
  field are quoted in the criteria. Do not loosen them to "contains FAIL" when
  the gate id is available. A refusal that names the wrong gate must not pass.
- **Settled, read the numbers out:** AC-1's control (`1 ran`, exit 0, `later`
  absent) and every AC-6 row, all measured at PLANNED on HEAD 1fa9815. Do not
  re-derive them. If a number differs on the post-MC-046 code, report it
  rather than adjusting the test. A difference in AC-6 means MC-046 changed a
  healthy summary, which is a finding in its own right.
- **Oracle-free:** none.

**The judgement call RED makes.** AC-1 is a disjunction. Its test must be red
on today's code, and it must accept both a refusal and a genuine run of
`later`. It must not accept "`later` absent and the run passed". Check the
test against all three outcomes; the first is measured, and the other two can
be produced by hand-editing the fixture's expected output in a scratch copy.

## Out of scope

<!-- Explicit non-goals. Prevents the Feature Developer from over-building. -->

- **Closing the in-place-rewrite path itself.** Snapshotting the manifest is
  *permitted* by AC-1, but not required. MC-046's Out of scope already says
  "a gate can still `rm` the manifest": `project.conf` is trusted input. This
  story makes such a loss *visible*. It does not have to make it impossible.
- **Surplus accounting.** A declared entry accounted for twice, or an
  accounted id that was never declared. No known path produces either, and the
  seam cannot simulate them, so any test would pass on arrival and earn
  nothing. An implementation that compares the two lists exactly will catch
  them anyway. That is allowed, but it is not claimed and not tested. (Open
  question 8.)
- **Duplicate gate ids in `project.conf`.** Accounting is per line (see
  Definitions), so two `gate | unit` lines are two entries. Whether `--audit`
  should reject duplicates is a separate story.
- **`--list` and `--audit`.** Neither runs a gate command, and neither applies
  the invariant or reads `GATES_FAULT_LOSE`. Their output must not change: the
  MC-045 byte-identical and exec-count tests pin it, and AC-7 runs them.
- **A new format for the pass line.** No `(N of M declared)` suffix, and no
  change to `All required gates passed (…)` on a healthy run. MC-046 pins that
  string. (Open question 6.)
- **A distinct exit code for a lost gate.** It exits 1, like a required
  failure. 2 is a usage error and 3 is "lock not obtained"; see open
  question 4.
- **A gate that kills `gates.sh` itself** (`kill $PPID`, an out-of-memory
  kill). No summary is printed and the exit is non-zero already. That is not a
  false certification.
- **`check-boundaries.sh`, `lib.sh`, `phase.sh`, `selftest.sh`,
  `project.conf`.** Only `scripts/gates.sh` changes on the source side, and
  only `.claude/tests/gates.test.sh` on the test side.
- **Any other change to how a gate runs**: cwd, `tee`, `PIPESTATUS`,
  evidence, floors, the lock, `record_in_story`, or what MC-046 changed about
  stdin and descriptors.
- **Using `GATES_FAULT_LOSE` for anything but tests.** Do not document it in
  `--help`, and do not add any other fault modes (duplicate, reorder, crash).

## Notes

### Open questions for the PO/user (answer before RED; the ACs use the recommended default)

Each item is a counting or reporting rule the criteria currently assume. If
you change one, the criteria are edited while the story is still PLANNED, so
no amendment is needed.

1. **What counts as declared.** *Recommended:* every `gate` line, counted per
   line, read before any gate command runs. The alternative is counting per
   unique id, which would hide a duplicated line.
2. **Manifest-error FAILs count as accounted for** (reasonless
   `slow`/`no-count`, a broken `floor`/`ci-factor`, a waiver on a required
   gate, a required gate with no command). *Recommended:* yes. They already
   fail the run with their own reason, and a second "never accounted for" line
   would be noise.
3. **`UNCONFIGURED` and `KNOWN` count as accounted for.** *Recommended:* yes.
   Both are reported outcomes.
4. **A lost gate exits 1**, the same as a required failure. *Recommended:* 1.
   Every caller (CI, `record_in_story`, the stamp) already treats 1 as "not a
   pass". A distinct code (such as 4) would say more, but every consumer would
   have to learn it.
5. **A lost gate is refused even when a filter would have excluded it**
   (`--gate a` losing `b`, `--required` losing an optional gate).
   *Recommended:* refuse. A lost line means the loop's integrity is broken,
   whatever was selected. The alternative is to apply the filter to the
   declared list, so a filtered run only checks what it selected. That is
   quieter, but it would hide a loss on exactly the runs RED and GREEN use
   most (`--fast`, `--gate unit`).
6. **The healthy pass line is unchanged** (no `N of M declared` suffix).
   *Recommended:* unchanged. MC-046's tests pin it, and a suffix is noise when
   the numbers always agree.
7. **AC-1 allows either fix** (refuse, or snapshot the manifest so that
