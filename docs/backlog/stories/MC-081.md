## Context

**The report (2026-10-04).** The user ran the app on their folder
`C:\Users\ryanc\OneDrive\Pictures\Screenshots 1\Eleceed` (2560x1440
screenshots; the app wrote its crops to the `cropped/` subfolder) and sent 11
of the app's crops. Many screenshots in that folder show **two browser
windows side by side**: the manhwa reader (`toongod`, Eleceed) on the left,
about columns 0..1820, and YouTube on the right. The orchestrator matched
each sent crop by sha256 to a file in `cropped/` and viewed the originals:

  instead of the manhwa page in the left window.

  frame.

## Acceptance criteria

"Both margins" means 0 (the default) and 3. Bounds are end-exclusive. "The
seven" are e01..e07 in `## Context`. The oracle is the user's adjusted marks,
frozen the day they are read back (`## Notes`); nothing here re-derives or
adjusts a mark.

- **AC-1** — *The files.* **Given** the seven, **when** they are copied into
  `fixtures/corpus/` under their own names, **then** each copy's SHA-256
  equals the one in `## Context` (checked with `sha256sum` at copy time) and
  each is 2560x1440 by header and exactly its byte count. No other file is
  added or removed: the corpus holds **130** image files and **130**
  manifest entries. A test pins all seven by name, as MC-069's
  `MC069_REPORTED` does, and was watched to fail before the files existed.
- **AC-2** — *The entries.* Each of the seven is **exactly one** manifest
  entry, `split: "tuning"`, `expect` the user's frozen box
  (`{ x, y, w, h }`), or `"flag"` where the user flagged it, and tags exactly
  its theme, `png`, `site:<site>` (expected `site:toongod`; the user's answer
  rules), and `white-gutter` or `black-gutter` per the user's gap answer, none
  for "can't tell". `READER_BY_FILE`, `READER_LABELS`, `MARKED_TUNING_RECTS`
  and the counts follow: **tuning 107 marked + 14 flag** if all seven are
  boxes (held-out unchanged, 9 marked + 0 flag across 4 readers).
  *Control:* the corpus without the seven fails this test. RED shows it.
- **AC-3** — *The ceiling.* `MAX_BYTES` is `160 * 1024 * 1024`, with a
  doc-comment paragraph naming this story and the user's ruling in their
  words (*"Raise cap to 160 MiB"*), and the before and after byte counts.
  *Control:* the size test is watched to fail at 140 MiB with the seven in
  place (about 141.6 MiB), on a scratch copy.
- **AC-4** — *Today's failures, named and exact in both directions.*
  - Each of the seven that fails a `tuning` test on `main` is named in that
    test's known-exception list (`KNOWN_CLIPS`, `KNOWN_MISSES`,
    `MC064_CROPS`, `KNOWN_BACKGROUND_SIDES`, `STAGE_DECLINED`, or any other
    RED finds), **pinned to its crop as measured in RED at both margins**.
  - A measured crop that does not match what the user saw (the right window
    for e01, e02, e04..e07; a full-height crop of the manhwa for e03) stops
    RED and is explained in `## Notes` before any pin is written. A file
    `main` already crops right enters with no exception, and `## Notes`
    names it.
  - Each list fails if any other entry fails its test, and fails if a
    listed entry's crop differs from its pin.
  - **Probe** (RED, recorded in `## Notes`): take each of the seven off each
    list it is on, in turn, watch that suite go red naming it, and restore.
  - **What no suite judges.** If e03's kept bookmarks bar and taskbar fail no
    `tuning` test (as MC-075 found for `n06`: a declined viewport stage
    leaves no rows to judge), RED says so in `## Notes`, by name. Adding the
    check is [MC-083](MC-083.md)'s, not this story's.
- **AC-5** — *Nothing else moves.* With the seven added, every other marked
  `tuning` crop is exactly what `main` produces at both margins
  (`corpus_tuning_crops_unmoved.rs`, the seven's rows added, measured, not
  chosen, and commented so), every other `STAGE_MEASURED` row is unchanged,
  and every flag entry stays flagged. The unit and integration commands with
  `--no-fail-fast` pass in full. No file under `crates/*/src/` changes.
- **AC-6** — *The record.* `docs/wiki/corpus.md` gains a dated section: the
  user's report, the seven and the four repeats left out, the ruling "Fix
  story + blind draw", the ceiling and the ruling "Raise cap to 160 MiB",
  the new counts, how the marks were made (pre-marked from the left window's
  pixels, adjusted and frozen by the user), and each exception list the seven
  are on until MC-082 and MC-083 land. "What the tests can and cannot say"
  says 160 MiB.

## Model guidance

Model: default. The Lead PO measures the pre-marks, orchestrates and drives
SCAFFOLD; the Test Developer writes RED, with MC-079's and MC-069's RED as the
template (same kinds of pins and lists).

**Oracle partition.**
- **Settled, read out:** the seven's names, bytes and hashes (`## Context`);
  the user's frozen marks and tags; the ceiling ruling.
- **Mechanical, pin exactly:** AC-1's files, AC-2's entries and counts, AC-3's
  constant, AC-4's lists and crop pins (measured in RED, not chosen), AC-5's
  unmoved crops.
- **Oracle-free:** none. Nothing is tuned, and the cause is not this story's.
- **A person's call:** the marks (Open question 1).

**Success condition, which can come out either way:** the seven are in as
`tuning` with the user's marks, the ceiling is 160 MiB, every failure of the
seven on `main` is named at its measured crop and the lists are exact in
both directions, and both test commands are green with nothing else moved.
It **fails** if a pre-mark enters the manifest without the user's
confirmation, if a mark is adjusted after it is frozen, if any of the four
repeats or any other file is added, if a pin is written for a crop that
differs from what the user saw without an explanation, or if any other crop,
stage row or list entry moves.
