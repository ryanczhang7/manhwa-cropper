## Context

`docs/wiki/audits/app-window-2026-09-13.md`, evidence **E-6**, found eleven
surviving mutants in `gui.rs`'s `text_width`, `truncate_left` and
`truncate_right` — including replacing each function's entire body with a
constant. `replace truncate_left -> String with "xyzzy".into()` leaves the
whole suite green.

The reason is worth stating plainly, because it is the clearest piece of test
theatre the audit found. `path_label` paints the truncated string and then
calls `response.widget_info(|| WidgetInfo::labeled(WidgetType::Label, .., full))`,
which overwrites the node's value with the **full** path. The only test near it,
`a_long_output_path_keeps_its_whole_path_as_the_accessible_name`
(`crates/app/tests/gui.rs:356`), asserts exactly one node is named with the full
path — which is true whatever `truncate_left` returned, including the empty
string. `flagged_row` does the same for rows, so `truncate_right` is in the
identical position.

That test is honest about what it says it checks: the accessible name is what a
screen reader reads, and `accessibility.md` requires it. **It must not be
weakened or deleted by this story.** The gap is that it is the *only* assertion
in the area, so the truncation itself is pinned by nothing.

**The audit's `## Decided` is settled.** **Its `## Evidence` is not, and this
story rests on one claim in E-6 that the audit explicitly flags as
undemonstrated:** that this cluster is killable *without* a renderer, because
the truncated value is a `String` a test could compare directly. No such test
was written. `truncate_left` and `truncate_right` currently take `&Ui` and are
private. **Establish in RED that an observable shape exists** — and if it does
not, or if making one distorts the module, say so and hand the cluster to
MC-021's snapshot surface instead of forcing it. That is a finding, not a
failure.

The required gate that would fail if this story's artifact broke is **`unit`**
(`cargo test --workspace`), which is required for the repo.

## Acceptance criteria

- **AC-1** — Given a path wider than the space available, when the folder row is
  painted, then the text actually shown begins with U+2026 and its rightmost
  characters are the innermost folder — i.e. the leaf survives and the head is
  what was dropped (`docs/wiki/design/layout.md`, "Output folder row").

- **AC-2** — Given a path that fits the space available, when the folder row is
  painted, then the text shown is the path unchanged, with no U+2026 anywhere.
  *Control for AC-1: a truncation that always fired would satisfy AC-1 and be
  wrong. This criterion is what makes AC-1 mean something.*

- **AC-3** — Given the same over-long path, when the folder row is painted, then
  the node's accessible name is still the whole untruncated path.
  *This is the behaviour the existing test already pins; it is restated so that
  a change made for AC-1 cannot quietly cost it.*

- **AC-4** — Given a flagged row whose file name is too long for the width, when
  the list is painted, then the shown text ends with the separator and the full
  reason word, and it is the **file name** that carries the U+2026
  (`docs/wiki/design/components.md`, the "overflow" row).

- **AC-5** — Given the shipped painter mutated so that `truncate_left` returns
  `"xyzzy".to_owned()` unconditionally (`gui.rs:602`), when the new tests run,
  then at least one fails. And given it mutated so that `truncate_left`'s first
  comparison is `>` instead of `<=` (`gui.rs:603`), when they run, then at least
  one fails. *Two named survivors from the audit's E-6, used as the negative
  controls for this story. Record both failures under `## Gate probes`: whole-body
  replacement and a flipped boundary fail for different reasons, and a test suite
  that catches only the first has pinned existence, not behaviour.*

## Model guidance

Oracle partition for RED:

| Criterion | Kind | Instruction |
|---|---|---|
| AC-1, AC-2, AC-4 | **Settled** | `layout.md` and `components.md` already decide which end gives way and what the mark is (U+2026, one character). Read them out. Do not re-derive a truncation policy. |
| AC-3 | **Mechanical** | An existing behaviour being held. Pin it exactly as `tests/gui.rs:356` already does. |
| AC-5 | **Mechanical** | Two named mutations at two named lines. Apply, watch red, revert, paste. |

The open question is **shape, not behaviour**: how a test gets to see the shown
text at all. Leave that to whoever writes RED — they will have the constraint in
front of them and this file will not. Say in the handoff which of the options
was taken and what it cost, so MC-021 knows whether this surface generalises.

Whatever shape is chosen, it may not make the *accessible name* stop being the
full path. That is a design decision in `accessibility.md`, and changing it
would need the product owner, not this story.

## Out of scope

- The look-only survivors — colour, fill, stroke, vertical offsets. MC-021.
- The progress bar fraction (MC-023) and `shell::count` (MC-024).
- Changing what the truncation does. The rule in `layout.md` stands; this story
  makes it observable, it does not revisit it.
- Rewriting `text_width` or optimising the character-by-character search. It is
  called once per frame on a path.
- Font-metric-dependent assertions that would break when a font package updates.
  Assert the *shape* of the result (leading U+2026, which end survives), not an
  exact character count at an exact width.
- Weakening, skipping or deleting
  `a_long_output_path_keeps_its_whole_path_as_the_accessible_name`. If it seems
  to be in the way, that is a signal to stop, not to edit it.
