## Context

The brief's feature 3: when no confident crop is found, say so rather than
guess. This story adds `decide(&Luma, &Tuning) -> CropDecision` on top of
`detect` (MC-006) with the discrete reasons from `architecture.md` (Data
model, decision 3): `Uniform`, `NoBorderFound`, `LowContent`, `Ambiguous`.
The engine will copy a flagged file unchanged; the core only decides.

Gate that fails if this breaks: `unit`.

## Acceptance criteria

- **AC-1** - Given a uniform image, when `decide` runs, then it returns `Flag(Uniform)`.
- **AC-2** - Given an image where the trim removed nothing and no strip was peeled (the whole screenshot is art), when `decide` runs, then it returns `Flag(NoBorderFound)` even though `detect` returned a rect equal to the full image.
- **AC-3** - Given the detected rect's area is below `min_content_fraction` (0.20) of the image area, or either side is below `min_content_side` (64 px), when `decide` runs, then it returns `Flag(LowContent)`. *Controls on the numbers:* a rect at 19% of the area is flagged and at 21% is cropped; a 63 px side is flagged and a 64 px side is cropped, each with the other dimension well inside the limits.
- **AC-4** - Given `detect` reports `ambiguous == true`, when `decide` runs, then it returns `Flag(Ambiguous)` regardless of the rect.
- **AC-5** - Given none of the above, when `decide` runs, then it returns `Crop(rect)` with the rect `detect` produced.
- **AC-6** - Given the reasons are checked in the order AC-1, AC-2, AC-4, AC-3, when an image is both ambiguous and low-content, then `Ambiguous` wins (the order is the contract; pin it).

## Model guidance

Model: default. Oracle partition:

- **Settled**: `min_content_fraction = 0.20`, `min_content_side = 64`.
- **Mechanical**: `CropDecision { Crop(Rect), Flag(FlagReason) }`, `FlagReason { Uniform, NoBorderFound, LowContent, Ambiguous }`, both deriving `Debug, Clone, PartialEq, Eq` and `serde::Serialize` (the summary will serialise them). Pin, including the precedence in AC-6.
- **Oracle-free**: none.

## Out of scope

Copying the file (engine, MC-009/MC-011), the words shown to the user for each
reason (`docs/wiki/design/voice.md`, MC-015), a numeric confidence score
(decision 3), any new detection heuristic.

## Test plan

One new test target, `crates/core/tests/decide.rs`: 27 unit tests over a pure
function. Unit is the right level and the only one that can falsify anything
here - `decide` has no I/O, no UI and one dependency (`detect`), and the
fixture generator in `tests/common/mod.rs` knows the true art rect, so every
expectation is exact rather than approximate. No new proptest: MC-006 already
carries the expensive generated suite (`any_chrome_recipe`, 256 cases up to
3184x3184), every criterion here is a discrete case, and a second generated
suite would double the `coverage` gate's cost for no new falsification.

### The oracle partition, honoured

* **Settled** - `min_content_fraction = 0.20` and `min_content_side = 64` are
  read out of the `Tuning` argument at every comparison site. Neither appears
  as a literal in an assertion *about behaviour*; each has one test that pins
  the default value itself, in the style of `the_default_margin_px_is_three`.
* **Mechanical** - the two enums, their payloads, their derives (including
  `serde::Serialize`) and the AC-6 order are pinned exactly.
* **Oracle-free** - none, as the story says. Nothing here invents a metric, so
  nothing here needed a threshold designed for it.

### What is deliberately not tested

* **Position 2 against position 3 of the order in the other direction**
  (`NoBorderFound` vs `LowContent`) is unconstructible: if nothing was trimmed
  and nothing was peeled then the rect is the whole image, so its area is 100%
  of the image's and no side is shorter than the image's own. Nothing in the
  file pretends to test it.
* **Position 1 against anything, as a competition**, likewise: `detect`
  returns `None`, so no later check has a rect to look at. What *is* tested is
  the nearest reachable thing - that a uniform image below `min_content_side`
  still comes back `Uniform`.
* The words shown to the user for each reason (MC-015), the copy of the file
  (MC-009/MC-011) and a numeric confidence score (decision 3). The first of
  these is pinned negatively and for free: the serde test fixes each reason as
  a bare variant name with no payload, so no user-facing string can be
  smuggled into `FlagReason` here.

### The export shape the tests already pin

Nothing below is a suggestion. Each name is already imported by a test, so
getting it wrong is a compile error rather than a debate.

```
crates/core/src/lib.rs

      // which is also how architecture.md's "Data model (outline)" lists them.
      // `pub mod decide;` and `pub use decide::decide;` coexist: a module lives

      // not E0255. Verified on a scratch crate at edition 2024 before this file
      // was written - do not rename the function to avoid a clash that does not
      // exist.

  #[derive(Debug, Clone, PartialEq, Eq, serde::Serialize)]
  pub enum CropDecision {
      Crop(Rect),
      Flag(FlagReason),

  pub enum FlagReason {

      LowContent,
      Ambiguous,

```

**No `#[serde(...)]` attribute on any of the three types.** The plain derive is
what the story asks for and the plain derive is what is pinned, byte for byte:
`"Uniform"`, `{"Flag":"LowContent"}`, `{"Crop":{"x":17,"y":37,"w":206,"h":156}}`.

**What is `Copy`.** `Rect` already is. `CropDecision` and `FlagReason` are *not*
required to be, and the tests are written so that they need not be - no
assertion uses a moved value, and the one `.clone()` carries
`#[allow(clippy::clone_on_copy)]` so adding `Copy` later would not break the
file either. Your choice.

**What is not constrained, and is yours:** the internal shape of `decide` -
whether the checks are an `if` chain, a `match`, or a table; whether the two
enums live in `decide.rs` or a new module re-exported from it (the tests only
import from the root); the order of the variants in the source, except that the
*checking* order is AC-6's and is pinned; and whether `decide` is `#[must_use]`.

### The serde finding

**`serde` is not currently a dependency of `cropper-core`.** Checked:
`crates/core/Cargo.toml` has an empty `[dependencies]` and one dev-dependency
(`proptest`). `serde` and `serde_json` *are* declared in the workspace table in
the root `Cargo.toml` (`serde = { version = "1", features = ["derive"] }`,
`serde_json = "1"`), so both are pinned already and neither is a new decision;
`serde 1.0.229` is in `Cargo.lock` (pulled in by another crate's tree) and
`serde_json` is not yet, but `serde_json-1.0.151` is in the local registry
cache, so `--offline` resolution will work.

Adding them is a **`Cargo.toml` change, which is config and frozen in RED**, so
it was not made. GREEN must make it:

```toml
# crates/core/Cargo.toml
[dependencies]
serde = { workspace = true }

[dev-dependencies]
proptest = { workspace = true }
serde_json = { workspace = true }
```

`serde` goes in `[dependencies]` because the derive is on a production type.
It does **not** also need to be a dev-dependency: integration test targets see
a crate's regular dependencies as well as its dev-dependencies (verified on a
scratch crate rather than recalled). `serde_json` is only used by the test, so
it belongs in `[dev-dependencies]`.

### Notes for the implementer

1. **Do the area arithmetic in `f32`.** `min_content_fraction` is an `f32`
   field and one test sits exactly on it: 32,000 px of 160,000.
   `32000f32 / 160000f32` is bit for bit `0.20f32`, so `<` is false and the
   rect is cropped - which is what AC-3's word "below" requires.
   `f64::from(area) / f64::from(total)` is 0.2000000000000000111 against a
   constant of 0.2000000029802322388 and reports the rect as *below* the
   limit; so does `f64::from(t.min_content_fraction) * total as f64`. Both
   fail that one test and nothing else. This is the same trap and the same
   resolution `tests/content.rs` already records for `chrome_flat_fraction`.
2. **The order is a chain of early returns over one `Detection`.** Nothing in
   `decide` needs to look at a pixel: `detect` returning `None` is `Uniform`,
   `!trimmed && removed.is_empty()` is `NoBorderFound`, `ambiguous` is
   `Ambiguous`, the two size tests are `LowContent`, and what is left is
   `Crop(found.rect)`. The reference composition that all 26 tests were run
   against is exactly that, so a straight translation will pass.
3. **`Rect` must derive `Serialize`.** `CropDecision::Crop(Rect)` cannot derive
   it otherwise. That is an edit to `crates/core/src/lib.rs`, and it is the one
   place this story reaches outside `decide.rs`.
4. **A semantic consequence of AC-6 worth knowing about, which is *not* an
   amendment.** On a screenshot with no border, nothing peeled, and a top strip
   that is nearly chrome, both AC-2's predicate and AC-4's hold. AC-4's wording
   is unconditional ("regardless of the rect"), but AC-6 explicitly puts AC-2
   ahead of AC-4, so the answer is `NoBorderFound` and the near-miss on the
   strip is not reported. AC-6 is the tie-breaker by construction and AC-4's
   "regardless" is about the *rect*, so the criteria are consistent as written
   and nothing was reinterpreted. It is recorded here because someone reading
   `decide.rs` later will ask, and because if the product owner ever decides
   `Ambiguous` should win there it is a one-line change guarded by exactly one
   test.
5. **`detect`'s margin is why AC-3's fixtures look arbitrary.** Every rect
   `decide` judges is the art grown by `margin_px` (3) on each side and
   clamped, so the fixtures are sized `art + 6` to land on whole percentages.
   Do not "simplify" them.

### Two escalations, and what I decided

**1. The exactly-20% boundary test, which dictates `f32` arithmetic. Kept.**

The test developer offered to cut
`a_rect_at_exactly_min_content_fraction_is_not_below_it_and_is_cropped`
because it is the only thing in the file constraining how the area fraction is
computed, and it is beyond the four controls AC-3 names. I reproduced the
arithmetic independently before deciding - a standalone `rustc` program, on
three exactly-20% pairs the test developer never used, none of them its
32000/160000:

```
25000/125000: f32 below=false | f64 quotient below=true  | f64 product a<f*n = true
12800/64000:  f32 below=false | f64 quotient below=true  | f64 product a<f*n = true
9000/45000:   f32 below=false | f64 quotient below=true  | f64 product a<f*n = true
32000/160000: f32 below=false | f64 quotient below=true  | f64 product a<f*n = true
0.20f32 as f64 = 0.200000002980232238769531
0.2f64         = 0.200000000000000011102230
```

So the effect is general, not an artefact of one fixture: at *exactly* the
fraction, `f32` says "not below" and every `f64` widening says "below".

Kept, because the test is not extra scope - it is AC-3's own word. AC-3 flags a
rect whose area is **below** the fraction, and the story already pins that
reading exactly on the other dimension: "a 63 px side is flagged and a 64 px
side is cropped", where 64 *is* `min_content_side`. The area boundary is the
same criterion in the other axis, and an implementation that widens to `f64`
flags a rect sitting exactly on the limit, which contradicts the criterion. The
house precedent is already in `tests/content.rs` for `chrome_flat_fraction`.
GREEN has a documented path and one named test if it gets it wrong.

**2. `NoBorderFound` beating `Ambiguous`. No amendment; product note filed.**

The test developer found that an image with no border, nothing peeled and a
nearly-chrome top strip satisfies AC-2's predicate and AC-4's at once, and
pinned AC-6's order as written, so the answer is `NoBorderFound` and the near
miss is not reported. That is correct handling: AC-6 is an explicit tie-breaker
and AC-4's "regardless" is about the *rect*, so the criteria are consistent and
nothing was reinterpreted. **This is not an ambiguity that leads to different
code** - the order is stated - so it is not a question to put to the user
mid-cycle, and there is no `## Amendments` entry.

It is worth someone's attention later, though: a screenshot whose only
interesting feature is a nearly-chrome toolbar gets told "no border found"
rather than "this one is a close call". If the product owner wants `Ambiguous`
to win there, it is one line in `decide` and one test
