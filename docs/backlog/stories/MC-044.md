## Context

Found while driving [MC-040](MC-040.md) on 2026-09-22. The `one run at a time`
block of `.claude/tests/gates.test.sh` (~line 344 onwards) takes the gate-run
lock with a **live background process**:

```bash
sleep 30 & LIVE=$!
fake_lock "$LIVE" "$(hostname 2>/dev/null || printf '%s' "${HOSTNAME:-unknown}")"
```

and then makes **seven** `gates.sh` invocations — `--no-wait`, `--gate`,
`--fast`, `--required`, `--audit`, `--list`, and finally the waiting run —
before the last four assertions fire. Under enough concurrent load those seven
invocations take longer than 30 seconds, the fixture owner dies during setup,
and `gates.sh`
**correctly** reports taking over a stale lock instead of waiting. The suite then
fails, having observed the behaviour a *different* assertion in the same file
exists to pin.

Observed during MC-040's GREEN, while several minutes-long release rebuilds were
running concurrently — `gates: 78 passed, 4 failed`:

```
    FAIL waiting is the default
         expected to contain: Waiting for it to finish
         actual:               note: the gate run lock was left behind by pid 3652562, which is gone. Taking it over.
    FAIL and it gives up out loud
         expected to contain: gave up waiting for the gate run lock
    FAIL saying nothing ran
         expected to contain: neither a pass nor a failure
    FAIL and exits 3
         expected: 3
         actual:   0
```

On an idle machine it passes: `bash scripts/selftest.sh gates` →
`82 passed, 0 failed`, `real 3m18.001s`. **So this is a flake, not a standing
red, and the suite is green today.** That is exactly what makes it worth a
story: a self-test that fails intermittently teaches everyone to re-run it, and
CI runners are loaded and slow, so this can fail on CI against a green tree.

### The obvious diagnosis is wrong, and was already made once

MC-040's GREEN concluded the machine had become ~25x slower, from timing
`bash scripts/gates.sh --list` at 73–154 s per invocation. **That timing is real
and reproduces** — re-measured at 103, 72, 96, 91, 142 s. It still cannot be the
explanation: the `gates` suite makes far more than eight such invocations and
completes in 198 s. The per-invocation cost belongs to the **outer shell path**
— a fresh top-level `bash` under this environment's command layer — and
invocations made as children of an already-running script do not pay it.

This is the same shape as the trap `project.conf` documents under `ci-factor`,
where a coverage gate's wall time was extrapolated to per-test time and read 14x
against a real 3.4x: *"Someone acting on the 14x would have spent a day making a
test faster that was already fine."* **Do not repeat the wrong diagnosis.** The
defect is not machine speed. The defect is that a test pins behaviour against a
wall clock.

### What the block is actually claiming, and which claim races

Read at PLANNED against `acquire_lock()` in `scripts/gates.sh` (~129–205). Five
distinct claims live in that block, and only one of them needs a live process:

| Claim | Needs a live owner? |
|---|---|
| A held lock blocks `--no-wait`, `--gate`, `--fast`, `--required` (exit 3, nothing runs) | No — it needs a lock that is *not taken over* |
| `--audit` and `--list` take no lock | No |
| Waiting is the default, gives up out loud, says nothing ran, exits 3 | No |
| A lock whose same-host owner is **gone** is taken over | No — it needs a *dead* pid, which is already deterministic |
| A lock whose same-host owner is **alive** is waited for, never taken over | **Yes** — this is the only one |

The first three are today driven by the `sleep 30` fixture and do not need it.
The fifth is the one real requirement, and the current fixture satisfies it only
for as long as the timer happens to outlast the setup.

### Two candidate mechanisms, named and not mandated

Both were read off `acquire_lock()` at PLANNED. **Neither is prescribed** —
confirm against `scripts/gates.sh` and `.claude/tests/gates.test.sh` rather than
taking this story's word, and if a third is better, take it and say why.

1. **Own the lock with a process that cannot die during the block.** The
   take-over branch requires `host = $LOCK_HOST` **and** `! kill -0 "$pid"`. A
   pid that is alive for the whole block by construction — the test runner's own
   — makes the live-owner case deterministic with **no production change at
   all**. This is the preferred direction precisely because it costs `gates.sh`
   nothing.
2. **An injected staleness signal** in `acquire_lock()`, so a lock can be made to
   look stale (or live) on demand. This was the direction raised when the flake
   was reported. It works, but it adds an input to the lock's take-over decision
   that exists only for tests, and AC-3 is where that has to be paid for.

The claims that need no live owner have a third option already proven in the
same file: `fake_lock 999991 some-other-host` is waited for and never broken,
because this host cannot see that process table. That is deterministic today.
**But note the trap** — converting *every* fixture to a foreign host would make
AC-1 pass and silently delete the fifth claim above. AC-2 exists to stop it.

### The gate question

`required_gates: []`, on [MC-039](MC-039.md)'s reasoning, re-checked here. No
`gate` line in `project.conf` runs the harness suite; they all run `cargo`, and
this story's artifact is `.claude/tests/gates.test.sh`. **CI covers it anyway**:
`.github/workflows/gates.yml` line 37 runs `bash scripts/selftest.sh` as a
blocking step with no `continue-on-error`, before `gates.sh --list`,
`gates.sh --audit` and `gates.sh` — and that ordering is why `selftest` is not
itself a gate: it guards the machinery `gates.sh` runs on, and a gate inside
`gates.sh` checking whether `gates.sh` works is circular.

There is one wrinkle MC-039 did not have: if the fix touches `acquire_lock()` in
`scripts/gates.sh`, then **every** gate run exercises the changed path, and the
full `bash scripts/gates.sh` run this story records in `## Gate results` is real
evidence for it. AC-3 turns that into a condition rather than a hope.

What the story still owes regardless: `bash scripts/selftest.sh` run locally and
its output pasted (AC-4).

## Acceptance criteria

- **AC-1** — *No assertion in the block depends on a timer.* Given `.claude/tests/gates.test.sh`, when the `one run at a time` block runs with **every background process the block starts killed immediately after it is started** — the condition load produces, induced deterministically — then `bash scripts/selftest.sh gates` reports `0 failed`. *Control:* applying that same forced kill to the suite **as it stands today** reproduces exactly the four failures quoted in `## Context` (`waiting is the default`, `and it gives up out loud`, `saying nothing ran`, `and exits 3`). That reproduction is this story's RED and must be shown red before the change and green after; a probe that produces some other set of failures is measuring something else and the story stops.
- **AC-2** — *Every claim the block draws is still drawn.* Given the changed block, then all five claims in `## Context`'s table are still carried by at least one assertion each, and the story names which assertion carries the fifth — *a lock whose same-host owner is alive is waited for and never taken over*. *Control:* the cheap fixes both satisfy AC-1 and destroy this one — deleting the live-owner case, or making every fixture a foreign-host lock, which is waited for because the host is unreadable rather than because the owner is alive. Neither is acceptable. No assertion is weakened, skipped, widened or deleted to reach green; if one cannot be made deterministic, that is a return to PLANNED, not a deletion.
- **AC-3** — *The production lock is unchanged, or the change is justified and exercised.* Given the story's diff, then **either** `scripts/gates.sh` is untouched, **or** every change to it is named in `## Notes` with the reason a test-side fix was insufficient, states what stops the new input being set in a real run, and is covered by the full `bash scripts/gates.sh` run recorded in `## Gate results`. *Control:* the default expectation is untouched — candidate 1 in `## Context` achieves AC-1 and AC-2 with no production change, and is to be tried first. A fix that adds a force-stale environment variable and nothing else would pass AC-1 and AC-2 while making the lock weaker in production than it is today; AC-3 is what makes that visible rather than invisible.
- **AC-4** — Given `bash scripts/selftest.sh`, when it runs in full, then every suite passes and the output is pasted in `## Notes`, together with the `gates` suite's wall time. No suite other than `gates.test.sh` is edited. *Control:* `selftest` is a CI step rather than a `gates.sh` gate and never appears in `## Gate results`, so this is the story's only in-story evidence that its artifact was verified. The wall time is recorded for the next person, **not** as a threshold — this machine's outer-shell timings are documented above as unreliable, and no criterion here is allowed to depend on one.

## Out of scope

- **Re-diagnosing the machine's speed.** The ~100 s per top-level
  `bash scripts/gates.sh --list` is real, belongs to the outer shell path, and is
  not this story's problem. It is recorded in `## Context` so the next person
  does not spend the day the `ci-factor` note warns about. Do not chase it, do
  not "optimise" `gates.sh --list`, and do not file a performance story off it
  without a measurement that separates the outer shell from the script.
- **Changing the lock protocol's semantics.** What counts as stale, `LOCK_POLL`,
  the default `GATES_LOCK_WAIT` of 1800, the rename-before-remove take-over, the
  foreign-host rule — all correct and all out of scope. This story changes how
  the *tests* set the lock up, not what the lock does. The one permitted
  exception is a change made under AC-3, with its reason recorded.
- **Speeding up the `gates` suite.** A deterministic fixture will probably be
  faster than a 30 second sleep; that is a side effect, not a goal, and it may
  not be bought by dropping a case. AC-2.
- **Any other suite under `.claude/tests/`.** If another one races a clock, write
  it in `## Notes` and file a story; do not widen this one. The `two real runs,
  racing` block further down the same file starts real `gates.sh` processes on
  purpose — that is a different fixture with a different justification and it is
  not in scope unless it is *also* shown to flake, which it has not been.
- **The `work_count` documentation defect.** Same file, unrelated, and it is
  [MC-043](MC-043.md). That story adds assertions elsewhere in
  `gates.test.sh`; this one changes the `one run at a time` block. They do not
  depend on each other and can be done in either order.
- **`scripts/selftest.sh` itself**, and how it reports or retries. Making a flaky
  test deterministic is the fix; adding a retry to hide it is the thing the
  harness exists to prevent.
