## Context

The primitive behind the brief's second mechanism, "detect the art's edges so
that non-uniform regions outside the panel are also removed". This story
computes the profiles and finds strong lines; MC-005 uses them. From
`architecture.md` (`edges`): the row profile has one value per adjacent row
pair - the mean absolute luma difference between row `i` and row `i+1` over
the columns of a rect - and the column profile likewise. A strong line is a
run of consecutive indices at or above `edge_threshold`, merged into one
`Line { start, end }` (inclusive indices into the profile).

Gate that fails if this breaks: `unit` — `gate | unit | required` in
`.claude/harness/project.conf`, so it is already binding repo-wide, and
`coverage` (also required) judges the new module too. Nothing here needs an
optional gate escalating to required, so `required_gates` stays empty. Checked
against `project.conf` in PLANNED, before the phase moved.

## Acceptance criteria

- **AC-1** - Given a `Luma` of height `H` whose rows `0..k` are constant luma `a` and rows `k..H` constant luma `b`, when `row_profile(&luma, full_rect)` runs, then it has length `H - 1`, value `|a - b|` at index `k - 1` and `0` everywhere else; and `col_profile` has length `W - 1` and is all `0`.
- **AC-2** - Given `row_profile` and `col_profile` are asked for a sub-rect, when computed, then only pixels inside the rect contribute (a bright band outside the rect changes nothing) and the lengths are `rect.h - 1` and `rect.w - 1`.
- **AC-3** - Given a profile with values `>= edge_threshold` at indices 10, 11, 12 and 40 only, when `strong_lines(&profile, &Tuning::default())` runs, then it returns `[Line { start: 10, end: 12 }, Line { start: 40, end: 40 }]`.
- **AC-4** - Given the two-band image from AC-1 with `|a - b| = edge_threshold` (24), when strong lines are computed, then exactly one line is found at `k - 1`; given `|a - b| = 23`, then none. *Control on the number:* 23 must produce no line.
- **AC-5** - Given a `Luma` of textured noise whose adjacent-row mean absolute difference is below `edge_threshold` everywhere (the generator's art texture; measured value recorded in the handoff), when strong lines are computed, then none are found - the art's own texture is not an edge.
- **AC-6** - Given a `Luma` with `H <= 1` (or a rect with `h <= 1`), when profiled, then the row profile is empty and `strong_lines` of an empty profile is empty.

## Model guidance

Model: default. Oracle partition:

- **Settled**: `edge_threshold = 24`. Read it out.
- **Mechanical**: `row_profile(&Luma, Rect) -> Vec<f32>`, `col_profile`, `strong_lines(&[f32], &Tuning) -> Vec<Line>`, `Line { start: usize, end: usize }`. Pin exactly.
- **Oracle-free**: AC-5's texture. The generator's texture must be measured, not assumed, and the handoff records the measured maximum adjacent-row difference so GREEN can confirm it is below 24 with room (target: below 16).

## Out of scope

Deciding which side of a strong line is chrome (MC-005), diagonal or curved
edges, sub-pixel positions, gradient operators beyond the adjacent difference
(no Sobel, no blur), colour edges (luma only).

### Comparing `f32`

Two disciplines, chosen per assertion, both stated in the test file's module
header so nobody has to infer them:

* **Exact equality** wherever the true mean is an integer. Every such fixture
  is built so the sum of the integer differences along a line is an exact
  multiple of that line's length, and every sum is far below `2^24`, so the
  sum is exact in `f32` under any summation order and the quotient is the
  exactly representable integer it should be. The plausible wrong answers -
  a sum instead of a mean, an integer truncation, a dropped term - differ by
  at least 1.0, so exactness costs nothing and rejects a class of near misses
  that a tolerance would wave through.
* **An explicit `EPS = 1e-5`**, used in exactly one test, whose true mean
  (`31/3`) is not representable at all. The wrong answers there are `10.0`
  (truncation) and `31.0` (a sum), 0.33 and 20.67 away - four to six orders of
  magnitude outside the tolerance. `EPS` is about 30 ulps at that magnitude,
  which absorbs an implementation that accumulates in `f64` and casts, and
  absorbs nothing else.

No tolerance anywhere is wide enough to also accept a wrong answer, which is
the property that matters.

### The generator gained a second art texture, and it had to

AC-5 says "the generator's art texture" and the Model guidance says to measure
it rather than assume it. Measured, over 200 seeds at 24x18, MC-003's
`Recipe::paint_art` has a **maximum adjacent-row mean absolute difference of
165.708** and a maximum adjacent-column one of **167.778** (minimums 158.5 and
156.7 at a sample seed). That is not near 24, it is seven times 24 - and by
construction, because MC-003 made the art a checkerboard of `40..=60` against
`200..=220` precisely so that no art row could ever be judged uniform.
Adjacent rows are opposite phases of that board, so MC-003's art is a strong
line at every single row and column. It is the exact opposite of the fixture
AC-5 needs.

So the generator was extended, additively, with a second texture:
`common::soft_art(width, height, seed)` - a triangular ramp in both axes
(period 8 / step 6 across, period 6 / step 6 down) over a base of 48, plus
seeded jitter of `0..=12`. The triangle is the point: a wrapping sawtooth
would put a strong line at every wrap, and a triangle's consecutive values
differ by exactly 1, so the field has no discontinuity at any size.

Measured on the shipped helper:

| Texture | max adjacent-ROW mean abs diff | max adjacent-COLUMN | whole-field spread |
|---|---|---|---|
| `Recipe::paint_art` (MC-003, 200 seeds, 24x18) | **165.708** | **167.778** | 180 |
| `soft_art(48, 36, seed)`, seeds 1..=8 - **the AC-5 fixture** | **8.750** | **9.361** | 93..96 |
| `soft_art`, 200 seeds x five sizes (7x5, 24x18, 40x30, 48x36, 64x48) | **13.143** | **13.200** | 49..96 |

9.361 against a threshold of 24, and below the story's stated 16 target with
room. Nothing existing in `common/mod.rs` changed behaviour: `paint_art`,
`Recipe`, `Border`, `Layout`, `flat_band`, `any_recipe` and `Rng` are
byte-for-byte what MC-003 shipped, and `cargo test -p cropper-core --test
trim` still reports **19 passed, 0 failed**.

**One non-additive edit, and it needs to be seen.** `tests/common/mod.rs`
gained a module-level `#![allow(dead_code)]`. MC-003's module note claimed the
`-D warnings` lint gate mechanically forbids an unused helper; that was true
while `trim.rs` was the only test target, and it stops being true the moment
there are two, because Cargo compiles `common/mod.rs` *separately into each
test binary*. Observed, against a shape-matching reference: `Layout::Gutters`,
`Recipe::art_rect`, `flat_band` and `any_recipe` are all dead code in the
`edges` target, and `soft_art` is dead code in the `trim` target - four
`-D warnings` errors that have nothing to do with anything being unused. A
per-item `allow` on `soft_art` alone does not fix it, and `#[expect]` is
actively wrong here: it fires `unfulfilled_lint_expectation` in whichever
target *does* use the item. The module note was rewritten to say the rule is
now enforced by review rather than by the compiler. This loses a real (if
narrow) guard, and it is recorded here rather than buried in a comment.

- **`architecture.md`'s step 2 has a clause this story does not use.** It says
  strong lines are found "after merging runs of adjacent strong lines into one

  parenthesis describes *which end MC-005 will read*, not a different merge:
  MC-004's AC-3 fixes the answer as `Line { start, end }` covering the whole
