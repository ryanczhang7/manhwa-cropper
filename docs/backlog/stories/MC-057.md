## Context

Found while planning [MC-056](MC-056.md) on 2026-09-29. A manifest change broke
14 integration tests across 6 suites, but the first `integration` run showed
only `corpus.rs`'s 2. The rest surfaced one binary per re-run.

The cause is cargo's default fail-fast: `cargo test` stops after the first
**test binary** that has a failing test and never runs the ones after it. The
gate commands in `.claude/harness/project.conf` were

    gate | unit        | required | . | cargo test --workspace
    gate | integration | optional | . | cargo test --workspace --release -- --ignored

so each gate reported one binary's failures and hid the rest. `integration`
costs minutes per run (a release rebuild plus the corpus), so every hidden
suite is another full round trip. `unit` has the same shape and gets the same
fix. `--no-fail-fast` makes cargo run every binary and still exit non-zero if
any failed, so `gates.sh`, which judges a gate by its exit status, grades it
exactly as before.

A harness chore with no production code. It changes two gate commands, so it
carries `## Gate probes` for both.

## Acceptance criteria

- **AC-1** — Given a change that breaks tests in two or more test binaries run
  by the `unit` gate, when `bash scripts/gates.sh --gate unit` runs, then the
  gate log contains the failures of every one of those binaries, not only the
  first one cargo ran.
- **AC-2** — Given the same kind of change for tests run by the `integration`
  gate, when `bash scripts/gates.sh --gate integration` runs, then the gate log
  contains the failures of every failing binary, not only the first.
- **AC-3** — Given such a change, when either gate runs, then cargo still exits
  non-zero and `gates.sh` still grades the gate as failed: FAIL with a non-zero
  exit for `unit`; for `integration`, WARN when it is optional and FAIL with a
  non-zero exit when a story's `required_gates` binds it, as this story's does.
  Negative control: before this story, the same change produced a log with
  exactly ONE `test result: FAILED` line per gate.
- **AC-4** — Given a clean tree, when the full `bash scripts/gates.sh` runs,
  then `unit` and `integration` PASS with their `evidence` lines matching and
  their floors (47 and 9) still met, and `gates.sh --list` shows both gates'
  evidence and floor lines unchanged.

## Out of scope

- The `coverage` gate (`cargo llvm-cov`). It fails fast the same way, but it
  runs the same tests as `unit`, which now reports all of them; a failure there
  that `unit` does not show is a timing or instrumentation problem, not a
  missing binary. A follow-up if it ever bites.
- `task | test`, which is a convenience for humans, not a gate.
- Any change to the evidence regexes or floors. On a passing run
  `--no-fail-fast` changes nothing in cargo's output, so the numbers they read
  do not move.

## Gate probes

Each probe is one production mutation, run through `bash scripts/gates.sh
--gate <id>` under the OLD command and then the NEW one, then reverted. The
old-command runs of `unit` and the first `integration` run happened with no
story active; the second `integration` pair ran with MC-057 in SCAFFOLD, whose
`required_gates` binds `integration`, which is why its before-run grades FAIL
rather than the WARN an optional gate gets.
