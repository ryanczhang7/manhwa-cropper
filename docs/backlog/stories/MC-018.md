## Context

The brief's open question 1: the success criteria ("zero clipped panels",
"nine of ten need no fix") can only be measured on the user's own
screenshots with hand-marked expected rectangles. **No agent can complete
this story; the user supplies the files.** It is a `chore` under SCAFFOLD:
the user drops screenshots into `fixtures/corpus/` and fills in
`fixtures/corpus/manifest.json`; the Lead PO writes the manifest validator
test (a test file, under `crates/engine/tests/`) and a loader module under
`crates/engine/tests/common/` that MC-019 reuses. No production source is
written, so `## Scaffold inventory` lists none.

How the user marks an expected rectangle: open the screenshot in any editor
with a selection tool (Paint shows the selection's origin and size in the
status bar), select the tightest rectangle that contains all the artwork and
none of the chrome or gutter, and record `x, y, w, h` in pixels. For a
screenshot that should be left alone (all art, or mostly blank with no
confident panel), record `"expect": "flag"` instead of a rect.

Manifest shape (one entry per file):

    { "entries": [
      { "file": "chrome-dark-01.png", "expect": { "x": 412, "y": 131, "w": 1096, "h": 949 },
        "tags": ["dark-theme", "black-gutter", "png"] },
      { "file": "all-art-01.jpg", "expect": "flag", "tags": ["all-art", "jpeg"] }
    ] }

**Two refinements to the marking rule, from the user's first 28 entries
(2026-09-14).** Both came out of annotating real screenshots and neither is
an acceptance-criteria change - MC-018's criteria constrain the *shape* of a
manifest entry, not how the rectangle is chosen.

*Diagonal gutters.* Panel edges are often slanted, on the top and bottom and
sometimes the left and right. The expected rect is axis-aligned, so the box
is the tightest axis-aligned rectangle containing all the art, which
necessarily swallows the gutter triangles. That is correct and not a
compromise. The detector should degrade gracefully here rather than clip: it
peels full-width *strips* by flat fraction, and a boundary strip that is
part gutter and part art falls below `chrome_flat_fraction` (0.85) and is not
peeled, so the crop comes out loose. The brief sanctions exactly that
outcome - "leftover border is a minor miss; cut-into art is a failure". **A
prediction for MC-019 to test, not a settled fact**: if `diagonal-gutter`
entries turn out to cluster in AC-1 failures rather than AC-2 misses, this
reasoning is wrong and the finding belongs in MC-019's `## Notes`.

*Overhanging text.* Sound effects, titles and ability names frequently sit
outside the panel, in the gutter. The user's first instinct was to extend the
box for those but **not** for ordinary speech bubbles, separating them by
whether the text sits in a bubble, whether the bubble is white, and whether
it is oval or rectangular.

That distinction cannot be implemented. The detector measures flatness, edge
strength and standard deviation; it has no notion of a bubble, and a sound
effect and an overhanging speech bubble are the same thing to it - non-flat
pixels in a gutter. No value of `chrome_flat_fraction` makes a flatness test
into a semantic classifier, so a corpus marked that way would have set MC-019
an unreachable bar and the failures would have read as tuning problems.

**Decided with the user on 2026-09-14: the rule is geometric, not semantic.**
Extend the expected rect to include *any* non-flat content overhanging into
the gutter - sound effects, titles, ability names **and speech bubbles
alike**. Only flat gutter and application chrome stay outside the box. This
is a rule the detector can satisfy, and it is the one the corpus is marked
to.

Entries exhibiting either case carry an extra tag, `diagonal-gutter` or
`overhang-text`. AC-3 requires the nine listed tags to be *covered*, not to
be exclusive, so extra tags are valid manifest content. They exist so that
MC-019's per-file table shows whether failures cluster on them - which is the
difference between "the constants need tuning" and "the detector needs a
capability it does not have".

`fixtures/**` classifies as `test` in `paths.conf`, so the images may be
added during any phase that permits tests.

Gate that fails if this breaks: `unit` (the validator test is not ignored).

## Acceptance criteria

- **AC-1** - Given `fixtures/corpus/manifest.json`, when the validator test runs, then it parses, has at least 20 entries, every named file exists under `fixtures/corpus/`, and every file decodes with the `image` crate.
- **AC-2** - Given an entry with a rect, when validated, then `w >= 1`, `h >= 1`, and `x + w <= image width`, `y + h <= image height`.
- **AC-3** - Given all entries' tags, when validated, then the union covers every one of: `light-theme`, `dark-theme`, `white-gutter`, `black-gutter`, `all-art`, `mostly-white`, `png`, `jpeg`, `webp`; and every `all-art` and `mostly-white` entry has `"expect": "flag"`.
- **AC-4** - Given the corpus directory, when its total size is summed, then it is below 60 MB (so the repository stays clonable without LFS).
- **AC-5** - Given the loader in `crates/engine/tests/common/corpus.rs`, when `load()` runs, then it returns `Vec<CorpusEntry { path, expect: Expect::Rect(Rect) | Expect::Flag, tags }>` in manifest order.
- **AC-6** - Given the corpus, when validated, then at least one entry is a WebP whose RIFF payload chunk is `VP8 ` or `VP8X` wrapping a lossy payload (not `VP8L`), and when that file is run through `process_file`, then the output is a WebP whose pixels equal the *decoded* source pixels inside the rect. **Inherited from MC-009 AC-3** by the amendment recorded in `docs/backlog/stories/MC-009.md`; it is here because nothing in this workspace can *write* a lossy WebP and this is the story where a real one arrives.

## Model guidance

Model: default. All criteria are **mechanical** checks on files the user
provides. The only judgement - is the hand-marked rect right - belongs to
the user, and the validator cannot check it; MC-019's zero-clip result on a
wrongly marked rect will show up as a "clip" that the user must re-examine.

## Out of scope

Tuning any constant (MC-019), generating screenshots artificially (the
whole point is that they are real), a marking tool, more than the minimum
coverage the tags require.

## Test plan

Two files, ten tests, no production source.

- **`crates/engine/tests/common/corpus.rs`** - the loader (AC-5).
  `CorpusEntry { path, expect: Expect::Rect(Rect) | Expect::Flag, tags }`,
  `load()`, `dir()`, `MANIFEST_FILE`. Parses the manifest with `serde`'s
  untagged enum, because `"flag"`-or-`{x,y,w,h}` is the shape a person writes
  by hand and the shape the annotation tool emits.
- **`crates/engine/tests/corpus_manifest.rs`** - the validator (AC-1 to AC-4,
  AC-6), **not** `#[ignore]`d, so the `unit` gate runs it on every commit. A
  corpus that has quietly rotted - a file renamed, an image replaced at a
  different size - would otherwise turn MC-019 into a test that measures
  nothing.

**Why the loader is included with `#[path]` and not declared in
`common/mod.rs`.** The first attempt added `pub mod corpus;` there and broke
the build: `crates/app/tests/headless.rs` reaches that module with `#[path]`,
so the declaration compiled the loader - and its `serde` dependency - into the
app crate's test binaries, which carry no `serde`:

```
error[E0432]: unresolved import `serde`
  --> crates\app\tests\..\..\engine\tests\common\corpus.rs:32:5
error: could not compile `manhwa-cropper` (test "headless") due to 3 previous errors
```

Including it per-target keeps the dependency where it belongs. MC-019 does the
same one-line include.

**What these tests deliberately do not check.** Whether a rectangle is the
*right* rectangle. No code can, and MC-019's guidance says so: a reported clip
may be a mis-marked rect rather than a detector fault. The validator's job is
that every entry is well formed and inside its image.

**Vacuity guards.** Two assertions exist only to stop a test passing because
it measured nothing: AC-2 asserts `checked > 0` (an all-`"flag"` corpus would
otherwise satisfy the bounds check trivially), and AC-5 asserts the loader
produced at least one `Rect` and at least one `Flag`.

## Handoff: RED -> GREEN

Not a RED->GREEN story. MC-018 is a `chore` run under SCAFFOLD: the corpus,
the loader and the validator only mean anything together, and the user - who
is the only one who can supply the files - had already built the corpus before
any test existed. So every assertion here was written against data that
already satisfied it and passed on its first execution, which is exactly the
situation the non-negotiables call out: *a test that has never been observed
to fail is not a test.* Five probes in `## Gate probes` discharge that.

**What the next agent (MC-019) needs.**

- `#[path = "common/corpus.rs"] mod corpus;` - do not add it to
  `common/mod.rs`, for the reason in the test plan above.
- `corpus::load()` returns all 28 entries **in manifest order**. That is
  asserted, and MC-019's per-file table depends on it.
- The corpus as built: **28 entries, 21 with a rect and 7 `"flag"`**, 21.3 MB,
  18 PNG / 8 JPEG / 2 WebP, both WebPs genuinely lossy (`VP8 `).
- **A structural caveat worth knowing before reading MC-019's failures.** All
  7 `"flag"` entries are the non-2560x1440 images (553x856 up to 1416x4476 -
  already-cropped panel images), and all 21 rect entries are 2560x1440 desktop
  captures. The correlation is causal rather than accidental - a cropped panel
  image has no chrome to find - but it means the corpus contains **no
  full-screen capture that should be flagged, and no mobile-sized screenshot
  that should be cropped**. A detector that over-crops a full-screen all-art
  image would not be caught here. Record it if it matters; do not quietly
  treat corpus coverage as complete.
- The marking rule the rects were drawn to is the **geometric** one in
  `## Context` - any non-flat overhang included, speech bubbles and sound
  effects alike.
- The `diagonal-gutter` and `overhang-text` tags are **not yet applied**. The
  user deferred that pass deliberately (2026-09-14). If failures look
  unexplained, applying them is the next diagnostic step, not a rewrite.

### MC-009 AC-3 landed here (2026-09-11, approved by ryanczhang7)

AC-6 above is not new scope invented for this story. It is MC-009's AC-3,
deferred here because `image` 0.25.10 / `image-webp` 0.2.4 can only *write*
lossless WebP, so MC-009 could not author the fixture the criterion needed.
Reading lossy WebP works; the full evidence is in MC-009's `## Amendments`.

**The practical consequence for the user supplying the corpus.** AC-3's
`webp` tag is no longer satisfied by any WebP: at least one of them must be a
lossy one. In practice this costs nothing - WebP screenshots saved by browsers
and messaging apps are lossy by default, and a lossless WebP is the harder one
to come by - but it is now checked rather than assumed, which is the point.

MC-018 is still PLANNED, so adding a criterion here is not an amendment: the
freeze begins when a story leaves PLANNED.

Every assertion in `corpus_manifest.rs` was written against a corpus that
already satisfied it, so all ten passed on first execution and none had ever
been observed to fail. Five probes fix that: break what the assertion guards,
run only that test, restore, confirm the restore. One mutation, one run, one
revert each. The corpus files and the manifest were restored from copies taken
beforehand and verified byte-for-byte at the end.
