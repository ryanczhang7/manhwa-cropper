## Context

The user labelled all 28 `tuning` entries by reader on **2026-09-21**, using the
**Corpus Reader Labeller** Artifact (a throwaway tool outside the repository,
like the marking annotator MC-018 `## Out of scope` keeps out of `crates/`).
This story writes those labels into the corpus and corrects what they falsify.

Until now **0 of the 28 tuning entries carried a `site:` tag; all 31 site tags
were on held-out entries.** `docs/wiki/corpus.md` explains why — attributing a
screenshot captured a year earlier "is exactly the situation that manufactures
guesses", and a guessed tag is worse than an absent one. The user is the only
person who could supply them, and now has.

### What the labels falsify, which `corpus.md` asked for by name

`corpus.md`'s `PRE_EPIC_07_SITES` section records the user's ruling of
2026-09-18, given as a **set** rather than per file: the original 28 came from
`toongod`, `rolia-scans`, `w-network` and `xbato`. It is explicit that this is
recall, not derivation, and says exactly what would overturn it:

> What would falsify it is someone going through the 28 and finding one of those
> three; if that ever happens, the unseen count drops and the entries stay where
> they are.

That has happened, and in **both** directions:

- **`kunmanga` (2) and `demonicrevolution` (4) are in the tuning set.** Both
  were counted as *unseen* readers.
- **`xbato` has zero tuning entries**, though the recalled set names it. The
  user re-checked on 2026-09-21 and confirmed: *"xbato wasn't in the old 28."*

So the unseen-reader set changes membership entirely — from `manhwaclan` 2,
`kunmanga` 2, `demonicrevolution` 1 across **three** readers, to `xbato` 3 and
`manhwaclan` 2 across **two**. Five entries either way, by coincidence; a
different five, and one fewer reader.

**That lands exactly on the floor.**
`corpus_manifest.rs::at_least_two_held_out_readers_are_absent_from_the_pre_epic_07_set`
requires `MIN_UNSEEN_SITES` = 2, and the corrected count is 2. The test still
passes; it has no margin left. AC-4 exists because that fact must be visible in
the file rather than discovered the next time someone edits the table.

### Why this matters more than a tagging chore

Two things become measurable that were not, and both bear on work already done:

1. **Every number in EPIC-07 is majority one reader.** `toongod` is **11 of the
   21 marked tuning entries**. MC-019's 20 of 21 on the column axis, MC-026's
   8 of 21, MC-028's 4, MC-031's 5, MC-034's 8, MC-035's re-score and MC-038's 8
   are all 52 % one site. No document says so, because nobody could.
2. **The difficulty is not spread evenly.** Splitting MC-038's per-file ceiling
   (`region-row-search.md` §8) by the new labels gives `rolia-scans` 2 of 2,
   `kunmanga` 2 of 2, `demonicrevolution` 2 of 4, **`toongod` 4 of 11** and
   **`w-network` 0 of 2**. The counts are tiny — two entries decide two of those
   rows — so this is a **pointer, not a finding**, and AC-5 requires it recorded
   with that caveat attached rather than as a result.

### What this story is not affected by

The user's decision of 2026-09-21 that the default crop removes **furniture**
rather than reaching the artwork (`product-brief.md` §5, third amendment;
`architecture.md` decision 14) changes the *target*, not the corpus. Reader
attribution is if anything worth more under it: a furniture rule has to
generalise across readers, and site-disjoint evaluation is the only way to tell
one that generalises from one that has memorised `toongod`.

## Acceptance criteria

- **AC-1** — *Every entry in the manifest names its reader.* Given
  `fixtures/corpus/manifest.json`, when it is parsed, then **all 59 entries**
  carry exactly one `site:` tag, the 28 `tuning` entries carrying the labels in
  `## Context`'s table and the 31 held-out entries keeping the tags they already
  have, unchanged. *Control:* the check is an assertion in
  `crates/engine/tests/corpus_manifest.rs`, not a property of today's file — an

  same file for the same reason. *Control:* changing one rectangle by one pixel

- **AC-3** — *`corpus.md` records the attribution and retires the recalled set.*

## Amendments

### AC-2, rewritten to be testable — lead-po, 2026-09-21, at PLANNED → RED

**What it said** (as merged to `main` in PR #52):

> **AC-2** — *Nothing but the tags moves.* Given the manifest before and after,
> when they are diffed, then the only changes are additions to `tags` arrays:
> no `expect` rectangle, no `split`, no `file`, no other tag, and no entry added
> or removed. The 21 marked rectangles are byte-identical, which is what keeps
> every prior number in EPIC-07 comparable.

**What it says now:** the 21 marked tuning rectangles are pinned in a named
constant in `crates/engine/tests/corpus_manifest.rs`, and the assertion names
the offending file and both rectangles when one differs.

**Why.** The original describes a `git diff`, not a test. "Given the manifest
before and after" is not a state any test can observe — a test sees one file —
so as written AC-2 was satisfied by a human reading a diff, which is the control
`rules.md` says is not one. Nothing in the repository guarded those 21
rectangles, and **every number in EPIC-07 rests on them**, while this story
hand-edits all 28 tuning entries. The rewrite makes the criterion assert the
property the original was reaching for, and gives it a probe: change one
rectangle by one pixel and the required `unit` gate goes red.

**Who approved it.** The lead-po orchestrator, at PLANNED, before the branch
existed — `/advance-story`'s PLANNED → RED step requires exactly this check
("confirm the acceptance criteria are testable") and names PLANNED as the last
phase in which criteria may change freely. No scope moved: AC-2 protected the
rectangles before and protects them now, more strictly.

**Why an entry is here anyway, which is worth knowing for the next story.**
`check-boundaries.sh` compares `## Acceptance criteria` against the **base
branch**, not against the phase the story was in when they changed. MC-042 was
merged to `main` at PLANNED in PR #52 and edited afterwards, so the change is
visible to that check however early it happened, and the PR fails without this
section. A story written and started in the same PR would never hit it. Neither
behaviour is wrong; the two just meet here, and the resolution is to write the
amendment rather than to argue the phase.

Model: default. Oracle partition, in the form `story-authoring` "Brief RED by

- **Settled — read out, never re-derived.** The 28 labels themselves (the user's,
  from the labeller; `## Context`'s table is the source and an agent may not

  and their meanings in `corpus.md`'s vocabulary; `MIN_UNSEEN_SITES` = 2;
  MC-033's rule that the documented table is the source and the test is the
  reader; every score quoted in `## Context`.
- **Oracle-free.** Nothing. This story invents no metric and chooses no
  threshold, which is why it is a `chore`.
- **Mechanical.** All of it: AC-1's tags, AC-2's diff discipline, AC-3's and
  AC-4's prose, AC-5's two tables.

**The one trap.** `w-network`'s five tuning entries are **three `flag` entries
and two marked**, and `toongod`'s fifteen are **four flag and eleven marked**.
An agent summarising "reader counts" without splitting marked from flag will
report 15 and 5 where the number that matters to every accuracy score is 11 and
2. AC-1's table carries both columns for that reason.

## Out of scope

- **Re-marking anything.** No `expect` rectangle changes. The marks stay tight
  and, per the 2026-09-21 amendment, become the never-clip oracle; that is a
  change of role recorded in `product-brief.md` and `architecture.md`, and it
  needs no edit to a single rectangle here.
- **Re-tagging anything but `site:`.** No `overhang-text`, which `corpus.md`
  records as defined and deliberately unapplied. No third `diagonal-gutter`
  entry, no fourth gutter-crossing band entry.
- **New screenshots.** The corpus is 61,586,536 bytes against a 60 MiB ceiling
  with about 1.27 MiB of headroom; this story adds no bytes.
- **Changing the split.** No entry moves between `tuning` and `held-out`.
  `corpus.md` is explicit that a falsified recall does **not** move entries:
  "the unseen count drops and the entries stay where they are." Contamination
  runs one way, and finding that `kunmanga` was in tuning all along does not
  make its held-out entries fresh.
- **Acting on the concentration.** AC-5 records that `toongod` is 11 of 21 and
  that MC-038's ceiling is uneven. It does **not** reweight a score, re-run a
  sweep, exclude a reader, or revisit a prior document's conclusion. Whether
  52 % one reader invalidates anything is a question for whoever next measures
  accuracy, and MC-038's numbers are not re-opened by a tagging story.
- **Scoring anything.** No accuracy run, no held-out selection, no new number
  beyond counting the manifest.
- **The furniture work.** EPIC-07 story 4 as rewritten on 2026-09-21 is a
  separate story and is not started here.

## Test plan

### The gate question

`crates/engine/tests/corpus_manifest.rs` is **not** `#[ignore]`d — its module
header says why: "these run in the `unit` gate on every commit, because a corpus
that has quietly rotted [...] turns MC-019 into a test that measures nothing".
So the gate that fails if this story's artifact breaks is **`unit`, which is
already `required`**, and `required_gates` is correctly empty. This is the
opposite of [MC-038](MC-038.md)'s situation, where the only gate touching the
artifact was the optional `integration` one and had to be escalated; checked
here rather than assumed, because the two stories sit one id apart and the wrong
answer is copyable. Neither `corpus.rs` nor `corpus_accuracy.rs` reads a tag, so
nothing under `integration` is affected by this change.

### The tests

`corpus_manifest.rs` is the whole of it. Four new assertions and two probes:

- **AC-1**: every entry carries exactly one `site:` tag. RED writes it against
  the current manifest, where 28 entries have none, so it fails for the right
  reason on 28 named files before a single tag is added.
- **AC-1, the labels themselves**: each of the 28 `tuning` entries carries
  exactly the tag `## Context`'s per-file table records for it, pinned as
  `READER_BY_FILE`. This is the criterion's actual contract — "the 28 `tuning`
  entries carrying the labels in `## Context`'s table" — and it belongs in the
  test as the specification, the way `PRE_EPIC_07_ENTRIES` and
  `MARKED_TUNING_RECTS` do. Red today on all 28.
- **AC-1, the summary**: the per-reader counts — tuning, of which marked, of
  which flag, held-out — equal the counts table. Strictly implied by the
  per-file pin and kept anyway: its failure message is seven rows rather than
  twenty-eight, so it is the one a person reads, and it is the only check on
  `READER_BY_FILE` itself, the two constants having been transcribed from
  different tables. The marked/flag columns are what make that bite; see
  `## Model guidance`'s trap. Red today on five of seven rows.
- **AC-2**: the 21 marked tuning rectangles match a pinned constant. This one
  **passes the moment it is written**, because the rectangles are already
  correct — so it is the case `rules.md` covers under "a test written against
  code that already exists": it earns its red by a probe. Change one rectangle
  by one pixel, watch that assertion and only that assertion go red, revert, and
  paste the output. Without that it could assert nothing and nobody would know.
- **AC-4**: the unseen-reader test already exists; this story changes the table
  it reads, so `## Gate probes` must show it failing — break it by attributing a
  sixth reader into tuning and watch the count drop below `MIN_UNSEEN_SITES`.

There is no new *behaviour* to test: the detector is untouched. This is why the
story is a `chore` and why AC-2 exists — the risk here is not a wrong rule, it
is a fat-fingered edit to a fixture that every number in the epic rests on.

  `MARKED_TUNING_RECTS` is a flat tuple and not an array of `Rect`.

### One thing the orchestrator broke and rebuilt, recorded because the rebuild is evidence

Reverting the first mutation with `git checkout -- fixtures/corpus/manifest.json`
discarded the 28 tags along with it — they were uncommitted, so HEAD is the
*untagged* manifest. The right revert here is a byte copy, and the second
mutation above used one.

The rebuild is worth recording. The tags were re-applied by extracting
`READER_BY_FILE` out of the frozen test file with `awk` and inserting
`site:<reader>` into each named entry's `tags` array — a script that aborts
unless it edits exactly 28 entries. The result is **byte-identical** to what
SCAFFOLD produced: `md5sum 7382187092e41ddc8c714687fb947991` before the revert
and after the rebuild. Two independent applications of the same mapping landing
on the same bytes is a stronger check on the tagging than either run alone, so
the accident bought something.
