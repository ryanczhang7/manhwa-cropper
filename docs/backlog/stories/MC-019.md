## Context

The brief's section 7 as a test: zero clipped panels across the corpus, and
at least nine in ten needing no manual fix. Runs the real pipeline
(`process_file` from MC-008/MC-009) over every corpus entry (MC-018) in an
`#[ignore]`d test under `crates/engine/tests/corpus.rs`, executed by the
`integration` gate in release mode, which this story requires. This is the
story where `Tuning::default()` may change: every constant in
`architecture.md`'s table was settled for RED on synthetic fixtures, and
this is the evidence that re-settles them. A constant change is a source
change under GREEN; record the before/after numbers in `## Notes`, and if
an *acceptance criterion* has to move, that is an `## Amendments` entry
approved by the user, with the orchestrator's own reproduction.

Gate that fails if this breaks: `integration`, required by this story.

## Acceptance criteria

- **AC-1** - *Zero clips.* Given every corpus entry with an expected rect, when processed, then for each entry whose outcome is `Cropped { rect, .. }`, `rect` contains the expected rect entirely (`rect.x <= e.x`, `rect.y <= e.y`, `rect.x + rect.w >= e.x + e.w`, `rect.y + rect.h >= e.y + e.h`). One violation fails the test and names the file and the offending side. *Control on the metric:* with every expected rect widened by 1 px on the top before comparison, the check must fail on at least one entry (recorded in the handoff; if it does not, the detector's margin is hiding the comparison and the control must move to 4 px).
- **AC-2** - *Nine in ten.* Given every corpus entry, when processed, then at least 90% are *right*: an entry with an expected rect is right when the outcome is `Cropped` and `rect` lies inside the expected rect expanded by `margin_px + 8` px on every side (AC-1 having held); an entry with `"expect": "flag"` is right when the outcome is `Flagged`. A flagged entry that expected a rect is a miss, and a cropped entry that expected a flag is a miss. The test prints a per-file table (file, expected, got, right/miss, reason).
- **AC-3** - Given the run, when it completes, then `failed() == 0` - every corpus file is readable and writable.
- **AC-4** - Given the constants in `Tuning::default()` changed in this story, when the story ends, then `## Notes` carries the table of old and new values with AC-1/AC-2 figures before and after, and `docs/wiki/architecture.md`'s tuning table is updated to match.

## Model guidance

Model: default. Oracle partition:

- **Settled**: 90%, `margin_px + 8`, the containment predicate. Read out.
- **Mechanical**: AC-3, AC-4.
- **Oracle-free**: nothing - the corpus is the oracle. But the corpus can be wrong: a "clip" on one file may be a mis-marked rect. The Feature Developer reports that as a finding with the file name; the orchestrator opens the image and decides, with the user, whether the manifest or the detector is wrong, and records which in `## Notes`. Never edit the manifest to make the test pass without that record.

## Out of scope

Per-reader special cases, any detection technique not already in
`cropper-core`, tuning beyond `Tuning::default()`'s existing fields, adding
corpus files (MC-018, or a follow-up chore).

## Test plan

One new file, `crates/engine/tests/corpus.rs`, five tests, no production
source. Four are `#[ignore]`d and run in the `integration` gate in release,
which this story's `required_gates` makes binding; the fifth reads a document
and runs in `unit` on every commit.

| Test | AC | Level |
|---|---|---|

| `widening_every_expected_rect_on_the_top_makes_the_zero_clip_check_fail` | AC-1's control | integration, `#[ignore]` |
| `at_least_nine_corpus_screenshots_in_ten_need_no_manual_fix` | AC-2 | integration, `#[ignore]` |
| `every_corpus_file_is_read_and_its_output_written_without_failing` | AC-3 | integration, `#[ignore]` |
| `the_architecture_tuning_table_says_what_tuning_default_says` | AC-4 (second half) | unit, not ignored |

Each of the four corpus tests drives [`process_file`] over all 28 entries into
its own `TempDir` - 1.8 s for the file, in release, all four in parallel. They
are not folded into one test the way `tests/perf.rs` folded its three, because
"a crop cut into the art", "fewer than nine in ten are right" and "a file could
not be read" are three different bug reports and a single test would have named
only the first one it hit.

**The table lives in the assertion message, not in `println!`.** AC-2 requires
a per-file table and the `integration` gate does not pass `--nocapture`, so a
printed table is swallowed on exactly the run whose output somebody needs.
Every assertion carries it; the tests print it as well, for `--nocapture`.

**The slack is computed, not written as 11.** AC-2's band is `margin_px + 8`,
and `margin_px` is a constant this story may change, so the test reads it from
the `Tuning` the run was given. That is not a loophole: raising `margin_px` by
*k* grows the produced rect by *k* on every side and grows the band by *k* at
the same time, so both of AC-2's comparisons are invariant under it. The
working is in the file's module documentation.

**Vacuity guards.** "Zero clips" is trivially true of a detector that flags
everything, so AC-1 asserts that at least one entry with an expected rect came
back `Cropped` before it reports zero clips (13 do today). AC-2 asserts the
corpus loaded at least 20 entries, so a percentage means something.

**AC-4 is half-testable and the half that is, is tested.** "`architecture.md`'s
tuning table is updated to match" is a mechanical claim about a file, so it is
an assertion rather than a promise: the test parses the table's `Default`
column and compares all nine values against `Tuning::default()`. The other half
- that `## Notes` carries old and new values with AC-1/AC-2 figures either side
- is prose about a decision and is checked at review.

**What is deliberately not asserted.** Nothing depends on the `diagonal-gutter`
or `overhang-text` tags, which MC-018 defined and has not applied to any entry;
the table takes a census of them so that the day they are applied, a cluster
shows up without anyone editing this file. And nothing re-derives a rectangle:
the manifest is the oracle, it can be wrong, and a reported clip is escalated
to the user with the file name, never fixed in the manifest.

returning the whole image clips nothing. That is exactly what the control was
put in AC-1 to detect, and it detects it.

### Why the side gutters are never peeled - the one number that explains 13 of the 21

Measured out-of-band from the manifest and the images, not from the detector:
each expected rect's gutter on each side, as the share of the image dimension
that `Tuning.chrome_max_extent` is compared against.

| | left | right | top | bottom |
|---|---|---|---|---|
| min across the 21 rect entries | 0.371 | 0.378 | 0.079 | 0.031 |
| max across the 21 rect entries | 0.446 | 0.457 | 0.238 | 0.247 |

`chrome_max_extent` is **0.30**. **All 21 rect entries have both side gutters
wider than the cap**, 0.371 to 0.457 of the width - the widest being
`Screenshot (93).jpg`'s right gutter at 0.457. A strip wider than the cap is
never chrome-like, so the left and right gutters cannot be peeled at any value
of `chrome_flat_fraction` or `min_content_stddev`. The top and bottom gutters
are all inside the cap, which is why the top band *is* peeled.

This is a real manhwa reader in a 2560-wide window: the content column is about
a quarter of the screen and each gutter is nearly two-fifths of it. The cap was
settled on synthetic fixtures with borders up to 200 px.

Two cautions before treating this as the whole answer:

- The peel is iterative and outside-in, so a gutter *could* come off in several
  passes if a strong line ran through it. A flat gutter has no strong line in
  it, which is why it is one strip and why the cap binds. Confirm rather than
  assume.
- Raising the cap does nothing for the 8 `Ambiguous` entries, which are a
  different failure - a strip landing within `ambiguity_band` below
  `chrome_flat_fraction`. Those and the over-cropped `mostly-white` flag entry
  need their own reasoning.

I did not try a candidate value for the cap. That is GREEN's job with the
corpus as the evidence, and AC-4 is how it gets recorded.

### The export shape these tests already pin

Stated as fact: a test imports each of these and a wrong guess is a compile
error.

From `cropper_core`:

```rust
pub struct Rect { pub x: u32, pub y: u32, pub w: u32, pub h: u32 }  // Copy
pub struct Tuning {
    pub uniform_tolerance: u8,
    pub edge_threshold: u8,
    pub min_content_stddev: f32,
    pub chrome_flat_fraction: f32,
    pub chrome_max_extent: f32,
    pub ambiguity_band: f32,
    pub min_content_fraction: f32,
    pub min_content_side: u32,
    pub margin_px: u32,
}
impl Default for Tuning { .. }
```

All nine fields are read by name by the AC-4 test, and `margin_px` by AC-2.
**Renaming or removing a field is a breaking change to this suite**, and to
`architecture.md`'s table with it.

From `cropper_engine`:

```rust
pub fn process_file(input: &Path, output: &Path, tuning: &Tuning) -> FileResult;
pub struct FileResult { pub input: PathBuf, pub outcome: Outcome }
pub enum Outcome {
    Cropped { rect: Rect, output: PathBuf },
    Flagged { reason: Flag, output: PathBuf },
    Failed  { error: String },
}
```

`output` is the **whole output path, name included**, not a directory - the
tests pass `temp_dir.join(entry.name())`. `Outcome::Flagged`'s `reason` is
formatted with `{:?}`, so `Flag` must keep `Debug`; nothing asserts on which
variant it is.

From the MC-018 loader, included as `#[path = "common/corpus.rs"] mod corpus;`
and **not** declared in `common/mod.rs`:

```rust
corpus::load() -> Vec<CorpusEntry>          // manifest order
struct CorpusEntry { path: PathBuf, expect: Expect, tags: Vec<String> }
enum Expect { Rect(Rect), Flag }
CorpusEntry::name() -> String
CorpusEntry::has_tag(&str) -> bool
```

`has_tag` is used for the deferred-tag census; without a use of it the shared
module warns `dead_code` and the `lint` gate (`-D warnings`) fails. Do not
remove that call without replacing the use.

From the document, `docs/wiki/architecture.md`:

- a line beginning `| Constant | Default |` starts the tuning table;
- each following row is `` | `name` | <value>... | ... | `` and the value is
  the **leading run of digits and dots** in the Default cell, so prose after
  the number ("0.30 of the image's height") is free; the rest of the cell is
  not constrained;
- the table ends at the first line that does not begin with `|`.

**Not constrained, and deliberately the implementer's choice:** which constants
change and to what; how the detector reaches its decision; which `FlagReason`
any entry produces; what the output files are named or what format they are in;
everything about `batch`, `naming` and `settings`.

One control, AC-1's, and it is the only one in the suite. Every assertion in
the file executed, so these are measured rather than predicted - the usual
"the suite failed at import so no control ran" caveat does not apply here.

| Control | Threshold | Candidate range | Measured today |
|---|---|---|---|
| Expected rects widened **1 px** on the top, re-run through the same containment check | at least 1 entry must fail | 0..13 of the compared crops | **0** |
| Expected rects widened **4 px** on the top (AC-1's prescribed fallback) | at least 1 entry must fail | 0..13 | **0** |
| Smallest top headroom (`expected.y - crop.y`) over the 13 compared crops | - | - | **97 px**, `Screenshot (2744).jpg` |
| Widening that *would* fire today | - | - | **98 px or more** |
| Expected rects sitting at `y = 0`, where widening is a no-op | must be small | 0..21 | **0** |

The 1 px figure was measured with a scratch binary outside the repository
driving the same predicate over the same corpus; the 4 px figure is the frozen
test's own output above. Both are 0.

**GREEN must confirm the 4 px control fires against the shipped tuning**, not
merely that the test passes. It fires when at least one crop's top sits within
3 px of its expected top. A detector that satisfies AC-1 and AC-2 has every top
headroom in `[0, margin_px + 8]`, which makes it likely but does not make it
certain - see the escalation below.

### Things that should change the implementation approach

1. **`chrome_max_extent` at 0.30 is the structural blocker for 13 of the 21
   misses.** The number is above; it is a fact about the corpus, not a
   suggested value.
2. **8 `Ambiguous` flags are a separate failure** and raising the cap will not
   touch them.
3. **`2025-02-27 22_46_15.png` is cropped when it should be flagged** - `0,3
   553x853` on a 553x856 image. A 3 px trim is `margin_px` worth of nothing. If
   tuning makes the detector more willing to crop, watch this one: it is the
   corpus's only over-crop and the only guard against the opposite failure.
4. **MC-018's coverage caveat still stands.** All 7 flag entries are the
   non-2560x1440 images and all 21 rect entries are 2560x1440 captures, so a
   detector keying on something size-correlated passes this suite. Raising
   `chrome_max_extent` to peel a 0.46-wide gutter makes that caveat sharper,
   not softer: there is no full-screen all-art capture here that would catch an
   over-crop.
5. **`tests/perf.rs` does not run while `tests/corpus.rs` is red.** Cargo stops
   at the first failing test binary and `corpus` sorts before `perf`, so MC-017's
   timing test is not reached under `cargo test --workspace --release --
   --ignored` until this story is green. Run it directly if you need it:
   `cargo test --workspace --release --test perf -- --ignored --nocapture`.
   The `integration` gate has an `evidence` line but no `floor`, so nothing
   else moves because of the new binary.
6. **A harness bug, not this story's to fix.** `bash` commands containing
   `2>/dev/null` are refused by the phase lock, which classifies the redirect
   target as `category: source`. It writes nothing. Per `CLAUDE.md` that is a
   case for `.claude/tests/phase-guard.test.sh`; it is recorded here and not
