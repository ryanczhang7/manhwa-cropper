## Acceptance criteria

- **AC-1** - *Zero clips.* Given every corpus entry with an expected rect, when processed, then for each entry whose outcome is `Cropped { rect, .. }`, `rect` contains the expected rect entirely (`rect.x <= e.x`, `rect.y <= e.y`, `rect.x + rect.w >= e.x + e.w`, `rect.y + rect.h >= e.y + e.h`). One violation fails the test and names the file and the offending side. *Control on the metric:* with every expected rect widened by 1 px on the **left and right** before comparison, the check must fail on at least one entry (recorded in the handoff). Measured at the time of the amendment below: it fails on exactly one, `2025-10-14 23_30_20.png`, whose crop sits flush with the marked right edge.
- **AC-2** - *Nine in ten, on the column axis.* Given every corpus entry, when processed, then at least 90% are *right*: an entry with an expected rect is right when the outcome is `Cropped` and `rect`'s **left and right** edges lie inside the expected rect's left and right expanded by `margin_px + 8` px (AC-1 having held on all four sides); an entry with `"expect": "flag"` is right when the outcome is `Flagged`. A flagged entry that expected a rect is a miss, and a cropped entry that expected a flag is a miss. The test prints a per-file table (file, expected, got, right/miss, reason), and prints the row-axis deltas alongside **without asserting on them**, so the number MC-032 has to move is visible on every run. *Control on the metric:* the per-entry column deltas are not all inside the window - `Screenshot (93).jpg` is +20 against a slack of 11 - so an implementation that widened the window to admit everything would be caught by that entry remaining a miss.
- **AC-3** - Given the run, when it completes, then `failed() == 0` - every corpus file is readable and writable.
- **AC-4** - Given the constants in `Tuning::default()` changed in this story, when the story ends, then `## Notes` carries the table of old and new values with AC-1/AC-2 figures before and after, and `docs/wiki/architecture.md`'s tuning table is updated to match.

### Judgement calls

1. **AC-1's control is asserted as "at least one", not as "exactly
   `2025-10-14 23_30_20.png`".** That is the criterion's own wording, and
   pinning the identity would make a detector that got *better* on that one file
   look like a broken control. The identity is printed on every run
   (`AC-1's control at 1 px on the columns fired on ["2025-10-14 23_30_20.png"]`)
   and recorded in the handoff, which is where the criterion says it goes.

2. **AC-1's control clamps the widened rect to the image.** Widening a mark past
   the image's own edge produces a rectangle *no* crop of that image could
   contain, so an unclamped control would fire on geometry rather than on the
   detector and look exactly like a real one. The clamp needs the image's
   dimensions, which is why `Run` carries them, read from the file header via
   `image::ImageReader` (a regular dependency of `cropper-engine`, so visible to
   `tests/`). On this corpus it is a no-op - 0 of 21 marks are flush with an
   edge, and the control's failure message reports that count - but a control
   that is only correct because of the data is not a control.

3. **AC-2's control is an assertion, not just a print.** The story says "the test
   should make that visible"; the amendment two sections above says "a control
   that cannot fail is not a control". Printing satisfies the first and not the
   second, so it asserts. The cost is stated in the test's own doc comment and
   in its failure message: this is the one assertion in the file that a *better*
   detector could turn red, and the message says that closing the last column
   miss is a change to what MC-019 characterises and belongs in a story with the
   user's decision on it, not in a quiet edit to the window.

4. **The row axis is printed and never asserted**, per the amendment: per-entry
   `rows(t,b)` in the table plus a sorted `worst row overshoot per entry` line
   under it, on every run of every test in the file. That is MC-032's number,
   visible without anyone opening MC-032.

5. **Five corpus passes, not one shared pass.** Each test does its own
   `process_file` sweep. Measured: 5 tests, 2.1-3.4 s wall in release for the
   whole file, and the full `integration` gate is 170 s with the file in, so a
   cached shared pass would buy nothing and would couple five tests through a
   `static`.
