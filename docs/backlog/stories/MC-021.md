## Context

`docs/wiki/audits/app-window-2026-09-13.md`, evidence **E-3**, found survivors
in `gui.rs` that change a colour nobody can see fail. The two the audit singles
out, because they are what a user would notice first:

```
crates/app/src/gui.rs:269:5: replace widgets -> Widgets with Default::default()
crates/app/src/gui.rs:428:16: delete ! in folder_button
```

`428` turns `if !enabled {` into `if enabled {`, so the **enabled** "Choose
folder…" button paints its caption in disabled grey and the **disabled** one
loses the three tokens `components.md` gives it. `269` discards the whole widget
palette in both themes: every button fill, boundary and text colour reverts to
egui's own. All 26 tests in `tests/gui.rs` and `tests/shell.rs` stay green
through both, because `add_enabled(enabled, ..)` — the part AccessKit can see —
is untouched. Three more in the same cluster are the row's own text style:

```
crates/app/src/gui.rs:582:5: replace format -> TextFormat with Default::default()
crates/app/src/gui.rs:583:9: delete field font_id from struct TextFormat expression in format
crates/app/src/gui.rs:584:9: delete field color from struct TextFormat expression in format
```

### This story was re-planned on 2026-09-15, and what changed is the instrument

It was written as *"The window's painted look is pinned by image snapshots"*:
seven looks, two themes, `egui_kittest`'s `snapshot` and `wgpu` features, and
committed reference PNGs. **MC-022 falsified the premise.**

The audit's **Decided-2 is still true exactly as written** — these mutants are
not killable by an *AccessKit* assertion, and none is proposed here. What it did
not consider is that a third surface exists, between the accessibility tree and
a rendered image: `egui_kittest`'s `Harness::output()` returns the frame's
`FullOutput`, whose `shapes` are the **untessellated** paint list. MC-022 read
`Shape::Text`'s galley out of it to kill eleven truncation survivors with no
production change and no renderer (`crates/app/tests/truncation.rs`, and that
story's `## Test plan`).

Colour is in the same list. Read at the pinned version rather than from memory:

| What carries it | Where | Fields |
|---|---|---|
| `epaint::RectShape` | `epaint-0.36.2/src/shapes/rect_shape.rs` | `rect`, `corner_radius`, `fill`, `stroke`, `stroke_kind` |
| `epaint::TextShape` | `epaint-0.36.2/src/shapes/text_shape.rs` | `pos`, `galley`, `fallback_color`, `override_text_color` |
| a galley's per-section style | `epaint-0.36.2/src/text/text_layout_types.rs` | `job.sections[].format.color`, `.font_id` |

**What that makes true, and what it does not.** MC-022 demonstrated the surface
end to end for `Shape::Text` only. That this window's frame contains a
`Shape::Rect` carrying the **button's** fill and boundary is established at the
API level and **not observed** — the button is painted by egui's own `Button`
widget, not by `gui.rs`, and how that arrives in the paint list is exactly the
kind of claim this harness does not take on trust.

**So RED's first job is to establish it**, before sizing anything. If the
button's fill does not reach the paint list as a value, say so and stop: the
fallback is the renderer, and then the audit's **E-7** — that `egui_kittest`
0.36.2 declares `snapshot` and `wgpu` features — has to be verified first. It
was read off a manifest and **nothing was ever compiled**; whether a wgpu
adapter exists under `cargo test` here, whether a software fallback is needed
and what the feature costs in build time are all still unmeasured. This story no
longer depends on any of it, which is the point of the re-plan.

words that "a story that treats them as one priority will over-invest", and it
is right: `269` and `428` change colours wholesale, the arithmetic shifts things
by a few points. This is the half worth doing first.

**Line numbers drift; identify every mutation by what it does.** The audit ran
before MC-023. At this story's base commit `fn widgets` is `gui.rs:268` (its

## Acceptance criteria

- **AC-1** — Given the window is idle with a folder chosen, when it is painted,
  then the enabled "Choose folder…" button's caption is painted in `text` and
  not in `text-disabled` (`tokens.md`, "Colour roles").

- **AC-2** — Given a run is under way, when the window is painted, then the
  disabled button is painted with `control-disabled` as its fill, `border` as
  its boundary and `text-disabled` as its caption — the three tokens
  `components.md` gives a disabled control.
  *Control for AC-1: `delete !` swaps these two looks, so a suite that pinned
  only one of them would pass on half the defect.*

- **AC-3** — Given the window is idle with a folder chosen, when it is painted,
  then the enabled button's fill is `control` and its boundary is
  `border-strong` — the values `widgets()` installs — and neither equals what
  `Widgets::default()` paints there.
  *Control: the second clause is what makes this criterion about **our**
  palette rather than about any palette. State the two default values in the
  test so a reader can see they differ.*

- **AC-4** — Given a finished run with one flagged row, when the list is
  painted, then that row's file name is painted in `text` and its reason word
  in `text-muted`, both in the `body` font — two sections of one galley, each
  keeping its own colour (`components.md`, the flagged row).

- **AC-5** — Given the same idle-with-folder window painted under the light
  theme and under the dark theme, when each frame's colours are read, then each
  matches its own column of `tokens.md` and the two differ.
  *Control: a harness that silently painted one theme twice would satisfy
  AC-1 to AC-4 and prove nothing about theming; the two frames being equal must
  fail this criterion.*

- **AC-6** — Given the shipped painter mutated so that `folder_button`'s
  `if !enabled` becomes `if enabled` (today `gui.rs:428`), when the new tests
  run, then at least one fails. And given it mutated so that `widgets` returns
  `Widgets::default()` (today `gui.rs:268`), when they run, then at least one
  fails. *The audit's two headline survivors, used as this story's negative
  controls. Record both failures under `## Gate probes`: they break different
  mechanisms — a per-widget override and the palette installed at startup — and
  a suite that catches only one has pinned half of what it claims.*

The open question is **identification, not colour**: which shape in the paint
list is the button's. MC-022 had the same question for text and answered it by
elimination in a frame with three strings; a frame has many more rects than
strings, so elimination will not carry over. Prefer something semantic — the
rect that contains the `Choose folder…` text shape's position, say — over an
index into the list, which pins paint order and will break on any refactor that
is not a defect. Say in the handoff which was taken and what it cost, because
MC-029 and MC-030 will both want the same helper.

**Assert against literals copied out of `tokens.md`, never against `gui.rs`'s
own `LIGHT`/`DARK` constants.** They are private, and reading them back would
assert only that the painter agrees with itself — which is the exact shape of
the theatre E-6 was. `tests/gui.rs` states this convention in its module docs
and already spells `SURFACE_LIGHT` out as a literal; follow it.

### How the button's rect is identified, and what that cost

`rect_containing` was the first design, straight from `## Model guidance`: the
rect whose area contains the `Choose folder…` text shape's `pos`. **It does not
work, and the spike's listing in `## Notes` is why it looked as though it
would.** That listing is not the whole paint list. The real idle frame is:

```
Rect [[8.0 8.0] - [512.0 432.0]] area=213696 fill=#20_20_20_FF stroke=w0 #00_00_00_00
Rect [[8.0 8.0] - [512.0 432.0]] area=213696 fill=#00_00_00_00 stroke=w0 #00_00_00_00
Rect [[24.0 24.0] - [496.0 144.0]] area=56640 fill=#2B_2B_2B_FF stroke=w0 #00_00_00_00
Text pos=[260.0 76.0] text="Drop images here"
Rect [[371.0 152.0] - [496.0 184.0]] area=4001 fill=#2D_2D_2D_FF stroke=w1 #9E_9E_9E_FF
Text pos=[383.0 160.0] text="Choose folder…"
Text pos=[24.0 160.0] text="D:\shots\out"
Rect [[24.0 240.0] - [24.0 240.0]] area=0 fill=#00_00_00_00 stroke=w0 #00_00_00_00
```

Two window-sized rects - the panel's `surface` fill and a transparent sibling -
are painted under everything and contain every caption in the window, so
**three** rects contain `[383, 160]`, not one. The first version of the helper
said so and failed:

```
assertion `left == right` failed: exactly one painted rect must contain [383.0 160.0], and 3 do
  left: 3
 right: 1
```

The helper that ships is `innermost_rect_containing`: among the rects containing
the point, the **smallest by area** - the one painted last and on top, which is
what a user sees under that point. Area rather than "the last one in the list"
because area is order-free, and an index or a position in the list is exactly
what `## Model guidance` rules out.

Two guards keep it from silently answering a different question:

- the smallest must be the **unique** smallest. A control that painted no
  background of its own would leave the two equal window-sized rects tied, and
  the helper fails loudly rather than reporting the panel's fill as the
  control's;
- every candidate must **contain** the innermost, so "nested, innermost last"
  is a fact about the frame rather than an assumption.

The cost, stated so MC-029 and MC-030 can price it: it needs a point known to be
inside the shape, which for a control means the control must paint text. A
control with no caption cannot be found this way. The drop zone can (its text
sits inside it); a bare progress track could not, and would need a different
handle. It is also blind to shapes that are not `Shape::Rect` - the drop zone's
dashed border is a path, so **MC-029 gets no help from this helper for the
border itself**, only for the zone's fill.

### Why sections are addressed by byte offset, not by index

`LayoutJob::append` merges a run into the previous section when the format is
identical and there is no leading space
(`epaint-0.36.2/src/text/text_layout_types.rs:207`). `flagged_row` appends three
runs - name, separator, reason - and the separator is in the same `text` as the
name, so the galley carries **two** sections, `0..10` and `10..15`, not three.
`section_at(byte)` asks which section covers a byte; an index would be asserting
that merge, which is epaint's business and not the design's.

### What is deliberately not asserted

No geometry: no position, size, radius or centring (MC-029, MC-030). A rect's
position is used to *identify* the button and never asserted. No hover or
pressed state - no survivor names them and a headless frame has no pointer. No
font metric: the only font assertion is the `body` `FontId`, which is a declared
style rather than a measurement, so nothing here moves when a font package
updates. No renderer, no image, no `snapshot` / `wgpu` feature.

### The export shape these tests already pin

Stated as fact: the file imports these today and a different shape is a compile
error. **Nothing here is new** - this story adds no API - so the practical
content of this section is that GREEN must not change any of it.

```rust
use cropper_core::FlagReason;                                  // ::Uniform
use cropper_engine::batch::RunSummary;                         // { results: Vec<FileResult> }
use cropper_engine::process::{FileResult, Flag, Outcome};
use eframe::egui;
use eframe::egui::{Color32, FontFamily, FontId, Pos2};
use egui_kittest::Harness;
use manhwa_cropper::{AppState, Model, gui};
```

- `gui::install_style(ctx: &egui::Context)` - called as
  `gui::install_style(ui.ctx())` **inside** the `build_ui` closure. Without it
  the frame is painted from egui's own `Visuals` and every colour in the file
  measures egui rather than `tokens.md`. It must stay idempotent and must keep
  registering **both** themes (`set_visuals_of(Light, ..)` and
  `set_visuals_of(Dark, ..)`), which is what lets AC-5 switch between them; and
  it must keep leaving `theme_preference` alone.
- `gui::paint(ui: &mut Ui, model: &Model, hovering: bool)` - the `FnMut(&mut Ui)`
  closure signature `HarnessBuilder::build_ui` needs.
- `Model { state: AppState, output_dir: Option<PathBuf> }`, both fields public.
- `AppState::Idle`, `AppState::Processing { done: u32, total: u32 }`,
  `AppState::Done { summary: RunSummary }`.
- `FileResult { input: PathBuf, outcome: Outcome }`,
  `Outcome::Flagged { reason: Flag, output: PathBuf }`,
  `Flag::Detector(FlagReason)`.
- The paint list itself, which is the real contract: `harness.output().shapes`
  yielding `ClippedShape`s whose `shape` is walked through `egui::Shape::Vec`,
  with `Shape::Rect(r)` carrying `r.rect`, `r.fill`, `r.stroke.{color,width}`
  and `Shape::Text(t)` carrying `t.pos`, `t.galley.text()`,
  `t.override_text_color` and `t.galley.job.sections[i].{byte_range, format}`.

**Not constrained, and GREEN's to choose:** everything inside `gui.rs`. Whether
the disabled tokens are set by mutating `ui.visuals_mut().widgets.inactive`, by
building a `WidgetVisuals` and assigning it, by a helper, or by passing a
`Button` its own `fill`/`stroke`; whether the `if !enabled` scope stays a scope;
every private constant, every doc comment. The tests read the frame, not the
code, so any of those is fine as long as the painted numbers come out right.
