## Context

MC-019 ran the detector over the user's 28 real screenshots and scored **6 of
28 (21.4%)** against a 90% bar, with **zero of the 21 crop entries right**. It
is blocked on this story. The evidence is in MC-019's `## Notes`; the part that
matters here is *why*.

**`edges` finds a boundary by adjacent-row gradient.** The row profile is the
mean absolute luma difference between neighbouring rows, and a strong line is
one that reaches `Tuning.edge_threshold` (24). That works on a hard boundary
and fails completely on a **gradual fade** - a dark panel bleeding into a dark
gutter over tens of pixels. The transition is real; it is simply spread thin
enough that no single row-to-row step ever reaches 24.

Measured at seven marked edges, each beside a control taken at the title bar
in the same file and the same columns - the boundary the detector *does* find:

```
edge_threshold = 24
file                           edge      marked   control
2025-10-14 23_30_20.png        bottom      4.42        28
2025-10-20 15_37_25.png        top          7.2        28
Screenshot (70).jpg            bottom      5.02        29
Screenshot (93).jpg            bottom      5.82        29
Screenshot (103).jpg           top         0.59        29
Screenshot (3187).png          bottom      4.99     27.43
Screenshot (3538).png          bottom      0.69     27.43
```

**Colour was measured and ruled out.** The first plan for this story was to add
a chroma signal. Peak chroma step across the same seven edges is **0.07 to
4.18** - weaker than luma. Texture-as-a-step is no better (0.53 to 12.74, one
value above 5). There is no *step* of any kind at these edges, so no
step-detector will find them. That measurement is why this story is about
flatness instead, and it is recorded so nobody re-proposes colour.

**What does work, measured.** Ask a different question - not "how much did this
row change from the last one" but **"is this row flat?"** Thresholding per-row
spread (mean absolute deviation about the row's own mean) at 8 locates the art
boundary at **0 px offset for 15 of 19 entries** and within 5 px for 17 of 19:

```
top    gutter inside marked rect: median 0, max 52
bottom gutter inside marked rect: median 0, max 18
edges with >11 px of flat gutter inside the rect: top 2, bottom 2, of 19
(2 WebP entries skipped - the measuring tool could not decode them)
```

Two things follow. The corpus is **well marked** - median zero gap between the
marked edge and where artwork actually starts, so the rectangles are not the
problem. And flatness is **already in `cropper-core`**: `chrome_flat_fraction`
uses exactly this notion, but only ever to classify a strip as chrome, never to
*locate* an edge. This story is not a new detection technique; it is an
existing signal applied where the gradient one is blind.

Gate that fails if this breaks: `unit`.

## Acceptance criteria

- **AC-1** - Given a `Luma` plane, when `spread_profile(&Luma, Axis)` runs, then it returns one value per row (or column) equal to the mean absolute deviation of that line about its own mean, in the same orientation and length convention as the existing `edges` profiles.
- **AC-2** - Given a synthetic fixture whose art fades to the gutter colour over 50 px, so that **no** adjacent-line step in the fade reaches `edge_threshold`, when the gradient locator runs, then it finds no strong line inside the fade; and when the flatness locator runs on the same fixture, then it places the boundary within 4 px of the first line whose spread exceeds the flatness threshold. *One fixture, both locators, opposite results* - that contrast is the story.
- **AC-3** - Given the same fade fixture, when `decide` runs at `Tuning::default()`, then the result is `CropDecision::Crop(rect)` whose rect contains the art the generator drew and excludes the flat gutter beyond it, where before this story the same fixture yields `Flag`.
- **AC-4** - Given every fixture the existing `crates/core/tests` suite builds, when the suite runs, then every current assertion still holds: this story adds a locator, it does not change what the gradient one reports.
- **AC-5** - Given a hard-edged fixture (a step the gradient locator finds easily), when the flatness locator runs, then it places the boundary at the same line, so the two agree where both can see.
- **AC-6** - Given the MC-018 corpus, when `process_file` runs over it, then the number of entries whose crop contains the marked rect **and** lies inside it expanded by `margin_px + 8` is recorded in `## Notes`, before and after. This is a **measurement, not a threshold** - MC-019 owns the 90% bar and this story must not pre-empt it.

## Model guidance

Model: default. Oracle partition:

- **Settled - read out, do not re-derive**: `edge_threshold` 24,
  `chrome_flat_fraction` 0.85, `margin_px` 3. This story adds a locator; it
  does **not** retune anything. Every constant in `Tuning::default()` is pinned
  by an exact-equality assertion in `crates/core/tests/content.rs`,
  `detect.rs` and `crates/engine/tests/process_file.rs`; **those pins stay**.
  Retuning is MC-019's job, under its own `## Amendments`.
- **Oracle-free, and the one place judgement is needed**: the flatness
  threshold this story introduces. 8 is what the investigation used and is a
  starting point, not a settled number. Derive it from the fixture and record
  how, with a negative control - a fixture whose "art" is flat enough that the
  locator must *not* fire. A threshold with no negative control is a threshold
  that means nothing.
- **Mechanical**: AC-1, AC-4, AC-5.

If a new `Tuning` field is needed for that threshold, adding one is in scope;
changing an existing field's value is not. A new field will need the `Tuning`
literal in every test that constructs one - check before assuming it is free.

## Out of scope

Retuning any existing constant (MC-019). Colour or chroma signals - measured
and ruled out above; do not revisit without new evidence. Per-reader special
cases. Changing the corpus or its manifest. Meeting the 90% bar, which is
MC-019's criterion and depends on retuning this story deliberately does not do.

`the_span_reaches_the_outermost_textured_lines_across_a_flat_gap_between_them`
pins it: a flat run *between* two textured ones is a panel gutter, and MC-005's

### Why the fade fixture is built the way it is

`common::fade_to_gutter` is 200x260: 40 rows of gutter, a 50-row fade, an
80-row core, a 50-row fade, 40 rows of gutter.

* the art is `FADE_TONE` plus the row's amplitude on even columns and minus it
  on odd ones, **the same phase in every row**. So it has no horizontal edges
  at all and the gradient locator is genuinely blind, which is what the
  story's measurement table describes at the seven marked edges. The amplitude
  climbs by exactly one per row, so no adjacent-row step anywhere reaches
  `edge_threshold` - measured peak **1.8** against 24;
* the width is even and a multiple of the speckle period, so every row's true
  mean is exactly `FADE_TONE` and its true spread is exactly the amplitude.
  That is what lets AC-1 compare with `==` instead of a tolerance;
* the gutter is **speckled, not perfectly flat**. One pixel in 25 is moved by
  20, on a diagonal walk, signs alternating. Row spread 0.8; row and column
  `max - min` 40, which is past `uniform_tolerance` (10), so `trim_uniform`
  will not take the gutter first. A perfectly flat gutter would be trimmed
  before any locator saw it and the fixture would not reproduce the corpus
  failure. This distinction *is* the story: flat in the deviation sense,
  not uniform in the `max - min` sense.

### Deriving `min_line_spread = 8.0`

The one calibrated number in this story. Two hard bounds from constants it does
not own, and the corpus for the value inside them:

1. **Floor 5.0**, from `uniform_tolerance = 10`. A line is uniform by MC-003's
   settled rule iff `max - min <= uniform_tolerance`, and the largest mean
   absolute deviation such a line can have is `uniform_tolerance / 2` - half
   its pixels at each end of the band. At or below 5.0 the flatness locator
   would call "art" a line stage 1 trims as a uniform border.
   `a_line_that_is_uniform_by_the_settled_rule_never_reads_as_art` builds that
   extreme line, measures exactly 5.0, and pins the inequality.
2. **Ceiling 8.261655**, from `common::soft_art`, the art in every scene
   `tests/content.rs` and `tests/edges.rs` build. Measured on
   `soft_art(100, 94, 7)`: row spreads 11.731198..13.456203, **column spreads
   8.261655..10.319375**. Above 8.261655 that art reads as flat on the column
   axis, and AC-4 breaks.
3. **8**, from the corpus. `## Context` records per-row spread thresholded at 8
   locating the art boundary at 0 px offset for 15 of 19 marked edges. It is
   the one value in `(5.0, 8.261655)` with a measurement behind it.

The headroom above the ceiling is 0.26 and is the thinnest margin in the file;
`the_art_the_existing_fixtures_use_stays_textured_on_both_axes` is where a
later story trying to raise this finds out, loudly, instead of in a corpus
score. The other direction is worth knowing too and is not a problem: a
high-contrast toolbar (dark text at 15% coverage on white) has a row spread
around 15 and reads as *art* to this locator, so the locator declines to cut
rather than cutting into a page, and it is an addition to the chrome peel
rather than a replacement for it.

### The export shape these tests already pin

Stated as fact, not suggestion: a test already imports each of these and a
different choice is a compile error.

```rust
// crates/core/src/edges.rs
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum Axis { Rows, Columns }

pub fn spread_profile(img: &Luma, axis: Axis) -> Vec<f32>;
pub fn textured_span(spread: &[f32], t: &Tuning) -> Option<(usize, usize)>;

// crates/core/src/lib.rs, a tenth field on Tuning
pub struct Tuning { /* the nine existing fields */ pub min_line_spread: f32 }
// Tuning::default().min_line_spread == 8.0
```

* `Axis` needs `Debug`, `Copy`, `Clone`, `PartialEq` and `Eq`
  (`axis_is_a_plain_comparable_copyable_value_type`), and `Debug` must print
  the variant name.
* `spread_profile` takes exactly two arguments - **no rect**. It measures the
  whole plane. `Axis::Rows` yields `img.height` entries top to bottom;
  `Axis::Columns` yields `img.width` entries left to right. A 0x0 plane yields
  an empty `Vec` on both axes.
* `textured_span` returns `(first, last)` as **inclusive indices into the
  profile it was given**, which for a spread profile are line indices. "At or
  above" is `>=`. It returns the *outermost* textured indices and does not stop
  at a flat run between them. `None` for an empty profile and for one with no
  index at or above the threshold.
* The threshold is read from the `Tuning` **argument** at the comparison site,
  never written as a literal there.
* All 16 `Tuning { .. }` literals in the workspace use `..Default::default()`,
  so the new field breaks none of them. Verified: `cargo test --workspace`
  reports exactly 20 errors and all of them are in `tests/flatness.rs`.

**What is deliberately *not* constrained, and stays GREEN's choice**: where in
the pipeline either function is called; whether `content`, `trim` or `decide`
is the caller; whether a private per-rect variant is added alongside;
the internal arithmetic width, provided the exact cases below come out exact.

#### Why, diagnosed rather than guessed

Three measurements, taken by the orchestrator on real corpus files with a mean
absolute deviation written from the definition rather than by calling
`spread_within` - independence being the point.

**1. The stage never speaks.** On the rect `detect` actually hands
`textured_box`, `strong_lines` finds lines on *both* axes, so `narrow` stands
down on both:

```
file                      rect handed to flat   strong lines rows / columns
Screenshot (1661).png     0,40 2545x1352        2 / 3
Screenshot (3187).png     0,40 2545x1352        2 / 2
Screenshot (2744).jpg     0,40 2545x1352        2 / 2
2025-10-20 15_37_25.png   0,40 2545x1400        8 / 2
```

A real screenshot always has *some* step somewhere on each axis. The
stand-down guard is correct for AC-4 - two frozen assertions in `tests/decide.rs`
enforce it, and the orchestrator confirmed that by mutation - but on a real
screenshot it is unconditional.

**2. Even ungated, the locator would say nothing.** With the guard removed the
span over that rect is `rows (4, 1351)` and `columns (0, 2544)` - the whole
rect, on both axes, on every file tried.

**3. The reason is `textured_span`'s "outermost" rule, and it is fundamental
here.** The signal itself is excellent - but only when the *other* axis is
already clipped to the page. Columns measured over the marked rect's rows:

```
file                      located x     marked x       left off   right off
Screenshot (3187).png       984..1560     987..1561          -3          -1
Screenshot (2744).jpg       948..1596     950..1589          -2          +7
2025-10-20 15_37_25.png    1006..1539    1008..1536          -2          +3
Screenshot (2630).jpg       955..1591     958..1593          -3          -2
Screenshot (2582).jpg      1006..1539    1008..1532          -2          +7
Screenshot (1661).png      1073..2556    1077..1470          -4       +1086
```

Five of six land within a few pixels, always on the safe side on the left. But
that requires knowing the row extent, and the row extent requires knowing the
column extent: rows measured over the marked rect's *columns* give `12..1435`
every time, because browser chrome above and the taskbar below are textured
inside those columns.

**Alternating the axes does not break the deadlock.** Starting from the rect
the pipeline hands over and narrowing columns, then rows, then repeating, it
reaches a fixed point on the first or second pass, essentially where it
started:

```
Screenshot (3187).png   start x 0..2545 y 40..1392
  pass 1  x 0..2545  y 44..1392
  pass 2  x 0..2545  y 44..1392   (fixed point)
  contains marked: true   within marked+11: false
```

Six files, same shape: a fixed point that still spans the whole width. The
cause is the rule itself. `textured_span` returns the **outermost** textured
lines, and on a real screenshot there is textured content - browser UI, a
second window, the taskbar - all the way out to the image edge, so the
outermost textured column is column 0 and there is no progress to make.

#### What this means for the premise

`## Context` says thresholding per-row spread at 8 "locates the art boundary at
0 px offset for 15 of 19 entries", and the table under it is headed *gutter
inside marked rect*. That measurement asked how much flat gutter sits inside
the rectangle a person had already drawn. It did not establish that the same
threshold can **find** that rectangle starting from the whole screenshot, and
the three measurements above are what happens when it is asked to: the
statistic separates gutter from art beautifully at a known boundary and cannot
locate one from the outside, because "outermost textured line" is the wrong
search on an image whose outermost content is always textured.

That is a finding about the *premise*, not a defect in the code below it. The
locator does exactly what AC-1, AC-2 and AC-5 specify, the fade fixture is a
fair statement of AC-2's scene, and AC-3 passes through the real `decide`.
MC-019 remains blocked, and what unblocks it is a search rule that can find an
**interior** low-spread boundary pair rather than the outermost textured line.
