## Context

[`EPIC-07`](../epics/EPIC-07.md) `## Stories` item 1, second half. MC-036 gave
the manifest a validated `split` field and assigned every pre-existing entry to
`"tuning"`. The held-out set is empty. This story fills it, with **new
screenshots that no v1 tuning has ever seen**, and puts floors under both sets
so the emptiness cannot come back.

Read MC-036's `## Context` first; the contamination argument is there and is not
repeated. The one-line version: the existing 28 entries are contaminated — six
investigations fitted thresholds against them — so held-out has to be built from
new files, and this story is the only place new files can arrive.

**The user supplies and marks the screenshots. An agent cannot.** `corpus.md`
is explicit that a mark is a person's call and that nothing in the repository
can check a rectangle is the right rectangle. This is MC-018's situation
repeated, and MC-018 is the procedure to copy: `chore` under SCAFFOLD, the user
drops files into `fixtures/corpus/` and fills in the manifest, the Lead PO
writes the validation and runs the gates.

**Why `chore` and not `feature`.** Same reason as MC-036, verified there:
`paths.conf` classifies `fixtures/**` and `**/tests/**` as `test`, GREEN may
write neither, and there is no production code that could make a criterion about
corpus composition pass. See MC-036 `## Context`.

**Gate that fails if this story's artifact breaks: `unit` (required).** The new
floors go in `crates/engine/tests/corpus_manifest.rs`, non-`#[ignore]`d, for the
reason MC-036's `## Out of scope` gives. `required_gates` is `[]` because `unit`
already binds. It must stay that way: a count assertion parked in `corpus.rs` or
`corpus_accuracy.rs` runs only under the optional, `slow` `integration` gate and
would let `All required gates passed` print over an unfilled held-out set.

### The hard constraint nobody will think of until it bites

`MAX_BYTES` is 60 MB (MC-018 AC-4, so the repository stays clonable without
LFS), and the corpus is **22 MB across 28 files today**. That leaves ~38 MB, and
the format of a new capture matters more than its count:

| Kind | Observed per-file | 34 new files would cost |
|---|---|---|
| 2560x1440 PNG capture | 0.77 – 1.47 MB (~1.1 MB) | ~37 MB → total ~59 MB, **over the line in practice** |
| 2560x1440 JPEG capture | 0.21 – 0.28 MB (~0.25 MB) | ~8.5 MB → total ~31 MB |
| even mix, 17 of each | — | ~23 MB → total ~45 MB |

So: a PNG-heavy growth of this size does not fit, and the ceiling is a DONE
story's acceptance criterion — raising it is the user's call, not an agent's.
An even mix fits comfortably and keeps the existing 18 PNG / 8 JPEG / 2 WebP
balance from skewing, which matters because JPEG ringing near a panel edge is
exactly the kind of thing a v2 edge rule will be sensitive to. **Recommendation:
roughly half the new captures as JPEG, and do not exceed ~17 new PNGs.**

### Numbers proposed here need the user's confirmation before this story leaves PLANNED

Criteria freeze on leaving PLANNED, so this is the moment. Everything in the
next section marked **[confirm]** is a proposal with reasoning, not a settled
fact. The reasoning is given so it can be argued with.

**Why 20 held-out marked entries and not fewer.** Read out of MC-018 AC-1's own
reasoning, which is already a `const` in the test file: *"Below this the corpus
cannot support a 'nine in ten' claim with any resolution: at twenty entries one
miss is five percent."* The bar EPIC-07 inherits is 20 of 21 with zero clips —
about 95%. A held-out set of 15 moves 6.7% per entry, so the reported number
would be decided by which screenshot happened to land in it. 20 is the smallest
set on which a 95% claim means anything, and it is a number this project already
committed to rather than one invented here.

**Why 34 new files and a 29:20 marked split.** 21 existing marked entries are
locked to tuning by MC-036, so the ratio is not free: to reach 20 held-out the
corpus needs at least 20 new marked entries, and the tuning set should grow too
— v2 is fitting two new signal classes (2D structure, known site furniture) and
fitting them on 21 entries is how v1 got here. 28 new marked entries gives
tuning 29 (21 + 8) and held-out 20, a 59:41 split, which is the usual shape for
a corpus this small where held-out resolution is the binding constraint. 6 new
flag entries, 4 of them held-out, keeps flags near their current quarter share
so the flag-and-copy behaviour is also measured on unseen data.

**Coverage beats count, and it is not a slogan.** v1's failure causes cluster by
site furniture: a site's navigation bar is pixel-identical across every
screenshot from that site, which is the whole premise of EPIC-07's story 3. A
screenshot from a site the corpus does not already contain is worth several from
one it does. Twenty held-out entries from one reader would measure almost
nothing.

### Two questions only the user can answer

**Q1 — is the split stratified by site, or site-disjoint?** They measure
different things and the difference is not cosmetic.

- *Stratified* (every site appears in both sets): measures whether a rule
  generalises to unseen **pages**. Optimistic for anything that learns site
  furniture, because the held-out entries share a pixel-identical navigation bar
  with entries the rule was tuned on.
- *Site-disjoint* (whole sites held out): measures whether a rule generalises to
  an unseen **reader**. Honest, and pessimistic for story 3 by construction —
  which may be the right answer to get, since story 3's approach is exactly the
  one stratification would flatter.

**Recommendation: stratified, plus at least one site held out entirely.** Both
numbers then come out of one corpus, and a gap between them is itself the
finding. It costs only that the user contributes enough files from one extra
site to make it a whole-site holdout.

**Q2 — does every entry gain a `site:` tag?** AC-4 below cannot be written
without one: "spans at least N sites" is not checkable unless the site is
recorded. A `site:<slug>` tag needs no parser change — `documented_tag_vocabulary()`
reads any table row whose first cell is a backticked tag — but it does need the
user to name the site for each of the 28 existing entries as well as the new
ones, because an agent reading a site off a screenshot is guessing, and
`corpus.md` is explicit that a guessed tag is worse than an absent one. If the
user declines, **AC-4 is dropped at PLANNED** and site coverage stays an
instruction to the person collecting files rather than an assertion.

Everything above marked **[confirm]** was put to the user and answered. The
answers are below; the criteria that follow are the answers, not the proposals,
and they are frozen from here.

| Question | Answer |
|---|---|
| **Q1** split rule | **Stratified, plus at least one whole site held out.** Recorded in AC-6 and enforced by AC-4's "≥2 unseen sites" clause — see below |
| **Q2** `site:` tag | **Held-out entries only** — see the revision below. The pre-EPIC-07 28 carry no `site:` tag |
| AC-1 held-out marked floor | **20**, as proposed |
| AC-2 held-out flag floor | **4**, as proposed |
| New file count | **24, not 34** — the user's change. See below |

| AC-4 `H` (held-out spans ≥H sites) | **4** |

**Q1 needs no assertion of its own, and that is worth spelling out.** Tuning is
frozen at exactly the 28 pre-EPIC-07 entries and every new entry is held out, so
a site appears *only* in held-out precisely when no pre-EPIC-07 entry carries
it. "At least one whole site held out" and AC-4's "at least 2 sites carried by
no pre-EPIC-07 entry" are therefore the same clause, and the stricter of the two
is the one written down. A second assertion saying the same thing in different
words is a second thing to keep in step, not a second check.

**Why that clause says "no pre-EPIC-07 *entry*" and not "no pre-EPIC-07 *marked*
entry"**, which is how AC-4 originally phrased it. A site carried only by a
pre-EPIC-07 *flag* entry would count as unseen under the looser wording, and it
is not: MC-026's decision gates were fitted against the flag entries too. The
tighter wording is also the mechanically simpler one — `PRE_EPIC_07_ENTRIES` is
a flat list of 28 names with no rect/flag distinction in it.

**Why 24 new files and not 34: the user declined to grow the tuning set.**
`## Context` argued tuning should grow to 29 marked because v2 is fitting two
new signal classes on the 21 that got v1 here. The user's ruling is that
held-out is what the new files are for, and tuning stays at its 21 marked / 7
flag. So the 24 new files are 20 marked + 4 flag, **all held-out**, and the
split is 28 tuning : 24 held-out by entry, 21 : 20 by marked entry. The argument
for growing tuning is not withdrawn — it is deferred, and any later story that
wants it is adding files, not reassigning these.

*Consequence for the byte budget, which gets easier:* 24 files against 38.67 MB
of headroom (measured 2026-09-18: the corpus is 22,361,231 bytes = 21.33 MB of a
60 MiB `MAX_BYTES`). An even 12/12 PNG/JPEG mix costs ~16 MB → ~37 MB total.
Even **all 24 as PNG** now fits, at ~26 MB → ~48 MB, though it would leave only
12 MB of headroom for every story after this one. The mix recommendation stands
for the JPEG-ringing reason in `## Context`, not for the bytes any more.

### Q2 revised the same day, after the user began marking

The first answer to Q2 was "tag all 52". On working through it the user declined
to tag the pre-EPIC-07 28, and **the repository's own doctrine says they are
right**: `corpus.md` rules that *a guessed tag is worse than an absent one*.
Attributing a reader to a screenshot captured in January 2026 is precisely the
situation that manufactures guesses, and 28 unreliable tags would have produced
a check that looks rigorous while resting on recall nobody can audit — the exact
failure this corpus keeps writing rules against.

So the pre-EPIC-07 entries carry **no `site:` tag at all**, and AC-4 now
quantifies over held-out entries only.

**What replaces the per-file attribution, so Q1 stays enforceable.** The
"≥2 unseen sites" clause is the only thing that enforces Q1's whole-site
holdout, and it needs to know which readers the old corpus came from. Naming
that **as a set** is a different and far easier act of recall than attributing
28 files one by one: the user declares the readers the pre-EPIC-07 corpus was
captured from, that set is pinned as `PRE_EPIC_07_SITES` in `corpus.md` and read
into the test, and "unseen" means a held-out slug outside it.

This is a person's ruling pinned in `corpus.md`, which is how this corpus
already handles its marking rule, its diagonal gutters and its gutter-crossing
band. It is no weaker than the rest of the corpus and no stronger: `corpus.md`
is explicit that nothing in the repository can check a rectangle is the right
rectangle either. What it buys is that the claim is **written down and
falsifiable by the person who made it**, rather than implicit in 28 fields
filled from memory.

**Why `S` was dropped.** AC-4 proposed "the corpus spans at least S distinct
sites" with S "fixed with the user once they list the sites in the existing 21".
Nobody in this repository knows that number, and it is not knowable until the
user tags the existing entries — which happens *during* SCAFFOLD, after the
criteria freeze. A floor chosen before the count is known is decorative, which
is the specific failure AC-4's own control clause warns about. The two clauses
that survive — held-out spans ≥4 sites, ≥2 of them unseen — are checkable
without knowing anything about the existing corpus, and the whole-corpus site
count becomes a fact the tags record rather than an assertion nobody can
justify.

## Acceptance criteria

- **AC-1** — Given the loaded corpus, when the held-out entries with a rect are counted, then there are **at least 20**. *Control:* moving any one held-out marked entry to `"tuning"` must fail this test naming the count 19, and the whole-corpus `MIN_ENTRIES` test must stay green while it does — a floor that fires only when the total drops is not measuring the split.
- **AC-2** — Given the loaded corpus, when the held-out entries expecting `"flag"` are counted, then there are **at least 4**. *Control:* as AC-1, with a flag entry; and the test must fail when all held-out entries carry rects, which is the way this criterion is silently satisfiable if it is written as a count over all held-out entries rather than over flags.
- **AC-3** — Given MC-036's `PRE_EPIC_07_ENTRIES` list, when the manifest is validated, then **no** held-out entry's file name appears in it, and the held-out set is non-empty. This is MC-036's AC-2 read in the other direction; it was vacuous there because held-out was empty, and it is the assertion that makes the held-out number mean anything. *Control:* flipping one pre-EPIC-07 entry to `"held-out"` must fail it by name.
- **AC-4** — Given every **held-out** manifest entry, when validated, then each carries **exactly one** tag matching `site:<slug>` and present in `corpus.md`'s vocabulary table; the held-out set spans **at least 4 distinct sites**; and **at least 2** of those are outside `PRE_EPIC_07_SITES` — the set of readers the user declares the pre-EPIC-07 corpus was captured from, pinned in `corpus.md` and read into the test. **Entries in `PRE_EPIC_07_ENTRIES` carry no `site:` tag and are not required to**, by the user's ruling of 2026-09-18 recorded below. *Control:* a held-out entry with two `site:` tags, and one with none, must each fail by name; a `site:` tag absent from the vocabulary table must fail; and **collapsing every held-out entry onto slugs inside `PRE_EPIC_07_SITES` must fail the "2 outside" clause while leaving the "at least 4 sites" clause satisfied** — if the two clauses cannot be made to disagree, one of them is decorative.
- **AC-5** — Given the grown corpus, when `corpus_manifest.rs` runs, then every MC-018 and MC-033 assertion still holds unchanged: every named file exists and decodes, every rect lies inside its image, the nine required tags are still covered, every tag is in the documented vocabulary, the `diagonal-gutter` list is still exactly two entries, and the whole directory is still under 60 MB. New files do not get to weaken the existing checks.
- **AC-6** — Given `docs/wiki/corpus.md`, when this story is done, then its split section records **how** the split was assigned — **stratified, plus at least one whole site held out**, the user's ruling of 2026-09-18 — by whom and on what date, and states that the held-out set is scored once, at the end of a v2 attempt, and is never tuned against. It also records that the 24 new entries are held out in their entirety and that tuning was deliberately not grown, so the next agent does not read the 21:20 marked ratio as an accident. A split whose assignment rule is not written down is a split the next agent can quietly re-draw.

## Out of scope

- **Any detection rule.** This story adds files and counts. It does not touch
  `crates/core/src/**`, `Tuning`, any threshold, or anything that looks at a
  pixel. Nothing here is scored against anything.
- **Scoring the held-out set.** Not once, not "just to see". The set's value is
  that it has never been looked at; the first look belongs to whichever EPIC-07
  story earns one, and `corpus.md` will say so (AC-6). Running the existing
  accuracy harness across the new entries to "check they are reasonable" spends
  the held-out set before v2 starts.
- **Re-marking anything.** The marks stay tight, by the user's decision of
  2026-09-17. MC-031 section 9 Option C was declined. No existing rectangle
  changes.
- **Changing any existing entry's `split`.** All 28 are `"tuning"` and stay so.
  If a new entry turns out to be a duplicate of an existing one, it is dropped,
  not swapped.
- **The column axis.** Settled at 20 of 21 and not reopened.
- **Applying `overhang-text`, or adding a third `diagonal-gutter` entry.** Both
  are a person's call under `corpus.md`, and both are a survey rather than a
  side effect of adding files. If the user tags new entries with either while
  marking, that is fine and needs no story; an agent inferring one is not.
- **Raising the 60 MB ceiling.** If the growth genuinely will not fit, stop and
  put it to the user — it is MC-018 AC-4 and a DONE story's criterion.
- **`gates.sh --fast` as sufficient evidence.** `integration` is `slow`, and
  `corpus.rs` / `corpus_accuracy.rs` decode every file in the corpus. Adding 24
  images makes that gate slower and is exactly the kind of change `--fast` hides.
  Run the full gates.
