## Context

First behaviour of `cropper-core`: the brief's feature 1, first mechanism -
"trim uniform solid-colour borders (white, black, grey gutters) on all four
sides". Introduces the `Luma` plane and `Rect` types from
`architecture.md` (Data model) and `trim::trim_uniform`. Pure function, no
I/O. Fixtures are generated in `crates/core/tests/common/` from a recipe (art
rect with textured content; per-side border colour and width; which pair of
sides spans the full extent) so the expected rect is known exactly.

Trimming is iterative: on each pass every side drops its outermost rows or
columns that are uniform *within the current rect*, and passes repeat until
no side changes. This is what makes both border layouts work - full-width
top and bottom bands, or full-height left and right gutters - without the
detector knowing which it has. Constants come from
`Tuning::default()` (`uniform_tolerance = 10`).

Gate that fails if this breaks: `unit`.

## Acceptance criteria

- **AC-1** - Given a `Luma` whose art rect is textured (every row and every column of the art region contains at least two pixels differing by more than `uniform_tolerance`) and whose four borders are each a single colour of width 0..=200 px (colours may differ per side; either the top/bottom bands span the full width or the left/right gutters span the full height), when `trim_uniform(&luma, &Tuning::default())` runs, then it returns `Some(rect)` equal to the art rect exactly, for every combination the generator produces including width 0 on any side.
- **AC-2** - Given border pixels that deviate from the side's border colour by at most `uniform_tolerance` (10), when trimmed, then those rows and columns are still removed; given a border row whose pixels deviate by `uniform_tolerance + 1` (11), then that row is kept and the returned rect starts at it. *Control on the number:* the same fixture at deviation 11 must not be trimmed.
- **AC-3** - Given a `Luma` every pixel of which is within `uniform_tolerance` of one value, when trimmed, then the result is `None`.
- **AC-4** - Given a `Luma` whose art fills the whole image (all four borders width 0), when trimmed, then the result is `Some(Rect { x: 0, y: 0, w, h })`.
- **AC-5** - Given the two-layout fixture from AC-1 with all four borders non-zero and four different colours, when trimmed, then the result is the art rect under both layouts (this is the iterative pass; a single top-then-sides pass fails one of the two layouts, which is the control on the mechanism).

## Model guidance

Model: default. Oracle partition:

- **Settled**: `uniform_tolerance = 10`. Read it from `Tuning::default()`; do not tune.
- **Mechanical**: the `Luma { width, height, data }` and `Rect { x, y, w, h }` shapes and the signature `trim_uniform(&Luma, &Tuning) -> Option<Rect>`. Pin them.
- **Oracle-free**: none; the generator knows the true rect.

The generator (`tests/common/mod.rs`) is the most reusable thing this story
writes: MC-004..MC-007 extend it. Give it a seeded RNG and a `Recipe` struct.

## Out of scope

Edge detection (MC-004), chrome removal (MC-005), the outward margin
(MC-006), flag reasons (MC-007), RGB-to-luma conversion (MC-008; tests
build `Luma` directly), any tolerance for a stray pixel inside an otherwise
uniform row - a row is uniform or it is not.
