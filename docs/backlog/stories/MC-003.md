## Context

First behaviour of `cropper-core`: the brief's feature 1, first mechanism -
"trim uniform solid-colour borders (white, black, grey gutters) on all four
sides". Introduces the `Luma` plane and `Rect` types from
`architecture.md` (Data model) and `trim::trim_uniform`. Pure function, no
I/O. Fixtures are generated in `crates/core/tests/common/` from a recipe (art
rect with textured content; per-side border colour and width; which pair of
sides spans the full extent) so the expected rect is known exactly.

Trimming is iterative: on each pass every side drops its outermost rows or
columns that are uniform *within the current rect*, and passes repeat until
no side changes. This is what makes both border layouts work - full-width
top and bottom bands, or full-height left and right gutters - without the
detector knowing which it has. Constants come from
`Tuning::default()` (`uniform_tolerance = 10`).

**What "uniform" means** — settled with the user on 2026-09-10, while this
story was still PLANNED, and `architecture.md` updated to match. A row or
column segment *within the current rect* is uniform iff its spread is at most
`uniform_tolerance`: `max - min <= 10`. There is no reference colour and no
median. The rule is symmetric, and it makes AC-1's texture precondition ("two
pixels differing by more than `uniform_tolerance`") exactly the negation of
uniform, so a fixture the generator declares textured can never be trimmed.
The alternative considered — every pixel within `uniform_tolerance` of the
segment's median, which is what `architecture.md` said before — lost because
an art row of `{c-10, c, c+10}` satisfies AC-1's precondition and would still
be judged uniform under it. AC-3 was tightened to match in the same breath;
the AC-2 and AC-3 fixtures deviate in one direction only (`v ..= v + 10`), so
they satisfy both readings literally and the choice is not load-bearing on
them.

Gate that fails if this breaks: `unit` (required repo-wide, and `coverage`
judges the new module too). Nothing here needs an optional gate escalating,
so `required_gates` stays empty.

## Acceptance criteria

- **AC-1** - Given a `Luma` whose art rect is textured (every row and every column of the art region contains at least two pixels differing by more than `uniform_tolerance`) and whose four borders are each a single colour of width 0..=200 px (colours may differ per side; either the top/bottom bands span the full width or the left/right gutters span the full height), when `trim_uniform(&luma, &Tuning::default())` runs, then it returns `Some(rect)` equal to the art rect exactly, for every combination the generator produces including width 0 on any side.
- **AC-2** - Given border pixels that deviate from the side's border colour by at most `uniform_tolerance` (10), when trimmed, then those rows and columns are still removed; given a border row whose pixels deviate by `uniform_tolerance + 1` (11), then that row is kept and the returned rect starts at it. *Control on the number:* the same fixture at deviation 11 must not be trimmed.
- **AC-3** - Given a `Luma` every pixel of which lies within a band of `uniform_tolerance` — that is, `max - min <= 10` over the whole image — when trimmed, then the result is `None`.
- **AC-4** - Given a `Luma` whose art fills the whole image (all four borders width 0), when trimmed, then the result is `Some(Rect { x: 0, y: 0, w, h })`.
- **AC-5** - Given the two-layout fixture from AC-1 with all four borders non-zero and four different colours, when trimmed, then the result is the art rect under both layouts (this is the iterative pass; a single top-then-sides pass fails one of the two layouts, which is the control on the mechanism).

## Amendments

**AC-3, wording — 2026-09-10, approved by the user (Ryan) in the PLANNED
phase, before the story left it.**

- It said: *"Given a `Luma` every pixel of which is within `uniform_tolerance`
  of one value, when trimmed, then the result is `None`."*
- It now says: *"Given a `Luma` every pixel of which lies within a band of
  `uniform_tolerance` — that is, `max - min <= 10` over the whole image — when
  trimmed, then the result is `None`."*
- No other criterion changed.

**Why.** The story never defined what makes a row uniform, and the two
candidate definitions each contradicted a different criterion, so the readings
led to different code and different fixtures:

- *spread* (`max - min <= 10`) makes AC-1's texture precondition — "two pixels
  differing by more than `uniform_tolerance`" — exactly the negation of
  uniform, which is what AC-1 needs to be true for every fixture the generator
  emits. But AC-3's old wording permitted a spread of 20 (`v-10 ..= v+10`),
  which this rule refuses to trim, returning `Some` where AC-3 demands `None`.
- *within tolerance of the median*, which `architecture.md` stated at the
  time, satisfies the old AC-3 but breaks AC-1: an art row of
  `{c-10, c, c+10}` holds two pixels 20 apart and is still within 10 of its
  own median, so a row the generator declares textured would be trimmed away.

Put to the user with both readings and their counterexamples; the user chose
the spread rule. AC-3 was tightened to match it — a clarification of the same
intent ("nothing to crop"), not a new requirement, and the AC-2 and AC-3
fixtures deviate in one direction only (`v ..= v + 10`) so they satisfy either
reading literally. `docs/wiki/architecture.md`'s step 1 was corrected in the
same edit; its median wording is dead.

This entry exists even though the change was made in PLANNED, where criteria
are not yet frozen, because `check-boundaries.sh` compares the criteria
against the base branch and cannot see *when* in the branch's history the edit
happened — only that it did.

## Model guidance

Model: default. Oracle partition:

- **Settled**: `uniform_tolerance = 10`. Read it from `Tuning::default()`; do not tune.
- **Settled**: the uniformity rule in the Context — `max - min <= uniform_tolerance` over the segment inside the current rect. Do not invent a reference colour, a median or a mean.
- **Mechanical**: the `Luma { width, height, data }` and `Rect { x, y, w, h }` shapes and the signature `trim_uniform(&Luma, &Tuning) -> Option<Rect>`. Pin them.
- **Oracle-free**: none; the generator knows the true rect.

The generator (`tests/common/mod.rs`) is the most reusable thing this story
writes: MC-004..MC-007 extend it. Give it a seeded RNG and a `Recipe` struct.

## Test plan

Two files, 19 tests, all in `crates/core/tests/`. Nothing here is
oracle-free: the fixture generator knows the true art rect, so every expected
value is an exact `Rect` or an exact `None`. `uniform_tolerance` is read out
of `Tuning::default()` and pinned by its own test; the uniformity rule is the
one settled in the Context (`max - min <= uniform_tolerance` over the segment
*within the current rect*), and nothing in the suite re-derives it.

### `crates/core/tests/common/mod.rs` - the generator

The reusable artefact. MC-004..MC-007 extend it, so it is a generator, not a
bag of images. Deterministic end to end: the same `Recipe` renders the same
bytes on any machine.

| Item | What it is |
|---|---|
| `Rng(u32)` | hand-rolled 32-bit xorshift, the same shape `crates/app/tests/cli.rs` uses. `new(seed)` (seed 0 is remapped, it is a fixed point of xorshift), `between(lo, hi)`. `cropper-core` has exactly one dev-dependency and RED may not add another. |
| `Layout::{Bands, Gutters}` | which pair of sides spans the whole image. `Bands` = full-width top/bottom, gutters only between them; `Gutters` = full-height left/right, bands only between them. |
| `Border { thickness, colour, spread }` | one side. Every border pixel is `colour` or `colour + spread`, alternating on a checkerboard, so **every** border row or column segment of >= 2 px contains both endpoints and has a spread of exactly `spread`. `Border::solid(t, c)` is `spread: 0`. |
| `Recipe { art_w, art_h, top, right, bottom, left, layout, seed }` | the whole image. `Recipe::new(w, h)` is art with no borders at all; every other fixture is `Recipe { .., ..Recipe::new(w, h) }`. |
| `Recipe::{width, height, art_rect, render}` | image is `left + art_w + right` by `top + art_h + bottom`; `art_rect()` is the answer; `render()` is the `Luma`. |
| `flat_band(w, h, low, spread)` | an image whose every pixel is `low` or `low + spread` on a checkerboard, so every row and every column has a spread of exactly `spread`. The sharpest available probe of the settled rule. |
| `any_recipe(max_border)` | the proptest strategy: art 2x2..24x24, four independently drawn thicknesses `0..=max_border` and colours `0..=255`, either layout, random seed. |

**Why the art is textured by construction.** Art pixels alternate between
`40..=60` and `200..=220` on a checkerboard, jittered by the seeded RNG. Any
art row or column of at least two pixels therefore holds one of each, so its
spread is at least 140. Under the settled rule that is exactly the negation of
"uniform", so no art row or column can ever be trimmed - which is AC-1's
precondition, satisfied mechanically rather than hoped for. Measured over 200
recipes: the smallest spread of any art row was 141, of any art column 145.

**Why `render` paints the spanning pair last.** Both layouts paint the art,
then both border pairs; the pair that spans the whole image goes second and
overwrites the other pair's ends. That single line is the entire difference
between the layouts, which is what makes AC-5 a one-field change.

**How AC-5 catches a non-iterative trim.** Both AC-5 tests use one recipe:
art 30x20, top 6 px (colour 10), right 5 (250), bottom 7 (128), left 4 (64);
image 39x33; art rect `{4, 6, 30, 20}`. A trim that makes a *single* pass over
the four sides gets exactly one of the two layouts wrong, whichever order it
visits them in - so the pair catches both orderings:

- top-then-sides, `Gutters`: row 0 spans the left gutter (64), the top band
  (10) and the right gutter (250), so it is not uniform and the top is
  refused. The gutters then trim, which leaves row 0 uniform inside the new
  rect - but a single pass never comes back to it. Wrong answer
  `Some(Rect { x: 4, y: 0, w: 30, h: 33 })`, observed verbatim (below).
- sides-then-top, `Bands`: column 0 spans the top band (10), the left gutter
  (64) and the bottom band (128), so the left is refused; the bands then trim
  and are never revisited. Wrong answer
  `Some(Rect { x: 0, y: 6, w: 39, h: 20 })`, also observed.

**Out of scope, deliberately not asserted.** A zero-sized `Luma`: the story
does not constrain it, so nothing here does either. No test tolerates a stray
pixel inside an otherwise uniform row - `flat_band` and `Border` make every
segment's spread exact, so the boundary is 10 against 11 and nothing in
between.

### Export shape the tests pin

Nothing below is negotiable: a test already imports each name and a different

### Notes for the implementer

- **The rule, once more, because it is the only place this story can go
  wrong.** A row or column segment, measured *within the current rect*, is
  uniform iff `max - min <= t.uniform_tolerance`. No reference colour, no
  median, no mean, and no per-side memory. The wording about "the median of
  the outermost row/column" that used to be in `architecture.md` is dead;
  the file was corrected on 2026-09-10.
- **Iterate.** On each pass every side drops its outermost uniform rows or
  columns, and passes repeat until no side changes. Draining a side greedily
  before moving to the next is fine - the reference does that and reaches the
  same fixed point - but you must go round again while anything changed.
- **Watch the empty rect.** Test the emptiness of the rect after *each* side,
  not once at the end: a fully uniform image drains all its rows on the first
  side, and a column scan over a zero-height rect has no `max` or `min`. The
  three `None` tests are the ones that will catch this.
- **Deliberately unconstrained**, so it stays your choice: a zero-sized
  `Luma` (the story puts it out of scope - assert nothing about it, and if
  you add an in-module test for the guard, that is a `src/` test written in
  GREEN, not a change here); the order the four sides are visited in; whether
  a side is drained greedily or one row per pass; whether `Luma` gets derives;
  which other `Tuning` fields exist; where in `crates/core/src/` the module
  lives, as long as `cropper_core::trim::trim_uniform` and the three types at
  the crate root resolve; whether `Rect` gains helper methods.
- **Coverage.** The new module is judged by the `coverage` gate at 95 % lines
  workspace-wide. Every branch of the rule has a test here (all four sides
  individually, both layouts, the tolerance boundary from both directions,
  the three `None` paths, the tuning-is-read path), so a straightforward
  implementation should come out at or near 100 % without extra in-module
  tests. `crates/core/src/lib.rs`'s `Dimensions` from MC-001 is still covered
  by `tests/scaffold.rs`.
- **`floor | unit | 1` in `project.conf` is now understated.** The floor reads
  the first `test result: ok. N` cargo prints, which is the first test binary
  that ran at least one test; this story adds 19 tests to `crates/core`.
  Raising it is the Lead PO's call (`project.conf` is theirs), not the Test
  Developer's, so it is flagged here rather than changed. Nothing fails
  because of it - the floor is a minimum.
- **Files touched in RED:** `crates/core/tests/trim.rs` (new),
  `crates/core/tests/common/mod.rs` (new), and this story's `## Test plan` and
  `## Handoff: RED -> GREEN`. No source, no `Cargo.toml`, no `.gitignore`.
