## Context

**MC-010 can silently destroy one of the user's files.** `naming::plan_outputs`
remembers what the batch has claimed in a `HashSet<PathBuf>`, and `PathBuf`
equality is byte-wise, while the filesystem this program ships on is not. So
two inputs whose names differ only by letter case are planned as two names and
written as one file.

Found while MC-010 was in REVIEW, measured there rather than guessed, and left
unfixed on purpose: no acceptance criterion of MC-010 mentions case, and
folding it in would have been an un-amended change to frozen behaviour. This
story is where it gets criteria of its own.

**The reproduction**, end to end on this NTFS volume, with no Rust and no
planner involved - the filesystem alone:

    $ printf 'FIRST FILE'  > casetest/a.png
    $ [ -e casetest/A.PNG ] && echo YES
    YES                      <- the disk already says A.PNG exists
    $ printf 'SECOND FILE' > casetest/A.PNG
    $ ls -1 casetest | wc -l
    1                        <- one file, not two
    $ cat casetest/a.png
    SECOND FILE              <- the first file's bytes are gone

`x/a.png` + `y/A.PNG` is not contrived. It is exactly the two-source-folders
case `docs/wiki/architecture.md` decision 7 exists for, and EPIC-03's "done
when" says "nothing ever overwritten" without qualification.

**Only the in-batch half is wrong.** `Path::exists` is itself case-insensitive
on Windows, so a name already *on disk* is found whatever its case: with
`out_dir/a.png` present, MC-010 already plans `A.PNG` as `A (2).PNG`. The
defect is entirely in the set the batch keeps of its own claims. AC-5 pins the
disk half so that fixing the batch half cannot regress it.

**Why it must be fixed before MC-011.** MC-011 is the story that actually runs
a batch, and it is the first point at which a user can hand the program two
files at once. `MC-011.depends_on` names this story, so `phase.sh set` refuses
to start it while this one is not DONE.

Gate that fails if this breaks: `unit`.

## Acceptance criteria

- **AC-1** - Given an empty `out_dir` and inputs `[x/a.png, y/A.PNG]`, when `plan_outputs` runs, then it returns `[out_dir/a.png, out_dir/A (2).PNG]`: the second is suffixed because its name differs from the first only by case, and its own case survives in both stem and extension.
- **AC-2** - Given those two planned paths, when `process_file` writes to each in turn, then `out_dir` holds **two** files and the bytes written by the first call are unchanged by the second. *Control:* under MC-010's planner this same scenario leaves **one** file holding the second call's bytes (reproduced above). A fix that does not flip this number has not fixed anything.
- **AC-3** - Given `[a.png, A.PNG, A.png]` into an empty `out_dir`, then the plan is `[out_dir/a.png, out_dir/A (2).PNG, out_dir/A (3).png]` - one counter shared across the case variants, not one counter per variant.
- **AC-4** - Given `[x/Shot.PNG]` into an empty `out_dir`, then the plan is `[out_dir/Shot.PNG]`, byte-identical to the input's own file name. *Control on the obvious wrong fix:* an implementation that folds case by lower-casing the name it then writes returns `out_dir/shot.png` and fails here. Folding is for **comparison** only.
- **AC-5** - Given `out_dir/a.png` already on disk and inputs `[y/A.PNG]`, then the plan is `[out_dir/A (2).PNG]`. MC-010 already satisfies this through `Path::exists`; it is pinned here so that the in-batch fix cannot regress the disk half.
- **AC-6** - Given `[Ä.png, ä.png]` into an empty `out_dir`, then the plan is `[out_dir/Ä.png, out_dir/ä (2).png]`. *Basis, measured on this volume rather than assumed:* `Ä.png` and `ä.png` are one file on NTFS, as are `Д.png`/`д.png` and `I.png`/`i.png` - so an ASCII-only fold would ship a known hole. `ß.png` and `SS.png` are **two** files, and Rust's `str::to_lowercase` agrees, which is the case that shows the fold must not be "uppercase and compare".

## Model guidance

Model: default. Oracle partition:

- **Settled by measurement**: which pairs NTFS treats as one file. The four
  measurements in AC-6 and the Context were taken on this machine on
  2026-09-12 and are recorded so RED reads them out rather than re-deriving
  them. If RED cannot reproduce one, stop - that is a finding about the volume,
  not a licence to change a criterion.
- **Mechanical**: `plan_outputs`'s existing signature and the ` (n)` format,
  both unchanged from MC-010. Pin; do not restate MC-010's own criteria as new
  ones.
- **Oracle-free**: none. Every number here is a count of files or a name.

The trap worth naming for RED: the obvious wrong fix passes AC-1, AC-2, AC-3
and AC-5 and fails only AC-4. Lower-casing the *written* name makes every
collision test go green while quietly renaming the user's files. That is why
AC-4 exists and why it is phrased as a byte-identity check. MC-010's mutation
run showed this exact mutation reds exactly one assertion.

## Out of scope

- **Exact parity with NTFS's `$UpCase` table.** The rule is "fold case for
  comparison, and err toward suffixing": a spurious suffix is a cosmetic
  annoyance, a missed collision loses a file, so disagreement with the volume
  is acceptable in one direction only. Rust's `to_lowercase` agreed with NTFS
  on every pair measured, including `ß`/`SS`, but parity is not claimed.
- **Unicode normalisation** - composed `é` against decomposed `e` + U+0301.
  Already out of scope in MC-010 and still is; it is a different question from
  case.
- **Names that are not valid Unicode.** A lossy decode may conflate two genuinely
  distinct names, which produces an unnecessary suffix - the safe direction.
- **Case-insensitive comparison against what is on disk.** Already correct; AC-5
  only guards it.
- **Other filesystems.** On a case-sensitive volume this yields an occasional
  unnecessary suffix and never a lost file. The product is Windows-only
  (Explorer "Send to"), so this is recorded rather than handled.
- Anything else in MC-010's `## Out of scope`: recursion into folders, a cap on
  `n`, cleaning up a partially written file after a crash.

### The three controls, and what each one refuses to let pass

The criteria here assert that a name **is taken** when a byte comparison says
it is free. That is only a demand if this volume really does conflate the two
names; on a case-sensitive filesystem every criterion in this story would be
asking for a gratuitous suffix, and a reader could not tell.

1. `names_that_differ_only_by_case_are_one_file_on_this_volume` writes each of
   five pairs and measures four things per pair: how many files are left,
   whether the second name was already taken before it was written, whether the
   first file's bytes survived, and which name survived. **Four pairs must
   leave one file and one pair must leave two** - so the control fires in both
   directions rather than only confirming what it hopes. A volume that
   conflated everything, or nothing, breaks it. The three non-ASCII pairs are
   what make an ASCII-only fold a known hole rather than a guess.
2. `rust_case_folding_agrees_with_the_volume_on_sharp_s` records that
   `to_uppercase("\u{df}")` is `"SS"` while `to_lowercase("\u{df}")` is
   `"\u{df}"`. This is the pair that separates "lower-case and compare" from
   "upper-case and compare" - see the deliberate non-pin below.
3. `a_pathbuf_set_compares_bytes_while_the_disk_does_not` is the defect itself
   in six lines and with no `naming` involved: the `HashSet<PathBuf>` says
   `A.PNG` is free, `Path::exists` says it is taken. It is what makes "only the
   in-batch half is wrong" (Context, AC-5) a measurement rather than a claim.

### One thing deliberately not pinned, and why

**Whether the fold lower-cases or upper-cases.** No test here distinguishes
them: the only pair on which they disagree is `\u{df}` / `SS`, and upper-casing
conflates those two into one name where the volume keeps them apart - which is
a *spurious suffix*, and `## Out of scope` blesses disagreement in exactly that
direction ("a spurious suffix is a cosmetic annoyance, a missed collision loses
a file"). An upper-case fold is therefore a legitimate implementation of these
criteria and a test that forbade it would be inventing scope. Control 2 records
the fact so the next reader does not have to re-derive it; it does not assert
it of `plan_outputs`.

### Edges, and the non-goals

One, two, many: AC-4 is one input, AC-1 and AC-6 are two, AC-3 is three with
the counter at both 2 and 3. The empty batch and the single free name are
MC-010's AC-1 and are not restated here, per `## Model guidance`. There is no
fallible path to cover - `plan_outputs` returns `Vec<PathBuf>`, not a `Result`.

Of `## Out of scope`, **names that are not valid Unicode are deliberately not
pinned**, though the hazard is real: MC-010 built `suffixed` on `OsString`
precisely so an undecodable name passes through unchanged, and a fix that
reaches for `to_str().unwrap()` would panic on one. Pinning it would mean
deciding what such a name is planned as, which this story explicitly declines
to decide. It is recorded as a hazard for GREEN in the handoff instead.
Unicode normalisation, other filesystems and `$UpCase` parity are all
unpinnable for the same reason: asserting them would state a behaviour the
story leaves open.

### The export shape these tests already pin

Nothing below is a suggestion: a test already imports each name, and a
different choice is a compile error in a file GREEN may not edit. **All of it
is unchanged from what MC-010 shipped** - this story changes `plan_outputs`'s
*behaviour* and none of its surface.

```rust
// crates/engine/src/naming.rs, reached as `cropper_engine::naming::plan_outputs`
pub fn plan_outputs(out_dir: &Path, inputs: &[PathBuf]) -> Vec<PathBuf>;

// crates/engine/src/process.rs, re-exported at the crate root
pub fn process_file(input: &Path, output: &Path, tuning: &Tuning) -> FileResult;
```

What the assertions require:

* `plan_outputs` takes `&Path` then `&[PathBuf]`, and the tests pass it a
  `&Vec<PathBuf>`, a borrowed array literal and `std::slice::from_ref(&input)`.
  It returns an owned `Vec<PathBuf>` compared with `assert_eq!` against
  `vec![out.join(..), ..]`, so the returned order is the input order.
* It must not require the inputs to exist. Every input in AC-1, AC-3, AC-4,
  AC-5 and AC-6 is a bare path under a folder that was never created.
* It must not write anything: AC-1 reads `out_dir` back after planning and
  asserts it is empty, and AC-5 asserts the occupied file's bytes.
* `process_file(&input, &planned[n], &Tuning::default())` returns a value with
  a public `.outcome` field; `Outcome` is matched with
  `matches!(.., Outcome::Failed { .. })` and formatted with `{:?}`. **Do not
  add a field to any `Outcome` variant** and do not change `Failed`'s shape -
  four test files now depend on it and none may be edited in GREEN.
* `Tuning: Default`, from `cropper_core`.

**Deliberately not constrained, and GREEN's to choose:** how the fold is
computed (`to_lowercase`, `to_uppercase` - see "One thing deliberately not
pinned" in the test plan - or anything else that agrees with the volume in the
over-suffixing direction); what holds the batch's claims (a `HashSet<String>`
of folded names, a `Vec`, a set of pairs); whether the disk is asked with
`Path::exists`, `try_exists` or one cached `read_dir`; whether the search from
`n` is linear; what happens to `\u{df}.png` against `SS.png`; what happens to an
input with no file name; any cap on `n`.

### What should change the implementation approach

1. **Fold for comparison, never for the name.** AC-4 is the only criterion that
   catches the difference and it is the whole reason the story is a `fix` and
   not a rename. MC-010 built `suffixed` on `OsString` so that the input's own
   bytes reach the disk; keep the candidate an `OsStr`/`OsString` and derive a
   folded *key* beside it.
2. **Do not reach for `to_str().unwrap()`.** `## Out of scope` puts names that
   are not valid Unicode outside this story, and no test here pins one - but
   `plan_outputs` returns a `Vec`, not a `Result`, so a panic on an undecodable
   name is a crash with nowhere to go. `to_string_lossy()` is the documented
   safe route and the story already says what it costs: two genuinely distinct
   undecodable names may fold together and produce an unnecessary suffix, which
   is the safe direction. This is a hazard, not a criterion; if you find
   yourself wanting a test for it, that is an amendment conversation.
3. **The disk half is already right - do not replace it.** `Path::exists` is
   case-insensitive on this volume (control 8, measured). A fix that switched
   to a cached `read_dir` and compared names byte-wise would *regress* AC-5
   while passing AC-1 to AC-3. If you cache the listing, fold it too.
4. **Only the in-batch set changes.** Context and control 7 both say so, and
   `tests/naming.rs`'s 14 tests are the regression net: they must stay 14/14.
5. **Plan sequentially, and keep it that way.** MC-011 writes in parallel; the
   whole reason `plan_outputs` exists is that "find a free name, then write it"
   inside a worker is a race. No test here can catch that, so it is stated.
6. **Expected counts after GREEN**: `cargo test --workspace` **228 passed, 0
   failed** - today's 224 passed plus this file's 4 failures flipping. Coverage
   should move very little: the fix is a handful of lines in a module already
   at 100%.

### The fold's direction is not pinned, and that is correct

The Test Developer flagged that no test distinguishes a lower-case fold from an
upper-case one, and asked whether a criterion was missing. **It is not, and the
reasoning is theirs and right.**

The only pair that separates the two directions is `ß`/`SS`. Lower-casing keeps
them distinct, matching the volume, which treats them as two files.
Upper-casing conflates them - Rust maps `ß` to `SS` - and produces a spurious
suffix on a pair that did not need one. `## Out of scope` blesses exactly that
outcome: *"a spurious suffix is a cosmetic annoyance, a missed collision loses
a file, so disagreement with the volume is acceptable in one direction only."*
An upper-case fold is therefore a legitimate implementation of these criteria,
and forbidding it would be a criterion this story does not have.

Recorded rather than fixed, because the distinction is real and the next agent
should not read the absence of a test as an oversight.

### One hazard GREEN must not walk into

`plan_outputs` returns a `Vec`, not a `Result`. A fold reached through
`to_str().unwrap()` **panics** on a name that is not valid Unicode, with
nowhere to report it - in a function whose whole purpose is that nothing is
lost. `## Out of scope` says such names may be conflated (an unnecessary
suffix, the safe direction); it does not say they may crash the program.
`to_string_lossy` has the required behaviour and no panic. Flagged here because
it is invisible until it happens and no test pins it.
