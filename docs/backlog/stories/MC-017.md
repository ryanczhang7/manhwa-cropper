## Context

The brief's performance constraint, made a gate: a batch of 100 screenshots
between 1080p and 4K completes in under 10 seconds on the user's machine.
The test lives in `crates/engine/tests/perf.rs`, is `#[ignore]`d so
`cargo test --workspace` (the `unit` gate, debug build) does not run it, and
is run in release mode by the `integration` gate
(`cargo test --workspace --release -- --ignored`). That gate is optional for
the repo and `slow`, so this story requires it in its frontmatter; without
that, every required gate passes with this story's only claim unrun.

Fixture generation (100 PNGs written to a temp dir) is excluded from the
timed region and may itself take a while; that is why the gate is slow.

Gate that fails if this breaks: `integration`, required by this story.

## Acceptance criteria

- **AC-1** - Given 100 RGB8 PNGs generated from recipes with uniform borders and a chrome band - 40 at 1920x1080, 30 at 2560x1440, 30 at 3840x2160 - in a temp dir, when `batch::run` processes them into another temp dir, then the wall time of `run` alone is below 10.0 s on this machine, and the measured time is written into `## Notes` by the orchestrator after the gate run.
- **AC-2** - Given the same run, when it completes, then 100 outputs exist and each decodes to the dimensions of its recipe's art rect plus `2 * margin_px` on each axis. *Control on the metric:* a stub that copied files without cropping would beat the clock and fail this assertion, so the time is measured on real work.
- **AC-3** - Given the same run, when it completes, then `failed() == 0` and `flagged() == 0`.

## Model guidance

Model: default. Oracle partition:

- **Settled**: the 10 s budget and the 40/30/30 mix.
- **Mechanical**: AC-2 and AC-3.
- **Oracle-free**: the timing itself. If the budget is missed, that is a real finding for GREEN (parallelism, decode settings, luma conversion cost), never a reason to reduce the image count or resolution. A test whose own overhead (fixture generation, decoding for AC-2) is inside the timed region is wrong; keep the timer around `run` only.

## Out of scope

Benchmarks on other hardware, a `ci-factor` line (there is no CI runner for
this gate yet), JPEG and WebP timing (PNG decode is the expensive case),
memory usage.

## Test plan

One new file, `crates/engine/tests/perf.rs`, and no change to any other.

**Level.** Integration, through `batch::run` over real files in a temp dir.
Nothing below that level can falsify AC-1: the claim is about a whole batch of
real PNGs on this machine's pool and filesystem, and a unit test of the
detector would measure neither the decode, the encode, nor the parallelism.
AC-2 and AC-3 are read off the same run because all three criteria say "the
same run".

**One heavy test, not three.** The run costs ~1 s of fixture generation, ~2 s
of `run` and ~1.3 GB of temp disk; running it three times would buy three test
names and nothing else. The three assertions are separately labelled and fire
in the order AC-3, AC-2, AC-1 - correctness first, so that a run which reached
a fast time by flagging or failing everything reports *that* rather than a
clean clock.

**The fixtures.** Three `Recipe`s - 40 at 1920x1080, 30 at 2560x1440, 30 at
3840x2160 - each with four uniform borders, a chrome band under the top border
and a jittered checkerboard inside, which is `common::screenshot`'s structure
at a size the recipe chooses. Because the recipe fixes the borders and the
band, the **art rect is known before a pixel is written**, so AC-2's expected
output size is computed (`art + 2 * margin_px`, with `margin_px` read from the
`Tuning` the run is given) rather than observed. `common::screenshot` itself is
deliberately left alone: it is one fixed 147x120 scene that five other engine
suites measure numbers on.

**What each test covers.**

| Test | Asserts | AC |
|---|---|---|
| `one_hundred_mixed_screenshots_are_cropped_correctly_within_the_ten_second_budget` (`#[ignore]`, release) | `failed() == 0` and `flagged() == 0`, naming every file that was not cropped | AC-3 |
| the same test | 100 files in the output folder, and every one of the 100 outputs measures its recipe's art rect plus `2 * margin_px` on each axis - read from each PNG's own IHDR, cross-checked once per recipe against a real decode | AC-2 |
| the same test | the wall time of `batch::run` alone is below 10.0 s, with fixture generation and the AC-2 decode pass outside the timed region | AC-1 |
| `the_settled_mix_is_what_is_generated` (cheap, debug) | the recipe table is still 40/30/30 at 1920x1080 / 2560x1440 / 3840x2160 and the plan lays out 100 files | guards AC-1's settled numbers |
| `margins_fit_inside_every_border` (cheap, debug) | every border is at least `margin_px` deep, so AC-2's expected size is never clamped and the expectation stays exact | guards AC-2's arithmetic |

**Edges.** Zero/one/many does not apply - the criteria describe one specific
batch of exactly 100 - so the shape of the problem is covered at the boundary
that does exist: the margin against the shallowest border (the guard test
above), and the three resolutions rather than one. The `## Out of scope` items
(other hardware, a `ci-factor`, JPEG/WebP timing, memory) are not tested, by
the story's own instruction.

### The export shape these tests already pin

Stated as fact, not suggestion - the file imports these today and a wrong
guess is a compile error:

- `cropper_engine::batch::{Progress, RunSummary, run}`
  - `run(inputs: &[PathBuf], out_dir: &Path, tuning: &Tuning, progress: &(dyn Fn(Progress) + Sync)) -> RunSummary`
  - `RunSummary { results: Vec<FileResult> }`, with `failed() -> usize` and
    `flagged() -> usize`
  - `results` is **in input order**, which is what maps result `i` back to
    plan entry `i` for AC-2
  - `Progress` is constructed only by the engine here; the test's callback is
    `&|_: Progress| {}` and must stay `Sync`
- `cropper_engine::{FileResult, Outcome}` - `FileResult { input: PathBuf,
  outcome: Outcome }`, `Outcome::Cropped { rect, output }`,
  `Outcome::Flagged { reason, output }`, `Outcome::Failed { error }`, with
  `reason: Flag` printed through `Debug` and `error: String`
- `cropper_core::{Luma, Rect, Tuning}` - `Luma { width, height, data }`,
  `Rect { x, y, w, h }`, `Tuning::default().margin_px: u32`
- `crates/engine/tests/common/mod.rs`: `Rng::new(u32)` / `upto(u8)`,
  `write_rgb8(&Luma, &Path)`, `ihdr(&Path) -> Ihdr { width, height, bit_depth,
  colour_type }`, `decode(&Path) -> DynamicImage`, and the scene constants
  `ART_LO`, `ART_HI`, `ART_JITTER`, `BAND_BG`, `BAND_DEVIATION`,
  `TEXT_PERIOD`, `TOP_COLOUR`, `BOTTOM_COLOUR`, `LEFT_COLOUR`, `RIGHT_COLOUR`

**Not constrained, and therefore still GREEN's choice:** how `run` schedules
the work (chunk size, thread count, whether rayon is used at all), what the
output files are *named* (the test takes each output path from the summary,
never from a name it guessed), the encoder's compression settings, and
anything about progress beyond the callback's type.

### Seeds and recipes, named

| Recipe | Size | Borders T/B/L/R | Band | Count | Base seed | Art rect | Expected output |
|---|---|---|---|---|---|---|---|
| `1920x1080` | 1920x1080 | 10 / 8 / 15 / 12 | 12 | 40 | 1 | 1893x1050 | 1899x1056 |
| `2560x1440` | 2560x1440 | 20 / 16 / 30 / 24 | 24 | 30 | 7 | 2506x1380 | 2512x1386 |
| `3840x2160` | 3840x2160 | 30 / 24 / 45 / 36 | 36 | 30 | 42 | 3759x2070 | 3765x2076 |

Image `i` of a recipe draws its art from `Rng::new(recipe.seed * 1000 + i)`, so
the seeds are exactly **1000..=1039**, **7000..=7029** and **42000..=42029** -
base seeds 1, 7 and 42. The three classes are interleaved 4-3-3 per round over
ten rounds, so the input folder reads like a mixed capture session and no
worker's share of the pool is all 4K. Expected output is art + `2 * margin_px`
with `margin_px = 3` from `Tuning::default()`, read from the tuning at
assertion time rather than written down.

### Negative control for the timing metric - measured, not assumed

The control AC-2 names: *a stub that copied files without cropping would beat
the clock and fail this assertion.* It was measured in RED, outside the
engine, with a throwaway test binary that generated the same 100 fixtures and
then only `fs::copy`-ed them on the same thread count (deleted afterwards;
nothing in the tree depends on it):

```
CONTROL: a copying stub finished 100 files in 0.270 s against the 10.0 s budget (1266 MB in, 1266 MB out)
CONTROL: 1920x1080: a copy measures 1920x1080, AC-2 demands 1899x1056 (off by 21x24)
CONTROL: 2560x1440: a copy measures 2560x1440, AC-2 demands 2512x1386 (off by 48x54)
CONTROL: 3840x2160: a copy measures 3840x2160, AC-2 demands 3765x2076 (off by 75x84)
```

| Control | Threshold it must not meet | Expected | Measured in RED |
|---|---|---|---|
| copy-only stub, wall time | below 10.0 s | comfortably under - it does strictly less I/O than the real run and no compute | **0.270 s** (7x faster than the real 1.877 s) |
| copy-only stub, output size 1920x1080 | equal to 1899x1056 | the *input* size, 1920x1080 | 1920x1080, off by 21x24 |
| copy-only stub, output size 2560x1440 | equal to 2512x1386 | 2560x1440 | 2560x1440, off by 48x54 |
| copy-only stub, output size 3840x2160 | equal to 3765x2076 | 3840x2160 | 3840x2160, off by 75x84 |

**What this means for AC-1.** The clock alone is nearly meaningless: the
cheapest possible wrong answer is *seven times faster* than the right one.
What makes 1.877 s a statement about cropping rather than about an SSD is that
AC-2 and AC-3 are asserted on the same run - 100 outputs, each exactly its
recipe's art rect plus the margin, none flagged, none failed. If a future
change ever makes AC-1 pass while AC-2 or AC-3 fails, read the time as
meaningless until the other two are green again.

**GREEN's job on these numbers.** The whole heavy test ran green in RED, so
unlike the usual import-failure case every assertion in it has executed. The
control above is the exception: it was driven outside the shipped code path.
Confirming it against the shipped module is GREEN's to do if anything in
`process_file` or the codec changes - the cheap version is that a run whose
outputs measure the *input* dimensions must fail AC-2, which is precisely what
probe 2 in `## Regressions` demonstrates.

### Fixture generation cost, so the next agent does not rediscover it

- 100 PNGs, 442 Mpx in total, **1,266 MB written** to the temp dir, plus
  **1,199 MB of outputs**: about **2.5 GB of temp disk per run**, and the
  `TempDir` takes it all away at the end of the test.
- The art is a per-pixel jittered checkerboard, which is close to
  incompressible - the fixtures are within 5% of raw RGB8. That is deliberate:
  it is the *pessimistic* case for PNG, so the budget is met on hard data
  rather than on a fixture that deflates to nothing.
- Generation is ~1.0 s wall on 12 threads (`std::thread::scope`, not rayon -
  the test must not borrow the machinery AC-1 is measuring), and it is
  **outside the timed region**, as is the AC-2 decode pass.
- Release build of the workspace for this gate is ~40 s cold, ~18 s after an
  engine-only edit (fat LTO, `codegen-units = 1`).
- **The `## Context` paragraph is out by an order of magnitude, and it is
  prose rather than a criterion, so nothing was amended.** It says fixture
  generation "may itself take a while; that is why the gate is slow".
  Measured, fixture generation is ~1.0 s and the whole test binary runs in
  3.29 s under the gate command; what actually makes `integration` slow is the
  fat-LTO release rebuild of the workspace. The `slow` line in `project.conf`
  is right for the right reason - it already names "release rebuild of the
  workspace" first - so there is nothing to change, but do not go hunting for
  minutes of fixture cost that are not there.
- Debug (`profile.test`, `opt-level = 2`) measures 3.3 s for the same run.
  That is under the budget too, and it means nothing: the assertion is a
  release claim and the gate runs it in release.

with it. The re-run is what produced the record below. It also proved the
