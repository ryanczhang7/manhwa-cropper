## Context

`EPIC-07` story 4 is *the crop removes browser, OS and reader furniture, and
nothing below it*, measured as containment of the mark plus absence of
furniture (`product-brief.md` §5, third amendment of 2026-09-21).
[MC-048](MC-048.md) removes the browser and OS part as an internal stage. What
is left is the **reader's own** header, navigation bar and footer — the part
whose survival made the user decline MC-031's Option B on 2026-09-17, and the
part the user's 2026-09-23 complaint still covers ("browser artifacts up top"
includes the site navigation in `Screenshot (67).png`).

**This is not an eighth run of the seven negatives.** MC-026, MC-028, MC-031,
MC-032, MC-034, MC-035 and MC-038 hunted the **panel boundary** — where the
art stops inside the page — and all failed on a bubble crossing a gutter. The
2026-09-21 amendment dropped that target. This spike asks a different question
about a different boundary: the one between the reader's UI and its page
content, which **touches the viewport edge** as browser chrome does, and which
MC-031 showed to be the tractable kind (a full-width signal separated chrome
from page at 99.70 %). `v2-candidates.md` lists what not to re-run; nothing in
it answers this.

**"Any reader" is binding.** The user's decision of 2026-09-21 — *"It should
work on any reader. Do not flag other readers."* — means the rule must place
furniture on a reader it has never seen. Per-site matching is permitted only
as an optimisation on top of a rule that works without it
([MC-041](MC-041.md), parked; brief §5). A rule that only works because it has
learned `toongod`'s header height does not answer this spike.

**There is no furniture oracle yet**, and building one is part of the work:
the marks are the never-clip oracle, not the furniture boundary, and nothing in
the manifest says where a reader's header ends. That is a person's
judgement, as the marks were.

## The question

> Inside the browser viewport, does a rule that uses no per-site constant
> locate the rows where the reader's own header ends and its footer begins,
> such that cropping to them **never clips a mark** and **leaves no reader
> furniture** in the crop, on the 21 marked `tuning` entries — and does it
> keep that when each reader is held out of its own tuning in turn?

## Acceptance criteria

- **AC-1** — *The furniture oracle.* For each of the 21 marked `tuning`
  entries, the document records the first page-content row below the reader's
  header and the last one above its footer (or "none visible" for either),
  **as ruled by the user** — proposed by the spike from the pixels, shown to
  the user with the images open, and corrected where they say so. Per
  Open question 1. Each value names who ruled it and when.
- **AC-2** — *The ceiling first.* Before any rule is scored, the document
  reports what cropping exactly to the AC-1 rows scores: clips against the
  marks (expected 0 — if not, the oracle and the marks disagree and that is the
  finding) and entries where furniture was present at all. If furniture is
  absent on nearly all 21 after MC-048, that is the answer and the spike stops.
- **AC-3** — *At most two rule families, each reader-agnostic by construction.*
  For each: its definition, the parameters swept, and for the best member the
  count of the 21 with (a) **zero clips** and (b) **no reader furniture**
  against AC-1, per edge. A rule containing any per-site constant or site
  lookup is out.
- **AC-4** — *Leave-one-reader-out.* For the best member, the same two counts
  when its parameters are chosen with each reader's entries withheld and then
  scored on that reader (`toongod` 11, `demonicrevolution` 4, `w-network` 2,
  `rolia-scans` 2, `kunmanga` 2 — `corpus.md`). MC-041's AC-3 protocol is the
  template. A rule that reaches the bar only with every reader in its tuning
  does not meet it. *Control:* a rule that memorises one fixed header height
  per reader must score well in-sample and fail this check — show both.
- **AC-5** — *Negative controls, each shown to fire.* A rule that crops to the
  AC-1 rows moved **10 rows inward** must report clips on at least one entry
  (the clip check is live); a rule that crops to the viewport alone (MC-048's
  output) must report furniture present wherever AC-2 found it (the absence
  check is live).
- **AC-6** — *The verdict and the recommendation.* Exactly one of: **a rule
  exists** — best member at zero clips on 21 of 21 and no furniture on at least
  **19 of 21**, holding under AC-4 — with the feature story it justifies
  sketched (criteria, the held-out run it would earn, `required_gates`); or a
  **reasoned negative** with the ceiling, the best rule's numbers and the
  failure causes by entry. A negative states which decision it forces
  (learned detection is the only untried signal class left; opening it is the
  user's decision, not this spike's).
- **AC-7** — *The record.* The document is `docs/wiki/reader-furniture-search.md`;
  `v2-candidates.md` gains a row; every number is reproducible from a harness
  outside the repository whose path the document records, as MC-031's §8 does.

## Model guidance

Model: default, on the same verdict MC-038's `## Notes` and `story-authoring`
record: the brief is the variable.

- **Settled — read out.** The marks and every ruling in `corpus.md`; the split
  and the contamination rule; MC-048's viewport stage as committed; the
  user's 2026-09-21 "any reader" decision; the 19-of-21 bar (the brief's 9 in
  10).
- **Oracle-free — the work.** The furniture rule and its parameters; the
  proposal of AC-1 rows before the user rules on them.
- **A person's call, never an agent's.** The AC-1 rows themselves. The spike
  proposes; the user rules.
- **Mechanical.** Reporting shape, denominators (21, per reader), AC-7.

**Success condition, which can come out either way.** A reader of the document
can say, with numbers, whether a reader-agnostic furniture rule exists on the
tuning set and whether it survives leave-one-reader-out. It fails if it scores
a rule before AC-2's ceiling, reports any number over a denominator other than
the 21 marked tuning entries, or reads a held-out entry. **Record the verdict in
`## Notes`.**

**Timebox.** AC-1 and AC-2 first. Two families at most. If neither family's
best member reaches the bar in-sample, write the negative without a wider
sweep.

## Out of scope

- **Held-out.** Not scored, not opened, not once. The feature this might
  justify earns the held-out run.
- Per-site matching as the mechanism (MC-041 stays parked), learned or
  model-based detection, colour and chroma, re-marking the art rectangles.
- The panel boundary and page gutter — out of the target since 2026-09-21.
- The column axis ([MC-049](MC-049.md)).
- Any production or test code in `crates/`. The harness lives outside the
  repository.

## Open questions — answer before it starts

**Answered 2026-09-23: the user accepted every recommended default below, before it started.**

1. **Who draws the furniture oracle, and how.** *Recommended:* the spike
   proposes a header-end and footer-start row for each of the 21 from the
   pixels and the user confirms or corrects them in one sitting through an
   Artifact page like the Corpus Reader Labeller (about 15 minutes), stored as
   a document table in `reader-furniture-search.md` — **not** as new manifest
   fields, which would need a schema story. *Alternative:* add the rows to
   `manifest.json` first via a small schema story, if you want tests to read
   them later.
2. **What counts as reader furniture at the bottom.** A chapter-navigation bar
   or comment box below the last page is in some screenshots; a floating
   "next chapter" button overlaid on the art is in others. *Recommended:*
   furniture is UI that occupies full rows of the viewport; an overlay drawn
   on top of art is out of scope, since removing it would clip.
