## Context

Composes the pipeline from `architecture.md` - trim (MC-003), content box
(MC-005), a second trim inside the box, then the outward margin - into
`detect(&Luma, &Tuning) -> Option<Detection>`, and establishes the brief's
feature 2, "never clip artwork", as a property checked with `proptest` over
random recipes rather than a handful of examples. `Detection` carries the
final rect and what the stages did (`trimmed: bool`, `removed: Vec<Side>`,
`ambiguous: bool`) so MC-007 can turn it into a decision. `margin_px = 3`.

Gate that fails if this breaks: `unit`.

## Acceptance criteria

- **AC-1** - Given a fixture with uniform borders on all sides and a chrome band at the top, when `detect` runs, then `rect` equals the art rect expanded by `margin_px` on every side and clamped to the image.
- **AC-2** - Given a fixture where full-width chrome sits above a page that has uniform gutters left and right of the art (so the first trim removes nothing because the top rows are chrome), when `detect` runs, then the chrome is peeled, the gutters are trimmed by the second trim, and `rect` is the art rect plus margin.
- **AC-3** - Given the art rect touches the image's right edge, when `detect` runs, then `rect.x + rect.w == width` (the margin clamps rather than overflows), and the other three sides carry the full margin.
- **AC-4** - *Property, proptest, at least 256 cases:* given any recipe the generator can produce (per-side border widths 0..=200 and colours 0..=255, either layout, zero to two chrome bands per edge with flat fraction in 0.86..=0.98 and heights up to 25% of the dimension, art size 100..=1200 per side, seeded texture), when `detect` returns `Some(d)`, then the art rect is contained in `d.rect` (never clip) and `d.rect` is contained in the art rect expanded by `margin_px + 2` on every side (never much junk). *Control on the metric:* the orchestrator mutates `margin` to shrink by 1 px on the top instead of expanding and records in `## Notes` that the property fails.
- **AC-5** - Given a uniform image, when `detect` runs, then it returns `None`.

## Model guidance

Model: default. Oracle partition:

- **Settled**: every constant in `Tuning::default()`, including `margin_px = 3`. The `+2` slack in AC-4 is settled too.
- **Mechanical**: `detect(&Luma, &Tuning) -> Option<Detection>`, `Detection { rect: Rect, trimmed: bool, removed: Vec<Side>, ambiguous: bool }`. Pin.
- **Oracle-free**: none - the generator knows the art rect. If the property finds a recipe that fails, that is a real finding about the algorithm, not the test; shrink it, record it in the handoff, and do not narrow the generator to avoid it without an `## Amendments` entry approved by the user.

## Out of scope

Flag reasons and the `CropDecision` type (MC-007), anything below 1 px of
precision, a margin that varies with image size (decision 5), performance
(MC-017).

### Two things you have to add, not change

1. **A rect-taking uniform trim.** `trim::trim_uniform(&Luma, &Tuning)` starts
   from the whole image; the pipeline's step 3 ends with "a second uniform trim
   inside [the content box]". `tests/trim.rs` is MC-003's and is frozen, and it
   imports `trim_uniform` with today's signature, so **add** a function
   (`trim::trim_within(img, within, t) -> Option<Rect>` or whatever you like)
   rather than changing the existing one. The obvious implementation is to make
   the existing body take a starting rect and have `trim_uniform` call it with
   the whole image.
2. **`trimmed` means "either uniform trim moved an edge".** The story defines
   the field but not its reading, and a bool with no definition is untestable,
   so RED pinned one. The discriminating test is
   `trimmed_is_true_when_only_the_second_trim_moved_an_edge`: on AC-2's scene
   the first trim moves nothing at all, and `trimmed` must still be true. A
   `trimmed` that reports only the first trim fails exactly that one test.
   Flagged to the orchestrator as a judgement call; if the product owner wants
   the other reading, that is an `## Amendments` entry and a return to RED.

### What `detect` must do, stage by stage

Taken from `architecture.md` and confirmed against every fixture in the file by
running the composition for real (below). Nothing here is a new decision.

1. `trim_uniform(img, t)`; `None` propagates straight out (AC-5).
2. `content_box(img, first, t)` - its `removed` and `ambiguous` go into
   `Detection` unchanged.
3. the second uniform trim, inside `found.rect`.
4. expand by `t.margin_px` on every side, **saturating at 0 and clamped to the
   image** - `x.saturating_sub(m)`, `(x + w + m).min(img.width)`, and the same
   on the other axis.
5. `trimmed = first != whole(img) || second != found.rect`.

**reference composition** written in a scratch test target
(`crates/core/tests/redprobe.rs`, since deleted): `trim_uniform` ->
`content_box` -> a local rect-taking trim -> the margin. Results:

### Performance - read this before you run the gates

AC-4 asks for 256 cases over art of 100..=1200 per side. With borders (0..=200)
and chrome outside the art, the largest image the generator produces is
**3184x3184**, not the ~1600 the story's framing assumes; the criterion bounds
the art, not the image. Measured on this machine, warm:

| | `cargo test --workspace` | `coverage` gate |
|---|---|---|
| before this story (MC-005) | ~1 s | **7 s** |
| with `detect.rs`, default `opt-level` | **99 s** | **120 s** |
| with `[profile.test] opt-level = 2` | **6 s** | **22 s** |

The cost is entirely the unoptimised build: the pipeline is ~50 passes over up
to 10 Mpx per case, and `cargo test` uses the dev profile at `opt-level = 0`.
**Recommendation: add to the root `Cargo.toml` in GREEN**

```toml
[profile.test]
opt-level = 2
```

It is a config file, which RED may not write, so it is yours. It is a 20x
saving on a required gate, it speeds every other target up too, and it costs
nothing in coverage fidelity: the instrumented run reports the identical
**675 regions, 405 lines, 0 missed** either way, so the `coverage` evidence
line and the 95% floor are untouched. Both numbers above were taken with
`CARGO_PROFILE_TEST_OPT_LEVEL=2`, which is exactly what that stanza sets.

**Do not** reach for a smaller generator instead: 256 cases and the ranges are
frozen acceptance criteria, and cutting either needs an `## Amendments` entry
approved by the user. Flagged to the orchestrator.

The `floor | unit | 47` line in `project.conf` needs no change: it tracks the
first test binary to run a test, cargo orders `crates/core`'s targets
alphabetically, and `content` still sorts before `detect`.

### Notes on the generator, and one gap I chose deliberately

- **The recipe nests border outside, chrome inside, art innermost.** The first
  trim takes the whole border frame off, `content_box` then works on a rect
  that is exactly chrome plus art, and every chrome/art boundary is a strong
  line because the art is a checkerboard.
- **The reverse nesting - chrome outside a uniform page gutter - is AC-2's
  scene and is built by hand, not by the generator.** I tried to put it in the
  generator and it cannot be made to work at AC-4's stated ranges: with borders
  up to 200 px on each side and art as small as 100 px, the column profile at a
  vertical chrome band's inner boundary is diluted by a factor of 5 by the
  horizontal border rows, and no chrome background exists that is 120 luma
  levels from an arbitrary border colour in 0..=255. That is a real limit of
  the algorithm on a fixture nobody will ever photograph, not a defect - but it
  means AC-4's property does not exercise the second trim at all (it is a no-op
  on every generated recipe). AC-2 is the only thing testing it. **Flagged to
  the orchestrator**; if that gap matters, it is a new story with a narrower
  generator, not a change here.
- Chrome band thickness is drawn as 50..=330 permille of the art extent. That
  satisfies "heights up to 25% of the dimension" by construction and can be
  saturated: a single band on an otherwise bare edge is `0.33a / 1.33a` =
  0.248 of the dimension. `Recipe::render` asserts the bound on every band.
- Adjacent chrome backgrounds are 90 luma apart and drawn from the seed, not
  from the strategy, so the strategy tuple stays inside proptest's arity.

### Judgement calls made in GREEN

- **`trimmed` is implemented as the handoff pinned it**:
  `first != whole(img) || second != found.rect`, compared rather than tracked.
  It is the reading that
  `trimmed_is_true_when_only_the_second_trim_moved_an_edge` demands, and the
  handoff already flagged it to the orchestrator as a judgement call rather
  than a story decision. Nothing here re-opens it.
- **`trim_within` is the rect-taking trim**, and `trim_uniform` is now one call
  to it with the whole-image rect. MC-003's frozen `tests/trim.rs` passes
  unchanged (19 tests), so the existing public behaviour is intact.
- **`margin::expand(rect, by, bounds: Dimensions)`** rather than taking a

- **`Detection` derives `Debug` and `Clone`.** `Debug` is required - a test

- **The second `?` is a dead branch in practice**, as the handoff's first
  finding predicted: a uniform image already left through the first trim, so
  `trim_within` inside a content box has never returned `None` in any test.
  It is kept because the type says it can, and it is the one missed region in
  `decide.rs` (28 regions, 1 missed; 21 lines, 0 missed).

### CI cost, measured on PR #7 (REVIEW)

Both checks passed: `boundaries` 5s, `gates` 22m17s. The gate wall time is up
from MC-005's 19m39s, and the naive reading - 22m17s on CI against a 201s full
local run, so "CI is 6.7x" - is exactly the extrapolation `project.conf` warns
against. Measured per test, against the same binary, it is not:

| Gate | `tests/detect.rs`, local | same, on CI | factor |
|---|---|---|---|
| `unit` (plain) | 3.93 s | **5.58 s** | **1.42** |
| `coverage` (instrumented) | 12.41 s | **20.28 s** | **1.63** |

So almost all of the 22 minutes is fixed overhead - checkout, toolchain,
rebuilds across four profiles (debug, llvm-cov, release, release again for
`build`) - and very little of it is test compute. These are the first real
ci-factor datapoints this project has; MC-004's note recorded the same shape
from wall time alone and could not separate the two.

Worth carrying to MC-017 (performance) and MC-019 (corpus): of `detect`'s
20.28 s instrumented on CI, **20.2 s is AC-4's property alone** - every other
test in the file finishes inside 0.1 s. The property is the suite. Rust's
libtest has no default per-test timeout, so there is no cliff here the way
`project.conf`'s vitest anecdote had one, but raising AC-4's case count or the
corpus size is the thing that will move the gate, and nothing else in this file
will.

**Not written into `project.conf`.** A `ci-factor` line there is the right home
for both numbers, but `project.conf` is a harness file and the gate tree hash
covers it, so adding one now would invalidate the `## Gate results` record this
PR is being merged on and force a full re-run. The next story that touches the
harness for any other reason should add:

    ci-factor | unit     | 1.42 | actions run 34568382246, tests/detect.rs 3.93s local -> 5.58s
    ci-factor | coverage | 1.63 | actions run 34568382246, tests/detect.rs 12.41s local -> 20.28s
