**What the move is, and what it is not.** It changes three `"split"` values
in `fixtures/corpus/manifest.json` from `held-out` to `tuning`. It also
widens `2025-07-17 14_20_23.png`'s left edge from 967 to 962, the user's
ruling on Open question 3. Nothing else about the three changes: the other
two keep their `expect`, and all three keep their tags. It changes no
production code. What makes it more than a one-line edit is that every
`tuning` suite starts measuring the three, and several of those suites pin
the exact set of marked `tuning` entries or assert properties one of the three
does not have.

- Luma over rows 171..1382: columns ≤961 are the page's grey (23).
- Columns 962..972 are flat black (median 0). The art's black panel starts
  at **962**, five columns left of the mark's 967.

1. **The minimum size of the set kept aside for the final test.** A check
   says the set of screenshots kept aside for the final score must still hold
   at least 19 marked screenshots. Moving these three leaves 16, so that check
   would fail. Lower it to 16? *Recommended: yes, lower it to 16*, the same
   way it went from 20 to 19 last time. That set has already given its one
   score, and the way it grows back is new screenshots, not a lower bar. At
   16, one wrong screenshot is about 6 % of the score (it was 5 % at 20).

2. **What the everyday checks do with the screenshot the app gives up on.**
   `2025-07-17 14_20_23.png` is the one the app says it is "not sure" about, so
   it crops nothing. Four existing checks say "no marked screenshot is ever
   given up on", and they would fail as soon as it joins the everyday set.
   *Recommended: name that one screenshot as a known exception in those four
   checks*, with the checks built so the exception has to be removed the day a
   later fix makes it crop. Everything they already check on the other 26
   stays exactly as strict. The alternatives are to leave those checks failing
   until the fix lands (not recommended: every later story that needs the full
   test run would start red), or to move only the other two and leave this one
   where it is (not recommended: it has already been looked at, so it can no
   longer give a fair score).

3. **The left edge of `2025-07-17 14_20_23.png`'s marked rectangle.** The
   check that looks at the edges of each marked rectangle reads its leftmost
   column (column 967) as plain page, not art: 99.9 % of that column matches
   the page colour. That is what the seven marks corrected earlier looked
   like. *Recommended: you look at a close-up of that edge before work starts
   and decide*, as with the earlier corrections: if it is page, the rectangle
   is trimmed to start where the art starts; if it is art, the rectangle stays
