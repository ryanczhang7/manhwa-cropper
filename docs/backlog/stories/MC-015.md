## Context

`crates/app/src/gui.rs` paints a `Model` (MC-014) with egui according to
`docs/wiki/design/components.md`, `layout.md` and `tokens.md`, and follows
the system light/dark theme. This story is painting only: the paint function
takes `&Model` and a `hovering: bool` and emits nothing; wiring inputs to
events is MC-016. Tests use `egui_kittest` to render a given `Model` headlessly
and query the AccessKit tree by the roles and names in
`docs/wiki/design/accessibility.md`. `gui.rs` is excluded from the coverage
threshold (`stack.md`), so these kittest tests are the only thing that
exercises it: every window state in the components table gets one.

Gate that fails if this breaks: `unit` (kittest tests run under
`cargo test --workspace`).

## Acceptance criteria

- **AC-1** - Given `Idle` with no folder, when painted, then labels `Choose an output folder, then drop images here` and `No output folder chosen` are in the tree, a button named `Choose folder…` is present and enabled, and no progress count, result line or list row is present.
- **AC-2** - Given `Idle` with folder `D:\shots\out`, when painted, then the drop zone reads `Drop images here` and the path label is `D:\shots\out`; when painted with `hovering == true`, then the drop zone reads `Release to crop`.
- **AC-3** - Given `Processing { done: 3, total: 10 }`, when painted, then the drop zone reads `Cropping…`, a label `3 of 10` is present, and the `Choose folder…` button is disabled.
- **AC-4** - Given `Done` with a summary of 10 cropped, 0 flagged, 0 failed, when painted, then a label `10 cropped, 0 flagged` is present and no list row is present.
- **AC-5** - Given `Done` with 7 cropped, 2 flagged (`a.png` Uniform, `b.gif` Unsupported) and 1 failed (`c.png`), when painted, then the result line is `7 cropped, 2 flagged, 1 failed` and exactly three rows are present in order: `a.png — Blank`, `b.gif — Unsupported format`, `c.png — Not written`.
- **AC-6** - Given `Error { message }`, when painted, then a label with exactly that message is present and the drop zone shows the idle text for the folder state.
- **AC-7** - Given the harness's raw input reports a dark system theme, when one frame is painted, then `ctx.style().visuals.dark_mode` is true and the panel fill equals the dark `surface` token from `tokens.md`; given light, then `dark_mode` is false and the fill equals the light `surface` token.
- **AC-8** - Given `viewport()` builds the eframe `ViewportBuilder`, when inspected, then the title is `Manhwa Cropper`, the inner size is `520 x 440` and the minimum inner size `400 x 320`.

## Model guidance

Model: default. Oracle partition: every string and number is **settled**
(`voice.md`, `layout.md`, `tokens.md`); read them out. The tree queries are
**mechanical**: use `harness.get_by_label(..)` / `query_by_label` and the
roles in `accessibility.md`. If egui 0.32's `ProgressBar` exposes no
AccessKit value, the `progress.count` label is the tested surface, as
`accessibility.md` says; do not add a test that depends on the bar's value.

## Out of scope

Handling clicks, drops, the dialog or the batch thread (MC-016), animation,
window icon, DPI-specific pixel assertions, screenshot snapshot tests
(kittest's image snapshots need a GPU renderer feature; tree queries are
enough).

## Design notes

Every component in `docs/wiki/design/components.md` is painted here, in the
four-region column of `layout.md`: drop zone (`size-dropzone` 120), folder
row (`size-control` 32), status slot (`size-status` 40, always allocated so
the list never jumps), flagged list (remaining height, `ScrollArea::vertical`
with `auto_shrink([false, false])`), inside `space-window` 16 with
`space-stack` 8 between. Strings come from MC-014's functions only; no
literal from `voice.md` appears in `gui.rs`.

**States per criterion.** AC-1 = window state "idle, no folder"; AC-2 =
"idle, folder chosen" and "drop-hover" (`hovering` is the flag; with no
folder the zone keeps `dropzone.no_folder` under hover); AC-3 =
"processing"; AC-4 = "done"; AC-5 = "done with flags"; AC-6 = "error". The
`hovering` flag paints the drop zone's drop-hover row (`drop-hover-fill`,
2 px solid `primary`, text `text`), the processing state paints its
disabled row (`surface`, dashed `border`, `text-disabled`); the zone is never
interactive and has no hover/focus/active look of its own.

**Theme (AC-7).** `surface` maps to `visuals.panel_fill` and
`visuals.window_fill`: light `#F3F3F3` = `Color32::from_rgb(0xF3,0xF3,0xF3)`,
dark `#202020` = `Color32::from_rgb(0x20,0x20,0x20)`. The test reads
`ctx.style().visuals.panel_fill` (and may read `window_fill`; both must be
equal) and `ctx.style().visuals.dark_mode`. Build one `Visuals` per theme
from `Visuals::light()` / `Visuals::dark()` with every `egui field` in
`tokens.md` overridden, and register both with
`ctx.set_visuals_of(Theme::Light, ..)` and `ctx.set_visuals_of(Theme::Dark, ..)`
at startup; never call `ctx.set_visuals`, `set_theme` or change
`theme_preference` - `ThemePreference::System` (eframe default) plus
`RawInput::system_theme` is what makes the palette switch on the next frame.
The test sets the harness raw input's `system_theme` to `Some(Theme::Dark)` /
`Some(Theme::Light)` and steps once; the handoff records the kittest call
used. The other fields the test may sanity-check are named in `tokens.md`
(`extreme_bg_color` = `surface-raised`, `override_text_color` = `text`,
`error_fg_color` = `danger`, `selection.bg_fill` = `primary`,
`widgets.inactive.bg_stroke` = `border-strong`); shadows are `Shadow::NONE`,
`style.animation_time = 0.0`, `ProgressBar::animate(false)`.

**Viewport (AC-8).** `ViewportBuilder::default().with_title("Manhwa Cropper").with_inner_size([520.0, 440.0]).with_min_inner_size([400.0, 320.0])`;
the test reads the builder's `title`, `inner_size`, `min_inner_size` fields.
No `with_decorations(false)`, no `with_position`, no icon. Build the harness
at 520 x 440 so the list has its default 8 rows.

**Accessibility tree, which is what the tests query.** Roles and names are
the table in `accessibility.md`. Every text is one `egui::Label` (role
Label, name = its full text) so `get_by_label` finds it; each flagged row is
one `LayoutJob` in one `Label` (`text` filename, `text-muted` reason) so
`a.png — Blank` is exactly one node. Set
`style.interaction.selectable_labels = false` so no label is focusable or
selectable; the `Choose folder…` button is the only focusable widget. Disabled
means `ui.add_enabled(false, Button::new(..))` so AccessKit reports the node
disabled and it leaves the Tab order (AC-3 asserts the disabled flag, not a
colour); the path label in processing is painted `text-disabled` via
`RichText::color`, not `add_enabled`, so it keeps its name. The path label
left-truncates with a single `…` when wider than its space but its
accessible name is always the full path (`WidgetInfo::labeled` with the
full string), so a test with a long temp path still finds it by name. The
message line is `danger` (`visuals.error_fg_color`) and is the only thing in
the slot in `Error`; progress bar and count are the only things in it in
`Processing`; result line alone in `Done`; nothing in `Idle`. The list paints
nothing (no border, no placeholder) when it has no rows.

**Focus ring.** When `response.has_focus()`, paint a 2 px `focus`
(`primary`) stroke at the button rect expanded by 2 px, radius `radius-focus`
6. No criterion in this story exercises focus (MC-016 does); implement it
here anyway, because the ring is part of the button's paint.

**Motion.** None: progress fill width is `done / total` set each frame; no
easing, no shimmer, nothing to reduce.

No criterion here forces an interaction that cannot work; the story is paint
only.

title bar, which `accessibility.md` puts on the **Window** node, not on a

`window_title_is_the_product_name` is untouched and still pins

`window.rs`'s module docs as well as here.

**Oracle partition.** Every string and number in this story is **settled** and

nine strings, `layout.md` for 520x440 and 400x320 and the title, `tokens.md`
for `surface` = `#F3F3F3` / `#202020`. The tree queries are **mechanical**:
exact role-plus-name lookups against the AccessKit tree. No metric is designed
anywhere in this file, and no threshold is chosen; there is nothing here to
tune.

Every expected string is a **literal in the test file**, copied character for

**What the ProgressBar actually exposes at egui 0.36.2.** Read out of the
vendored source, `egui-0.36.2/src/widgets/progress_bar.rs:119-128`, and
confirmed by running it: the widget sets
`info.value = Some((progress as f64 * 100.0).floor())`, so AccessKit reports
`numeric_value = Some(30.0)` for a bar at 3/10 - **a percentage**, not `done`,
and there is no max. It sets a `label` only when `ProgressBar::text(..)` is
given, which the design does not use; measured `label = None`, `value = None`.
So `accessibility.md`'s "numeric value `done`, min 0, max `total`, when egui
exposes it" is not something this egui version can be held to, and the story's
own Model guidance already anticipates it: **the `progress.count` Label is the
tested surface**. No assertion in this file reads the bar's numeric value. The
bar is still asserted to *exist* (role ProgressIndicator) in the negative
control, because AC-1's "no progress count" needs a state where the query
finds something.

**`ctx.style()` is `ctx.global_style()` at this version.** The Design notes
name `ctx.style().visuals`. `egui::Context::style` does not exist in 0.36.2;
the accessor was renamed to `global_style()` (`egui-0.36.2/src/context.rs`,
around line 2176) and `style_of(theme)` is the per-theme one. Same value, same
criterion - AC-7 asks for `dark_mode` and the panel fill, and the test reads
both off `harness.ctx.global_style().visuals`. Recorded here because the prose
in the design docs still says "egui 0.32" in places and the next reader should
not go looking for a method that is gone.

**What this file deliberately does not pin.** AC-5's fixture puts `a.png`,
`b.gif`, `c.png` in that relative order because AC-5 fixes it, and that order
is also "both flagged files, then the failed one". So this fixture alone cannot
distinguish `RunSummary.results` order from a painter that groups flagged
before failed. It does not need to: the painter takes its rows from MC-014's
`rows()`, and `tests/model.rs`'s `mixed_summary` already puts a *failed* file
between two flagged ones and pins `rows()` against it, so that mutation dies
one layer down. The three rows are still interleaved among the cropped
results - none first, none last, never two adjacent - so a painter that walks a
contiguous slice, or drops the head or tail of the list, fails here.

Also not pinned, and out of scope by the story's own list: pixels, rects,
colours of painted shapes, the focus ring, the dashed border, the 2 px hover
stroke, and anything needing a GPU renderer.

### The export shape these tests already pin

Stated as fact: a test imports each of these, so a different shape is a compile
error, not a preference.

In `crates/app/src/gui.rs`, all three `pub`:

```rust
pub fn paint(ui: &mut egui::Ui, model: &Model, hovering: bool)
pub fn install_style(ctx: &egui::Context)
pub fn viewport() -> egui::ViewportBuilder
```

- `paint` returns `()`; the tests call it as a statement inside a
  `FnMut(&mut egui::Ui)` closure, and `model` is borrowed for the whole life of
  the harness, so `paint` must not take it by value or require `&mut`.
- `install_style` returns `()` and takes `&egui::Context` - the tests pass
  `&harness.ctx`.
- `viewport` returns `egui::ViewportBuilder` **by value**, and the test reads
  its public fields directly: `title: Option<String>` (compared with
  `.as_deref()`), `inner_size: Option<Vec2>`, `min_inner_size: Option<Vec2>`.
- `egui` is reached as `eframe::egui` in the tests, so `gui.rs` keeping
  `use eframe::egui;` is compatible; the types are the same crate either way.
- `Model`, `AppState`, `APP_TITLE` and `window_title` keep their MC-014
  shapes - `Model { state, output_dir }` with both fields public,
  `AppState::{Idle, Processing{done: u32, total: u32}, Done{summary}, Error{message}}`.

**Not constrained, and therefore GREEN's choice**: everything about how the
frame is laid out - `CentralPanel` or not, `Frame::inner_margin`, whether the
regions are `ui.vertical`, `allocate_ui_with_layout` or sized allocations, the
order in which `install_style` writes the two `Visuals`, whether `paint` takes
its strings through local bindings, the shapes drawn for the dashed border,
the hover stroke and the focus ring, and any private helper in the module. Any
`#[derive]`, doc comment or module split is free.

### AC-7: the exact kittest calls, and the one trap

```rust
let mut harness = Harness::builder()
    .with_size(egui::vec2(520.0, 440.0))
    .build_ui(move |ui| gui::paint(ui, model, hovering));
harness.run();

gui::install_style(&harness.ctx);
harness.ctx.set_theme(egui::ThemePreference::System);   // see the trap below

harness.input_mut().system_theme = Some(egui::Theme::Dark);
harness.step();
harness.ctx.global_style().visuals            // .dark_mode, .panel_fill, .window_fill

harness.input_mut().system_theme = Some(egui::Theme::Light);
harness.step();
harness.ctx.global_style().visuals
```

**The trap.** `HarnessBuilder` defaults `theme: egui::Theme::Dark` and
`Harness::from_builder` calls `ctx.set_theme(theme)`
(`egui_kittest-0.36.2/src/lib.rs:142`), which sets
`theme_preference = ThemePreference::Dark`. With a fixed preference,
`RawInput::system_theme` is ignored entirely
(`egui-0.36.2/src/memory/mod.rs:367`), so the palette would never switch and
AC-7 would be untestable. The **test** restores
`ThemePreference::System` - eframe's own default, which kittest does not
reproduce. That call belongs to the test and must **not** migrate into
`install_style`: the Design notes forbid the painter from touching
`theme_preference`, and a `set_theme` there would silently pin the window to
one palette on a real machine.

Confirmed by running it before the tests were written: preference after the
builder is `Dark`; after `set_theme(System)` + `system_theme = Some(Dark)` +
`step()`, `dark_mode=true panel_fill=#20_20_20_FF window_fill=#20_20_20_FF`;
with `Some(Light)`, `dark_mode=false panel_fill=#F3_F3_F3_FF
window_fill=#F3_F3_F3_FF`. `RawInput::take` copies `system_theme` rather than
clearing it, so one assignment survives later steps.

### Things that should change the implementation approach

- **`use egui_kittest::kittest::NodeT;` is required** to call
  `node.accesskit_node()`. Without it rustc reports "private field, not a
  method", which reads like an API that does not exist. Already imported here.
- **`main.rs` currently opens a 480x320 window with no minimum.** AC-8 does not
  test `main.rs`, but shipping `viewport()` without using it there would leave
  the product contradicting `layout.md`. Point 7 above.
- **Do not give the `ProgressBar` a `.text(..)`.** `accessibility.md` asks for
  the bar to be *named* `progress.count`, but the only way to name it is
  `ProgressBar::text`, which also renders that text inside a 4 px bar and puts
  a second node with the same name in the tree. The tests query the count by
  role **and** name (`Role::Label`), so a named bar would not break them - but
  it would break `get_by_label("3 of 10")` for anyone who writes that later,
  and it contradicts `components.md`'s "no percentage text". Leave the bar
  unnamed; the Label beneath it is the accessible surface, which is what the
  story's Model guidance already decided.
- **`selectable_labels` does not affect the tree.** Measured: with egui's
  default (`true`) a Label still produces exactly one node with the same name.
  Set it to `false` because `accessibility.md` says the button is the only
  focusable widget, not because a test depends on it.
- **`Harness::run` is enough.** Every test calls it once; with
  `animation_time = 0.0` and `animate(false)` the frame is stable in one or two
  steps and `run` returns well inside `max_steps` (4). If `install_style` ever
  leaves something animating, `run` panics with `ExceededMaxStepsError` rather
  than looping - that would be a real defect, not a test to relax.

## Notes

### GREEN: what the tests did not constrain, decided here

**The column.** `paint` wraps its four regions in
`egui::Frame::NONE.inner_margin(Margin::same(16))` and sets
`item_spacing = (8, 8)` itself, so the padding and the stack gap hold whether
the caller is `CropperApp` (a `CentralPanel`) or kittest (which supplies a bare
`Ui`). Each region is one `allocate_ui_with_layout(size, layout, ..)` **plus
`ui.set_min_size(size)` as its first statement**. The `set_min_size` is not
decoration: `Ui::scope_dyn` advances the parent's cursor by the child's
`min_rect`, not by the size asked for, so without it the 120 px drop zone
collapses to the height of its one line of text and the 40 px status slot
vanishes in `Idle` - which is exactly the jump `size-status` exists to prevent.
The next story to add a region should copy the pattern.

**The drop zone's boundary.** `Shape::dashed_line` dashes a polyline with one
continuous phase, so the dashed rounded rectangle is built as a closed polyline
by `rounded_rect_outline` (six segments per corner, clockwise in screen space,
starting where the top edge leaves the top-left corner) and handed to it whole;
dashing the four straight edges separately would have restarted the phase at
each corner. The outline is inset by half the stroke width so the boundary is
not half-clipped by the rect it draws. The 2 px drop-hover boundary is solid and
therefore an ordinary `rect_stroke(.., StrokeKind::Inside)`.

**The focus ring** is painted by `folder_button` after the button, from the
button's own response: `rect_stroke` on `response.rect.expand(2.0)`, corner
radius `radius-focus` 6, 2 px `primary`, `StrokeKind::Middle`. Nothing in this
story gives the button focus (MC-016 does), so the ring is unexercised code
paths in a file the coverage gate ignores - worth a look by eye when MC-016
first Tabs into the window.

**Left truncation** (`path_label`/`truncate_left`) measures with
`ui.painter().layout_no_wrap(..)` and drops leading characters until
`… + tail` fits, then re-states the accessible name on the same response:
`response.widget_info(|| WidgetInfo::labeled(WidgetType::Label, .., full))`.
That second call reaches the AccessKit node the `Label` already created - same
widget id, so `set_value` overwrites the truncated galley text - which is how
one node ends up showing `…\cropped-output-folder` and answering to the whole
path. A flagged row uses the mirror of it (`truncate_right`) so that a long
file name gives way and the reason word survives, as `components.md`'s
"overflow" row asks; the row's name is re-stated the same way.

**Two crate-private constants moved into `lib.rs`**, so that `gui.rs` still
contains no string from `voice.md`'s table: `FOLDER_BUTTON` (`folder.button`
has no view-model function - it is a caption, not a state) and `ROW_SEPARATOR`
(` — `, which `row_text` now formats with and which `gui.rs` `rsplit_once`s on
to give the file name and the reason word their own colours). Both are
`pub(crate)`: the window's string table stays in one file and the public API
of MC-014 is unchanged. The one character `gui.rs` does own is
`const ELLIPSIS: char = '…'`, which is `layout.md`'s truncation mark rather
than a table entry - no function can supply it, because which text is cut is a
painting decision.

**Drop-hover versus a run.** `components.md` lists drop-hover as an overlay on
"any" state, and `processing` as a state of its own; the two cells collide when
files are dragged during a run. The **text** rule is already settled -
`dropzone_text` keeps `Cropping…` - so the **look** follows it: `is_processing`
is tested first and the zone paints its disabled row, never the hover row.
`processing_ignores_a_hovering_drag` pins the text half; the look half is
uncovered by any test.

**`CropperApp`** now holds a `Model` (built in `main.rs` from `Settings::load()`,
so a remembered folder is on screen from the first frame) and calls
`install_style` once in `CropperApp::new(cc, model)`. It reads
`hovered_files` for the `hovering` flag, which is paint state rather than an
event; every actual event - the drop, the dialog, the batch thread - is MC-016,
and until it lands nothing mutates the model.

### GREEN: what egui 0.36.2 would not do exactly as the design says

1. **The progress track.** `ProgressBar` paints its track with
   `visuals.extreme_bg_color`, which `tokens.md` maps to `surface-raised`,
   while the same file says the progress track is `border`. Honoured by scoping
   `extreme_bg_color = border` for the width of that one `ui.scope`, so the bar
   gets the token it is owed and the drop zone and list keep theirs. If a later
   story sees a track in the wrong grey, this is the line that did it.
2. **A disabled button's colours.** egui paints a disabled widget from
   `widgets.noninteractive` and then multiplies the whole painter's opacity by
   `visuals.disabled_alpha`; `components.md` gives the disabled button three
   exact tokens instead. So `disabled_alpha` is set to `1.0` (fading a colour
   that was chosen for the disabled state would paint neither), and
   `folder_button` writes `control-disabled` / `border` / `text-disabled` into
   `widgets.noninteractive` inside the scope that adds the button. AC-3 reads
   the AccessKit disabled flag, not a colour, so none of this is under test.
3. **The `ProgressBar` is unnamed**, per the PO's reconciliation of
   `accessibility.md`'s `progress.count` name with `components.md`'s "no
   percentage text": at 0.36.2 the only way to name the bar is
   `ProgressBar::text`, which also renders that text inside a 4 px bar. The
   count `Label` beneath it is the accessible surface.
4. **`primary-contrast` and `success` are not in the code.** Both are reserved
   in `tokens.md` with no consumer in v1, and an unread field of the private
   `Palette` struct is a `dead_code` warning, which `-D warnings` makes a lint
   failure. `warning` **is** there, because `visuals.warn_fg_color` would
   otherwise keep egui's own value. The three are still in `tokens.md`; the
   first story that needs one adds the field.
5. **The bundled font is not Ubuntu-Light.** `tokens.md` names egui 0.32's
   default proportional font; 0.36.2 ships a different default. Nothing in the
   type scale changes - sizes are points, and the scale has no weight axis -
   but the rendered widths differ slightly from anything measured against 0.32,
   which matters only to the truncation helpers, and they measure at runtime.
6. **`ctx.style()` does not exist at 0.36.2**; it is `ctx.global_style()`, as
   the Test plan already records. `install_style` writes through
   `set_visuals_of(theme, ..)` for the palette and `all_styles_mut` for the
   text styles, spacing, `animation_time = 0.0` and
   `interaction.selectable_labels = false`, so both themes get both halves.
7. **kittest's harness is 8 px smaller than the product on every side.**
   `AppKind::run_ui` wraps the callback in a `Frame` with `outer_margin(8.0)`,
   so a 520 x 440 harness gives `paint` 504 x 424 and the flagged list 16 px
   less height than `layout.md` computes for the real window. No assertion in
   this story counts visible rows, and the real window (checked by eye, below)
   has the design's height.
