## Context

Found while planning [MC-038](MC-038.md) on 2026-09-19, which is a `spike` that
escalates `integration` to `required_gates` because that optional gate carries
the only check exercising the filter every number in its document is
denominated by. The escalation does nothing.

`scripts/check-boundaries.sh` line 195:

```bash
# 3e. The gate record was written by gates.sh and matches the code being merged
case "$ph:$story_type" in
  REVIEW:spike|DONE:spike) note "spike story; gate record not required" ;;
  REVIEW:*|DONE:*)
    ...
      # A gate the story escalated must appear in the record as having passed.
      for g in $(frontmatter_list "$sfile" required_gates); do
        ...
```

The `required_gates` re-check lives **inside** the non-spike branch, so a spike
is exempted from it along with the gate record. A spike may therefore declare
`required_gates: [integration]`, never run the gate, and merge with
`check-boundaries.sh` reporting `note  spike story; gate record not required`.

**The exemption is right; its width is wrong.** A spike normally writes only a
document, and demanding a full recorded gate run to merge a markdown file would
be ceremony — that is why the exemption exists and it should stay. But a spike
that has gone to the trouble of naming a gate in `required_gates` has made a
deliberate claim that something in the repository does need checking, and that
claim is the one case the exemption should not cover.

### Why this is a `fix` and not a `chore`

It is a defect with a reproduction: a story file that merges today and should
not. `story-authoring` gives `fix` the rule that its acceptance criteria
*reproduce the bug*, and the failing test that captures it becomes the
permanent regression test. That is exactly the shape here — `.claude/tests/boundaries.test.sh`
already builds real two-branch fixture repositories, so the bug can be written
as a test before the fix exists.

### Why MC-038 waits for it

MC-038 carried a workaround: an eighth acceptance criterion demanding a full
recorded run with `PASS integration` in it. **That was declined at PLANNED on
2026-09-19 — the product owner was shown the hole, the workaround and three
alternatives, and chose "fix the harness, drop AC-8"** — for two reasons. It makes a commit-integrity check into a story's
acceptance criterion, which no prior spike has and which is not about the
document MC-038 delivers; and the next spike author would have copied it
without knowing why, which is how a workaround becomes folklore. Fixing the
exemption enforces the escalation for every future spike rather than one.

MC-038 therefore has `depends_on: [MC-037, MC-039]`.

### The gate question

No gate in `project.conf` covers this story's artifact — they all run `cargo`,
and `scripts/check-boundaries.sh` is bash. **CI covers it anyway**, and an
earlier draft of this section said otherwise; that was checked and corrected at
PLANNED on 2026-09-19 before the criteria froze.

`.github/workflows/gates.yml`:

```yaml
      # The harness's own tests. They need nothing but bash and git, and they
      # guard the machinery every other check in this workflow depends on: the
      # phase lock, the path classifier, the quote-aware command parsing.
      - name: Harness self-test
        run: bash scripts/selftest.sh
```

It is a blocking step with no `continue-on-error`, and it runs **before**
`gates.sh --list`, `gates.sh --audit` and `gates.sh`. So the tests AC-1 to AC-3
add are enforced on every PR, and a regression in them fails the build.

**And that ordering is the reason `selftest` is not a `gates.sh` gate, rather
than an oversight to correct.** It guards the machinery `gates.sh` itself runs
on — the phase lock, the path classifier, the command parsing. A gate inside
`gates.sh` that checks whether `gates.sh` works is circular; a step that runs
first is not. `required_gates: []` is therefore correct and is not a workaround:
the artifact is verified, by the step designed to verify exactly this.

What the story still owes, because a CI step is not a recorded gate run:
`bash scripts/selftest.sh` is run locally and its output pasted in `## Notes`
(AC-4), so the evidence is in the story and not only in a workflow log.

## Acceptance criteria

- **AC-1** — *The bug, reproduced.* Given a story file with `type: spike`, `phase: REVIEW` and `required_gates: [integration]`, whose `## Gate results` section is absent or records no `PASS integration`, when `check-boundaries.sh` runs against it, then it **fails**, naming the story id and the gate. *Control:* this same fixture passes on `main` today — the test must be shown red before the fix and green after, and a run against the unfixed script is what earns it.
- **AC-2** — *The exemption still exists for the case it was written for.* Given a story file with `type: spike`, `phase: REVIEW` and `required_gates: []` and no `## Gate results` section, when `check-boundaries.sh` runs, then it **passes**, still emitting the `spike story; gate record not required` note. *Control:* a fix that simply deleted the exemption would fail this, and deleting it is the obvious wrong fix — every prior spike (MC-028, MC-031, MC-034, MC-035) merged without a gate record and none of them should have needed one.
- **AC-3** — *A spike that escalates a gate and runs it merges.* Given a spike at `REVIEW` with `required_gates: [integration]` **and** a `## Gate results` section written by `gates.sh` recording `PASS integration` against a matching tree, when `check-boundaries.sh` runs, then it passes. *Control:* AC-1 and AC-3 differ only in the recorded run, so a fix that rejected every escalating spike would pass AC-1 and fail this; both are needed or "fails" is indistinguishable from "always fails".
- **AC-4** — Given `bash scripts/selftest.sh`, when it runs, then every existing test still passes unchanged and its output is pasted in `## Notes`. The other eight suites are not edited to accommodate this change. *Control:* this is the story's evidence that its artifact was verified, because `selftest` is a CI step rather than a `gates.sh` gate and so never appears in `## Gate results`. A pasted summary without the run is what `## Gate results` exists to prevent elsewhere; the same standard applies here.

## Out of scope

- **Removing the spike exemption.** AC-2 exists to stop it. A spike with no
  escalation still merges without a gate record.
- **Any other branch of that `case`.** `feature`, `fix` and `chore` already
  enforce the gate record and the `required_gates` re-check; they are not
  touched, and AC-4 is what notices if they are.
- **Wiring `selftest.sh` into `gates.sh`.** Not a gap — see "The gate question"
  above. It is a blocking CI step that runs *before* `gates.sh`, deliberately,
  because it guards the machinery `gates.sh` runs on. Making it a gate would be
  circular.
- **Putting a `floor` under `integration`.** That is [MC-040](MC-040.md).
- **Anything under `crates/`, `fixtures/` or `docs/wiki/`.** This story touches
  `scripts/check-boundaries.sh` and `.claude/tests/boundaries.test.sh` and
  nothing else.

**The records are written by a real `gates.sh` run inside the fixture, never
pasted.** A hand-written block cannot carry a `tree:` hash that
`check-boundaries.sh` will agree with, and AC-3 says "against a matching tree";
the only reliable way to get one is to let the script that owns the hash
produce it. So each recording fixture writes its own `project.conf` (gate
commands are `printf`s, as everywhere else in these suites), runs
`bash scripts/gates.sh --story T-1` in the fixture, then commits.

Three of the assertions are *fixture* self-checks rather than claims about
`check-boundaries.sh`: that `gates.sh` said it recorded, that the record
carries `PASS         integration`, and that the recorded `tree:` equals what
`gate_tree_hash` computes for the fixture. They are there because the code
under test does not look at any of that today, so a fixture that quietly
stopped being what it claims would look exactly like a pass.

`story_on_branch` gained two optional arguments - a story `type` and one extra
frontmatter line - both defaulting to what it produced before (`type: feature`,
no extra line), so the existing call sites are untouched and produce a
byte-identical story file. That is the entire change to the pre-existing part
of the suite. No other suite is edited (AC-4).

### Deliberately not asserted

- Whether an escalating spike must *also* satisfy the marker, `result:` and
  `tree:` checks. The AC-1 record fixture is otherwise valid - it carries the
  marker, `result: pass` and a matching tree - so it fails only for the missing
  `PASS integration`, and a fix is free to demand the rest of the record from an
  escalating spike or not.

  **What is *not* free**, and it is the one thing likely to catch GREEN out:
  today the `required_gates` loop sits *inside* the `else` of the marker check,
  so a fix that merely deletes the spike arm and lets an escalating spike fall
  into the existing non-spike branch makes AC-1's first fixture - the one with
  no `## Gate results` at all - fail on
  `## Gate results was not written by scripts/gates.sh` and never reach the
  loop. That names the story but not the gate, and AC-1 says "naming the story
  id and the gate". So the re-check has to be reachable for a spike whose
  record is absent or unrecognised, not only for one whose record parses.
- Whether the `spike story; gate record not required` note is still printed for
  an *escalating* spike. Only the AC-2 case asserts that note.
- Any other `case` arm, any other story type, and the wording of any message
  beyond the substrings in the table.

### The shape of the fix, as a constraint on behaviour

Stated so GREEN does not have to re-derive it. `scripts/check-boundaries.sh`,
section 3e, is the only production file this story touches.

1. For `REVIEW`/`DONE` with `type: spike`, every gate named in the story's
   `required_gates` must still be re-checked against the `## Gate results`
   body, with the same message and the same exit-1 consequence the other story
   types already get, naming the story id and the gate.
2. An escalating spike with no `## Gate results` section at all must fail
   **with the message that names the gate** - not crash, not pass, and not stop
   at "the record was not written by gates.sh". The section body is empty in
   that case, so whatever reads it has to cope with empty input, and the

4. A spike with `required_gates: [integration]` and a `gates.sh`-written record

### Three things found while writing the tests

1. **`gates.sh` ignores an escalated gate that `project.conf` does not
   configure - silently.** Its escalation loop only ever sees gates that have a
   `gate |` line, so `required_gates: [integration]` against a conf with no
   `integration` line produces `result: pass` with no mention of integration
   anywhere and no warning. That is exactly the hole 3e's re-check was written
   for (its own comment says so), and it is how the AC-1 record fixture is
   built. It also means the escalation is unenforced at *two* levels today, not
   one. Whether `gates.sh` should say something is not this story's business -
   it is not in the criteria and not in scope - but it is worth a look later.
2. **`project.conf` is inside the gated tree; the story file is not.**
   `.claude/**` classifies as `harness` and `gated_stdin` keeps harness files
   that are not `.md`, so writing a fixture's `project.conf` *after* its
   recording run would move the tree hash and make the record stale. Docs are
   dropped, so committing the story file that holds the record does not. The
   fixtures therefore write the conf, run `gates.sh`, then commit - in that
   order - and GREEN should keep that order if it touches them.
3. **`gates.test.sh` has a timing sensitivity that a loaded machine can trip,
   and it is not this story's.** In a full `selftest.sh` run made while
   `gates.sh --fast` was compiling in parallel, three assertions in *one run at
   a time: two gate runs on one checkout* failed - `and it gives up out loud`,
   `saying nothing ran`, `and exits 3`. The block holds the lock with
   `sleep 30 &` and then makes six `gates.sh` invocations before asserting;
   with `cargo` saturating the CPU the sleeper expired first, so the lock had no
   live owner, `gates.sh` took it over and exited 0 instead of giving up. Run
   alone the suite is `82 passed, 0 failed` in 228 s, and the clean full run
   above confirms it. Nothing to do here - noted so that nobody reading a red
   `gates` suite in a busy CI log spends the afternoon on the wrong story.
